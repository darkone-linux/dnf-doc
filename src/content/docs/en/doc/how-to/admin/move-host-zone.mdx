Move a workstation or a server to another zone, during a move for instance. The
host's `zone` key carries most of the change&nbsp;; its backups, the services it
hosts and the deployment order remain to be handled.

A gateway does not change zone, it defines it. To replace one, see
[Migrate gateway hardware](/en/doc/admin-guide/install/gateway-hardware-migration/).

{/* t:p 286f5d1f3a485a173490590ce6ca037ad49755d5bca04c4025c8e58b867b572c */}
## What follows automatically

Regenerated by `just clean`, then propagated to the deployment.

| Handled automatically | Why |
|---|---|
| Address, DNS and DHCP | Derived from the `zone` key |
| [Gateway address](/en/doc/admin-guide/understand/network/#machines-outside-their-zone) in the old zone | Same last octet everywhere |
| Supervision and logs | Features attached to the zone |
| Zone binary cache | Selected according to the zone |
| Zone-scoped firewall | Follows the zone prefix |
| Users, secrets, SSH keys | Zone-independent |

{/* t:p 51739fb0ff46563269e469a27625adb08f71ad0a91c842221b97b67c321f7545 */}
## What still needs handling

| Item | Risk | To do |
|---|---|---|
| Restic backups | Target and passphrase follow the zone | Pin the old server |
| Hosted services | Change zone and URL | Warn users |
| Features in `:<zone>` | Explicit zone, does not follow | Fix the zone |
| Time zone, locale | Those of the new zone | Override if needed |
| Machine configuration citing `zone` | Follows the declared zone | Review `usr/machines/<host>/` |

A hosted service moves from `<service>.<old-zone>.domain.tld` to
`<service>.<new-zone>.domain.tld` and now only serves its new zone. A `global`
service keeps its public address, relayed by the HCS.

```sh
grep -rn 'zone\.' usr/machines/poste/
```

Time zone and locale are overridden via `darkone.system.i18n.timeZone` and
`darkone.system.i18n.locale`.

## Procedure

Example&nbsp;: `poste` leaves the `maison` zone (`10.0`) for the `atelier` zone
(`10.1`).

<Steps>

1. **Enable the roaming cache**

   Substituters become neutral and follow the zone the machine is plugged into,
   which saves the first deployment after the move from downloading through the
   VPN. See [Binary cache](/en/doc/admin-guide/operate/deploy/#binary-cache).

   ```nix
   # usr/machines/poste/configuration.nix
   darkone.service.nix-cache.roaming = true;
   ```

   ```sh
   just apply poste
   ```

2. **Change the zone**

   Pick a free address according to the [addressing convention](/en/doc/how-to/admin/config/#section-zones)
   of the destination zone.

   ```yaml
   # etc/config.yaml
   - hostname: "poste"
     zone: "atelier:2.1"   # old value: "maison:2.1"
     mac: "aa:bb:cc:dd:ee:ff"
   ```

   :::caution[`mac` key required]
   The destination gateway assigns the fixed address based on the MAC address.
   Without it, the host gets a dynamic address and its name designates an
   address it does not have.
   :::

3. **Pin the backups**

   To keep the history, the target continues to point at the old zone's server,
   with that zone's passphrase.

   ```nix
   # usr/machines/poste/configuration.nix
   darkone.service.restic = {
     enable = true;
     targets = [
       {
         root = "rest:http://100.64.0.20:8888"; # tailnet IP of the maison server
         zone = "maison"; # restic-password-maison passphrase
         categories = [ "system" ];
       }
     ];
   };
   ```

   On the server side, `listenAll` must be enabled: see
   [Off-site backups](/en/doc/how-to/admin/network-backup/#off-site-backup).

   :::danger[A target in `restic.${zone.domain}` follows the zone]
   Against a server in the new zone, it initialises an empty repository and
   starts from scratch. Without a server, every backup is skipped without error,
   and only the `ResticBackupStale` alert reveals it.
   :::

4. **Regenerate and validate**

   ```sh
   just clean
   git diff var/generated/
   just commit "chore(poste): move from maison to atelier"
   ```

   The diff must show the fixed address in `atelier` and a `10.0.6.x` gateway
   address in `maison`.

5. **Prepare the arrival**

   Deploy the HCS, then the destination gateway, then the other gateways,
   **except the departure one**.

   ```sh
   just apply hcs
   just apply gw-atelier   # then the other gateways, except gw-maison
   ```

   The destination gateway reserves the new address on the host's MAC address.
   The HCS relays `global` services and enforces the VPN rules of the
   administration workstations&nbsp;: both target the host's address.

6. **Move the machine**

   Once plugged into `atelier`, it receives its new address via DHCP, before any
   redeployment.

7. **Finish the gateways**

   With the host gone, the departure gateway can publish its new name and
   reserve its gateway address.

   ```sh
   just apply gw-maison
   ```

8. **Deploy the host**

   ```sh
   just apply poste
   ```

   :::caution[Not before the move]
   Supervision exporters listen on the declared address. A host deployed before
   it has its new address sees those services fail.
   :::

9. **Verify**

   - `dig poste.atelier.domain.tld` returns the new address.
   - The `poste` target is `UP` in the `atelier` Prometheus.
   - A [manual backup](/en/doc/how-to/admin/network-backup/#running-a-manual-backup) finds the old snapshots.

10. **Remove the roaming cache**

    Delete `darkone.service.nix-cache.roaming`, except for a laptop that
    frequently changes zone, then `just apply poste`.

</Steps>

## FAQ

{/* t:p e3a11460e30631e66cc7294e419295a623df374a55c7235686dc4f4a45403fc4 */}
### What if the host is the administration workstation&nbsp;?

During transport, nothing deploys any more&nbsp;: plan an
[alternate deployer](/en/doc/admin-guide/operate/alternate-deployer/). On
arrival, it deploys the departure gateway through the VPN, then itself with
`just apply-local`.

{/* t:p 171d614f2aa119129bbd82fde4ae0de005e36227aef92be2fe908e12a5fa5c9d */}
### Why the departure gateway last&nbsp;?

It takes away the host's fixed address. Still plugged in, it would receive its
gateway address when the lease renews, without the matching configuration, and
the host name would no longer designate the address it occupies.

{/* t:p bb06670cd3f4bf7fdae33c7660f34facd59aefb70f7558c44d2b39799d4c7b73 */}
### Should alerts be expected&nbsp;?

Yes, during transport the host is unreachable from both sides. It is expected by
`atelier` from step 5 onwards and still monitored by `maison` until step 7. For
a workstation, these are only warnings (see
[alert classes](/en/doc/admin-guide/understand/monitoring-alerts/)).

{/* t:p b64122ee9babbaf68462817a7e77eaacacb919598741f2dba1a44a610b7f67d8 */}
### How to roll back&nbsp;?

Restore the old `zone`, regenerate, then replay the procedure in reverse.
Thanks to the gateway addresses, the host stays reachable in each zone in the
meantime.
