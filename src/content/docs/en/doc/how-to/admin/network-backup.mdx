The `darkone.service.restic` module backs up fleet hosts with
[restic](https://restic.net/): each host (client) pushes its data to a
repository, either local or remote via a zone REST server.

{/* t:p 7b847c7793b34e795bee64a83826740234ad221c41eaab9d66deb345ded336c4 */}
## Principles

Two roles, one module:

- **REST server**: a host that declares the `restic` service in `config.yaml`.
  It stores the repositories of all hosts and listens on the internal network.
- **Client**: any host with `enable = true` that declares `targets`
  (backup destinations).


<Aside type="caution" title="Don't confuse these two passwords">
- **Repository passphrase** `restic-password-<zone>`: encrypts the *content* of
  the repository. Without it, no restore is possible.
- **REST credential** `restic/<hôte>/rest-password`: *authenticates* the host
  to the REST server. One per host.

Both are generated by `just passwd-restic` (see below).
</Aside>

Repository layout: one repository per category, named after it.

```
<racine>/<hôte>/system  # catégorie "system" (/ moins les exclusions)
<racine>/<hôte>/nfs     # catégorie "nfs"    (/srv/nfs/<...>)
<racine>/<hôte>/medias  # catégorie "medias" (/srv/medias/<...>)
```

<Aside type="caution" title="The repository path is exactly two levels deep">
`rest-server` only serves repositories located **two components** below its
data directory: `<hôte>/medias` responds, `<hôte>/srv/medias` returns 404, and
restic then shows the misleading message `repository does not exist` even
though the data is intact.

The subpath is therefore the **category name**, never the source directory.
Since this layout is identical locally and over REST, a repository can switch
from one to the other without being renamed.
</Aside>

<Aside type="danger" title="Repositories created before this layout">
Repositories written while the subpath copied the source directory are located
under `<hôte>/srv/nfs` or `<hôte>/srv/medias`. Rename them on the server
**before the next run**: with `initialize` set to `true`, restic would
otherwise create an empty repository at the new path and silently start a full
backup, several TB over a slow link.

```sh
mv <données>/<hôte>/srv/medias <données>/<hôte>/medias
rmdir <données>/<hôte>/srv
```

Renaming within the same filesystem: instantaneous, no data moved, history and
incrementality preserved.
</Aside>

## Setting up a backup server

<Steps>

1. In `etc/config.yaml`, add the `restic` service to the server host:

   ```yaml
   services:
     restic:
   ```

2. Attach the backup disk and mount it on `/mnt/backup` in the host
   configuration (`usr/machines/<host>/`), with the `nofail` option:

   ```nix
   fileSystems."/mnt/backup" = {
     device = "/dev/disk/by-uuid/<uuid>";
     fsType = "ext4";
     options = [ "nofail" ];
   };

   # The REST server only starts once the disk is mounted.
   systemd.services.restic-rest-server = {
     requires = [ "mnt-backup.mount" ];
     after = [ "mnt-backup.mount" ];
   };
   ```

3. The repository is stored under `serverDataDir` (default `/mnt/backup/restic`).
   The firewall opens the REST port on the internal interface automatically.

</Steps>

<Aside type="note" title="Server is also a client">
A server can back up its own data by pointing a `target` to its local disk
(`root = "/mnt/backup/restic"`).
</Aside>

## Adding a client

Declare one or more `targets` in the host configuration:

```nix
darkone.service.restic = {
  enable = true;
  targets = [
    {
      # Remote repository via the zone's REST server.
      root = "rest:http://restic.home.example.net:8888";
      zone = "home";
      categories = [ "system" "nfs" ];
    }
  ];
};
```

`target` fields:

| Field        | Role                                                       |
| ------------ | ---------------------------------------------------------- |
| `name`       | Identifier (default `main`), suffix for jobs/units.        |
| `root`       | Local path or `rest://` URL.                               |
| `zone`       | Zone that selects the `restic-password-<zone>` passphrase. |
| `categories` | Data to back up: `system`, `nfs`, `medias`.                |

<Aside type="tip" title="Multiple destinations">
Add a second `target` (different `name`, different `root`/`zone`) to replicate
the backup, for example to the REST server of another zone.
</Aside>

## Generating passwords

An idempotent recipe creates missing secrets (never overwrites):

```bash
just passwd-restic
```

It generates, in `usr/secrets/secrets.yaml`:

- one `restic-password-<zone>` passphrase per zone;
- one `restic/<host>/rest-password` credential per fleet host.

<Aside type="note" title="New host">
Re-run `just passwd-restic` after adding a host, then redeploy the
servers so they pick up its new REST account.
</Aside>

## Running a manual backup

The module creates one systemd service per target × category pair, named
`restic-backups-<category>-<name>` (the `<name>` comes from the target's `name`
field, `main` by default). Examples: `restic-backups-system-main`,
`restic-backups-nfs-main`.

<Steps>

1. List the backup services present on the host:

   ```bash
   systemctl list-units 'restic-backups-*'
   ```

2. Trigger an immediate backup without waiting for the timer:

   ```bash
   sudo systemctl start restic-backups-system-main.service
   ```

3. Follow its progress in real time:

   ```bash
   journalctl -fu restic-backups-system-main.service
   ```

</Steps>

<Aside type="tip" title="Simulate without writing anything">
Setting `darkone.service.restic.enableDryRun = true` adds `--dry-run` to all
jobs: the backup runs in dry mode, no snapshot is created.
</Aside>

## Repository isolation

The REST server runs with private repositories (`privateRepos = true`): each host
only accesses the repository whose path starts with its own hostname. The
module automatically aligns the REST account (`<hôte>`) with the repository prefix
 (`<racine>/<hôte>/...`), so isolation is permanent → no configuration needed.
An attempt to access another host's repository returns a **403** error.

## Restore

On the host in question, the secrets are already in place. List and restore:

```bash
# Adapter la zone du dépôt (et la catégorie : system, nfs, medias).
ZONE=home

# Variables d'accès REST (générées par sops) et passphrase de dépôt.
set -a; . /run/secrets/rendered/restic-rest-env; set +a
export RESTIC_PASSWORD_FILE=/run/secrets/restic-password-$ZONE
export RESTIC_REPOSITORY=rest:http://restic.$ZONE.example.net:8888/$(hostname)/system

restic snapshots
restic restore latest --target /restore
```

<Aside type="caution" title="Adapter zone and category">
Set `ZONE` to the repository zone and replace `system` in
`RESTIC_REPOSITORY` with the category (`nfs`, `medias`) to restore.
</Aside>

## Verifying

<Steps>

1. On a server, one account per fleet host in the htpasswd file:

   ```bash
   sudo cut -d: -f1 /run/restic-rest/htpasswd
   ```

2. On a client, run a manual backup (see above) and check that it completes
   without errors.

3. Isolation: from a client, accessing another host's repository must be
   **denied** (401/403 error).

</Steps>
