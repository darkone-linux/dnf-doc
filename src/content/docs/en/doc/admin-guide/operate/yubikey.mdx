Every network member can associate a **YubiKey** primary key and a **backup**
key with their account, in addition to their password (which remains mandatory
and serves as automatic fallback).

The key principle: **one single enrollment** per key, on the administration
machine. Everything else propagates declaratively with `just apply` — the key
is never plugged into the fleet hosts, only when it needs to be used.

## What a key covers

| Usage | Mechanism | Effect |
|---|---|---|
| **Session, sudo, login screen** | pam_u2f (`sufficient`) | Touching the key replaces the password |
| **Encrypted disks (LUKS)** | FIDO2 `hmac-secret` | Boot unlock by touching the key |
| **SSO (Kanidm)** | Passkey WebAuthn | Passwordless login to services |
| **Vaultwarden** | WebAuthn (2FA) | Second factor for the vault |

:::note[No risk of lockout]
The session password (sops) and the installation LUKS passphrase are
**never removed**: without a key (lost, forgotten), everything works as before.
At boot, a plugged-in key that nobody touches also blocks nothing —
the passphrase prompt appears after about thirty seconds, on the console
as well as remotely (see
[Unlock at boot](/en/doc/admin-guide/operate/luks/#unlocking-at-boot)).
:::

:::caution[Boot touch cannot be bypassed]
LUKS unlock relies on the FIDO2 `hmac-secret` extension: the key
**recalculates** the keyslot secret at each boot, from a salt stored
in plaintext in the LUKS header.

YubiKeys **enforce** user presence for this extension. A
request without a touch is rejected (`FIDO_ERR_UP_REQUIRED`) before even
looking up the credential. Firmware rule, not a setting: systemd re-enables
user presence by itself, both at enrollment and at unlock.

For a host that must reboot unattended (gateway, headless machine), the
path is **TPM2** (`systemd-cryptenroll --tpm2-device=auto`), which coexists with
FIDO2 keyslots in the same LUKS header. Trade-off: the disk opens
without a human, so stolen **with** its motherboard it remains
decryptable.
:::

## The four Kanidm authentication methods

A Kanidm account exposes several authentication methods, independent of each
other. The goal is that no lost key ever locks an account out.

| Method | Kanidm nature | Support |
|---|---|---|
| **Primary YubiKey** | WebAuthn passkey | Physical key (PIN + touch) |
| **Backup YubiKey** | WebAuthn passkey | Physical key stored separately |
| **Software key** | WebAuthn passkey | Vault (Bitwarden, KeePassXC) |
| **Password + TOTP** | Primary credential | Safety net, never removed |

The first three are **passkeys**: Kanidm stores them side by side and offers them
together to the browser. The fourth lives elsewhere (the primary credential)
and cannot be overwritten by a WebAuthn ceremony.

:::note[Enrollment is an administrator task]
Users do not create their own passkeys, except
[technicians](/en/doc/admin-guide/operate/onboarding/#alternative-for-technical-users),
who follow the order below. Each web ceremony involves a choice
(vault or physical key) whose wrong selection destroys an existing key.
:::

## Enrolling a key

<Steps>

1. Plug the user's YubiKey into the admin workstation, then:

   ```sh
   just yubikey <login>          # primary key (FIDO2 PIN + ~3 touches)
   just yubikey <login> backup   # backup key (optional)
   ```

   If the key does not have a FIDO2 PIN yet, the recipe creates it first
   (required for Kanidm, see below).

2. Commit and deploy:

   ```sh
   git add usr/secrets/yubikeys.json
   just commit "user(yubikey): <login>"
   just apply
   ```

3. That's it: session and sudo respond to the key on all of the user's
   workstations, and encrypted hosts register the key in their LUKS
   headers **themselves**, at deployment.

</Steps>

:::tip[Kanidm and Vaultwarden: a web ceremony, only once]
WebAuthn requires (by anti-phishing design) an interactive registration in the
browser. `just yubikey` generates the Kanidm reset link to send to the user;
for Vaultwarden, the key is added in the web vault (*Settings → Security →
Two-step login → WebAuthn*).
:::

:::danger[The password manager can destroy a passkey]
A vault extension (Bitwarden, KeePassXC) intercepts the WebAuthn ceremony and
offers to save the passkey **in its vault**, not on the physical key. Worse: if
the registration targets a vault item that **already** holds an access key, the
latter is **replaced**, not supplemented. The previous software passkey
disappears from the vault, while Kanidm still requires it.

See [Passkey enrollment order](#passkey-enrollment-order) for the procedure that
makes this accident impossible.
:::

:::caution[FIDO2 PIN required]
Kanidm requires user verification, so the browser asks for the key's PIN in
addition to the touch. Session, sudo and LUKS never ask for the PIN: they
remain touch-only.
:::

## Passkey enrollment order

The principle: **isolate each ceremony** from anything that could intercept it.
A physical passkey is enrolled in a browser without vault extension, a software
passkey is enrolled in the usual browser. The order ensures a safety net exists
before each risky step.

<Steps>

1. **Password and TOTP first.** They live outside passkeys and cannot be
   overwritten. As long as they exist, no error in the following steps locks
   the user out.

2. **Software key next**, in the usual browser, vault extension unlocked. When
   the vault offers to save, choose **create a new item**, never "save in an
   existing item".

3. **Primary YubiKey**, in a **throwaway and clean** browser: without any
   extension, interception is impossible.

   ```sh
   firefox --new-instance --profile "$(mktemp -d)" https://idm.domain.tld
   ```

   Then paste the Kanidm reset link printed by `just yubikey`.

4. **Backup YubiKey**, in the same throwaway browser, another key plugged in.

5. **Verify the result** before closing: the account must show three passkeys.
   See [Passkey diagnostics](#passkey-diagnostics).

</Steps>

:::tip[One throwaway profile per ceremony]
The profile created by `mktemp -d` disappears on the next system cleanup.
Nothing to uninstall, nothing to reactivate, and no risk of forgetting to
reactivate the vault extension afterwards.
:::

:::caution[Procedure being validated]
This section describes an accident observed once, whose exact mechanism on the
vault side has not yet been reproduced under controlled conditions. The
sequence above makes it impossible regardless.
:::

## Passkey diagnostics

:::danger[The credential status command never shows passkeys]
`kanidm person credential status <login>` only shows the **primary credential**
(password, TOTP, recovery codes). An account full of passkeys appears without
any. Never conclude there are none.
:::

To actually list an account's passkeys, open an interactive credential update
session:

```sh
kanidm person credential update <login> --name idm_admin
```

To see what the server actually sends the browser, open the console (`F12`) on
the login page, paste this code, then click **Passkey**:

```js
const _get = navigator.credentials.get.bind(navigator.credentials);
navigator.credentials.get = (o) => {
  const b64 = (v) => btoa(String.fromCharCode(...new Uint8Array(v)));
  const p = o.publicKey;
  console.log("rpId:", p.rpId, "| uv:", p.userVerification);
  console.log("allowCredentials:", (p.allowCredentials || []).map((c) => b64(c.id)));
  return _get(o);
};
```

The number of entries in `allowCredentials` is the truth: it is the exact list
of passkeys Kanidm knows for this account.

| Symptom | Likely cause |
|---|---|
| The browser asks for a YubiKey PIN, no vault window appears | Orphaned software passkey, missing from the vault |
| `allowCredentials` has fewer entries than expected | A ceremony overwrote a passkey |
| PIN is requested even though the physical key is not targeted | Kanidm does not emit `transports`, see below |

:::note[Spurious PIN prompt]
Kanidm does not fill in the `transports` of its passkeys. Without this
indication, the browser probes **all** transports, including USB, and asks for
the PIN of the plugged YubiKey even when the targeted passkey is software.
Workaround: unplug the key.
:::

## GNOME keyring asks for a password again

On a desktop machine, opening the session by touching the key brings up a window shortly after: **"Enter the password to unlock your login keyring"**. The symptom never occurs when the session is opened with the password.

Cause&nbsp;: pam_u2f is declared `sufficient`. As soon as the key is touched, the authentication stack stops before `pam_gnome_keyring`, which therefore receives no password.

Remedy&nbsp;: a [passwordless keyring](/en/doc/admin-guide/operate/users/#a-passwordless-keyring), enabled by default for non-technical profiles on an encrypted host. For a technical profile&nbsp;:

```nix
# usr/users/<login>/default.nix
darkone.home.gnome.passwordlessKeyring = true;
```

:::caution[Seahorse is not enough]
Clearing the keyring password in Seahorse does not hold&nbsp;: the first session opened with the password re-encrypts it with that password. The option, however, never passes this password to the keyring.
:::

## One key for multiple accounts

The same physical key can serve multiple users: simply repeat enrollment for
each login, key plugged in.

```sh
just yubikey <login1>
just yubikey <login2>   # same physical key, different account
```

Each enrollment creates credentials **specific to the account** (PAM, LUKS, and
a Kanidm reset link per user to redo the web ceremony with the same key).
Kanidm passkeys are non-resident: they do not occupy any slot on the key, the
number of accounts is unlimited. A revocation (`just yubikey <login> main
revoke`) only affects the targeted login.

## Encrypted isolated hosts

An [isolated host](/en/doc/admin-guide/operate/secrets/#isolated-hosts) never receives the fleet value&nbsp;: each key is enrolled there with a **salt specific to the host** ([why](/en/doc/admin-guide/understand/yubikey-salts/)).

<Steps>

1. **Install** the host with `just install`&nbsp;: its secrets file then exists.

2. **Capture**, with each key plugged alone into the admin machine&nbsp;:

   ```sh
   just yubikey <login>          # une pression par hôte isolé chiffré
   just yubikey <login> backup
   ```

   A key already enrolled only computes what it is missing.

3. **Deploy**: commit `usr/secrets/`, then `just apply <hôte>`.

</Steps>

A key left away from the admin machine is not enrolled on that host, its passphrase remains. `just luks <hôte> show` lists the keys to catch up.

## Under the hood

| File | Content | Status |
|---|---|---|
| `usr/secrets/yubikeys.json` | Public credentials (PAM, FIDO2 id, salt) | Public, versioned |
| `secrets.yaml` → `yubikey/<login>/<clé>/luks-secret` | LUKS secret derived from the key | sops-encrypted |
| `secrets.yaml` → `luks-passphrase` | Passphrase entered at disko install | sops-encrypted (requested on first enrollment) |
| `yubikeys.json` → `hostSalts.<hôte>` | Salt specific to an isolated host | Public, versioned |
| `hosts/<hôte>.yaml` → `luks/<hôte>/fido2/<login>/<clé>` | Value with the host salt | sops-encrypted (admin and host) |

- **PAM**&nbsp;: the origin is fixed (`pam://<domaine>`), so one credential is valid across the whole fleet. The `darkone.system.yubikey` module (enabled automatically as soon as the registry exists) distributes `/etc/u2f_mappings` on each host.
- **LUKS**&nbsp;: the derived secret (`HMAC(clé, sel)`) can only be computed with the physical key. Each encrypted host writes it into its LUKS header (keyslot + `systemd-fido2` token, the exact format of `systemd-cryptenroll`) via an idempotent service, and removes those no longer declared. The full passphrase policy and remote unlocking are described in [Disk encryption (LUKS)](/en/doc/admin-guide/operate/luks/).

:::caution[Fixed origin]
Changing `darkone.system.yubikey.origin` (or the network domain) invalidates all PAM credentials&nbsp;: every key would have to be re-enrolled.
:::

## Revoking a lost key

```sh
just yubikey <login> main revoke   # ou backup
just commit "user(yubikey): revoke <login>" && just apply
```

On deployment, the PAM credential disappears from the hosts and the corresponding LUKS keyslots are removed, isolated hosts included (their values go away with the revocation). Also remember to remove the passkey on the Kanidm side (web interface or reset token) and Vaultwarden.

## Limitations and next steps

- TOTP remains available on the web side (Kanidm, Vaultwarden), not at local login.
- LUKS unlock **without a PIN code** (touch only) in this version.
- LUKS unlock **without touching** is out of reach of a YubiKey (hardware
  limit, see above); TPM2 is not yet integrated into the framework.
- Coming soon: FIDO2 SSH keys (`ed25519-sk`) and git signing, per-host
  "mandatory second factor" mode, admin sops decryption conditioned on the
  key (`age-plugin-fido2-hmac`).
