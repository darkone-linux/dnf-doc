The VPN links the zones, the coordination server and remote devices&nbsp;:
[Headscale](https://headscale.net/) coordinates from the HCS,
[Tailscale](https://tailscale.com/) is the client on each node. This page gathers
the operating procedures. Routing, DNS, MagicDNS, access policy and keys are
explained in [How the tailnet works](/en/doc/admin-guide/understand/tailnet/).

{/* t:p 547e4b30ce1969dd37e7a9de994d22365c893599114ca3b2dae3fc45f7618b1b */}
## Enable the VPN

Enabling coordination and declaring the HCS (`profile: hcs`) is enough&nbsp;:

```yaml
# etc/config.yaml
network:
  coordination:
    enable: true
    hostname: "hcs"
    domain: "headscale"
```

The role of each node follows from the topology&nbsp;:

| Node | Identity | Role |
|---|---|---|
| HCS | `tag:hcs` | coordination, pivot DNS, global services, exit node (closed) |
| Gateway | `tag:gw-<zone>` | subnet router&nbsp;: advertises the `/16` of its zone |
| Admin workstation | `tag:admin` | SSH to all machines |
| Personal device | its owner | services, according to its groups |

An admin workstation is a host whose `groups` contains `admin` and whose host file enables the client&nbsp;:

```nix
# usr/machines/portable/configuration.nix
darkone.service.tailscale.enable = true;
darkone.service.tailscale.autoPauseOnLan.enable = true;
```

`autoPauseOnLan` pauses the client when the laptop is plugged into a zone (NetworkManager required).

## Enroll a machine

Machines join the tailnet **without a shared key**&nbsp;: the HCS creates a single-use key
for each one, with its declared tags. `just configure` handles it,
so does `just full-install`. The recipe alone can be rerun at any time&nbsp;:

```sh
just tailnet-enroll gw
```

```
[ DNF ] TAILNET • gw not enrolled, backend NeedsLogin: sending a single-use key...
[ DNF ] TAILNET • gw: gw tag:gw-maison 100.64.0.8
```

It is **idempotent**&nbsp;:

| Situation | Effect |
|---|---|
| Node enrolled, name and tags compliant | nothing (`already enrolled`) |
| Tags or name differ | corrected on the HCS, without reconnection |
| Never enrolled, deleted or reinstalled | new key, registration |
| Old node with the same name offline | deleted, the new one takes the name |
| Old node with the same name online | refused&nbsp;: two machines carry this name |
| Host without Tailscale client | ignored |

The mechanism is detailed in [Activation keys and
enrollment](/en/doc/admin-guide/understand/tailnet/#pre-authorized-keys-and-enrollment).

:::caution[Deploy the HCS after declaring the host]
The HCS only creates a key for a host it knows. A host just added to
`etc/config.yaml` first requires `just apply hcs`, otherwise&nbsp;:
`no declared tailnet identity`. `just install` checks it before formatting.
:::

:::note[Failure during an installation]
HCS unreachable, `just configure` warns without stopping&nbsp;: rerun
`just tailnet-enroll <hôte>` once the HCS is back.
:::

:::note[New address after a reinstallation]
Headscale assigns addresses in order and does not allow fixing them. A
reinstalled machine receives a new tailnet address&nbsp;: for a gateway, report it in
`vpn.ipv4`. To keep it, restore the client state instead of re-enrolling (see [Migrating gateway hardware](/en/doc/admin-guide/install/gateway-hardware-migration/)).
:::

## Register a gateway

A gateway enrolls like any machine&nbsp;; two points are specific to it.

<Steps>

1. **Check the route of its zone**

   The gateway advertises the `/16` of its zone, which the policy approves automatically
   for `tag:gw-<zone>`. On the HCS&nbsp;:

   ```sh
   sudo headscale nodes list-routes
   ```

2. **Declare its tailnet address**

   The HCS reaches the zone resolver through this address (pivot DNS), as do
   the services that target it (backups, monitoring). Read it from the output of
   `just tailnet-enroll`, then report it&nbsp;:

   ```yaml
   # etc/config.yaml
   zones:
     maison:
       gateway:
         vpn:
           ipv4: "100.64.0.8"
   ```

3. **Propagate the address**

   ```sh
   just generate
   just apply hcs
   just apply gw-atelier   # passerelle du poste d'administration, si autre zone
   just apply gw
   ```

   The admin workstation resolves the short name `gw` through its zone's gateway.
   If not redeployed since `gw` was added, it ignores it and `just apply gw` fails.

   Applying the gateway closes its public SSH (WAN, open until then).
   Also redeploy the other gateways and the hosts targeting this address.
   `HeadscaleNodeDrift` reports a declared address that no longer matches.

</Steps>

## Connect a personal device

A smartphone or personal computer connects with the [Kanidm](/en/doc/admin-guide/understand/auth-idm/) identity of its owner&nbsp;: no key,
no manual validation.

| Can connect | Condition in `etc/config.yaml` |
|---|---|
| Administrator | `admin` or `nix-admin` profile |
| Member of a zone | `zone-<zone>` group |
| Member of an AI space | in the `users` of an `ai-space` host |

These accounts form the Kanidm group `tailnet`, provisioned automatically&nbsp;; Kanidm
refuses the others. To open access, add the group to the user,
regenerate, then `just apply hcs`. The user then follows [Connect a
device](/en/doc/how-to/user/connect-device/#from-outside).

The device joins the **web services** (HTTPS) of its zones, of those of its AI spaces and of the HCS, nothing else.
A Samba share, a printer or SSH requires a rule&nbsp;: see [Adapting
the access policy](#adapt-the-access-policy).

The device belongs to the person (`alice@`) and **expires after 180 days**&nbsp;:
they then reconnect with their login.

**Removing access**&nbsp;: remove the group, `just apply hcs`, then delete their
devices. Otherwise, they keep the DNS and HTTPS of the HCS until they expire
(alert `HeadscaleUnexpectedNode`).

```sh
sudo headscale nodes list                 # appareils, propriétaires, expiration
sudo headscale nodes expire -i <id>       # forcer une reconnexion
sudo headscale nodes delete -i <id>       # retirer l'appareil
```

## Adapt the access policy

The policy is generated from the topology&nbsp;: its rules are detailed in
[Access policy](/en/doc/admin-guide/understand/tailnet/#access-policy-acl).
Options adjust it, on the HCS&nbsp;:

| Option `darkone.service.headscale.` | Default | Effect |
|---|---|---|
| `policy.adminDevices` | `{ }` | personal devices allowed SSH&nbsp;: name → tailnet IPv4 |
| `policy.exitNodeSources` | `[ ]` | sources allowed to exit to the Internet via the HCS |
| `policy.extraHosts` | `{ }` | aliases of undeclared devices&nbsp;: name → CIDR |
| `policy.extraAcls` | `[ ]` | rules added after the generated rules |
| `policy.enforce` | `true` | `false`&nbsp;: everything allowed, for migration only |
| `nodeExpiry` | `"180d"` | expiry of personal devices (`0`&nbsp;: never) |

Each declared host of a zone is already an alias (its name → its LAN address)&nbsp;:
a rule targets `nas:445` without going through `extraHosts`.

```nix
# usr/machines/hcs/configuration.nix
darkone.service.headscale.policy = {

  # SSH depuis le téléphone d'Alice (adresse lue dans `headscale nodes list`)
  adminDevices.phone-alice = "100.64.0.9";

  # Exit node du HCS ouvert aux administrateurs
  exitNodeSources = [ "group:admins" ];

  # Imprimante réseau pour tous les appareils personnels
  extraHosts.printer = "10.0.4.10/32";
  extraAcls = [
    {
      action = "accept";
      src = [ "autogroup:member" ];
      dst = [ "printer:631" ];
    }

    # Partage Samba du serveur `nas` (hôte déclaré) pour Alice
    {
      action = "accept";
      src = [ "alice@" ];
      dst = [ "nas:445" ];
    }
  ];
};
```

Then `just apply hcs`&nbsp;: the policy is checked at build time, and Headscale
reloads it without restarting.

:::caution[Address of a declared device]
`adminDevices` targets an IPv4 address. A device re-registered as a new node
changes address&nbsp;: `HeadscaleNodeDrift` reports it, report the new one.
:::

:::note[Exit node]
Opening `exitNodeSources` is not enough&nbsp;: the user chooses the HCS as exit
node in their application.
:::

## Administration

On the HCS (`just enter hcs`)&nbsp;:

| Command | Usage |
|---|---|
| `sudo headscale nodes list` | nodes, owner, tags, addresses, expiry |
| `sudo headscale nodes list-routes` | advertised and approved routes |
| `sudo headscale nodes rename -i <id> <nom>` | rename a node |
| `sudo headscale nodes expire -i <id>` | force a reconnection |
| `sudo headscale nodes delete -i <id>` | delete a node |
| `sudo headscale users list` | personal device owners |
| `sudo headscale preauthkeys list` | pre-authorized keys&nbsp;: tags, usage, expiry |
| `sudo headscale policy get` | served policy |
| `sudo dnf-tailnet-enroll status <hôte>` | declared identity of a host |

Tags and routes are not set by hand&nbsp;: `just tailnet-enroll` sets the declared
tags, the policy approves the routes. The other client settings (advertised routes,
Tailscale SSH disabled, exit node) are realigned by
`tailscaled-autoconnect`, at startup and during deployments that change them.

:::caution[JSON outputs]
`nodes list -o json` and `preauthkeys list -o json` may contain pre-authorized keys&nbsp;:
do not copy them into a ticket or a channel.
:::

### On a node

| Command | Answers |
|---|---|
| `tailscale status` | peers, online or not, direct path or relay |
| `tailscale ping <nœud>` | real path&nbsp;: `via <ip>:41641` (direct) or `via DERP` |
| `tailscale whois <ip>` | node, tags or owner behind an address |
| `tailscale dns status` | MagicDNS, split DNS, search domains received |
| `journalctl -u tailscaled-autoconnect` | last record or realignment of settings |

### Test a policy

Without a `--bypass…` option, `headscale policy check` compiles a file **against the real nodes** and runs its `tests` block, without touching the policy in place.

<Steps>

1. Start from the served policy&nbsp;:

   ```sh
   sudo headscale policy get > /tmp/policy.json
   ```

2. Add a `tests` block&nbsp;: a source, then the expected destinations,
   each a **single host** (address and port)&nbsp;:

   ```json
   "tests": [
     { "src": "alice@", "accept": ["100.64.0.8:443"], "deny": ["100.64.0.8:22"] }
   ]
   ```

3. Check&nbsp;:

   ```sh
   sudo headscale policy check -f /tmp/policy.json
   ```

</Steps>

### Common failures

| Symptom | Check | Remedy |
|---|---|---|
| `TailscaleUnhealthy`, backend `NeedsLogin` | `tailscale status` on the node | `just tailnet-enroll <hôte>` |
| Login showing `headscale auth register` | `HeadscaleOidcFallback` alert | `sudo systemctl restart headscale` on the HCS |
| Kanidm refuses access to Headscale VPN | user's groups | admin profile, `zone-<zone>` or AI space member, `just apply hcs` |
| Zone unreachable from the tailnet | `headscale nodes list-routes` | gateway enrolled with its tag, route approved |
| Zone service refused to a device | user's groups, `tailscale whois <ip>` | add `zone-<zone>`, `just apply hcs` |
| Non-web service unreachable (Samba, ping) | policy rules | `policy.extraAcls` rule |
| SSH refused on a tailnet address | `tag:admin` workstation or `adminDevices` device | declare the device |
| Internal names unresolved outside the zone | `tailscale dns status` | enable "Use Tailscale DNS" |
| Login page not found | "Use Tailscale DNS" active | disable it for the duration of the login |
| Slow traffic | `tailscale ping` shows `via DERP` | outbound UDP filtered, or strict NAT on both sides |
| `no declared tailnet identity` | tagged host, HCS deployed from its declaration | `just apply hcs` |
| `named … is online, not deleting it` | two machines carry the same name | turn off the old one or rename the host |

## Audit and alerts

Every 15 minutes, `headscale-audit` compares the real nodes to the declared topology, without changing anything. Details of the discrepancies are in its log&nbsp;:

```sh
journalctl -u headscale-audit -n 20
```

| Alert | Reports | After |
|---|---|---|
| `HeadscaleNodeDrift` | HCS or gateway missing, wrong tags, address different from the declared one | 30 min |
| `HeadscaleUnexpectedNode` | undeclared tagged node, or device of an account outside the `tailnet` group | immediately |
| `HeadscalePolicyInvalid` | policy refused, or served policy different from the file | 30 min |
| `HeadscaleOidcFallback` | Kanidm absent at Headscale startup&nbsp;: OIDC connections cut | immediately |
| `HeadscaleNodeExpiring` | personal device expiring within 7 days | 1 h |
| `HeadscaleAuditStale` | audit without success for more than one hour | immediately |

All are `warning`, on the Prometheus that monitors the HCS. An absent admin workstation is not an anomaly&nbsp;; when present, its tags are checked.

:::tip[After `HeadscaleOidcFallback`]
Once Kanidm is back, restart Headscale&nbsp;: `sudo systemctl restart headscale`. Do not manually create the account that `headscale auth register` asks for&nbsp;: a namesake of the OIDC account would make it refuse any policy that cites this user.
:::

## Client self-repair

A `tailscaled` can **silently drop off** Headscale&nbsp;: the control connection is lost while the service stays "active", and a gateway's subnet becomes unreachable. A local *watchdog* detects and fixes this case, on **every Tailscale client**.

| Aspect | Behavior |
|---|---|
| Probe | every 60&nbsp;s&nbsp;: `tailscale status` (backend, online state) |
| Debounce | 3 consecutive failed probes (~3&nbsp;min) before acting |
| Fix | restarts `tailscaled`, which reconnects to the control plane |
| Anti-loop | one fix per 10&nbsp;min window |
| Unenrolled node | no restart (`NeedsLogin`)&nbsp;: `just tailnet-enroll` |
| Paused laptop | watchdog stopped, metric removed |
| Observability | `dnf_tailscale_healthy`, `dnf_tailscale_selfheal_restarts_total` (textfile node_exporter) |

Two [alerts](/en/doc/admin-guide/operate/alerts/) accompany the mechanism&nbsp;:

- **`TailscaleUnhealthy`**&nbsp;: still disconnected after 10&nbsp;min, despite the fix&nbsp;;
- **`TailscaleFlapping`**&nbsp;: more than 3 fixes in one hour.

:::note[Enabled by default]
To disable it on a host&nbsp;: `darkone.service.tailscale.selfHeal.enable = false;`.
:::

## Control plane bootstrap

On a gateway, dnsmasq sends every `domain.tld` query to the HCS resolver **through the tailnet**&nbsp;: the client would need the VPN to find the server that brings up the VPN. At boot, moreover, the local resolver is not yet listening.

Each Tailscale client therefore receives the HCS public address in its `/etc/hosts`, derived from `etc/config.yaml` (the HCS itself is excluded). dnsmasq answers this name from that file, without ever forwarding it&nbsp;:

```sh
grep headscale /etc/hosts     # 203.0.113.10 headscale.domain.tld
```

The client thus connects without any resolver, including when local DNS is down, precisely when self-repair must be able to act.

:::caution[HCS address change]
`/etc/hosts` **takes precedence over DNS**. If the VPS changes address, update `etc/config.yaml` then **redeploy the Tailscale clients**&nbsp;: as long as they carry the old entry, they do not reconnect, even with a correct public DNS.
:::

## Outside a zone

- **Personal device**&nbsp;: see [Connect a personal device](#connect-a-personal-device).
- **Admin laptop**&nbsp;: when away, it reaches all zones through the tailnet (`just enter <hôte>`). Plugged back into a zone, its client pauses and the local gateway takes over again.
