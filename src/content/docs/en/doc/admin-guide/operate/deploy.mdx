The fleet is deployed with [colmena](https://github.com/zhaofengli/colmena): a single command builds and applies the configuration on one or more hosts, remotely, from the admin workstation.

{/* t:p d4a06fc139c0d5029ddc5205311c422d5da5a5e1fe1b2e6d014d42aae5b8629c */}
## Apply a configuration

```sh
just apply <target> [action]    # alias : a
```

- **target** = hostname, pattern (`'*'`), list (`a,b`) or colmena tag (`@server`).
- **action** = `switch` (default), `boot`, `test` or `build`.

| Command | Purpose |
|---|---|
| `just apply <target>` | Build + activate on the target(s) |
| `just apply-local` | Apply on the current machine (alias `al`) |
| `just apply-verbose <target>` | Same as `apply` in trace mode (alias `av`) |

:::tip[Build on target]
`apply` builds **on the target host** (`--build-on-target`): the admin workstation doesn't need the power or architecture of the deployed machines.
:::

## Deploy safely

**Build confidence through action**: each step is less risky than the next.

```sh
just apply <host> build      # downloads + compiles: 100% safe, nothing is activated
just apply <host> test       # activates without switching: no generation, no boot
just apply <host>            # switch: activates and creates a new generation
```

**Progress from core to edge**: deploy nodes in this order, to never cut off
access to a node by the one preceding it.

```d2
style.fill: transparent
direction: right

hcs: HCS
gwl: Local gateway
hl: Local hosts
gwd: Remote gateways
hd: Remote hosts

hcs -> gwl -> hl -> gwd -> hd
```

:::caution[Why this order]
A remote host's connectivity depends on its gateway, which depends on the VPN
coordinated by the HCS. Deploying a link before its support can make subsequent
hosts unreachable.
:::

## Updating

The system is locked down by *flakes*. Updating = refreshing the inputs,
then redeploying.

```sh
just update-flake     # met à jour dnf/ + racine, commit les locks
just apply '*'        # déploie la mise à jour
```

:::caution[Always test first]
Before a wide rollout, validate locally: `just check`, then
`just apply <pilot-host>` on **a** single test host.
:::

## Updating the fleet with fleet-update

`fleet-update` runs the entire update in a single command&nbsp;: flakes, building
of all hosts, testing in waves (the hosts the network depends on first), then
final activation of validated hosts.

![Interface of fleet-update](../../../../../../assets/dfu-screenshot-01.png)

:::caution[Options not yet available]
The `--ai-*` options are accepted, with no effect for now.
:::

### Launch

```sh
just fleet-update [options]
```

The recipe picks the tool to run, in this order&nbsp;:

| Situation | Tool run |
|---|---|
| Co-development (`src/dnf-fleet-update/` present) | The sources, with `bun` |
| Active `darkone.admin.fleet-update` module | The installed `fleet-update` command |
| Any other case | `nix run .#fleet-update`, per the project's `flake.lock` |

:::caution[Prerequisites]
- Clean git trees: project, and `dnf/` in co-development.
- `var/deployments/` ignored by git: `/var/*` rule from the boilerplate.
:::

{/* t:p 5a5612c044a6c26c7b9082190d8fa9494c2c9c9af02ece0f48358324cbbf49d3 */}
### How a launch runs

<Steps>
1. **Update** : `nix flake update` of the project then of `dnf/` (co-development), `just clean`, one commit per repository.
2. **Selection** : hosts, profiles and zones read from `var/generated/`, filtered by `--on` ; current zone inferred from the local IP.
3. **Build** : all selected hosts, reachable or not, on the deployment machine.
4. **Test** : `switch-to-configuration test`, one wave per profile; the next wave starts when all its hosts are OK or excluded.
5. **Switch** : all hosts validated in test, **all at once**, regardless of wave order.
</Steps>

Three options shorten this launch&nbsp;:

| Option | Effect |
|---|---|
| `--build-only` | Stops after the build; in interactive mode, offers to continue |
| `--skip-test` | No test: the switch happens wave by wave, right after the build |
| `--skip-switch` | No switch: the launch stops on what the test left in place |

:::note[Why the switch is not done in waves]
Waves protect an unproven configuration. Once the test succeeds on each host,
there is nothing left to protect&nbsp;: the switch goes out in one go, with at
most `--max-parallel` hosts activated simultaneously. With `--skip-test`,
nothing has been proven&nbsp;: the switch follows the wave order again.
:::

:::tip[Resuming an interrupted launch]
`--resume` restarts from the last folder in `var/deployments/`&nbsp;: update
skipped, waves and options of the original launch, and the hosts that still had
to be done (remaining, offline, failed, or only tested). Builds are reused if
the project and `dnf/` revisions have not moved and the paths are still in the
store&nbsp;; otherwise they are rebuilt. Nothing to resume&nbsp;: exit code `2`,
no launch.
:::

### Wave order and critical hosts

The fleet's default values are declared in `config.yaml`&nbsp;:

```yaml
# etc/config.yaml
network:
  fleetUpdate:
    deploymentOrder: "hcs:gateway:server:[others]:laptop"
    criticalProfiles: "hcs:gateway:server"
```

| Key | Role |
|---|---|
| `deploymentOrder` | One test wave per host profile, in that order |
| `criticalProfiles` | Profiles whose failures also go to the incident room |

Profiles separated by `:`, `[others]` designates the unlisted profiles. Optional block&nbsp;: without it, the tool applies the values above. The `--deployment-order` and `--critical-profiles` options take precedence over `config.yaml`.

{/* t:p 886fda88630e88793bf0ce85a815564400da16f6285ec72524117ef0c9674244 */}
### Timeouts and monitoring

Two other optional blocks in `config.yaml` set the durations&nbsp;:

```yaml
# etc/config.yaml
network:
  fleetUpdate:
    pingInterval: 15
    timeouts:
      build: 10800
      ssh: 30
```

| Key | Role | Default |
|---|---|---|
| `pingInterval` | Seconds between two pings of the tracked hosts | `15` |
| `timeouts.<clé>` | Maximum duration of an operation, in seconds | depends on the operation |

`timeouts` keys, in the order of the launch&nbsp;:

| `timeouts.<clé>` | Default (s) |
|---|---|
| `flakeUpdate` | 120 |
| `clean` | 60 |
| `commit` | 60 |
| `eval` | 1200 |
| `build` | 10800 |
| `copy` | 3600 |
| `activation` | 300 |
| `ssh` | 30 |
| `ping` | 5 |
| `matrix` | 30 |
| `killGrace` | 10 |

:::note[An unknown key stops generation]
`just generate` checks the key names and rejects a zero or negative timeout&nbsp;:
otherwise a typo would silently fall back to the default value.
:::

### Report and Matrix alerts

Each launch writes its folder in `var/deployments/<date>-<mode>/`&nbsp;:
`report.md` (the report), `state.json` (the state `--resume` picks up),
`events.jsonl` and the logs per host. The path is displayed at the end of the
launch.

The `--send-report` option sends this report to the rooms of the
[alert bot](/en/doc/admin-guide/operate/alerts/), installed beforehand with
`just configure-alert-bot`.

| Situation | Room | Content |
|---|---|---|
| Launch finished | warnings | Summary&nbsp;: hosts by status, duration, known errors |
| Critical hosts not deployed | incidents | Separate message&nbsp;: affected hosts and reasons |
| Stopped on error | incidents | Error that stopped the launch, then summary |

A host is critical when its profile appears in `criticalProfiles`. After a
stop, hosts left in `test` complete the incident message&nbsp;: a reboot would
bring them back to their previous generation.

The message reuses the report header, with the exit code in the title&nbsp;:

```markdown
**Fleet Update Report** (1)

Error: srv-ag: activation failed

- Started at 2026-09-17 02:00:00 UTC, duration: 4m12s
- Options: partial run, selection gw-*, test skipped, 10 in parallel
- Hosts: 5 deployed, 1 failed (srv-ag)
- Run stopped on error
```

:::note[When the send fails]
The launch stays valid and the report is written, but the command exits with `3`.
Under the timer, the unit goes into a failed state, hence the
`SystemdUnitFailed` alert.
:::

:::caution[What sending requires]
Sending goes through the recipe [`just send-msg`](/en/doc/admin-guide/operate/alerts/#sending-a-message-to-a-room)&nbsp;:
rooms and token remain the framework's responsibility, the tool only writes the
text. Nothing is sent if the bot is not provisioned, nor on an abort (`^C`,
service stop).
:::

### Daily execution

On the deployment host, the module installs the tool and, with `timer.enable`,
runs `fleet-update --no-ui` every day&nbsp;:

```nix
# usr/machines/<hôte>/default.nix
darkone.admin.fleet-update = {
  enable = true;
  user = "admin";
  timer.enable = true;
};
```

| Option | Default | Role |
|---|---|---|
| `user` | none | Project owner: git, age key, AI, Matrix |
| `workDir` | `/etc/nixos` | Consumer project on disk |
| `timer.onCalendar` | `*-*-* 04:00` | Launch time |
| `timer.extraArgs` | `[ ]` | Options added to `--no-ui`, `--send-report` for example |
| `timer.timeout` | `6h` | Maximum duration of a launch |

:::note[Exit codes and alerts]
An already-running launch (code `4`) is not an error. Any other failure, or an
overrun of `timer.timeout`, puts the unit into a failed state and triggers the
[alert](/en/doc/admin-guide/operate/alerts/) `SystemdUnitFailed`.
:::

:::caution[Account and deployment host]
The timer requires `darkone.admin.nix` on the host, and a `user` account with
passwordless `sudo`.
:::

:::note[Daily report]
`--send-report` will become the default of `timer.extraArgs` when the packaged
version of the tool knows how to send it. Until then, add it after checking the
send manually.
:::

## Binary cache

Two services combine to avoid recompiling or re-downloading derivations on each
deployment.

| Service | Role |
|---|---|
| `harmonia` | Serves the local `/nix/store`, signed, **directly** to hosts (LAN, or VPN if `global`). |
| `nix-cache` | Per-zone `nginx` proxy that caches the public `cache.nixos.org` cache on the gateway. |

A host queries these sources in the following priority order. The first fetch
from the Internet is thus shared across the whole zone.

| Priority | Source | Scope |
|---|---|---|
| 20 | zone `harmonia` | LAN, what the zone has compiled |
| 35 | zone `nix-cache` proxy | LAN, shared mirror of the public cache |
| 40 | `cache.nixos.org` directly | safety net if the gateway is down |
| 45 | `global` `harmonia` | last resort, over the VPN |

:::note[How the order is guaranteed]
Nix does not follow the order of the `substituters` list; it sorts caches
according to the priority each one announces in its `nix-cache-info`. But these
announced values are equal: all `harmonia` services declare 30, and the proxy
relaying `cache.nixos.org` as-is declares 40, like direct access to the public
cache. DNF therefore sets the priority in the substituter URL (`?priority=35`),
which overrides the announced value and makes the table order explicit.

Two intended consequences. The zone proxy goes **before** direct access to the
public cache, otherwise zone sharing would never happen. And a `global`
`harmonia` goes **after** this public cache: `harmonia` serves a whole
`/nix/store` without being able to tell what it compiled from the rest, so a
well-stocked host would capture all the traffic the public cache is meant to
serve. As a last resort, it is only consulted for what `cache.nixos.org` does
not have, that is, its own builds.
:::

:::note[A host does not use its own `harmonia`]
This service serves its own `/nix/store`, so it can only provide paths already
present locally. On that host, anything missing necessarily comes from another
source: that is normal, its `harmonia` only benefits the **other** machines in
the zone.
:::

:::tip[Roaming host (multi-zone portable)]
A laptop that moves between zones should not keep substituters frozen to its
declared zone: unreachable elsewhere, they cost timeouts on every request.
Enable *roaming* mode:

```nix
# usr/machines/<hôte>/default.nix
darkone.service.nix-cache.roaming = true;
```

Its substituters become **neutral** names (`harmonia.dnf.internal`,
`nix-cache.dnf.internal`) that each zone's DNS resolves to its own caches → the
cache follows the machine. Outside any zone, immediate NXDOMAIN response →
direct fallback to `cache.nixos.org`, with no delay. Since signing keys are
shared across the whole network, nothing else to configure.
:::

:::note[Activation]
`harmonia` and `nix-cache` are [services](/en/doc/admin-guide/operate/services/)
to enable on a network host (`nix-cache` on the zone gateway). The harmonia
signing key is managed by
[sops](/en/doc/admin-guide/operate/secrets/) (`just configure-admin-host`).
:::

:::tip[Why a single-upstream proxy]
`nix-cache` relays only **one** upstream (`cache.nixos.org`): it caches
`narinfo` and `nar` as-is, signatures intact. No URL rewriting and no database,
hence no HTTP 500 "invalid nar hash" error from the old `ncps` relay.
:::

## Build farm

Fetching a package and building it are two distinct needs. The binary cache
above covers the first. For the second, a powerful network host can take over
the long compilations of an administration host.

Declare it with the `build-farm` feature:

```yaml
# etc/config.yaml
    features: ["build-farm"]
```

Each administration host then adds it to its `nix.buildMachines`, connecting
over SSH with the `nix` deployment account. Nothing else to configure: the key
and the authorization are already in place across the whole fleet.

:::tip[Only long compilations leave]
The delegation is deliberately narrow: the farm is only offered derivations
declaring `requiredSystemFeatures = [ "big-parallel" ]`, i.e. the kernel,
browsers, `llvm`, `rustc`… Everything else is built locally. This is decisive
when the farm sits behind a slow link, since only the requested result makes
the return trip.

Adjust with `darkone.admin.nix.remoteBuilders`: `maxJobs`, `speedFactor`, and
`mandatoryFeatures` (empty list = everything goes to the farm).
:::

:::caution[A farm is not a priority cache]
Do not promote a remote farm to a priority `global` `harmonia` to share its
results: `harmonia` serves the whole `/nix/store` and would capture the traffic
the public cache is meant to serve, across the slowest link on the network.
That is the role of level 45 in the table above: last resort, never the main
source.
:::

:::note[Fallback if the farm is unreachable]
The administration host keeps `big-parallel` in its own `system-features`. When
the farm does not respond, Nix simply resumes the build locally instead of
failing. Do not remove this feature to force delegation.
:::
