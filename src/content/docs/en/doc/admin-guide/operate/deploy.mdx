The fleet is deployed with [colmena](https://github.com/zhaofengli/colmena): a single command builds and applies the configuration on one or more hosts, remotely, from the admin workstation.

{/* t:p d4a06fc139c0d5029ddc5205311c422d5da5a5e1fe1b2e6d014d42aae5b8629c */}
## Apply a configuration

```sh
just apply <target> [action]    # alias : a
```

- **target** = hostname, pattern (`'*'`), list (`a,b`) or colmena tag (`@server`).
- **action** = `switch` (default), `boot`, `test` or `build`.

| Command | Purpose |
|---|---|
| `just apply <target>` | Build + activate on the target(s) |
| `just apply-local` | Apply on the current machine (alias `al`) |
| `just apply-verbose <target>` | Same as `apply` in trace mode (alias `av`) |

:::tip[Build on target]
`apply` builds **on the target host** (`--build-on-target`): the admin workstation doesn't need the power or architecture of the deployed machines.
:::

## Deploy safely

**Build confidence through action**: each step is less risky than the next.

```sh
just apply <host> build      # downloads + compiles: 100% safe, nothing is activated
just apply <host> test       # activates without switching: no generation, no boot
just apply <host>            # switch: activates and creates a new generation
```

**Progress from core to edge**: deploy nodes in this order, to never cut off
access to a node by the one preceding it.

```d2
style.fill: transparent
direction: right

hcs: HCS
gwl: Local gateway
hl: Local hosts
gwd: Remote gateways
hd: Remote hosts

hcs -> gwl -> hl -> gwd -> hd
```

:::caution[Why this order]
A remote host's connectivity depends on its gateway, which depends on the VPN
coordinated by the HCS. Deploying a link before its support can make subsequent
hosts unreachable.
:::

## Updating

The system is locked down by *flakes*. Updating = refreshing the inputs,
then redeploying.

```sh
just update-flake     # met à jour dnf/ + racine, commit les locks
just apply '*'        # déploie la mise à jour
```

:::caution[Always test first]
Before a wide rollout, validate locally: `just check`, then
`just apply <pilot-host>` on **a** single test host.
:::

## Updating the fleet with fleet-update

`fleet-update` chains the entire update into a single command&nbsp;: flakes,
building all hosts, publishing the locks across the fleet, testing in waves
(hosts the network depends on first), then final activation of the approved
hosts.

![fleet-update interface](../../../../../../assets/dfu-screenshot-01.png)

:::note[AI at work]
AI **analyzes**, acts on services, fixes code and proposes
improvements&nbsp;: see [AI analysis](#ai-analysis),
[Repairing a service](#repairing-a-service),
[Repairing through code](#repairing-through-code) and
[Improvement suggestions](#improvement-suggestions).
:::

### Launch

```sh
just fleet-update [options]
```

The recipe picks the tool to run, in this order&nbsp;:

| Situation | Tool run |
|---|---|
| Co-development (`src/dnf-fleet-update/` present) | The sources, with `bun` |
| Active `darkone.admin.fleet-update` module | The installed `fleet-update` command |
| Any other case | `nix run .#fleet-update`, per the project's `flake.lock` |

:::caution[Prerequisites]
- Clean git trees: project, and `dnf/` in co-development.
- `var/deployments/` ignored by git: `/var/*` rule from the boilerplate.
:::

{/* t:p 2281cf145dd58450b9b79836a9794b5bb6d08cfad2eabd91e6f23afe91fe018e */}
### How a run unfolds

<Steps>
1. **Update**: `nix flake update` of the project then of `dnf/` (co-development), `just clean`, one commit per repository.
2. **Selection**: hosts, profiles and zones read from `var/generated/`, filtered by `--on`; current zone inferred from the local IP; one builder elected per host.
3. **Build**: all selected hosts, reachable or not, each on its builder.
4. **Publish**: the closure of each reachable host is brought into its store, outside waves, before any activation.
5. **Test**: `switch-to-configuration test`, one wave per profile; the next wave starts when all its hosts are OK or set aside.
6. **Switch**: all hosts validated in test, **all at once**, regardless of wave order.
</Steps>

:::note[Why publish before activating]
Serving and activating are two distinct needs. Once each host is served, a wave
depends only on `ssh`: a gateway that restarts its network no longer deprives
anyone of their substituter.

The host **pulls** first (`nix build --max-jobs 0`, which substitutes without
ever compiling locally), and is only **pushed** as a fallback. A pull that fails
is the ordinary case: a very fresh path is not yet in any cache.
:::

Three options shorten this flow:

| Option | Effect |
|---|---|
| `--build-only` | Stops after the build; in interactive mode, offers to continue |
| `--skip-test` | No test: the switch happens wave by wave, right after the build |
| `--skip-switch` | No switch: the run stops on what the test left in place |

:::tip[Preload the fleet without activating anything]
`--skip-test --skip-switch` builds **and** publishes, then stops: each host
holds its closure (state `ready`) without having activated anything. A
subsequent run, or a `--resume`, then activates without copying anything more.
Handy for separating a large package download from a short intervention window.

`--build-only` is the other extreme: nothing leaves the deployment machine, the
publication itself is skipped.
:::

:::note[Why the switch is not wave-based]
Waves protect an unproven configuration. Once the test passed on each host,
there is nothing left to protect: the switch fires at once, at most
`--max-parallel` hosts activated simultaneously. With `--skip-test`, nothing has
been proven: the switch resumes the wave order.
:::

:::tip[Resume an interrupted run]
`--resume` restarts from the last folder of `var/deployments/`: update skipped,
waves and options of the original run, and the hosts that still had work
(remaining, offline, failed, or only tested). Builds are reused if the revisions
of the project and of `dnf/` have not moved and the paths are still in the
store; otherwise they are redone. Nothing to resume: exit code `2`, no run.
:::

### Distributed build

The deployment machine must not be the bottleneck of the fleet. Each host is
therefore built by the **elected builder** for it. The election is recomputed at
each run from `var/generated/`, never declared: changing the deployment topology
must not rebuild the fleet.

| Order | Builder kept | Condition |
|---|---|---|
| 1 | The host itself | `auto-build` feature declared on the host |
| 2 | The `harmonia` host of its zone | The zone has one |
| 3 | The `global` `harmonia` host | One exists in the fleet |
| 4 | The deployment machine | Default |

The rule fits in one sentence: **a builder must be able to serve what it
builds**. Hence the choice of `harmonia` hosts, whose `/nix/store` is already the
cache of their zone, with nothing to bootstrap. A gateway without `harmonia`
does not fit: its paths are not in any substitute.

The result stays on the builder. Publication then brings it to the hosts of the
zone, over LAN, through their usual substitute.

:::note[`nixpkgs` sources downloaded by the builder]
Each system embeds the `nixpkgs` source (about 200&nbsp;MiB), new at each update
and absent from any cache. Before sending it the derivations, the tool therefore
asks the builder to download itself, from GitHub, the sources locked in
`flake.lock` that its builds need: they no longer go through the upstream link of
the deployment machine. A builder that cannot reach `github.com` receives them
pushed, as before, without failure.
:::

```yaml
# etc/config.yaml
    features: ["auto-build"]
```

:::tip[When to declare `auto-build`]
A host that builds itself no longer receives any closure. This is decisive for a
host isolated behind a slow link that carries a large package absent from the
public cache, and it is the answer for a host of another architecture.

The choice is made **per host**, never per zone: RAM and disk are properties of
the machine. Counterpart to weigh: the closure of derivations, several hundred
MiB, goes up to it at each run that moves `nixpkgs`. It is the report's copy
counters that settle the case, not intuition.
:::

:::note[Automatic fallback]
Builder unreachable, failing, or of an architecture incompatible with its
target&nbsp;→ the build falls back to the deployment machine. No host fails
because of a delegation, and the report names the builder that actually built.
:::

The `--no-distributed-build` option brings everything back to the center,
whatever the election. It is a debugging escape hatch: the rule comes from the
fleet, the exception from the command line.

:::caution[A zone without `harmonia` is expensive]
Without a zone cache, there is neither local builder nor common source: each
host gets its closure pushed, one by one, from the deployment machine. The
report lists these zones and the number of pushed bytes shows it. Declare a
[`harmonia`](#binary-cache) on a host of the zone.
:::

### Wave order and critical hosts

The fleet's default values are declared in `config.yaml`&nbsp;:

```yaml
# etc/config.yaml
network:
  fleetUpdate:
    deploymentOrder: "hcs:gateway:server:[others]:laptop"
    criticalProfiles: "hcs:gateway:server"
```

| Key | Role |
|---|---|
| `deploymentOrder` | One test wave per host profile, in that order |
| `criticalProfiles` | Profiles whose failures also go to the incident room |

Profiles separated by `:`, `[others]` designates the unlisted profiles. Optional block&nbsp;: without it, the tool applies the values above. The `--deployment-order` and `--critical-profiles` options take precedence over `config.yaml`.

### Timeouts and monitoring

Two other optional `config.yaml` blocks set the durations:

```yaml
# etc/config.yaml
network:
  fleetUpdate:
    pingInterval: 15
    timeouts:
      build: 10800
      ssh: 30
```

| Key | Role | Default |
|---|---|---|
| `pingInterval` | Seconds between two pings of tracked hosts | `15` |
| `timeouts.<clé>` | Maximum duration of an operation, in seconds | depending on the operation |

`timeouts` keys, in the order of the run:

| `timeouts.<clé>` | Default (s) |
|---|---|
| `flakeUpdate` | 120 |
| `clean` | 60 |
| `commit` | 60 |
| `eval` | 1200 |
| `build` | 10800 |
| `publish` | 3600 |
| `copy` | 3600 |
| `activation` | 300 |
| `ssh` | 30 |
| `ping` | 5 |
| `matrix` | 30 |
| `killGrace` | 10 |

:::note[An unknown key stops generation]
`just generate` checks key names and refuses a zero or negative timeout: a typo
would otherwise fall back to the default value, in silence.
:::

### Errors, diagnostics and repair

A common error should be readable without knowing Nix. The tool keeps a **signature
table**: a recognized pattern in a command's output gives a plain-language
message and the action to take.

| Recognized pattern | What it means | Action |
|---|---|---|
| `mismatch in field 'narHash'` | `nix-eval-jobs` isn't bound to the same Nix as the system | Stop |
| `lacks a signature by a trusted key` | The deployment account isn't a *trusted user* on this host | Stop |

The message is shown as the run progresses (`hint:`), once only, and is also
found in the report's **Known errors** section. It is added to the host's reason,
it never replaces it: the full trace stays in `logs/`.

| Table action | What the tool does |
|---|---|
| Retry | Replays the command, at most three times, if it is replayable: evaluation, build, derivation copy, pull |
| Exclude | Continues without the host; if already activated, first brings it back to its origin |
| Stop | Stops the run, without asking any question |

No signature calls for a retry today: the two known entries are stops.

:::caution[A table action is not discussed]
It also applies in interactive mode: a deterministic repair comes before the
question. A nightly run and a supervised run therefore handle the same error
the same way. The `known error decides: stop` line says it as the run
progresses, and the host's reason stays in the report.

Activation, profile installation, commit, and unit restart are **never**
replayed on their own: only commands that can be re-executed without
consequence are.
:::

**Deterministic collection.** A host that fails while remaining reachable is
interrogated before any decision: `systemctl status`, list of failing units, then
each one's log since the start of its wave.

| What is collected | Where it goes |
|---|---|
| Full output of commands and logs | `logs/<hôte>.diag` in the run folder |
| Failing units, error extract | Report's **Diagnostics** section, incident message |

**Unit restart.** An activation that ends with failing units leaves the host in
`error` state. The tool then attempts a simple repair.

<Steps>
1. Ten-second wait: a unit that is slow to start isn't a failing unit.
2. `systemctl restart` of all the failing units, in a single command.
3. Re-reading the failing-unit list: it is what concludes, not the exit code.
</Steps>

Everything comes back up → the host resumes its course, rejoins the switch with
the others, and the report notes a **probable activation-order issue**
(**Notes** section). A unit resists → the host stays in `error`, its name and the
unit's are in the report.

:::note[What the interface shows meanwhile]
The host carries a blinking label to the right of its name, with its activity
indicator: `under repair` in yellow during deterministic repair,
`AI analysis` and `AI repair` in magenta when the AI takes over.
:::

### AI analysis

AI **explains** a failure&nbsp;: it reads the deployment state, the logs and,
when needed, the code, then returns a plain-language analysis. With
`--ai-error-action repair` it can then **act on the failed units**, and nothing
else (see [Repairing a service](#repairing-a-service)). The deployment never
waits for it&nbsp;— an analysis that fails, times out or exceeds its budget
leaves the host exactly where it was.

Two options drive it, **both set to `none` by default**&nbsp;: nothing goes to
an AI until you ask for it. A third one selects the tool.

| Option | Default | Role |
|---|---|---|
| `--ai-analysis none\|passive\|active` | `none` | Analysis depth, plus an end-of-deployment summary in the report |
| `--ai-error-action none\|analysis\|repair` | `none` | What AI does when a host fails |
| `--ai-model <tool>[:<model>][@<effort>]` | `claude:opus@high` | Tool and model, for instance `opencode:ollama/qwen3:32b` |
| `--ai-context <text>` | none | Instruction or context added to every AI prompt |

```sh
just fleet-update --ai-analysis passive          # enriched report, nothing more
just fleet-update --ai-error-action analysis     # every failure is explained
```

For instance, `--ai-context "Answer in French and stay concise."` guides the
style of the answers. To avoid repeating it on every deployment, set it once
per host with the module's `aiContext` option&nbsp;: it writes it to
`/etc/fleet-update/ai-context`, which every deployment reads, `just fleet-update`
as well as the timer. The `--ai-context` option takes precedence over that file.
When resuming, the context of the initial deployment is picked up&nbsp;; an
explicit `--ai-context` replaces it.

```nix
# usr/machines/<host>/configuration.nix
darkone.admin.fleet-update.aiContext = "Answer in French and stay concise.";
```

The fleet's default model is set in `config.yaml`, the option takes
precedence&nbsp;:

```yaml
# etc/config.yaml
network:
  fleetUpdate:
    aiModel: "claude:opus@high"
```

**AI tools are not a dependency of the tool.** `claude` and `opencode` are
looked up in the `PATH`&nbsp;; the module's `aiPackages` option puts them there
for the daily deployment. Missing or declined&nbsp;→ a warning in the
deployment log, a note in the report, and the rest of the run proceeds without
AI.

#### What AI is allowed to do

AI has **neither a shell nor free-form SSH**. It only acts through
`fleet-update` tools, and the requested level determines the list it is
shown&nbsp;: what it does not see there, it cannot ask for.

| Level | Tools presented |
|---|---|
| `passive` | Deployment state, host diagnostics, build and activation logs, grouped deployment warnings |
| `active`, `analysis` | + reading, searching and listing code (project and `dnf/`), host units and logs (including user units), read-only |
| `repair` | + one action on a host's failed units, and editing the code that describes them |

The effective level is the **highest of the two options**&nbsp;: `--ai-analysis
passive --ai-error-action analysis` gives `active`. The built-in tools of
`claude` and `opencode` are cut off, and the instructions those tools would
pick up in the project (`CLAUDE.md`, user settings) are neutralized&nbsp;: AI
only sees what we show it.

| Guardrail | Effect |
|---|---|
| Read path | Confined to the project and `dnf/`, after symlink resolution&nbsp;; `usr/secrets/` and `.trash/` refused |
| Host, unit | Checked against the deployment table before any command |
| Excerpts | 200 log lines, 400 source lines, truncated at the end&nbsp;: the error is at the bottom |
| Timeout, budget | 300 seconds per analysis&nbsp;; dollar budget for `claude` |

**Every tool call leaves a trace** — one line in the deployment log
(`AI reads usr/modules/nginx.nix`) and one line in `logs/ai.log` of the
deployment directory. A call refused by a guardrail is traced too, along with
its reason.

#### When it steps in

<Steps>
1. **A host fails**, with `--ai-error-action` ≠ `none` : after deterministic collection and unit restart, before the question that decides its fate. The host shows `AI analysis` in magenta during that time, then returns to its state.
2. **A host recovers** after a unit restart, with `--ai-analysis` ≠ `none` : the analysis explains the activation order, without touching the host's state.
3. **End of deployment**, with `--ai-analysis` ≠ `none` : a summary of everything, written before the report that carries it.
4. **End of deployment**, with `--ai-analysis active` : a review of the warnings, which files [improvement suggestions](#improvement-suggestions).
5. **`a` key**, at any time : a free-form question. It gets an answer even under `--ai-analysis none` — with no tool at all: `none` removes the tools and automatic analysis, not the conversation.
</Steps>

#### Repairing a service

`--ai-error-action repair` opens a **second session** on the host, right after
the analysis and in the `AI repair` state. The first of its tools acts on
services: `systemctl start`, `stop`, `restart` or `reset-failed` **on the
units the run saw fail**. This is the gesture to prefer: it
is local and reversible. When it is not enough, the AI fixes the code
([Repairing through code](#repairing-through-code)).

```sh
just fleet-update --ai-error-action repair
```

<Steps>
1. The grouped deterministic restart failed: the host stays in `error`.
2. The AI analyses, in the `AI analysis` state, read-only.
3. The AI repairs, in the `AI repair` state: it acts, then re-reads the failed units.
4. Nothing failing anymore → the host resumes its course and joins the switch. Otherwise → the usual question, `revert` / `keep` / `stop` / `rollback`.
</Steps>

| Guard-rail | Effect |
|---|---|
| Units | **Only those the collection saw failing** on this host; any other is refused |
| Host | Refused if it is not currently being repaired: a read session never acts |
| Attempts | Three actions per host, refusals not counted; the fourth is refused |
| Stopping mid-run | A run that stops repairs nothing: it is a new operation |
| Confirmation | In interactive mode, a button question before each action: `apply` or `skip` |

In non-interactive mode (night timer, `--no-ui`), **the action passes without asking**.
It is strictly less risky than what the run already does without
witness: the deterministic repair restarts **all** the host's
failed units.

Each action is **counted**, not just traced: it ends up in
`state.json` and in the **AI repair** section of the report, refusals included, with its
reason. A repaired host also carries a note in the report.

#### Repairing through code

When no restart can help, AI **writes the fix** in the project, validates it,
commits it, and **that host alone** is rebuilt then redeployed.

<Steps>
1. `edit_code` replaces an exact passage (present only once), or rewrites an entire file. The git tree must be clean before the first edit, and the diff goes into `logs/ai.log`.
2. `validate` runs the project cleanup, then re-evaluates and rebuilds **that host alone**.
3. `commit` writes `fix(<scope>): <subject>`, the scope naming what the fix touches (`fix(nginx): …`). In co-development, `dnf/` is committed first, then the project and its realigned lock.
4. The host goes back to `built` with its new path&nbsp;; its wave serves it one more time: copy, activation, conclusion.
</Steps>

| Guardrail | Effect |
|---|---|
| Paths | The project, and `dnf/` in co-development&nbsp;; never `usr/secrets/`, `.trash/`, `.git/`, `var/generated/`, `etc/config.yaml` nor a `*.lock` |
| Outside co-development | `dnf/` is a store path&nbsp;: writing to it is refused, and would have changed nothing anyway |
| Tree | Dirty before the first edit → refusal&nbsp;: a repair commit carries only the fix |
| Attempts | **One attempt is a change.** Validating and committing cost none, otherwise fixing would cost three times more than restarting |
| Hooks | Never bypassed&nbsp;: the commit goes through the repository gate like any other |
| Message | `dnf/` is published&nbsp;: a framework commit naming a fleet host is refused |

:::danger[The fleet ends up straddling two revisions]
Only the repaired host is rebuilt&nbsp;: **all the others keep the path the
deployment built at the start**, and switch over with it. Until the next
deployment, the fleet therefore runs on two revisions. The report and the
alert message say so in plain words&nbsp;: `Repaired in flight: <host>`.

Consequence on resume&nbsp;: after a repair commit, `--resume`
**rebuilds everything**. That is the guarantee itself — you do not redeploy
paths built before the fix.
:::

:::caution[Non-interactive too]
Under the night timer, AI edits, commits and redeploys **without asking**. An
unreviewed commit can therefore land on the branch. What makes this
acceptable&nbsp;: the required clean tree, the confined paths, the logged diff,
the three attempts, and the automatic rollback that stays armed. If this is
not what you want, leave `--ai-error-action` at `none` or at `analysis`
in `timer.extraArgs`.
:::

:::caution[What AI repair is not]
It is neither [deterministic repair](#errors-diagnostics-and-repair)
(grouped restart, once, without AI), nor the re-run of a command decided by
the signature table, nor a decision — excluding or stopping happens first,
without questions. AI only arrives after what is deterministic.
:::

:::note[Analysis adds, it replaces nothing]
A host's raw reason, its failed units and the entire trail of `logs/`
remain what they were. The analysis complements them, like the plain-language
message of a known error.
:::

#### Improvement suggestions

With `--ai-analysis active`, the deployment ends with a **review of its
warnings**&nbsp;: renamed or deprecated option, a change that would silence a
warning, an issue to investigate. AI proposes, it changes **neither the code
nor the fleet**.

<Steps>
1. The warnings from all deployment logs are grouped by shape&nbsp;: the same one on ten hosts counts once. No warning → no review, nothing is paid.
2. AI reads the suggestions already filed, then searches the code for where each warning comes from.
3. Every useful finding becomes a `var/deployments/suggestions/<slug>.md` file&nbsp;: what, where (`file:line`), why, and the proposed improvement.
4. The report's **Suggestions** section lists what the deployment filed or reviewed. Nothing goes to Matrix&nbsp;: this is not an alert.
</Steps>

The files **survive deployments**. A finding that comes back does not rewrite
its file&nbsp;: only the `Last seen` and `Runs` header lines change.

```markdown title="var/deployments/suggestions/nginx-deprecated-option.md"
# Replace a deprecated nginx option

- Status: open
- First seen: 20260101T020000Z-full
- Last seen: 20260108T020000Z-full
- Runs: 4

The option is deprecated upstream: `usr/modules/web.nix:12`, …
```

| To | Do |
|---|---|
| Silence a suggestion | Write `Status: ignored` in its header&nbsp;: it stays tracked, out of the report |
| Forget it | Delete the file&nbsp;: a finding that comes back starts from scratch |
| Apply it | Fix the code, then delete the file |

The scope follows the mode&nbsp;: in co-development, the project and `dnf/`&nbsp;;
otherwise the project alone (a finding that only the framework can fix is not
filed).

### Report and Matrix alerts

Each deployment writes its directory under
`var/deployments/<date>-<mode>/`&nbsp;:
`report.md` (the report), `state.json` (the state `--resume` picks up),
`events.jsonl` and the per-host logs. The path is displayed at the end of the
deployment.

The report details what the deployment actually did&nbsp;:

| Section | What it gives |
|---|---|
| **Steps**, **Waves** | Duration of each step, composition and duration of each wave |
| **Builders** | Who built what, including fallbacks |
| **Copies** | Per host: pulled paths and by which substituter, pushed paths, volume |
| **Zones without a cache** | Deployment zones that no `harmonia` serves |
| **Hosts not deployed** | Hosts left aside, and the reason |
| **Diagnostics** | Per failed host: failed units, then an excerpt of the error |
| **Notes** | What the deployment observed: probable activation order after a unit restart |
| **AI analysis** | AI analysis: one entry per analyzed host, then the deployment summary |
| **AI repair** | AI actions: host, action, outcome, and the reason for a refusal. A repair commit also appears in the header, `Repaired in flight` |
| **Suggestions** | Improvement suggestions filed or reviewed by the deployment, except the ignored ones |
| **Known errors** | Pitfalls recognized by the signature table, in plain language |

:::tip[Reading the copy counters]
A host that pulls most of its data from `harmonia <zone>` proves that its
zone's cache does its job. A host that gets **pushed** a lot of volume is
instead a candidate for a `harmonia` in its zone, or for `auto-build`. No copy
line for a host&nbsp;→ it already had everything, nothing travelled.
:::

The `--send-report` option sends this report to the
[alert bot](/en/doc/admin-guide/operate/alerts/) rooms, installed beforehand by
`just configure-alert-bot`.

| Situation | Room | Content |
|---|---|---|
| Deployment finished | warnings | Summary&nbsp;: hosts by state, duration, known errors |
| Critical hosts not deployed | incidents | Separate message&nbsp;: hosts concerned, reasons and failed units |
| Stopped on error | incidents | Error that stopped the deployment, then the summary |

A host is critical when its profile is listed in `criticalProfiles`. After a
stop, the hosts left in `test` complete the incident message&nbsp;: a restart
would bring them back to their previous generation.

**Only the end-of-deployment summary** joins the message, never the per-host
analyses, and it is capped at six lines there&nbsp;: beyond that, the message
refers to `report.md`. An alert room is not a report.

The message reuses the report's header, with the exit code in the title&nbsp;:

```markdown
**Fleet Update Report** (1)

Error: srv-ag: activation failed

- Started at 2026-09-17 02:00:00 UTC, duration: 4m12s
- Options: partial run, selection gw-*, test skipped, 10 in parallel
- Hosts: 5 deployed (hcs, gw-ag, pc-ag, gw-cp, lt-cp), 1 failed (srv-ag)
- Run stopped on error
```

:::note[Sending not possible]
The deployment remains valid and the report is written, but the command exits
with `3`. Under the timer, the unit fails, hence the `SystemdUnitFailed` alert.
:::

:::caution[What sending requires]
Sending goes through the [`just send-msg`](/en/doc/admin-guide/operate/alerts/#sending-a-message-to-a-room)
recipe&nbsp;: rooms and token remain the framework's business, the tool only
writes the text. Nothing goes out if the bot is not provisioned, nor on an
abort (`^C`, service stop).
:::

### Daily run

On the deployment host, the module installs the tool and, with `timer.enable`, runs `fleet-update --no-ui` every day&nbsp;:

```nix
# usr/machines/<hôte>/configuration.nix
darkone.admin.fleet-update = {
  enable = true;
  user = "admin";
  aiContext = "Répondre en français et rester concis.";
  timer.enable = true;
};
```

| Option | Default | Role |
|---|---|---|
| `user` | none | Project owner: git, age key, AI, Matrix |
| `workDir` | `/etc/nixos` | Consumer project on disk |
| `aiContext` | `null` | Context added to the AI prompts of every run on the host, written to `/etc/fleet-update/ai-context`, even without `enable`&nbsp;; `--ai-context` overrides it |
| `timer.onCalendar` | `*-*-* 04:00` | Run time |
| `timer.extraArgs` | `[ ]` | Options added to `--no-ui`, `--send-report` for example |
| `timer.timeout` | `6h` | Maximum duration of a run |

:::note[Exit codes and alerts]
A run already in progress (code `4`) is not an error. Any other failure,
or a `timer.timeout` overrun, fails the unit and triggers
the `SystemdUnitFailed` [alert](/en/doc/admin-guide/operate/alerts/).
:::

:::caution[Deployment account and host]
The timer requires `darkone.admin.nix` on the host, and a `user` account with
passwordless `sudo`.
:::

:::note[Daily report]
`--send-report` will become the default for `timer.extraArgs` when the packaged
version of the tool knows how to send it. Add it in the meantime, after checking
the delivery by hand.
:::

## Binary cache

Two services combine to avoid recompiling or re-downloading the derivations at
each deployment.

| Service | Role |
|---|---|
| `harmonia` | Serves the local, signed `/nix/store` **directly** to the hosts (LAN, or VPN if it is `global`). |
| `nix-cache` | Per-zone `nginx` proxy that caches the public `cache.nixos.org` cache on the gateway. |

A `harmonia` host has a second role: it is the
[elected builder](#distributed-build) of its zone, because it can serve
what it builds.

A host queries these sources in the following priority order. The first fetch
from the Internet is thus shared across the whole zone.

| Priority | Source | Scope |
|---|---|---|
| 20 | zone `harmonia` | LAN, what the zone compiled |
| 35 | zone `nix-cache` proxy | LAN, shared mirror of the public cache |
| 40 | `cache.nixos.org` directly | safety net if the gateway is down |
| 45 | `global` `harmonia` | last resort, over the VPN |

:::note[How the order is guaranteed]
Nix does not follow the order of the `substituters` list, it sorts the caches
according to the priority each announces in its `nix-cache-info`. Yet these
announced values are tied: all `harmonia` declare 30, and the proxy relaying
`cache.nixos.org` as-is declares 40, like the direct access to the public cache.
DNF therefore fixes the priority in the substituter URL (`?priority=35`), which
overrides the announced value and makes the order in the table explicit.

Two intended consequences. The zone proxy sits **ahead of** the direct access to
the public cache, otherwise zone sharing would never happen. And a `global`
`harmonia` sits **behind** this public cache: `harmonia` serves a whole
`/nix/store`, without being able to tell what it compiled from the rest, so a
well-stocked host would capture all the traffic the public cache must serve. As
a last resort, it is only consulted for what `cache.nixos.org` does not have,
that is, its own builds.
:::

:::note[A host does not use its own `harmonia`]
This service serves its own `/nix/store`, so it can only provide paths already
present locally. On this host, everything missing necessarily comes from another
source: that is normal, its `harmonia` only benefits the **other** machines of
the zone.
:::

:::tip[Nomadic host (multi-zone portable)]
A laptop that changes zone must not keep substituters fixed on its declared
zone: unreachable elsewhere, they cost timeouts on every request. Enable the
*roaming* mode&nbsp;:

```nix
# usr/machines/<hôte>/configuration.nix
darkone.service.nix-cache.roaming = true;
```

Its substituters become **neutral** names (`harmonia.dnf.internal`,
`nix-cache.dnf.internal`) that the DNS of each zone resolves to its own caches →
the cache follows the machine. Outside any zone, an immediate NXDOMAIN response
→ direct fallback on `cache.nixos.org`, without delay. Signature keys being
common to the whole network, nothing else to configure.
:::

:::note[Activation]
`harmonia` and `nix-cache` are [services](/en/doc/admin-guide/operate/services/)
to enable on a network host (`nix-cache` on the zone gateway). The harmonia
signature key is managed by [sops](/en/doc/admin-guide/operate/secrets/)
(`just configure-admin-host`).
:::

:::tip[Why a single-upstream proxy]
`nix-cache` only relays **one** upstream (`cache.nixos.org`)&nbsp;: it caches
`narinfo` and `nar` as-is, signatures intact. No URL rewriting nor database,
therefore no HTTP 500 "invalid nar hash" error like the old `ncps` relay.
:::

## Build farm

Fetching a package and building it are two distinct needs. The binary cache
above covers the first. For the second, a powerful host of the network can take
on the long compilations of an administrative host.

Declare it with the `build-farm` feature:

```yaml
# etc/config.yaml
    features: ["build-farm"]
```

Each administrative host then adds it to its `nix.buildMachines`, joined over
SSH by the deployment account `nix`. Nothing else to configure: the key and the
authorization are already in place across the whole fleet.

:::tip[Only long compilations go away]
The delegation is deliberately narrow: the farm is only offered derivations
declaring `requiredSystemFeatures = [ "big-parallel" ]`, i.e. the kernel,
browsers, `llvm`, `rustc`... Everything else is built locally. This is decisive
when the farm is behind a slow link, since only the requested result makes the
return trip.

Adjust with `darkone.admin.nix.remoteBuilders`: `maxJobs`, `speedFactor`, and
`mandatoryFeatures` (empty list = everything goes to the farm).
:::

:::note[`build-farm` or `auto-build`?]
Two distinct mechanisms, combinable on the same host.

| Feature | Who uses it | What it moves |
|---|---|---|
| `build-farm` | Nix, on administrative hosts | Only the `big-parallel` derivations, whatever tool is launched |
| `auto-build` | `fleet-update`, at fleet build | The whole system closure of the host that declares it |

`build-farm` relieves an admin machine of its long compilations.
[`auto-build`](#distributed-build) removes a transfer to a host. They do
not replace each other.
:::

:::caution[A farm is not a priority cache]
Do not promote a remote farm to a priority `global` `harmonia` to share its
results: `harmonia` serves the whole `/nix/store` and would capture the traffic
the public cache must serve, across the slowest link of the network. That is the
role of level 45 of the table above: last resort, never primary source.
:::

:::note[Fallback if the farm is unreachable]
The administrative host keeps `big-parallel` in its own `system-features`. When
the farm does not answer, Nix simply resumes the compilation locally instead of
failing. Do not remove this feature to force delegation.
:::
