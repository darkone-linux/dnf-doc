Two paths, depending on how autonomous the user is&nbsp;: **non-technical** (we
ask them as little as possible) or **technical** (they define all their secrets,
the administrator knows none of them).

{/* t:p 2cef649a573d8ae4cb71a068c62eae3dd4356a1bba31bf4506c9c1955111391e */}
## Three account types

| Type | Declaration | Access |
|---|---|---|
| **Linux** | `users` + attached to a host | Session, services, vault, Matrix |
| **Services** | `users`, attached to no host | Services (SSO), vault, Matrix |
| **Matrix friend** | None | Matrix only |

- Every declared user automatically receives a [Kanidm](/en/doc/admin-guide/operate/sso/) **account**. Only its credentials are defined by hand.
- The Matrix account is created on first login in Element, **IDM** button.
- A Matrix friend signs up on their own with a token: see [Registering friends](/en/doc/admin-guide/operate/matrix/#inviting-friends).

## Choosing a path

| Secret | Non-technical | Technical |
|---|---|---|
| **Linux session** | Set by the admin | Entered by the user |
| **Kanidm identity** | Set by the admin, stored in the vault | Set by the user |
| **Master password** | Set by the user | Set by the user |
| **Vault 2FA** | Optional | At the user's choice |
| **Forgot master password** | The admin resets it | Lost vault |

:::tip[Non-technical: only one secret to remember]
The user only remembers their **master password**. Bitwarden fills in the
Kanidm username, password and 2FA code for them.
:::

## Declaring the account

Step common to both paths.

<Steps>

1. **Declare** the user in `etc/config.yaml`, with their `email`, and attach
   them to their hosts if they have a Linux account. See
   [Declaring a user](/en/doc/admin-guide/operate/users/#declare-a-user).

2. **Deploy** the HCS (Kanidm account) and the user's hosts:

   ```sh
   just clean
   just commit "user(new): alice"
   just apply @user-alice,hcs     # Services account: just apply hcs
   ```

</Steps>

The Kanidm account exists, with no credentials at all.

## Non-technical path

The administrator prepares all the credentials and stores them in a **shared
collection** of their vault. The user only defines their master password.

:::note[One-time setup: the organization]
Create a Vaultwarden organization (e.g. `Family`), then enable
*Security policies → Account recovery administration*, with *Automatic
enrollment*. Every new member is enrolled there: the administrator will be able
to reset their master password.
:::

<Steps>

1. **Collection**: in the organization, create the `alice` collection.

2. **Linux session** (Linux account only): choose the password, store it in the
   collection, then
   [define and deploy it](/en/doc/admin-guide/operate/users/#set-the-password).

3. **Kanidm identity**: create a reset link on the HCS, and open it
   **yourself**&nbsp;:

   ```sh
   just enter hcs
   kanidm person credential create-reset-token alice --name idm_admin
   ```

   Set there a Bitwarden-generated password and a TOTP code. Store both in an
   item of the collection (username, password, *Authenticator key (TOTP)*).

4. **Invite** the user to the organization (*Members → Invite member*), with the
   email from `config.yaml` and access to their collection.

5. **The user** receives the email, creates their vault and defines their
   **master password**. That is their only action.

6. **Confirm** the member (*Members → Confirm*): the collection appears in their
   vault.

7. **Install Bitwarden** on their browsers and smartphone.

</Steps>

:::note[Kanidm requires 2FA]
By default Kanidm refuses a password alone: a TOTP code or a security key is
required. Once stored in the item, the TOTP is filled in by Bitwarden.
:::

:::caution[Choose "self-hosted" in Bitwarden]
Bitwarden connects to bitwarden.com by default. Enter the URL of the network's
Vaultwarden **before** the master password.
:::

:::tip[YubiKey]
A [YubiKey](/en/doc/admin-guide/operate/yubikey/) replaces the session password
with a touch. It is the only credential the vault cannot fill in, since the
session opens before it.
:::

:::caution[A trust compromise]
The administrator knows the Kanidm and session credentials, and can reset the
master password. To make the user autonomous later on: they redefine their
credentials following the technical path, then leave the organization.
:::

## Technical path

The administrator only provides entry points: they know no secrets.

<Steps>

1. **Linux session** (Linux account only): the user enters their own password
   at the `just passwd alice` prompt. Only the hash is stored.

   Remotely, they instead send the hash (`mkpasswd -m sha-512`), which the
   administrator pastes with `just sops` under `user.alice.password-hash`.
   Then [validate and deploy](/en/doc/admin-guide/operate/users/#set-the-password).

2. **Kanidm identity**: create the reset link, and pass it on (link or
   QR code)&nbsp;:

   ```sh
   just enter hcs
   kanidm person credential create-reset-token alice --name idm_admin
   ```

   The user sets their password, TOTP and security keys there.

3. **YubiKey** (optional): `just yubikey alice`, with the user's key, who
   enters their own PIN. See
   [Passkey enrollment order](/en/doc/admin-guide/operate/yubikey/#passkey-enrollment-order).

4. **Vault**: invite them from the Vaultwarden administration
   (`/admin`, *Invite User*). They create their vault, then enable their 2FA
   (*Two-step login*).

5. **Install Bitwarden** on their browsers and smartphone.

</Steps>

:::danger[Not in the recovery organization]
With *Automatic enrollment*, inviting the user there gives the administrator the
power to reset their master password. To share items, use another organization
without that policy.
:::
