:::danger[Important]
A user can have up to 3 linked accounts, each of which can be declared
independently.

* **Linux (POSIX)** : Linux & SSH session, declared in config.yaml.
* **Kanidm (IDM)** : access to services, SSO, declared with kanidm.
* **Matrix** : access to the Matrix messaging.
:::

:::tip[The creation order and the links between accounts are important]

- A Linux account `alice`
  - implies the creation of a Kanidm account `alice` / `alice@domain.tld`
  - which implies the creation of a Matrix account `alice:domain.tld`.
- Conversely, creating a Matrix account alone, without a linked IDM or POSIX account, is consistent.
  - For example, a friend's `john.doe:domain.tld` account.
:::

## Create a Linux (POSIX) account

Users are declared **once** in `etc/config.yaml`, then **attached** to the hosts
where they need to open a session. The same account can exist on several machines.

{/* t:p 875f3ee8246831006547317554684773380c9a7fdc858a07ebba456a2770e30e */}
### Declare a user

```yaml
# etc/config.yaml
users:
  alice:
    uid: 1000
    name: "Alice Martin"
    email: "alice@domain.tld"
    profile: "advanced"
    groups: ["global", "idm-devs"]
```

| Field | Role |
|---|---|
| *(key)* | Account login (e.g. `alice`) |
| `uid` | Stable numeric identifier |
| `name` | Display name |
| `email` | Address (also used for the SSO identity) |
| `profile` | [User profile](/en/doc/admin-guide/understand/user-profiles/) (environment) |
| `groups` | Groups (network and services access) |

{/* t:p f93adb95d0c4124c98ae91d5835b63faf346221b89bc26b732dea3d70af6ffd4 */}
### Attach to a host

Under a host, `users` lists the **existing logins** allowed to connect to it:

```yaml
# etc/config.yaml
hosts:
  poste-alice:
    profile: "desktop"
    users: ["alice"]
```

:::tip[Via a group]
Another possibility: attach a user to a host through a common group declared in the shared `groups` list.
:::

### Deploy the changes

Any change to `etc/config.yaml` follows the **same cycle**:

<Steps>

1. **Describe the change**

   Create or modify the user and their machines in `etc/config.yaml`.

2. **Regenerate and clean the code**

   ```sh
   just clean       # generate + fix + format
   ```

3. **Commit in git**

   ```sh
   just commit "user(new): alice"
   ```

4. **Deploy**

   ```sh
   just apply poste-alice     # creates the account on the host
   ```

</Steps>

:::caution[Always commit before deploying]
`just clean` rewrites `var/generated/`. Without `clean` + `commit`, the
deployment starts from an inconsistent or unversioned state.
:::

### Set the password

<Steps>

1. **Set the hash**

   ```sh
   just passwd alice
   ```

2. **Commit in git**

   ```sh
   just commit "chore(user): alice password"
   ```

3. **Deploy**

   ```sh
   just apply @user-alice,hcs
   ```

</Steps>

:::tip[An account has no password until one is set]
`just passwd <login>` is what enables the session; `just passwd-default`
only records the reference password of the fleet. See
[Secrets](/en/doc/admin-guide/operate/secrets/).
:::

:::note[Password redefinition (todo)]
For now, a user cannot redefine their POSIX password for the whole fleet.
:::

## SSH access

SSH access is **key-only** and **fully declarative**, across the entire
fleet:

- password and keyboard-interactive disabled (`darkone.system.core`);
- only declared keys count
  (`users.users.<login>.openssh.authorizedKeys`) : `~/.ssh/authorized_keys`
  is no longer read;
- an account without a declared key opens its local session, never SSH.

:::note[The forge is the exception]
The `forgejo` account serves the `git push` of all repositories: its keys are
those each user deposits in the forge's web interface, not
those of the NixOS configuration. `sshd` fetches them via
`AuthorizedKeysCommand`, not from a file. A key is therefore added in
Forgejo (**Settings → SSH / GPG keys**), never in `config.yaml`.
:::

:::caution[No more ssh-copy-id bootstrap]
Without a password channel or a `~/.ssh/authorized_keys` file, `ssh-copy-id` has
no door in or target either. Every key goes through the configuration then
`just apply`. Keep a fallback access (console, or the LUKS initrd sshd on
port 2222) before deploying to a remote host.
:::

### Denying SSH to a group

The `groups` in `config.yaml` are **logical**: they do not become Unix
groups, so `DenyGroups` would see nothing. DNF translates them into `DenyUsers`,
on a per-host basis:

```nix
# Default: guest accounts keep their local session, no SSH.
darkone.user.build.sshDeniedGroups = [ "guests" ];
```

## Identities and SSO

Beyond the system account, the user has a **single identity**
(Kanidm) that opens the network's services.

- `groups` control access to services.
- `idm-admins` / `idm-devs` are the administration and development groups.
- Details: [SSO and identities](/en/doc/admin-guide/operate/sso/).

:::note[Create an end-to-end account]
The full journey (account + identity + first password) is described in
[Create a user account](/en/doc/admin-guide/operate/sso/#create-a-user-account).
To reset: [Reset a password](/en/doc/how-to/admin/reset-user-password/).
:::

## Disable an account

- **On one host**: remove the login from the host's `users` list.
- **Everywhere**: remove the entry under `users:`.
- **Service access**: removing the user from `groups` cuts SSO access.

In all cases, then apply the `just clean` → `just commit` →
`just apply` cycle on the affected hosts.
