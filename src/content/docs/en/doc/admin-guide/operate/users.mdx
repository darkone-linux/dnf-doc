## Create a Linux (POSIX) account

Users are declared **once** in `etc/config.yaml`, then
**attached** to the hosts where they must log in. The same account can
exist on several machines.

:::tip[End-to-end creation]
Vault, Kanidm identity, alternatives&nbsp;: see
[Create a user account](/en/doc/admin-guide/operate/onboarding/).
:::

{/* t:p 2152a1939de6a4b39e490580942bcce71bb9ca043cc0b2d3c1f39efc1aa43ebf */}
### Declare a user

```yaml
# etc/config.yaml
users:
  alice:
    uid: 1000
    name: "Alice Martin"
    email: "alice@domain.tld"
    profile: "advanced"
    groups: ["global", "idm-devs"]
```

| Field | Role |
|---|---|
| *(key)* | Account login (e.g. `alice`) |
| `uid` | Stable numeric identifier |
| `name` | Display name |
| `email` | Address (also used for SSO identity) |
| `profile` | [User profile](/en/doc/admin-guide/understand/user-profiles/) (environment) |
| `groups` | Groups (network access and [services](/en/doc/admin-guide/operate/sso/#identities-and-groups)) |

The HCS deployment also creates a [Kanidm](/en/doc/admin-guide/operate/sso/)
account for them, without credentials.

### Attach to a host

Under a host, `users` lists the **existing logins** allowed to connect to it:

```yaml
# etc/config.yaml
hosts:
  poste-alice:
    profile: "desktop"
    users: ["alice"]
```

:::tip[Via a group]
Another possibility: attach a user to a host through a common group declared in the shared `groups` list.
:::

### Deploy the changes

Any change to `etc/config.yaml` follows the **same cycle**:

<Steps>

1. **Describe the change**

   Create or modify the user and their machines in `etc/config.yaml`.

2. **Regenerate and clean the code**

   ```sh
   just clean       # generate + fix + format
   ```

3. **Validate in git**

   ```sh
   just commit "user(new): alice"
   ```

4. **Deploy**

   ```sh
   just apply @user-alice,hcs     # alice's machines + Kanidm account
   ```

</Steps>

:::caution[Always commit before deploying]
`just clean` rewrites `var/generated/`. Without `clean` + `commit`, the
deployment starts from an inconsistent or unversioned state.
:::

### Set the password

<Steps>

1. **Set the hash**

   ```sh
   just passwd alice
   ```

   The user can enter their own password. Remotely, they send
   their hash (`mkpasswd -m sha-512`), to be pasted with `just sops` under
   `user.alice.password-hash`.

2. **Validate in git**

   ```sh
   just commit "chore(user): alice password"
   ```

3. **Deploy**

   ```sh
   just apply @user-alice,hcs
   ```

</Steps>

:::note[Only `just passwd` is authoritative]
- No session before `just passwd <login>`.
- If changed on a host, the password is overwritten at the next deployment.
- `just passwd-default` only records the fleet's reference password ([Secrets](/en/doc/admin-guide/operate/secrets/)).
:::

## SSH Access

SSH access is **key-only** and **entirely declarative**, across the whole
fleet&nbsp;:

- Passwords and interactive keyboard are disabled.
- Declare public keys in `usr/users/<login>/authorized_keys`.
- The file applies to all hosts of the account.
- An account with no declared key can open a local session, outside SSH.

```sh
# usr/users/<login>/authorized_keys : one key per line, `#` starts a comment
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA… alice@portable
```

:::note[The forge is the exception]
The `forgejo` account serves the `git push` of every repository: its keys are
the ones each user deposits in the forge's web interface, not the ones from
the NixOS configuration. `sshd` asks it for them via `AuthorizedKeysCommand`
rather than from a file. A key is therefore added in
Forgejo (**Settings → SSH / GPG Keys**).
:::

### Private keys

A private key never goes **anywhere near** the repository or sops&nbsp;: the infra key, present on every host, would make it readable by any root account of the cluster. It lives in the user's Vaultwarden vault, encrypted end to end.

On the selected workstations, `rbw` acts as the SSH agent and reads the keys from the vault&nbsp;:

```nix
# usr/users/<login>/default.nix (advanced, admin, nix-admin profiles…)
darkone.home.advanced.enableVaultwardenSsh = true;
```

- The user stores their key in the vault ([Use my SSH key](/en/doc/how-to/user/ssh-key/)).
- Its public key then goes into `authorized_keys`.
- Locks after 12&nbsp;h of inactivity&nbsp;: `programs.rbw.settings.lock_timeout` (seconds).

:::caution[Not on a host reached via `ssh -A`]
The local `rbw` agent would there mask the agent forwarded from the workstation.
:::

### Denying SSH to a group

The `groups` in `config.yaml` are **logical**: they do not become Unix
groups, so `DenyGroups` would see nothing. DNF translates them into `DenyUsers`,
on a per-host basis:

```nix
# Default: guest accounts keep their local session, no SSH.
darkone.user.build.sshDeniedGroups = [ "guests" ];
```

## Disable an account

- **On one host**: remove the login from the host's `users` list.
- **Everywhere**: remove the entry under `users:`.
- **Service access**: removing the user from `groups` cuts SSO access.

In all cases, then apply the `just clean` → `just commit` →
`just apply` cycle on the affected hosts.

### An SSH key on a YubiKey?

The private key is born inside the YubiKey (FIDO2) and never leaves it&nbsp;: nothing to
store in the vault. Every connection requires touching the key.

```sh
ssh-keygen -t ed25519-sk -O resident -O verify-required   # creation, once

# On another workstation: retrieve the handle under the default name
cd ~/.ssh && ssh-keygen -K && mv id_ed25519_sk_rk id_ed25519_sk
```

- The public key (`sk-ssh-ed25519@openssh.com …`) joins `authorized_keys`.
- `rbw` does not manage these keys&nbsp;: `ssh` reads them from `~/.ssh`.

:::caution[To be validated]
Procedure not tested on the estate.
:::
