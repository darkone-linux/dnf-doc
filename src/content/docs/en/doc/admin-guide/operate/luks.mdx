An encrypted host (LUKS2 volume declared in its disko configuration) protects
its data in case of theft or disposal, but asks for a passphrase at every
boot. DNF industrializes this point of friction with two guarantees:

- **several unlocking methods coexist** at all times, so losing one method
  (forgotten passphrase, misplaced YubiKey) never locks you out;
- **the boot prompt is answered remotely**, from the administration
  workstation, with no screen or keyboard attached to the host, and that from
  the **very first boot** that follows the installation.

## Unlocking methods

Each method occupies its own keyslot in the LUKS2 header. All are valid at the
same time, on every encrypted volume of the host.

| Method | Where it lives | Role |
|---|---|---|
| **Shared passphrase** | sops → `luks-passphrase` | A single one for the whole fleet, authorizes keyslot management. It is also the one that **formats** the disk |
| **Host passphrase** | sops → `luks/<host>/passphrase` | To be entrusted to the machine's user without exposing the fleet |
| **FIDO2 YubiKeys** | Derived from the physical key | Touch the key at boot, nothing to type |

:::note[Why two passphrases and not one]
They are not meant for the same people: the shared one is the fleet
administrator's key, the per-host one is entrusted to the user of a single
machine. And because there are two of them, rotating one remains **authorized
by the other**: the synchronization service never ends up without a way to act
on the keyslots, it adds the new slot before killing the old one.
:::

:::note[There is no installation passphrase anymore]
`just install` formats the volume with the shared passphrase
(`nixos-anywhere --disk-encryption-keys`): the formatting keyslot **is** the
shared keyslot. Nothing to remember from the installation, nothing to retype
afterwards. A host installed before that switch is detected by `just luks <host>`,
which then asks for its installation passphrase one last time to seed the
shared slot.
:::

:::note[Nothing to declare in the Nix configuration]
The `darkone.system.luks` module is active by default but **totally inert** as
long as the host does not appear in the manifest `usr/secrets/luks.json` **and**
does not declare a LUKS volume in its disko. Existing encrypted hosts do not
change until `just luks <host>` has been run.
:::

## Provisioning a host

```sh
just luks <host>            # provisions (or converges) the encryption
just luks <host> pre        # offline half, without touching the machine
just luks <host> passwd     # rotates the per-host passphrase
just luks <host> show       # audit: keyslot table + compliance
just luks <host> '' <ip>    # targets an explicit IP (host not resolved yet)
```

The recipe is **idempotent**: each run converges and only asks for what is
missing. It is called automatically at two moments, and it is rare to have to
run it yourself:

| Called by | Action | What it does |
|---|---|---|
| `just install <host>` | `pre` | Before the build, hence before the installation |
| `just configure <host>` | (default) | After the first boot |

Without a LUKS volume in the disko, it is a logged no-op.

The **`pre`** phase never touches the machine. It prepares what must exist
*before* the system is built:

1. the **shared passphrase** in sops if missing (asked only once for the whole
   fleet);
2. the **host passphrase** in sops if missing (empty entry = strong random
   value, the host stays unlockable by the shared passphrase and the
   YubiKeys);
3. the **SSH host key of the initrd**, generated locally and stored in sops
   (`luks/<host>/initrd-key`, base64 encoded);
4. the registration of the host in the **public manifest**
   `usr/secrets/luks.json` (versioned in clear text, it contains no
   secret): it is this entry that activates the module.

The default phase adds what requires the machine:

5. re-deploys the **initrd key** from sops if missing on the target (it never
   regenerates a new one, that would invalidate the one the installation
   placed);
6. on a **gateway**, records the current **WAN IP** in the manifest (fallback
   for `just enter` and `just unlock`, see below), to be re-run if the
   provider renumbers;
7. if **no managed passphrase** unlocks the volume (host installed before the
   switch to the shared formatting), asks for its installation passphrase one
   last time and enrolls the shared one with it.

Then commit and deploy:

```sh
git add usr/secrets/luks.json
just commit "system(luks): <host>"
just apply <host>
```

At deployment, two idempotent services converge the LUKS header at every
apply: `luks-passphrase-sync` (shared and per-host passphrases) and
`yubikey-luks-enroll` (one FIDO2 entry per YubiKey enrolled on the fleet, see
[Strong authentication](/en/doc/admin-guide/operate/yubikey/)).

:::caution[The initrd key must precede the bootloader]
The initrd secrets are embedded **at the bootloader installation time**: a key
created afterwards simply is not in the initrd that boots. A fresh
installation is covered, `just install` drops the key under `/mnt` before
`nixos-install`. On a machine already in service, it is `just luks <host>` that
places it over SSH: never add a host to `luks.json` by hand, and never deploy
before the key is on the target. In doubt, `just luks <host> show` verifies it.
:::

## Passphrase rotation

- **Per host**: `just luks <host> passwd`, then commit and apply. The old
  keyslot is removed and replaced at the next deployment.
- **Shared**: modify `luks-passphrase` via `just sops`, then apply on the whole
  fleet — each encrypted host rotates its keyslot along the way.

The synchronization service detects changes thanks to a local registry
(`/var/lib/luks-passphrase/ledger`): a modified sops value enrolls the new
passphrase **then** kills the old slot. Slots absent from the registry (FIDO2,
manual enrollments) are never touched.

## Unlocking at boot

Every encrypted host follows the same sequence, with nothing to configure:

1. **YubiKey** — an enrolled key plugged in makes its diode blink: touching it
   opens the volume, nothing to type. No key plugged in, the step lasts ~6 s; a
   key nobody touches, ~30 s (firmware limit).
2. **Passphrase** — a prompt is then shown, **with no time limit**. It accepts
   the per-host passphrase, the shared one or the installation one.

The step 2 prompt is **one single request**, served in parallel on the
physical console (`/dev/tty1`) and over SSH on port 2222. Nothing to choose, no
window to miss: the first one to answer opens the volume.

:::note[How the key is tried]
`fido2-device=` is not written in the `crypttab` entry but in a **separate
initrd unit**, `yubikey-luks-unlock-<volume>`, ordered before
`systemd-cryptsetup@<volume>` and only linked to it by a `Wants=`: it is
allowed to fail, and its failure changes nothing to the boot.

This separation avoids two defects that contradict each other:

- **the option in the `crypttab` kills the boot** when a key is plugged in
  without anyone touching it: `systemd-cryptsetup` exits with an error instead
  of offering the passphrase, no prompt is shown — neither console nor port
  2222 — and the initrd drops into `emergency`. A power cut on a host with
  nobody in front of it was enough to immobilize it;
- **without the option, the token is only tried if it is already enumerated**.
  Yet `hidraw0` appears about one second after `systemd-cryptsetup` starts:
  never in time. The key then stops unlocking anything, silently, and with
  nothing in the journal.

What the option really brings is waiting for the device
(`token-timeout=`, set to 5 s).
:::

Remotely, the initrd starts a **dedicated sshd on port 2222** with its own
persistent host key, reachable only with the `nix` deployment key. Two ways to
answer the prompt:

```sh
just unlock <host>     # without a human: the passphrase is read from sops
just enter <host>      # interactive: the prompt is presented to the terminal
```

`just unlock` waits until port 2222 appears (a dot per attempt), reads the
per-host passphrase from sops (falling back on the shared one) and pushes it
into the initrd. That is what `just full-install` calls on its own after the
first reboot. On a non-encrypted host, it is a logged no-op.

`just enter` does the same thing in interactive mode: when port 22 does not
answer, it probes 2222 on the explicit IP (if provided), the hostname, then
the **WAN IP recorded in the manifest**, and presents the LUKS prompt via
`systemd-tty-ask-password-agent`. In both cases, once the passphrase is
accepted, the boot continues and port 22 comes back.

:::note[Why two paths]
`systemd-tty-ask-password-agent` only talks to a terminal: no script can
drive it. The initrd therefore embeds a small utility `dnf-unlock` that takes
the passphrase from a pipe and answers all pending requests. It is what
`just unlock` calls.
:::

:::note[Why the WAN IP?]
A zone's VPN dies with its gateway: when the latter waits for its passphrase,
only its WAN link is reachable. Its initrd moreover replicates the production
addressing (static IP on the `lan0` bridge, DHCP on the WAN side), since it is
itself the DHCP server that its initrd would otherwise wait for. The other
hosts simply do DHCP on their wired interfaces.
:::

:::note[Laptops on Wi-Fi]
No network in the initrd without a cable: an encrypted laptop is unlocked at
the console (passphrase or YubiKey), remote unlocking does not apply.
:::

## Verifying a host

`just luks <host> show` writes nothing: it queries the machine and reports. It
exits with an error as soon as a check fails, so it can also be used in a
script.

```sh
just luks <host> show
```

A first block draws up the **keyslot table** of each volume. Nothing there is
assumed: every managed passphrase is really tried against the header, so the
"Check" column says what the volume accepts today, not what a registry has
remembered.

```
/dev/disk/by-partlabel/disk-main-luks
  Slot  Content              Source                       Check
  ----  -------------------  ---------------------------  -----------------
  0     Shared passphrase    sops luks-passphrase         opens the volume
  1     Host passphrase      sops luks/poste/passphrase   opens the volume
  2     YubiKey alice/main   systemd-fido2 token          enrolled
  7     Unknown              -                            not managed by DNF
  Slots in use: 4/32
```

A second block audits the **remote unlocking**, point by point:

| Check | What it catches |
|---|---|
| Host present in `luks.json` | The module would stay inert |
| Initrd key on the target (+ fingerprint) | Next apply without remote unlocking |
| sops backup with the same fingerprint | A reinstall would lose remote access |
| initrd sshd enabled in the configuration | `nix.pub` missing, or host outside the manifest |
| Bootloader newer than the key | **The** trap: key absent from the booting initrd |
| Booted system = audited configuration | A pending apply would make the audit misleading |
| WAN IP recorded (gateways) | Unreachable in the initrd once the VPN is down |

## Under the hood

| Location | Content | Status |
|---|---|---|
| `usr/secrets/luks.json` | Manifest of provisioned hosts + WAN IP of gateways | Public, versioned |
| `secrets.yaml` → `luks-passphrase` | Shared fleet passphrase | Encrypted sops |
| `secrets.yaml` → `luks/<host>/passphrase` | Per-host passphrase | Encrypted sops |
| `secrets.yaml` → `luks/<host>/initrd-key` | Initrd SSH host key (base64) | Encrypted sops |
| `/var/lib/luks-initrd/` (target) | Working copy of the initrd key | Persistent, outside the repo |
| `/var/lib/luks-passphrase/ledger` (target) | Registry of managed keyslots (rotation detection) | Persistent, outside the repo |

The module exposes two options: `darkone.system.luks.enable` (default `true`)
and `darkone.system.luks.sshPort` (default `2222`).

:::danger[Keyslot budget]
A LUKS2 header contains at most **32 keyslots**. Each enrolled YubiKey consumes
one on **every** encrypted host (fleet policy), on top of the shared and
per-host passphrases. The module warns when the projected total approaches the
limit.
:::
