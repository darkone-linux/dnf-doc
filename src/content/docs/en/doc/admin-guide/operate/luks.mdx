An encrypted host (LUKS2 volume declared in its disko configuration) protects
its data in case of theft or disposal, but asks for a passphrase at every
boot. DNF industrializes this point of friction with two guarantees:

- **several unlocking methods coexist** at all times, so losing one method
  (forgotten passphrase, misplaced YubiKey) never locks you out;
- **the boot prompt is answered remotely**, from the administration
  workstation, with no screen or keyboard attached to the host, and that from
  the **very first boot** that follows the installation.

## Unlock methods

Each method occupies its own keyslot in the LUKS2 header. All of them are valid
at the same time, on every encrypted volume of the host.

| Method | Where it lives | Role |
|---|---|---|
| **Shared passphrase** | sops → `luks-passphrase` | A single one for the whole fleet, it authorizes keyslot management. It is also what **formats** the disk |
| **Per-host passphrase** | sops → `luks/<hôte>/passphrase` | To hand over to the machine's user without exposing the fleet |
| **FIDO2 YubiKeys** | Derived from the physical key | Touch the key at boot, nothing to type |

:::note[Why two passphrases and not one]
They are not meant for the same people&nbsp;: the shared one is the key of the
fleet administrator, the per-host one is handed to the user of a single
machine. And because there are two of them, rotating one remains **authorized
by the other**&nbsp;: the synchronization service never finds itself without a
way to act on the keyslots, it adds the new slot before killing the old one.
:::

:::note[There is no installation passphrase anymore]
`just install` formats the volume with the shared passphrase
(`nixos-anywhere --disk-encryption-keys`)&nbsp;: the formatting keyslot **is**
the shared keyslot. Nothing to remember from the installation, nothing to
retype afterwards. The first machine, installed via `darkone new`, is
formatted with the passphrase typed in the wizard&nbsp;: it becomes the shared
passphrase of the fleet. A host installed before that switch is detected by
`just luks <hôte>`, which then asks for its installation passphrase one last
time to bootstrap the shared slot.
:::

:::note[Nothing to declare in the Nix configuration]
The `darkone.system.luks` module is active by default but **completely inert**
as long as the host does not appear in the `usr/secrets/luks.json` manifest
**and** declares no LUKS volume in its disko. Existing encrypted hosts do not
change until `just luks <hôte>` has been run.
:::

## Provisioning a host

```sh
just luks <host>            # provisions (or converges) encryption
just luks <host> pre        # offline half, without touching the machine
just luks <host> passwd     # rotates the per-host passphrase
just luks <host> show       # audit: keyslot table + compliance
just luks <host> '' <ip>    # targets an explicit IP (host not yet resolved)
```

The recipe is **idempotent**&nbsp;: each run converges and only asks for what is
missing. It is called automatically at two moments, and it is rare to have to
run it yourself&nbsp;:

| Called by | Action | What it does |
|---|---|---|
| `just install <host>` | `pre` | Before the build, thus before installation |
| `just install-here <host>` | `pre`, without a `nix` account (`bootstrap-keys`) | First machine, from the ISO |
| `just configure <host>` | (default) | After the first boot |

Without a LUKS volume in disko, it is a logged no-op.

The **`pre`** phase never touches the machine. It prepares what must exist
*before* the system is built&nbsp;:

1. the **shared passphrase** in sops if absent (asked only once for the whole
   fleet) ;
2. the **per-host passphrase** in sops if absent, **randomly generated and
   without asking anything** (see the callout below) ;
3. the **initrd SSH host key**, generated locally and stored in sops
   (`luks/<host>/initrd-key`, base64-encoded) ;
4. registering the host in the **public manifest** `usr/secrets/luks.json`
   (versioned in the clear, it contains no secret)&nbsp;: it is this entry
   that activates the module.

:::note[Why the per-host passphrase is never asked for at installation]
It serves to entrust the unlocking of a workstation to its user without giving
them the key to the whole fleet. But at formatting time we still don't know who
will use the machine&nbsp;: the answer was always "&nbsp;empty&nbsp;". And an
interactive question in the middle of an installation is exactly what breaks a
remote installation.

It is therefore drawn at random and kept in sops alone. The slot keeps its
usefulness — it is a second means of opening the volume, and the fallback of
`just unlock`. The day someone really has to type a passphrase on this machine,
`just luks <host> passwd` gives them one of their choosing, and
`luks-passphrase-sync` swaps the slot on the next `apply`.
:::

The default phase adds what requires the machine&nbsp;:

5. re-lays the **initrd key** from sops if it is missing on the target (it
   never regenerates a new one, that would invalidate the one placed by the
   installation) ;
6. on a **gateway**, records its **public address** in the manifest
   (fallback of `just unlock`, see below). It is only a backup&nbsp;: the
   gateway [reports its own address](#wan-address-of-gateways) to the HCS.
   Behind a box, the WAN interface only carries a private IP&nbsp;: the public
   address is the one used to reach the machine, or is passed as an argument
   (`just luks <host> '' auto <IP or DDNS name>`) ;
7. if **no managed passphrase** unlocks the volume (host installed before the
   switch to shared formatting), asks for its installation passphrase one last
   time and enrolls the shared one along with it.

Then commit and deploy&nbsp;:

```sh
git add usr/secrets/luks.json
just commit "system(luks): <host>"
just apply <host>
```

At deployment, two idempotent services converge the LUKS header on each
apply: `luks-passphrase-sync` (shared and per-host passphrases) and
`yubikey-luks-enroll` (one FIDO2 entry per YubiKey enrolled on the fleet, see
[Strong authentication](/en/doc/admin-guide/operate/yubikey/)).

:::caution[The initrd key must precede the bootloader]
Initrd secrets are embedded **when the bootloader is installed**: a key created
after the fact is simply not in the initrd that boots. A fresh installation is
covered, `just install` lays the key under `/mnt` before `nixos-install`. On an
already-running machine, it is `just luks <host>` that lays it over SSH&nbsp;:
never add a host to `luks.json` by hand, and never deploy before the key is on
the target. If in doubt, `just luks <host> show` checks it.
:::

## Passphrase rotation

- **Per host**: `just luks <hôte> passwd`, then commit and apply. The old
  keyslot is removed and replaced on the next deployment.
- **Shared**: edit `luks-passphrase` via `just sops`, then apply across
  the whole fleet: each encrypted host rotates its keyslot in the process.
- **Isolated host**: `just luks <hôte> passwd`, machine booted. Rotation happens
  on the spot, without apply (see [Isolated encrypted host](#isolated-encrypted-host)).

The synchronization service detects changes through a local ledger
(`/var/lib/luks-passphrase/ledger`)&nbsp;: a modified sops value
enrolls the new passphrase **then** kills the old slot. Slots missing from
the ledger (FIDO2, manual enrollments) are never touched.

## Isolated encrypted host

An [isolated host](/en/doc/admin-guide/operate/secrets/#isolated-hosts) holds
no fleet secret, nor does its encryption&nbsp;:

| Item | Isolated host |
|---|---|
| Keyslots | Its passphrase, its YubiKeys, no shared one |
| Formatting | With its passphrase |
| `luks/<hôte>/*` | `usr/secrets/hosts/<hôte>.yaml` |
| YubiKeys | At the host's salt, once captured |
| `just unlock` | Sends only its passphrase |
| Rotation | `just luks <hôte> passwd`, immediate |

Without a synchronization service, `passwd` acts on the machine itself&nbsp;:
new slot, sops, then removal of the old one. At every step, the value
stored in sops opens the volume.

Each key there is enrolled to a salt specific to the host, authorized by its
passphrase&nbsp;: see [Isolated encrypted hosts](/en/doc/admin-guide/operate/yubikey/#encrypted-isolated-hosts)
and [YubiKey, salts and isolated hosts](/en/doc/admin-guide/understand/yubikey-salts/).

A host that becomes isolated is reinstalled (`just install`)&nbsp;: its old
`luks/<hôte>` entries remain in `secrets.yaml`, flagged by `just luks`,
to be deleted with `just sops`.

## Unlocking at boot

Every encrypted host follows the same sequence, with nothing to configure:

1. **YubiKey** — an enrolled and plugged-in key makes its LED blink: touching
   it opens the volume, nothing to type. No key plugged in, the step lasts
   ~6 s ; a key that nobody touches, ~30 s (firmware limit).
2. **Passphrase** — a prompt is then presented, **with no time limit**.
   It accepts the per-host passphrase, the shared one or the installation one.

The prompt of step 2 is **one and the same request**, served in parallel
on the physical console (`/dev/tty1`) and over ssh on port 2222. Nothing to
choose, no window to miss: the first one to answer opens the volume.

:::note[How the key is tried]
`fido2-device=` is not written in the `crypttab` entry but in a **separate
initrd unit**, `yubikey-luks-unlock-<volume>`, ordered before
`systemd-cryptsetup@<volume>` and only linked to it by a `Wants=`:
it is allowed to fail, and its failure changes nothing about the boot.

This separation avoids two flaws that contradict each other:

- **the option in the `crypttab` kills the boot** when a key is plugged in
  without anyone touching it: `systemd-cryptsetup` exits with an error instead
  of offering the passphrase, no prompt is presented — neither console nor port
  2222 — and the initrd switches to `emergency`. A power cut on a host with
  nobody in front of it was enough to immobilize it ;
- **without the option, the token is only tried if it is already
  enumerated**. But `hidraw0` appears about a second after the launch of
  `systemd-cryptsetup`: never in time. The key then stops unlocking
  anything, silently, and with nothing in the log.

What the option really brings is the **waiting** for the device
(`token-timeout=`, set to 5 s).
:::

Remotely, the initrd starts a **dedicated sshd on port 2222**, with its
own persistent host key, accessible only with the deployment key `nix`.
`just unlock` answers it there&nbsp;:

```sh
just unlock <host>     # passphrase read from sops, otherwise asked at the terminal
```

`just unlock` waits for port 2222 to appear (a dot per attempt), reads
the **shared** passphrase from sops and pushes it into the initrd, then verifies
that the machine has indeed left its initrd before announcing success. If it is
refused, it retries with the per-host passphrase. This is what
`just full-install` calls on its own after the first reboot. On a non-encrypted
host, it is a logged no-op.

Before any sending, `just unlock` verifies that the **initrd host key** is
the one stored in sops, then enforces it on each connection. Key absent from
sops or different → stop, nothing is sent&nbsp;: an impostor could listen on 2222.

:::note[Why the shared one first]
On the very first boot, the per-host slot does not exist yet: disko formats
with the shared passphrase, and `luks-passphrase-sync` only adds the per-host
slot from the booted system, thus *after* unlocking. The shared one is
the only way in at that moment.

Moreover `dnf-unlock` only knows that it has **answered** the request, never
whether the passphrase was accepted: systemd simply asks again. The only
reliable witness is therefore the machine leaving its initrd and answering on
port 22, and that is what `just unlock` observes from the administration
workstation.
:::

No stored passphrase accepted, or no infrastructure key on the
workstation&nbsp;: from a terminal, `just unlock` presents the LUKS prompt via
`systemd-tty-ask-password-agent`. It probes port 2222 on the explicit IP (if
provided), the host name, the **WAN IP reported to the HCS**, then that of the
manifest. In both cases, once the passphrase is accepted, the boot continues and
port 22 comes back.

:::note[Why two paths]
`systemd-tty-ask-password-agent` only talks to a terminal&nbsp;: no script
can drive it. The initrd therefore embeds a small utility `dnf-unlock` which
takes the passphrase from a pipe and answers all pending requests.
It is this one that `just unlock` calls.
:::

:::note[Why the WAN IP?]
The VPN of a zone dies with its gateway: when it awaits its
passphrase, only its WAN leg is reachable. Its initrd also replicates
the production addressing (static IP on the `lan0` bridge, DHCP on the WAN side),
since it is itself the DHCP server that its initrd would otherwise await.
The other hosts do a simple DHCP on their wired interfaces. Behind
a box, this fallback requires a port-forward of 2222 to the gateway.
:::

:::note[Wi-Fi laptops]
No network in initrd without a cable: an encrypted laptop is unlocked at the
console (passphrase or YubiKey), remote unlocking does not apply.
:::

:::caution[A NIC driver is not always enough]
A virtio card does not attach to its PCI slot but to the
`virtio0` device created by its **transport** (`virtio_pci`, `virtio_mmio`).
Without this module in the initrd, `virtio_net` is never loaded: no link,
no IP, and the sshd of port 2222 listens into the void — the host waits
indefinitely for its passphrase, with nothing in the log to say so.

Both transports are now embedded by default, and
`just luks <host> show` compares the drivers actually used by the machine's
wired cards with those carried in the built initrd.
:::

:::note[Network drivers detected at installation]
`nixos-generate-config` never puts a network driver in the initrd. A
card outside the list embedded by default (Broadcom `tg3` for example) therefore
leaves the host unreachable in initrd.

`just install` and `just copy-hw` run `just detect-hw`&nbsp;: it collects on
the machine the modules of its wired cards and writes them to
`usr/machines/<host>/hardware/detected-hardware.nix`, imported automatically.
These modules are only added to the initrd if it has network (remote
unlocking).

On an already-installed host, if `just luks <host> show` reports a missing
driver&nbsp;: `just detect-hw <host>`, then `just apply <host>`.
:::

## WAN address of gateways

A gateway that reboots may come back on a **different public address**,
awaiting its passphrase and without VPN. It therefore reports its address to
the HCS, over SSH, and `just unlock` tries it first, before the manifest one.

| Moment | Who reports | Frequency |
|---|---|---|
| Waiting in initrd | `dnf-wan-report` (initrd) | Every 15 min |
| System booted | `dnf-wan-report.timer` | At boot, then every hour |

On the HCS side, the `dnf-wan-report` account accepts only one key per gateway
(its initrd key, tied to a forced command). The retained address is the one seen
by sshd, stored in `/var/lib/dnf-wan-report/<host>`.

Bringing it into service, in this order&nbsp;:

1. `just luks <gateway>` copies the initrd public key into
   `usr/secrets/luks.json` (nothing activates before) ;
2. `git add usr/secrets/luks.json`, then `just apply <hcs>` ;
3. `just apply <gateway>`, then `just luks <gateway> show` confirms the
   first report.

:::caution[The HCS first]
A key that the HCS does not yet know is refused, and fail2ban bans
the zone's address after 3 refusals. The initrd only retries a refused key
every 15 minutes.
:::

Each change of address or phase (`initrd`, `system`) is logged on
the HCS&nbsp;: `journalctl -t dnf-wan-report` retraces the reboots of
each gateway there.

## Verifying a host

`just luks <host> show` writes nothing&nbsp;: it queries the machine and reports.
It exits with an error as soon as a check fails, so it can also be used
in a script.

```sh
just luks <host> show
```

A first block draws up the **keyslot table** of each volume. Nothing is
assumed there&nbsp;: each managed passphrase is really tried against the header,
so the "Check" column says what the volume accepts today, not what
a registry has remembered.

```
/dev/disk/by-partlabel/disk-main-luks
  Slot  Content              Source                       Check
  ----  -------------------  ---------------------------  -----------------
  0     Shared passphrase    sops luks-passphrase         opens the volume
  1     Host passphrase      sops luks/poste/passphrase   opens the volume
  2     YubiKey alice/main   systemd-fido2 token          enrolled
  7     Unknown              -                            not managed by DNF
  Slots in use: 4/32
```

:::note[An "Unknown" slot]
No managed passphrase opens it and no FIDO2 token claims it. Most often it is a
YubiKey enrollment interrupted between the creation of the keyslot and the
writing of its token — typically during an installation, where the passphrase
convergence restarts the enrollment service. The service now repairs this case
itself on the next `just apply`&nbsp;: it adopts the keyslot if it belongs to a
declared key, deletes it if it is a duplicate. A slot that persists after an
apply therefore comes from elsewhere&nbsp;: a manual `systemd-cryptenroll`, for
example — DNF never touches it, for lack of being able to prove who it belongs
to.
:::

A second block audits **remote unlocking**, point by point&nbsp;:

| Check | What it catches |
|---|---|
| Host present in `luks.json` | The module would stay inert |
| Initrd key on the target (+ fingerprint) | Next apply without remote unlocking |
| sops backup of the same fingerprint | A reinstallation would lose remote access |
| initrd sshd enabled in the configuration | `nix.pub` missing, or host outside the manifest |
| Bootloader newer than the key | **The** trap&nbsp;: key absent from the initrd that boots |
| Drivers of the wired cards present in the initrd | No network in stage 1&nbsp;: nothing answers on 2222 |
| Booted system = audited configuration | A pending apply would make the audit misleading |
| WAN address reported to the HCS (gateways) | Report missing or older than 2 h |
| Public address collected (gateways) | Unreachable in initrd once the VPN is down |

## Under the hood

| Location | Content | Status |
|---|---|---|
| `usr/secrets/luks.json` | Provisioned hosts, WAN IP, initrd public keys | Public, versioned |
| `secrets.yaml` → `luks-passphrase` | Shared passphrase of the fleet | sops encrypted |
| `secrets.yaml` → `luks/<host>/passphrase` | Per-host passphrase | sops encrypted |
| `secrets.yaml` → `luks/<host>/initrd-key` | initrd SSH host key (base64) | sops encrypted |
| `secrets.yaml` → `luks/<host>/initrd-key-pub` | Its public key, pinned by `just unlock` | sops encrypted |
| `/var/lib/luks-initrd/` (target) | Working copy of the initrd key | Persistent, outside the repo |
| `/var/lib/luks-passphrase/ledger` (target) | Registry of managed keyslots (rotation detection) | Persistent, outside the repo |
| `/var/lib/dnf-wan-report/<host>` (HCS) | Last reported WAN address | Persistent, outside the repo |

The module exposes three options: `darkone.system.luks.enable` (default `true`),
`darkone.system.luks.sshPort` (default `2222`) and
`darkone.system.luks.wanReport.enable` (default `true`).

:::danger[Keyslot budget]
A LUKS2 header contains at most **32 keyslots**. Each enrolled YubiKey
consumes one on **each** encrypted host (fleet policy), in addition to the
shared and per-host passphrases. The module warns when the projected total
approaches the limit.
:::

### Machine without DNS after unlocking?

The initrd takes a DHCP lease for port 2222. Kept at boot, NetworkManager
sees the interface as *connected (externally)*: no DHCP, no DNS, `resolv.conf`
empty. The initrd now returns its lease on a NetworkManager host: effective at
the first reboot after deployment.
