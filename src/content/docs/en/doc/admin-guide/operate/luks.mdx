An encrypted host (LUKS2 volume declared in its disko configuration) protects
its data in case of theft or disposal, but asks for a passphrase at every
boot. DNF industrializes this point of friction with two guarantees:

- **several unlocking methods coexist** at all times, so losing one method
  (forgotten passphrase, misplaced YubiKey) never locks you out;
- **the boot prompt is answered remotely**, from the administration
  workstation, with no screen or keyboard attached to the host, and that from
  the **very first boot** that follows the installation.

## Unlocking methods

Each method occupies its own keyslot in the LUKS2 header. All are valid at the
same time, on every encrypted volume of the host.

| Method | Where it lives | Role |
|---|---|---|
| **Shared passphrase** | sops → `luks-passphrase` | A single one for the whole fleet, authorizes keyslot management. It is also the one that **formats** the disk |
| **Host passphrase** | sops → `luks/<host>/passphrase` | To be entrusted to the machine's user without exposing the fleet |
| **FIDO2 YubiKeys** | Derived from the physical key | Touch the key at boot, nothing to type |

:::note[Why two passphrases and not one]
They are not meant for the same people: the shared one is the fleet
administrator's key, the per-host one is entrusted to the user of a single
machine. And because there are two of them, rotating one remains **authorized
by the other**: the synchronization service never ends up without a way to act
on the keyslots, it adds the new slot before killing the old one.
:::

:::note[There is no installation passphrase anymore]
`just install` formats the volume with the shared passphrase
(`nixos-anywhere --disk-encryption-keys`): the formatting keyslot **is** the
shared keyslot. Nothing to remember from the installation, nothing to retype
afterwards. A host installed before that switch is detected by `just luks <host>`,
which then asks for its installation passphrase one last time to seed the
shared slot.
:::

:::note[Nothing to declare in the Nix configuration]
The `darkone.system.luks` module is active by default but **totally inert** as
long as the host does not appear in the manifest `usr/secrets/luks.json` **and**
does not declare a LUKS volume in its disko. Existing encrypted hosts do not
change until `just luks <host>` has been run.
:::

## Provision a host

```sh
just luks <hôte>            # provisions (or converges) the encryption
just luks <hôte> pre        # offline half, without touching the machine
just luks <hôte> passwd     # rotates the passphrase per host
just luks <hôte> show       # audit: keyslot table + compliance
just luks <hôte> '' <ip>    # targets an explicit IP (host not yet resolved)
```

The recipe is **idempotent**&nbsp;: each run converges and only asks for what is
missing. It is called automatically at two points, and you rarely need to run
it yourself&nbsp;:

| Called by | Action | What it does |
|---|---|---|
| `just install <hôte>` | `pre` | Before the build, hence before the installation |
| `just configure <hôte>` | (default) | After the first boot |

Without a LUKS volume in disko, it is a logged no-op.

The **`pre`** phase never touches the machine. It prepares what must exist
*before* the system is built&nbsp;:

1. the **shared passphrase** in sops if absent (asked only once for the whole
   fleet);
2. the **per-host passphrase** in sops if absent, **generated at random without
   asking anything** (see the callout below);
3. the **initrd SSH host key**, generated locally and stored in sops
   (`luks/<hôte>/initrd-key`, base64-encoded);
4. the registration of the host in the **public manifest** `usr/secrets/luks.json`
   (versioned in clear text, it contains no secret)&nbsp;: this entry is what
   enables the module.

:::note[Why the per-host passphrase is never asked at installation time]
It exists to entrust unlocking a workstation to its user without giving them the
key to the whole fleet. But at formatting time we still do not know who will use
the machine&nbsp;: the answer was always "empty". And an interactive question in
the middle of an installation is exactly what breaks a remote installation.

It is therefore drawn at random and kept only in sops. The keyslot remains
useful — it is a second way to open the volume, and the fallback for
`just unlock`. On the day someone really has to type a passphrase on that
machine, `just luks <hôte> passwd` gives them a chosen one, and
`luks-passphrase-sync` swaps the keyslot at the next `apply`.
:::

The default phase adds what requires the machine&nbsp;:

5. restores the **initrd key** from sops if it is missing on the target (it never
   generates a new one, which would invalidate the one the installation placed);
6. on a **gateway**, records the current **WAN IP** in the manifest
   (fallback for `just unlock`, see below), to re-run if the access provider
   renumbers;
7. if **no managed passphrase** unlocks the volume (host installed before the
   switch to shared formatting), asks for its installation passphrase one last
   time and enrols the shared one alongside it.

Then commit and deploy&nbsp;:

```sh
git add usr/secrets/luks.json
just commit "system(luks): <hôte>"
just apply <hôte>
```

At deployment, two idempotent services converge the LUKS header on each
apply: `luks-passphrase-sync` (shared and per-host passphrases) and
`yubikey-luks-enroll` (one FIDO2 entry per YubiKey enrolled on the fleet, see
[Strong authentication](/en/doc/admin-guide/operate/yubikey/)).

:::caution[The initrd key must precede the boot loader]
Initrd secrets are embedded **at boot loader installation time**: a key created
afterwards simply is not in the initrd that boots. A fresh installation is
covered, `just install` places the key under `/mnt` before `nixos-install`. On a
machine already in service, it is `just luks <hôte>` that places it overSSH&nbsp;: never add a host to `luks.json` by hand, and never deploy before the
key is on the target. When in doubt, `just luks <hôte> show` checks it.
:::

## Passphrase rotation

- **Per host**: `just luks <host> passwd`, then commit and apply. The old
  keyslot is removed and replaced at the next deployment.
- **Shared**: modify `luks-passphrase` via `just sops`, then apply on the whole
  fleet — each encrypted host rotates its keyslot along the way.

The synchronization service detects changes thanks to a local registry
(`/var/lib/luks-passphrase/ledger`): a modified sops value enrolls the new
passphrase **then** kills the old slot. Slots absent from the registry (FIDO2,
manual enrollments) are never touched.

## Unlocking at boot

Every encrypted host follows the same sequence, with nothing to configure:

1. **YubiKey** — an enrolled, plugged-in key makes its LED blink: touching it
   opens the volume, nothing to type. With no key plugged in, the step takes
   ~6 s; with a key nobody touches, ~30 s (firmware limit).
2. **Passphrase** — a prompt is then displayed, **with no time limit**.
   It accepts the per-host passphrase, the shared one, or the installation one.

The prompt in step 2 is **one and the same request**, served in parallel on the
physical console (`/dev/tty1`) and over ssh on port 2222. Nothing to choose, no
window to miss: whoever answers first opens the volume.

:::note[How the key is tried]
`fido2-device=` is not written in the `crypttab` entry but in a **separate
initrd unit**, `yubikey-luks-unlock-<volume>`, ordered before
`systemd-cryptsetup@<volume>` and only linked to it by a `Wants=`: it is allowed
to fail, and its failure changes nothing at boot.

This separation avoids two flaws that contradict each other:

- **the option in the `crypttab` kills the boot** when a key is plugged in and
  nobody touches it: `systemd-cryptsetup` exits with an error instead of
  offering the passphrase, no prompt is displayed — neither on the console nor
  on port 2222 — and the initrd switches to `emergency`. A power cut on a host
  with nobody in front of it was enough to immobilise it;
- **without the option, the token is only tried if it is already enumerated**.
  Yet `hidraw0` appears about one second after `systemd-cryptsetup` starts:
  never in time. The key then stops unlocking anything, silently, and with
  nothing in the log.

What the option actually brings is the **wait** for the device
(`token-timeout=`, set to 5 s).
:::

Remotely, the initrd starts a **dedicated sshd on port 2222**, with its own
persistent host key, accessible only with the `nix` deployment key.
`just unlock` answers it&nbsp;:

```sh
just unlock <hôte>     # passphrase read from sops, otherwise asked at the terminal
```

`just unlock` waits for port 2222 to appear (one dot per attempt), reads the
**shared** passphrase from sops and pushes it into the initrd, then verifies that
the machine really left its initrd before announcing success. If it is refused,
it retries with the per-host passphrase. That is what `just full-install` calls
by itself after the first reboot. On an unencrypted host, it is a logged no-op.

:::note[Why the shared one first]
On the very first boot, the per-host keyslot does not exist yet: disko formats
with the shared passphrase, and `luks-passphrase-sync` only adds the per-host
keyslot from the booted system, hence *after* unlocking. The shared one is the
only way in at that moment.

Moreover `dnf-unlock` only knows it has **answered** the request, never whether
the passphrase was accepted: systemd simply asks again. The only reliable proof
is therefore the machine leaving its initrd and answering on port 22, and that is
what `just unlock` observes from the administration workstation.
:::

If no stored passphrase is accepted, or there is no infrastructure key on the
workstation&nbsp;: from a terminal, `just unlock` presents the LUKS prompt via
`systemd-tty-ask-password-agent`. It probes2222 on the explicit IP (ifprovided), the hostname, then the **WAN IP recorded in the manifest**. In both
cases, once the passphrase is accepted, the boot continues and port 22 comes
back.

:::note[Why two paths]
`systemd-tty-ask-password-agent` only talks to a terminal&nbsp;: no script can
drive it. The initrd therefore embeds a small `dnf-unlock` utility that takes
the passphrase on a pipe and answers all pending requests. That is what
`just unlock` calls.
:::

:::note[Why the WAN IP?]
A zone's VPN dies with its gateway: when the latter waits for its passphrase,
only its WAN leg is reachable. Its initrd moreover replicates the production
addressing (static IP on the `lan0` bridge, DHCP on the WAN side), since it is
itself the DHCP server its initrd would otherwise wait for. The other hosts do a
simple DHCP on their wired interfaces.
:::

:::note[Laptops over Wi-Fi]
No network in the initrd without a cable: an encrypted laptop is unlocked at the
console (passphrase or YubiKey), remote unlocking does not apply.
:::

:::caution[A NIC driver is not always enough]
A virtio card does not plug into its PCI slot but into the `virtio0` device that
its **transport** creates (`virtio_pci`, `virtio_mmio`). Without that module in
the initrd, `virtio_net` is never loaded: no link, no IP, and the sshd on port
2222 listens into the void — the host waits indefinitely for its passphrase,
with nothing in the log to say so.

Both transports are now shipped by default, and `just luks <hôte> show`
compares the drivers actually used by the machine's wired cards with those
carried by the built initrd.
:::

:::note[Network drivers detected at installation time]
`nixos-generate-config` never puts a network driver in the initrd. A card
outside the list shipped by default (Broadcom `tg3`, for example) therefore
leaves the host unreachable in the initrd.

`just install` and `just copy-hw` run `just detect-hw`&nbsp;: it records on the
machine the modules of its wired cards and writes them into
`usr/machines/<hôte>/hardware/detected-hardware.nix`, imported automatically.
Those modules are only added to the initrd if it has a network (remote
unlocking).

On an already installed host, if `just luks <hôte> show` reports a missing
driver&nbsp;: `just detect-hw <hôte>`, then `just apply <hôte>`.
:::

## Checking a host

`just luks <hôte> show` writes nothing&nbsp;: it queries the machine and reports. It exits with an error as soon as a check fails, so it can also be used in a script.

```sh
just luks <hôte> show
```

A first block draws up the **keyslot table** of each volume. Nothing is assumed&nbsp;: every managed passphrase is actually tried against the header, so the "Check" column says what the volume accepts today, not what a registry has remembered.

```
/dev/disk/by-partlabel/disk-main-luks
  Slot  Content              Source                       Check
  ----  -------------------  ---------------------------  -----------------
  0     Shared passphrase    sops luks-passphrase         opens the volume
  1     Host passphrase      sops luks/poste/passphrase   opens the volume
  2     YubiKey alice/main   systemd-fido2 token          enrolled
  7     Unknown              -                            not managed by DNF
  Slots in use: 4/32
```

:::note[An "Unknown" slot]
No managed passphrase opens it and no FIDO2 token claims it. Most often it is an interrupted YubiKey enrollment between the keyslot's creation and its token being written — typically during an installation, where passphrase convergence restarts the enrollment service. The service now repairs this case on its own at the next `just apply`: it adopts the keyslot if it belongs to a declared key, deletes it if it is a duplicate. A slot that persists after an apply therefore comes from elsewhere&nbsp;: a manual `systemd-cryptenroll`, for example — DNF never touches it, since it cannot prove who owns it.
:::

A second block audits the **remote unlocking**, point by point&nbsp;:

| Check | What it catches |
|---|---|
| Host present in `luks.json` | The module would stay inert |
| Initrd key on the target (+ fingerprint) | Next apply without remote unlocking |
| sops backup with the same fingerprint | A reinstall would lose remote access |
| initrd sshd enabled in the configuration | `nix.pub` missing, or host outside the manifest |
| Boot loader more recent than the key | **The** trap&nbsp;: key missing from the initrd that boots |
| Wired-card drivers present in the initrd | No stage-1 networking&nbsp;: nothing answers on 2222 |
| Booted system = audited configuration | A pending apply would make the audit misleading |
| WAN IP recorded (gateways) | Unreachable in initrd once the VPN is down |

## Under the hood

| Location | Content | Status |
|---|---|---|
| `usr/secrets/luks.json` | Manifest of provisioned hosts + WAN IP of gateways | Public, versioned |
| `secrets.yaml` → `luks-passphrase` | Shared fleet passphrase | Encrypted sops |
| `secrets.yaml` → `luks/<host>/passphrase` | Per-host passphrase | Encrypted sops |
| `secrets.yaml` → `luks/<host>/initrd-key` | Initrd SSH host key (base64) | Encrypted sops |
| `/var/lib/luks-initrd/` (target) | Working copy of the initrd key | Persistent, outside the repo |
| `/var/lib/luks-passphrase/ledger` (target) | Registry of managed keyslots (rotation detection) | Persistent, outside the repo |

The module exposes two options: `darkone.system.luks.enable` (default `true`)
and `darkone.system.luks.sshPort` (default `2222`).

:::danger[Keyslot budget]
A LUKS2 header contains at most **32 keyslots**. Each enrolled YubiKey consumes
one on **every** encrypted host (fleet policy), on top of the shared and
per-host passphrases. The module warns when the projected total approaches the
limit.
:::
