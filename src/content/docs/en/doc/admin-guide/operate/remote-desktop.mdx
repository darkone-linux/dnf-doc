Take control of a graphical workstation in the fleet to help its user, without
installing anything permanently and without entering a password.

```sh
just rd clemence            # observation only (default)
just rd clemence rw         # take control
just rd clemence login      # your own session, via GDM
```

`ro` and `rw` attach to the session **already open** on the host: if no one is
logged in, the command stops with an error. `login` does the opposite and opens
**your own session** behind a GDM login screen, whether or not someone is at
the machine. See [Open your own session
(`login`)](#opening-your-own-session-login).

## Enabling a host

Remote desktop is an explicit opt-in. It is enabled through the `remote-desktop`
**feature** in `etc/config.yaml`:

```yaml
  - hostname: "clemence"
    profile: "umi"
    features: ["remote-desktop", "nfs-client"]
```

Then `just generate` and `just apply clemence`. A host without this feature
cannot be troubleshooted, and the configuration states in black and white which
ones can.

:::tip[Templated host groups]
A feature is inherited by all hosts in a `range:` or `hosts:` group, which
covers an entire family of identical workstations in one line:

```yaml
  - hostname: "fd-%'02s"
    profile: "desktop"
    range: [1, 2]
    features: ["monitoring-node", "nfs-client", "remote-desktop"]
```

This is why `features` is chosen over `services`: the `services:` block of a
templated group is **not** propagated to generated hosts.
:::

:::caution[This is not trivial]
Attaching to a session means seeing — and in `rw`, driving — the screen of
someone who is likely sitting in front of it. GNOME shows a sharing indicator
for the whole duration, but **nothing asks for their consent**.
Reserve this activation for workstations where this is the intended use.
:::

## The three modes

| Mode | Effect | Applied by |
|---|---|---|
| `ro` (default) | You see the user's screen, your inputs are ignored | The remote server |
| `rw` | The same screen, keyboard and mouse forwarded | The remote server |
| `login` | A GDM login screen, then a session of your own | — |

The `ro`/`rw` filtering is done **host-side**, not by the client: a hacked
client cannot turn a `ro` into a `rw`.

:::caution[`ro` and `rw` never open a session]
Without anyone logged in, they have no screen to mirror and fail outright.
Asking to observe a user must not drop you off somewhere else without saying
so — it is `login`, and only `login`, that opens a new session.
:::

## Window shortcuts

The client is `sdl-freerdp`. Its shortcuts use **Right Shift** as the modifier
— not `Ctrl+Alt` like the old X11 client:

| Shortcut | Effect |
|---|---|
| `Right Shift` + `Enter` | Fullscreen (and back) |
| `Right Shift` + `G` | Capture keyboard/mouse. When captured, `Alt+Tab` and the other shortcuts go to the remote workstation; when released, they come back to yours |
| `Right Shift` + `R` | Allow / block window resizing |
| `Right Shift` + `M` | Minimize the window |
| `Right Shift` + `D` | Disconnect cleanly |

:::tip[Getting back to your machine]
In fullscreen with keyboard capture active, `Right Shift` always stays
intercepted locally: `Right Shift` + `Enter` brings you back, no matter what.
Closing the window disarms the session on the host.
:::

## Resolution and sharpness

The window opens at the **native resolution of the remote screen**: one remote
pixel for one local pixel, so no resampling and no blur.

Any other size goes through scaling, which softens the image — that is the
price of free resizing. To get back to 1:1:

- `Right Shift` + `Enter`: fullscreen is exact if your screen has the same
  resolution as the one in front of you;
- otherwise, bring the window back to its opening size.

If the remote screen is larger than yours, the window overflows and your window
manager constrains it: the image is then reduced, so softened.
Fullscreen remains the best compromise in this case.

## Opening your own session (`login`)

`just rd <host> login` arms the **system daemon** of `gnome-remote-desktop` and
shows you the GDM login screen. You authenticate with your usual account, and
GDM opens a session for you. This is the mode to use when no one is logged in
on the workstation — but it also works equally well when someone is, without
changing anything displayed on the monitor.

The system daemon is already installed and idle on every GNOME host, exactly
like the user daemon: nothing new is added, you arm it then you disarm it. It
is also the only one able to work without an unlocked keyring, which a machine
where no one is logged in obviously cannot provide.

:::caution[This is not the machine's screen]
GDM opens a **new and screenless session**, alongside what is displayed on the
monitor. So you do not see the physical screen: you are on your own, not on
someone else's. To troubleshoot a user, it is `ro` or `rw` that you need.

Mirroring the GDM greeter itself is not possible: the user daemon only accepts
its credentials from a keyring, and the greeter's session does not have one.
:::

Good to know: that session is a *virtual* monitor, which the server can resize.
So it is your client that sets the resolution, and the display is sharp at 100%
without any adjustment.

## What actually happens

1. The command connects to the host over SSH under the `nix` identity, like all
   of the fleet's administration commands.
2. It arms the session there: RDP server configuration, ephemeral TLS
   certificate, random single-use credentials.
3. It mounts an **SSH tunnel** to the RDP port, which remains closed to the
   network.
4. It launches the FreeRDP client under your own account, on `127.0.0.1`.
5. When the window closes, everything is disarmed and the host's original
   configuration is restored.

Nothing is ever exposed on the network: the fleet's firewall stays
deny-by-default, no rule is added, even temporarily. The RDP server only
listens for the duration of the session, and the only path to reach it is the
tunnel.

The certificate is self-signed and regenerated at every session, in the
machine's volatile memory. Its fingerprint is captured over SSH and pinned in
the client: the machine's identity is therefore guaranteed by the SSH channel
itself, which binds it more tightly than a certified domain name would.

On the login screen, the fingerprint is not pinned: the system daemon hands
over to the login session, which presents a certificate of its own — pinning
the first one would break the second step. It is then the tunnel, and it
alone, that carries the trust.

## Automatic shutdown

The host disarms itself after **60 minutes** (adjustable with
`darkone.graphic.remote-desktop.timeout`). This safeguard covers the case where
your machine shuts down, the network goes down, or the command is killed
brutally: access cannot stay open by accident.

## The three engines

The requested mode and the type of the open session determine the engine.

| Situation | Engine | What you see |
|---|---|---|
| `ro`/`rw`, open GNOME Wayland session | `gnome-remote-desktop`, user daemon | The user's screen |
| `ro`/`rw`, open Cinnamon X11 session (UMI workstations) | `freerdp-shadow-cli` on the existing display | The user's screen |
| `login` | `gnome-remote-desktop`, system daemon | GDM, then your own session |

In all three cases: same RDP protocol, same client, same tunnel, same port.

## Known limitations

- **One session at a time** per host. A second attempt is refused as long as
  the first one is not closed.
- **Several graphical sessions open** on the same host: in `ro`/`rw`, the
  command refuses to guess and lists what it found. `login` is not affected, it
  does not look at existing sessions.
- **Screen sharing already enabled** on the target session: the command does
  not touch it and stops. This is intentional — a configuration set by hand
  must not be overwritten then "restored" the wrong way.
- No sound, no shared clipboard, no file transfer.
- **Manual resizing of the window does not respect the proportions.**
  The opening size, on the other hand, is correct.
- **`gnome-remote-desktop` is rebuilt** on the affected hosts (see the
  following section). The build is cached, but a `just update` that moves
  GNOME can make the patch fail, noisily.

## The user's pointer

As shipped, `gnome-remote-desktop` forwards the *shape* of the cursor but never
its *position* when it mirrors a physical screen: the client therefore draws
the remote cursor at the location of **your** mouse. In `rw` this is not
noticeable since you are the one driving it, but in `ro` you do not see at all
where the user is pointing — which empties the observation of its value.

DNF fixes this by patching the server so that it asks mutter to embed the
pointer in the image (*embedded* cursor mode, already used upstream for
virtual monitors). One line of code, and cursor metadata stops being emitted —
so no second stray cursor.

The price is a local recompilation of `gnome-remote-desktop` on each
troubleshootable host. To do without it:

```nix
darkone.graphic.remote-desktop.embedCursor = false;
```

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| `nobody is logged in` | No one is logged in: `ro`/`rw` have nothing to reflect, use `login` |
| `could not arm a … session` | The `remote-desktop` feature is not declared on this host, or the host has not been redeployed |
| `Failed to enable service: … EROFS` | Host not redeployed since the `login` mode was added: `just apply <host>` |
| `screen sharing is already enabled` | GNOME sharing was manually enabled on this session |
| `several active graphical sessions` | Multiple accounts have an active session on the same workstation |
| `a support session is already open` | A session is still actually armed on the host: close it first |
| `no DISPLAY among the processes of session …` | X11 session whose X server has disappeared (session closing): try again |
| `the shadow server did not get port …` | The RDP port is already occupied on the host by something else |
| The window opens then immediately closes | Verify that the host is reachable and that the tunnel could be established |

To inspect host-side state:

```sh
just enter clemence
sudo dnf-remote-desktop probe    # which session would be chosen
sudo dnf-remote-desktop stop     # manually disarm
```
