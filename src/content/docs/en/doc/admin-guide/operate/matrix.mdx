bridges (WhatsApp, Signal, Telegram, Messenger, Discord). For the architecture, see

## Enable Matrix

<Steps>

1. Declare the services on the target host in `etc/config.yaml`&nbsp;:

   ```yaml
   # etc/config.yaml
       services:
         matrix:
           title: "Matrix"
           description: "Messagerie instantanée"
         element:        # client web
         turn:           # relais audio/vidéo des clients historiques
   ```

2. Declare the Matrix administrator (global key, outside hosts)&nbsp;:

   ```yaml
   # etc/config.yaml
   matrix:
     admin: "alice"    # local part du compte administrateur
   ```

   This account manages the bridges and receives the
   [supervision alerts](/en/doc/admin-guide/operate/alerts/).

3. Create the required [secrets](/en/doc/admin-guide/operate/secrets/)
   (see table below), then deploy.

</Steps>

Authentication goes through [Kanidm SSO](/en/doc/admin-guide/operate/sso/)
(OIDC)&nbsp;: every declared user signs in with their network account,
no Matrix account creation is needed.

### Required secrets

All internal&nbsp;: `just configure-admin-host` creates them in
`usr/secrets/secrets.yaml`, without overwriting existing entries.

| Sops key | Role |
|---|---|
| `matrix-rss-password` | Synapse registration shared secret |
| `oidc-secret-matrix` | Kanidm OIDC client secret (see [SSO](/en/doc/admin-guide/operate/sso/)) |
| `turn-secret` | coturn shared secret (if `turn` enabled) |
| `livekit-secret` | MatrixRTC shared secret (if `matrixRtc` enabled) |
| `mautrix-doublepuppet-as-token` | *double puppeting* appservice token (shared across bridges) |
| `mautrix-doublepuppet-hs-token` | Same, required by Synapse, never used |

## Two authentication modes

The server runs in **one** of these two modes, set by
`darkone.service.matrix.mas.enable`. The chosen mode changes the compatible
clients, how to invite friends and the administration tools.

| | Synapse historique (défaut) | MAS activé (recommandé) |
|---|---|---|
| Option | `mas.enable = false` | `mas.enable = true` |
| Connexion SSO | Synapse est client OIDC de Kanidm | MAS est client OIDC de Kanidm |
| Element Web / Desktop | oui | oui |
| **Element X** (Android, iOS) | **non** | **oui** |
| Connexion par QR code | non | oui |
| Application proposée sur mobile | Element Classic | Element X |
| Portail de compte | aucun | `https://matrix.domain.tld/account/` |
| Jetons d'inscription | API admin Synapse | `dnf-mas` sur l'hôte |
| Promotion administrateur | SQL dans la base Synapse | `dnf-mas manage promote-admin` |

<Aside type="tip" title="Element X exige MAS">
L'application mobile nouvelle génération [Element X](https://element.io/app/)
ne sait se connecter qu'à un serveur piloté par MAS. Sans MAS, elle échoue à
la connexion&nbsp;; il faut rester sur l'application Element classique.

Le client web s'aligne tout seul&nbsp;: sa page d'accueil mobile propose
Element X quand l'hôte porte un serveur Matrix avec MAS, Element Classic
sinon. Rien à régler.
</Aside>

### Enable MAS

The [Matrix Authentication Service](https://element-hq.github.io/matrix-authentication-service/)
replaces Synapse's built-in authentication. For what it changes and
how it fits in, see
[architecture](/en/doc/admin-guide/understand/matrix/#next-generation-authentication-mas).

<Steps>

1. Generate the three dedicated secrets (idempotent, never overwrites
   existing entries)&nbsp;:

   ```sh
   just configure-admin-host
   ```

   | Sops key | Role |
   |---|---|
   | `mas-encryption-secret` | MAS internal encryption |
   | `mas-synapse-secret` | MAS ↔ Synapse shared secret |
   | `mas-rsa-private-key` | Token signing key |

2. Enable the option in the host's Nix config&nbsp;:

   ```nix
   # usr/machines/<host>/default.nix
   darkone.service.matrix.mas.enable = true;
   ```

3. Deploy. On a **fresh** server, that's it. On a server that already has
   accounts, proceed to the [migration](#migrating-a-server-already-in-production)
   **without letting anyone log in between the two**.

</Steps>

:::danger[Immutable secret]
`mas-encryption-secret` must **never** change after MAS's first startup&nbsp;:
it protects encrypted data in the database that would become unreadable.
Same for the Kanidm provider ULID, frozen in the module.
:::

### Migrating a server already in production

MAS becomes the owner of accounts and sessions&nbsp;: they must be imported
with the official `syn2mas` tool, served by the host's `dnf-mas` command.
Without this import, all accounts are invisible and everyone is signed out.

<Steps>

1. **Back up**, in this order (the dump must make it into the snapshot)&nbsp;:

   ```sh
   sudo systemctl start postgresqlBackup.service
   sudo systemctl start restic-backups-system-main.service
   ```

2. **Deploy** the configuration with `mas.enable = true` (see above). The
   maintenance window starts here.

3. **Stop** both services&nbsp;: `syn2mas` requires Synapse to be offline, and
   MAS must not provision accounts in the meantime.

   ```sh
   sudo systemctl stop matrix-synapse matrix-authentication-service
   ```

4. **Check**, then run a dry run, then migrate&nbsp;:

   ```sh
   sudo dnf-mas syn2mas check
   sudo dnf-mas syn2mas migrate --dry-run
   sudo dnf-mas syn2mas migrate
   ```

   The report announces the recovered accounts, SSO links, access tokens and
   devices. The hundreds of "ignored" users are the bridges' ghosts&nbsp;: that's
   normal.

5. **Restart**, MAS first&nbsp;:

   ```sh
   sudo systemctl start matrix-authentication-service
   sudo systemctl start matrix-synapse
   ```

</Steps>

<Aside type="note" title="What the migration preserves">
Current sessions **survive**&nbsp;: existing access tokens are converted into
compatibility sessions, nobody needs to sign in again, and the alerts bot
keeps its token. The bridges do **not** need a registration regeneration&nbsp;:
Synapse enforces MSC4190 on all appservices as soon as authentication is
delegated.
</Aside>

:::caution[One-way only]
The migration is not reversible&nbsp;: going back requires restoring the
backup. Do not run it without having verified step 1.
:::

## Registering friends

In addition to SSO users, you can open **token-based** registration for local
password accounts (the friends). Without a token, no registration is possible.
The switch is the same in both modes, only how the token is produced differs.

```nix
# usr/machines/<host>/default.nix
darkone.service.matrix.friendRegistration.enable = true;
```

<Tabs>
<TabItem label="With MAS">

<Steps>

1. Create a token on the Matrix host. Here valid **once** and **7 days**
   (without options, the token is single-use and without expiry)&nbsp;:

   ```sh
   sudo dnf-mas manage issue-user-registration-token --usage-limit 1 --expires-in 604800
   ```

   The response displays the token, for example `Created user registration token:
   9SwPTGIFGQPa`. Send it to the friend.

2. The friend opens `https://matrix.domain.tld/register` and chooses
   password-based creation.

3. He enters his username and password, **then** the token, requested at the
   next step.

4. He then signs in with this username / password pair from any client,
   Element X included.

</Steps>

<Aside type="tip" title="Managing one's account">
A friend changes their password and revokes their sessions from the portal
`https://matrix.domain.tld/account/`, without the administrator's involvement.
</Aside>

</TabItem>
<TabItem label="Without MAS">

<Steps>

1. Promote the `matrix.admin` account to *server admin* (only once), on the
   Matrix host&nbsp;:

   ```sh
   sudo -u matrix-synapse psql matrix-synapse \
     -c "UPDATE users SET admin = 1 WHERE name = '@alice:domain.tld';"
   ```

2. Retrieve an *access token* for the promoted account&nbsp;: in Element,
   *Settings → Help & About → Advanced*.

3. Create a registration token via the administration API&nbsp;:

   ```sh
   curl -X POST \
     -A "Mozilla/5.0" \
     -H "Authorization: Bearer <ACCESS_TOKEN>" \
     -H "Content-Type: application/json" \
     -d '{"uses_allowed": 1, "expiry_time": null}' \
     https://matrix.domain.tld/_synapse/admin/v1/registration_tokens/new
   ```

   The response contains the `token` to send to the friend.

4. The friend registers in Element&nbsp;: *Create account* → server `domain.tld`
   → he pastes the token when it is requested.

</Steps>

<Aside type="caution" title="The anti-bot filter">
The Matrix vhost returns `403` for any call whose *User-Agent* contains
`curl`, `wget` or `bot`. Hence the `-A "Mozilla/5.0"` above&nbsp;: without it,
the call fails for reasons unrelated to the token.
</Aside>

</TabItem>
</Tabs>

### Identifier collision with a declared user

Friends and SSO users share **a single namespace**&nbsp;:
`@bob:domain.tld` belongs to only one account, regardless of its origin. And a
Matrix identifier is **permanent** — the `users` table of MAS enforces its
uniqueness, and deactivating an account does not free its identifier. No
renaming, no recycling.

The typical case&nbsp;: a friend registers as `bob`, then `bob` is declared
later as a DNF user in `etc/config.yaml`. Their first SSO connection then stops
on a **`User exists`** error page&nbsp;:

```text
Upstream account provider returned "bob" as username, which is not linked to
that upstream account. Your homeserver does not allow linking an upstream
account to an existing account
```

Check before declaring a user, on the Matrix host&nbsp;:

```sh
sudo -u postgres psql matrix-authentication-service \
  -c "SELECT username FROM users WHERE lower(username) = lower('bob');"
```

Two outcomes, depending on what you want to keep&nbsp;:

<Tabs>
<TabItem label="Merge the two accounts">

Links the Kanidm identity to the existing friend account, which **keeps
everything**&nbsp;: rooms, history, encryption keys, bridges. This is almost
always what you want, and the person concerned does it themselves.

<Steps>

1. First declare `bob` in `etc/config.yaml` and deploy, so that they get
   Kanidm credentials.

2. Bob signs in on `https://matrix.domain.tld/account/` with their **friend
   password**.

3. In the **same browser**, they open the link account of the IDM
   provider&nbsp;:

   ```text
   https://matrix.domain.tld/upstream/authorize/01JDNF0000000000000KAN1DM0
   ```

4. They authenticate on Kanidm&nbsp;; MAS then offers "&nbsp;Link to your
   existing account&nbsp;", which they confirm.

</Steps>

Bob then signs in through SSO like any declared user. Their friend password
stays valid&nbsp;: deleting it is done from the account portal.

<Aside type="note" title="The provider's ULID">
`01JDNF0000000000000KAN1DM0` is set by the framework and identical on every
DNF deployment (cf. [architecture](/en/doc/admin-guide/understand/matrix/#next-generation-authentication-mas)).
</Aside>

</TabItem>
<TabItem label="Give up the identifier">

If the friend account has nothing to save, it is simpler to **declare the DNF
user under another login**&nbsp;: the `bob` identifier is lost for good,
deactivating the friend account will not make it available.

Lock the old account to avoid confusion&nbsp;:

```sh
sudo dnf-mas manage lock-user bob
```

</TabItem>
</Tabs>

<Aside type="caution" title="Why the merge is not automatic">
MAS can link an upstream identity to a same-name account by itself, via
`claims_imports.localpart.on_conflict`. DNF deliberately leaves it at its
default value&nbsp;:

| Value | Effect |
|---|---|
| `fail` *(DNF default)* | Refuses the upstream connection |
| `add` | Links to the same-name account, whether a link already exists or not |
| `replace` | Replaces the existing link of this provider on this account |
| `set` | Links only if this provider does not already have a link |

Anything other than `fail` means that **the first person whose Kanidm login
matches a local account takes it over**, without anyone validating anything.
On a network where logins are assigned by hand, the risk is low but the gain
is zero&nbsp;: the manual merge above does the same work, once, knowingly.
</Aside>

## Managing bridges

WhatsApp, Signal, Telegram and Messenger bridges are **enabled by
default** with Matrix&nbsp;; Discord is **disabled by default**. Per-host setting in
the machine's nix configuration&nbsp;:

```nix
# usr/machines/<host>/default.nix
darkone.service.matrix.bridges = {
  discord.enable = true;     # opt-in
  messenger.enable = false;  # disable a default bridge
};
```

Each bridge has its own secrets&nbsp;:

| Bridge | Sops keys | Note |
|---|---|---|
| WhatsApp | `mautrix-whatsapp-as-token`, `mautrix-whatsapp-hs-token`, `mautrix-whatsapp-encryption-pickle-key` | `openssl rand -hex 32` each |
| Signal | `mautrix-signal-as-token`, `mautrix-signal-hs-token`, `mautrix-signal-encryption-pickle-key` | `openssl rand -hex 32` each |
| Messenger | `mautrix-meta-as-token`, `mautrix-meta-hs-token`, `mautrix-meta-encryption-pickle-key` | `openssl rand -hex 32` each |
| Telegram | `mautrix-telegram-api-id`, `mautrix-telegram-api-hash`, `mautrix-telegram-as-token`, `mautrix-telegram-hs-token` | API id/hash to create on [my.telegram.org](https://my.telegram.org) |
| Discord | `mautrix-discord-as-token`, `mautrix-discord-hs-token` | `openssl rand -hex 32` each |

The `as`/`hs` tokens make each bridge's appservice *registration*
deterministic (see
[appservice tokens](/en/doc/admin-guide/understand/matrix/#appservice-tokens)).

<Aside type="caution" title="Migrating an already deployed bridge">
On a WhatsApp or Signal bridge deployed **before** these tokens were
introduced, the existing registration keeps the old auto-generated tokens. To switch
to sops tokens&nbsp;: delete `/var/lib/mautrix-<pont>/<pont>-registration.yaml`,
restart the bridge (the registration is regenerated from the config), then
restart `matrix-synapse`. For Messenger and Discord, a simple redeployment
followed by a Synapse restart is enough&nbsp;: their modules rewrite the
registration from the config at every start.
</Aside>

### Permissions

Nothing to manage&nbsp;: any local account (`@*:domain.tld`) can use each
bridge with **their own** remote account, without interference between
users. The `matrix.admin` account has the bot administration
commands (`help` in direct conversation with the bot for the
list).

### Double puppeting

Bridges share a `doublepuppet` appservice (token
`mautrix-doublepuppet-as-token`)&nbsp;: messages sent from the
phone appear in Matrix as coming from the user's **real account**.
This is automatic for all local accounts, no action per
user.

## Audio and video calls

Two stacks coexist, because neither covers all clients. They are
enabled separately and do not replace each other&nbsp;:

| | Legacy WebRTC | MatrixRTC |
|---|---|---|
| Option | `darkone.service.turn.enable` | `darkone.service.matrix.matrixRtc.enable` |
| Components | coturn | LiveKit (SFU) + authorization service |
| One-on-one calls | yes | yes |
| Group calls | no | yes |
| Element Classic (Android) | **yes** | no |
| Element Web / Desktop | yes | yes |
| **Element X** (Android, iOS) | **no** | **yes** |

Keep **both** enabled&nbsp;: Element Classic only speaks the first,
Element X only the second.

<Aside type="danger" title="The two stacks cannot talk to each other">
A call started from Element X is **invisible** in Element Classic, and
vice versa&nbsp;: the two report via different Matrix events (`m.call.*`
vs. `m.rtc.member`), and the legacy app contains no LiveKit code. No server
configuration reconciles them&nbsp;; upstream, the issue is
[classified "not planned"](https://github.com/element-hq/element-x-android/issues/3937).

The only client that speaks **both** is Element Web/Desktop&nbsp;: a user
who stayed on Element Classic can join an Element X call by opening
`https://element.domain.tld` in their phone's browser.
Otherwise, migrate to Element X — the classic app is in maintenance
only, with no new features.
</Aside>

<Aside type="caution" title="Element X: two separate prerequisites">
Element X refuses to call with *"Call not supported"* (code
`MISSING_MATRIX_RTC_TRANSPORT`) as long as MatrixRTC is absent, **even**
if MAS is active. MAS gates login, MatrixRTC gates calls&nbsp;: enabling
one does not give you the other.
</Aside>

<Steps>

1. Enable the MatrixRTC stack in the host's Nix config&nbsp;:

   ```nix
   # usr/machines/<host>/default.nix
   darkone.service.matrix = {
     mas.enable = true;         # required by Element X to log in
     matrixRtc.enable = true;   # required by Element X to call
   };
   ```

2. Generate the shared secret, then deploy&nbsp;:

   ```sh
   just configure-admin-host
   just apply <host> switch
   ```

3. Verify the server advertises a transport&nbsp;:

   ```sh
   # must contain "org.matrix.msc4143.rtc_foci"
   curl -A Mozilla/5.0 https://domain.tld/.well-known/matrix/client

   # org.matrix.msc4143 must be true
   curl -A Mozilla/5.0 https://matrix.domain.tld/_matrix/client/versions
   ```

</Steps>

No extra subdomain or certificate&nbsp;: the SFU and its authorization
service are served on the Matrix vhost, under `/livekit/sfu` and
`/livekit/jwt`. On the client side, nothing to configure either&nbsp;—
Element X and Element Web ship Element Call and discover the transport
on their own.

### Media ports

Media does **not** go through the reverse proxy: clients reach the host
directly. These ports must therefore be opened up to it, and forwarded if it
sits behind NAT:

| Port | Stack | Usage |
|---|---|---|
| 30000-30100/udp | MatrixRTC | WebRTC media, one port per participant |
| 7881/tcp | MatrixRTC | Fallback for networks that block UDP |
| 3478/udp, 3478/tcp, 5349/tcp | coturn | STUN and TURN negotiation |
| 61000-65535/udp | coturn | Relayed media |

<Aside type="note" title="Why not the default ranges">
Both upstream ranges fall into an already occupied window. The LiveKit one
(50000-51000/udp) sits inside coturn's default relay range (49152-65535):
co-hosted, the two would fight over the same ports and randomly break calls.
And this coturn range overlaps the kernel's ephemeral range
(`net.ipv4.ip_local_port_range`, 32768-60999 by default): any outgoing
connection from a neighboring service can steal a media port from it. DNF
therefore moves coturn above the ephemeral range and LiveKit below it.
</Aside>

{/* t:p 8e53db5780635f4b9a1ce0e6e1bb416bdb0c184b020c65aa5ad91365f0a9aa14 */}
### Permanently relayed calls

A WebRTC client discovers its public address with a **STUN Binding**
request, which it always sends **without authentication**, including to the
TURN server. If coturn rejects it (the `secure-stun` option), the client
gets no *server-reflexive* candidates: all it has left are its local
addresses, unusable outside the local network, and its relay address. No
direct path is ever attempted then: **all** calls traverse coturn, slower
to establish and with no fallback when the relay saturates.

DNF therefore leaves `secure-stun` disabled. TURN allocations, for their
part, remain authenticated through the shared secret (`use-auth-secret`):
only the Binding is anonymous.

To check from an external machine:

```sh
nix shell nixpkgs#stuntman --command stunclient turn.domain.tld 3478
```

`Binding test: success` followed by the address as seen by the server: correct.
`Binding test: fail`: anonymous requests are rejected, every call will be
relayed.

## Opening the network to federation

By default, the server federates with **all** Matrix servers, while remaining
**invisible in searches** (directories not exposed). To control the scope, set
`darkone.service.matrix.federation` in the host's nix config:

```nix
# usr/machines/<host>/default.nix
darkone.service.matrix.federation = {
  enable = true;       # false = federation fully blocked
  whitelist = [ ];     # empty = open ; otherwise whitelist
};
```

| Goal | Setting |
|---|---|
| Isolated network (no federation) | `enable = false;` |
| Open to the entire Matrix ecosystem | `enable = true; whitelist = [ ];` |
| Restricted to trusted servers | `enable = true; whitelist = [ "ami.org" "matrix.org" ];` |

<Aside type="caution" title="Family network">
The whitelist is **bidirectional**: an unlisted server can neither write to
your users nor receive from them. For a network used by children, fill in
`whitelist` rather than leaving federation open.
</Aside>

Verify after deployment:

<Steps>

1. Test incoming federation with
   [federationtester.matrix.org](https://federationtester.matrix.org/) on
   `domain.tld` → all green lights.

2. With a whitelist, an **unlisted** server is denied (Synapse log:
   `Federation denied`), a listed domain works.

</Steps>

## Public rooms with approval (knock)

A **public** room in the Matrix sense can be joined **freely**: no validation.
For a room that is "joinable but on approval", use the **knock** access rule —
a **per-room** setting, on the client side, no server configuration needed.

<Steps>

1. In Element: room → *Room Settings* → *Security & Privacy*.

2. Room access → **"Ask to join"** (knock).

3. A user (local or federated remote) requests access; a moderator approves or
   denies.

</Steps>

<Aside type="tip" title="Really private?">
For a confidential room: remove it from the directory **and** set it to `knock`
or invitation only. End-to-end encryption is already active by default on new
rooms.
</Aside>

### Administering accounts with MAS

`dnf-mas` wraps the official `mas-cli` tool on the Matrix host&nbsp;: it
reconstructs the service's configuration and secrets, and therefore works
whether the **service is stopped or started**. Always with `sudo`.

| Action | Command |
|---|---|
| Create a registration token | `sudo dnf-mas manage issue-user-registration-token` |
| Promote an administrator | `sudo dnf-mas manage promote-admin alice` |
| List administrators | `sudo dnf-mas manage list-admin-users` |
| Create an account (bot, service) | `sudo dnf-mas manage register-user` |
| Change a password | `sudo dnf-mas manage set-password alice` |
| Close an account's sessions | `sudo dnf-mas manage kill-sessions alice` |
| Lock an account | `sudo dnf-mas manage lock-user alice` |
| Full diagnostic | `sudo dnf-mas doctor` |

<Aside type="caution" title="No more shared registration secret">
With MAS, `/_synapse/admin/v1/register` is disabled. This is the mechanism
used by [`just configure-alert-bot`](/en/doc/admin-guide/operate/justfile/)
to create a missing bot account&nbsp;: create this account **before**
migrating, or recreate it with `sudo dnf-mas manage register-user`.
</Aside>

### Diagnosing a refused SSO connection

After a migration, sessions that are already open keep working: a broken
connection therefore only shows up **on the first fresh login**. Watch MAS
during an attempt:

```sh
journalctl -u matrix-authentication-service -f
```

| Message | Cause | Fix |
|---|---|---|
| `wrong signature alg` on `/upstream/callback/…` | MAS expects an RS256 `id_token`, Kanidm signs with ES256 | `id_token_signed_response_alg` of the upstream provider: set to `ES256` by the module |
| `client registration denied by the policy: invalid redirect_uri` | The `client_uri` advertised by the client does not match its redirect scheme | Do not force `oidc_metadata` in the Element config; its defaults pass |
| `M_UNRECOGNIZED` on `/login/sso/redirect` | The path goes to Synapse instead of MAS | Check the `@masCompat` matcher of the Caddy vhost |
| Page `User exists`: 'returned "bob" as username, which is not linked' | Another account already occupies the declared user's identifier | Merge or rename (see [identifier collision](#identifier-collision-with-a-declared-user)) |
| "The QR code is not supported" on the client side | The MSC4108 rendezvous channel is missing | `experimental_features.msc4108_enabled`: enabled by the module along with MAS |
| "The call is not supported", `MISSING_MATRIX_RTC_TRANSPORT` | No MatrixRTC backend advertised | Enable `matrixRtc.enable` (see [Audio and video calls](#audio-and-video-calls)) |
| Call that rings but stays silent, or drops after a few seconds | Media ports do not reach the host | Open 30000-30100/udp and 7881/tcp up to it |
| Call slow to establish, or failing outright, with all traffic going through coturn | Clients get no *server-reflexive* candidates, hence no direct path | coturn must answer **anonymous** STUN Binding requests (see [Permanently relayed calls](#permanently-relayed-calls)) |

Quick checks, without logging in:

```sh
# org.matrix.msc4108 doit valoir true
curl -A Mozilla/5.0 https://matrix.domain.tld/_matrix/client/versions

# doit répondre 201 et une url publique
curl -A Mozilla/5.0 -X POST --data probe \
  https://matrix.domain.tld/_matrix/client/unstable/org.matrix.msc4108/rendezvous
```

<Aside type="note" title="Two symptoms, two causes">
A client falling back to authentication **in the browser** instead of its
native screen signals a dynamic registration refusal; any error that may
follow is a separate problem. Address both.
</Aside>

### Diagnosing a silent bot

:::note[Client-side checks]
Check on the client (Element, Fractal...) that the bot is not ignored.
Right-click on the bot's user → information
→ security, then "ignored". If the bot replies in the logs but
nothing happens, the block may be on the client side.
:::

A bot that does not reply to `help` while its service is running almost
always falls into one of two cases&nbsp;: its tokens no longer match the
registration loaded by Synapse, or it receives messages but cannot
**decrypt** them. Diagnose in order&nbsp;:

<Steps>

1. **Is the service actually running ?**

   ```sh
   systemctl status mautrix-<bridge>
   journalctl -u mautrix-<bridge> -n 50
   ```

   If it keeps restarting with «&nbsp;The as_token was not accepted&nbsp;»,
   Synapse's in-memory registration no longer matches the bridge's tokens
   (typical after a reset or migration, see the box above)&nbsp;:
   `systemctl restart matrix-synapse`, then restart the bridge.

2. **Does the message reach the bridge ?** Follow Synapse while sending
   a `help` to the bot&nbsp;:

   ```sh
   journalctl -u matrix-synapse -f | grep transactions
   ```

   A `PUT .../_matrix/app/v1/transactions/... 200` line should appear.
   If nothing goes out, the appservice is not loaded&nbsp;: check for the
   registration file in `/var/lib/mautrix-<bridge>/` and restart Synapse.

3. **Can the bridge decrypt it ?** If the transaction goes through (200)
   but the bot stays silent, follow its logs while sending a new message&nbsp;:

   ```sh
   journalctl -u mautrix-<bridge> -f
   ```

   Look for `decrypt`, `session`, `verification`, `dropping`. A
   decryption failure means the room's session key has not been
   shared with the bot's current device (typical after a bridge
   reset&nbsp;: its e2ee identity has changed).

4. **Recreate the conversation.** Leave the direct message with the bot and
   start a new one&nbsp;: the client establishes a fresh encryption session
   and shares the key with the bot's current device. Also check
   that your own Element session is **verified**.

5. **Last resort**&nbsp;: reset the bridge state (box
   below), then restart Synapse to reload the registration.

</Steps>

<Aside type="note" title="WhatsApp statuses disabled">
The WhatsApp bridge does not relay « statuses » (stories): the
`network.enable_status_broadcast` option is forced to `false`, otherwise
every user would be repeatedly re-invited to a « WhatsApp Status
Broadcast » room.
</Aside>

<Aside type="caution" title="Resetting a bridge">
A bridge's data (sessions, room mappings) lives in
`/var/lib/mautrix-*`. Deleting this directory disconnects **all**
bridge users and breaks existing room mappings:
only do this as a last resort, with the service stopped.
</Aside>
