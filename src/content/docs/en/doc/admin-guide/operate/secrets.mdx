All network secrets (passwords, keys, tokens) live **encrypted** in a single
file, managed by [sops-nix](https://github.com/Mic92/sops-nix). It is versioned
in git **in encrypted form**; only key holders can decrypt it.

```yaml
# usr/secrets/secrets.yaml (encrypted at rest)
user:
  alice:
    password-hash: ...
```

## The two keys

Decryption relies on two [age](https://age-encryption.org/) keys:

| Key | Where | Role |
|---|---|---|
| **Admin key** | `~/.config/sops/age/keys.txt` | Edit secrets from the admin workstation |
| **Infra key** | `/etc/sops/age/infra.key` | Decrypt on each host at deploy time |

- The **admin key** derives from your SSH key (`~/.ssh/id_ed25519`, via `ssh-to-age`).
- The **infra key** is generated once, then **pushed to each host**.
- Recipients are listed in `usr/secrets/.sops.yaml` (admin + infra).

:::danger[Never commit a private key]
The infra key lives **outside the repo** (`/etc/sops/age/`). The `usr/secrets/`
`.gitignore` already excludes `*.key`. Never copy it into the repo.
:::

## Initialize (admin workstation)

A single command prepares all the secrets machinery:

```sh
just configure-admin-host
```

It is **idempotent** and creates, as needed:

- the deployer's SSH key (`nix`);
- a random password, known to no one, for the `nix` account: it can only be
  accessed via its key;
- the admin key (from the SSH key) and the infra key (`age-keygen`);
- the `.sops.yaml` file (recipients);
- the Harmonia binary cache signing key;
- **all internal secrets** of the declared services (see below).

:::tip[Rerun after enabling a service]
The command reads the secrets required by each host in the fleet and creates
the missing ones. Enabling a new service, adding a host or a zone: rerun
`just configure-admin-host`, it will only fill in what is missing.
:::

:::note[Part of the journey]
This step is part of the [initial installation](/en/doc/admin-guide/install/first-network-installation/).
:::

## Internal secrets and external secrets

The framework sorts each secret into one of two families. The reference list
lives in `dnf/lib/secrets.nix`&nbsp;; each host of the farm is the authority on
what is *claimed*.

**Internal** — the value only makes sense to machines, no one remembers it.
`just configure-admin-host` draws them at random, once and for all&nbsp;:

| Family | Examples |
|---|---|
| Kanidm OAuth2 clients | `oidc-secret-<client>`, oauth2-proxy cookie |
| Backup | `restic-password-<zone>`, `restic/<host>/rest-password` |
| Matrix | MAS secrets, `livekit-secret`, bridge tokens, `turn-secret` |
| Identities | Kanidm fallback passwords, internal TLS pair |
| Services | AdGuard Home, Nextcloud, Grafana, SearXNG, Vaultwarden, Garage, MinIO... |

**External** — the value comes from elsewhere, DNF cannot invent it&nbsp;:

| Family | Origin |
|---|---|
| Account passwords | chosen by a human (`just passwd`) |
| `smtp/password` (with `network.smtp`), `wifi-password-<zone>` | provider, box, operator |
| `mautrix-telegram-api-*` | my.telegram.org |
| `luks-passphrase`, `yubikey/...` | typed at boot, or derived from the physical key |
| `alertmanager-matrix-*` | account created on the server (`just configure-alert-bot`) |

:::tip[An internal secret can still be useful to a human]
AdGuard Home admin password (`adguardhome-admin-password`, whose hash only
partially lands on the gateways), Kanidm fallback accounts, Vaultwarden token:
re-read them with `just sops`.
:::

:::note[Nothing is ever overwritten]
Generation only creates what is missing. Rotating a secret remains a deliberate
act&nbsp;: delete it with `just sops`, then rerun
`just configure-admin-host`.
:::

:::caution[What DNF does not know about]
A missing secret that the registry cannot classify is reported on every pass.
Fill it in with `just sops` — or, if it belongs to a framework module, add its
rule in `dnf/lib/secrets.nix`.
:::

## Manage passwords

| Command | Effect |
|---|---|
| `just passwd <user>` | Sets a user's password |
| `just configure-admin-host` | Generates missing internal secrets (OIDC, backup, service tokens…) |
| `just yubikey <user>` | Enrolls a YubiKey (derived LUKS secret + `luks-passphrase`) |
| `just luks <host>` | Provisions disk encryption (shared + per-host passphrases) |
| `just sops` | Edits the secrets file by hand (`$EDITOR`) |

After a change, **deploy** to propagate it:

```sh
just passwd alice
just apply @user-alice     # deploys the new hash
```

:::tip[Hashes, never plaintext]
Account passwords are stored **hashed** (`password-hash`). The plaintext is
never deployed to hosts.
:::

:::note[No more default password]
The fleet no longer has a reference password: `just passwd-default` and the
`default-password-hash` secret are gone, no host was reading them. Each
account gets its own with `just passwd <login>`. In an existing project, the
key remains in `secrets.yaml` with no effect; `just sops` removes it if
desired.
:::

:::caution[Disabling sops disables passwords]
`darkone.system.core.enableSops = false` removes the secrets
`user/<login>/password-hash`, the framework's only password source: declared
accounts would be created without any authentication. Evaluation therefore
stops with a message naming the option to restore. For a host intentionally
without DNF accounts, also set
`darkone.user.build.enable = false`.
:::

:::note[YubiKey: public registry + secrets]
YubiKey enrollment places its **public** credentials in
`usr/secrets/yubikeys.json` (versioned in plaintext, unusable without the
physical key) and its secrets (`yubikey/<user>/<key>/luks-secret`,
`luks-passphrase`) in the sops file. See
[Strong authentication](/en/doc/admin-guide/operate/yubikey/).
:::

## Push the key to a host

A host can only decrypt secrets with the infra key. It is placed automatically
by `just configure <host>`, or manually:

```sh
just push-key <host>      # copies /etc/sops/age/infra.key to the host
```

:::note[Rarely needed]
`push-key` is already built into `just install` (and `just configure`): in
practice, you should not need to call it yourself.
:::

## Rotating the infra key

Rotation replaces the infra key across the entire fleet, in three verified steps:

:::danger[Finalize only when the entire fleet is updated]
`finalize` **removes the old key**. If a host hasn't yet received the new one (`rotate push-keys` + `just apply`), it becomes **impossible to decrypt**, and thus inaccessible to deployment. Only run `finalize` after confirming that **all** hosts are using the new key.
:::

<Steps>

1. **Introduce the new key**

   ```sh
   just rotate init        # new key + re-encryption (old + new)
   ```

2. **Distribute to all hosts**

   ```sh
   just rotate push-keys   # each host receives both keys
   just apply '*'
   ```

3. **Finalize**

   ```sh
   just rotate finalize    # discards the old key (after verification)
   just apply '*'
   ```

</Steps>

:::caution[Mandatory order]
The presence of `/etc/sops/age/infra.key.old` indicates a rotation **in progress**. Always finish with `finalize`: until then, hosts carry both keys.
:::

## Isolated hosts

A host running AI agents reads untrusted content (emails, web, messaging)&nbsp;: it must never hold the secrets of the fleet. With `darkone.system.sops.isolated = true`&nbsp;:

| Element | Isolated host |
|---|---|
| Secrets file | `usr/secrets/hosts/<host>.yaml` |
| Infra key | Never pushed, removed if present |
| Passwords | None, access by SSH key |
| LUKS encryption | Its own passphrase ([details](/en/doc/admin-guide/operate/luks/#isolated-encrypted-host)) |
| YubiKeys | Host-specific salt ([why](/en/doc/admin-guide/understand/yubikey-salts/)) |

This is the default for the `ai-space` profile and for any [microVM guest](/en/doc/admin-guide/operate/microvm/).
`just configure-admin-host` never writes its secrets to `secrets.yaml`.

A fleet secret declared on an isolated host (`luks-passphrase`, password fingerprint, FIDO2 value with the fleet salt) will cause evaluation to fail&nbsp;: remove it from this host, never copy it to its file.

The infra key follows `sops.age.keyFile`&nbsp;: a host whose sops-nix does not read it will neither receive it from `just install` nor from `just push-key`, and `just rotate finalize` will not look for it there.

<Steps>

1. **Initialize** (admin workstation)

   ```sh
   just space-init espace1
   ```

   Creates the host key (on the hypervisor for a microVM guest), the encrypted file, and the internal secrets. Can be rerun safely. For a physical machine&nbsp;: `just install` already performs this sealing, using the installer key.

2. **Complete**

   ```sh
   just space-sops espace1
   ```

   For secrets that DNF cannot generate, reported by `space-init`.

3. **Commit** `usr/secrets/.sops.yaml` and `usr/secrets/hosts/espace1.*`

</Steps>

:::caution[Host key replaced]
A new host key (guest recreated, machine reinstalled outside of `just install`)
will make the file unreadable for the host&nbsp;: rerun `just space-init`, which will
re-encrypt it.
:::

### Hashed Vaultwarden token (Argon2)?

`just invite` connects on its own to the `/admin` panel with the **plaintext**
`vaultwarden-admin-token` value. A manually set Argon2 hash forces it to
ask for the token;&nbsp;`just configure-admin-host` reports it.

To migrate&nbsp;delete the entry with `just sops`, run
`just configure-admin-host` again, then `just apply hcs`. Vaultwarden restarts with
the new token. The panel remains protected by the network&nbsp;: it only responds
from the LAN and the tailnet.

### New admin machine, existing project?

The project's secrets are encrypted for the old admin machine's keys.
`just configure-admin-host` therefore refuses to create new ones: first restore
`/home/nix/.ssh/id_ed25519` and `/etc/sops/age/infra.key` (owned by `nix`, mode
`600`).

### Prepare a machine without a `nix` account?

`just bootstrap-keys` creates the keys and the sops skeleton under a given root,
for example `/mnt` from the installer, with the credentials NixOS will give the
`nix` account. See the [Justfile](/en/doc/admin-guide/operate/justfile/).
