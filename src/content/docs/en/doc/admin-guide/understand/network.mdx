The DNF network operates at two scales: an isolated local **zone**, then
multiple zones connected by a mesh **VPN**. The vocabulary is defined in
[Concepts](/en/doc/admin-guide/understand/concepts/).

{/* t:p dc9534f835e0e09db41110a71aa8e46e59668b5a9a710b8379ec1c2ae465ed93 */}
## Simple network (one zone)

A zone is a gateway and its machines.

```d2
style.fill: transparent
direction: down

net: Internet { shape: cloud }

gw: Gateway {
  fw: NAT + Firewall
  dns: dnsmasq\nDNS + DHCP
  fw -> dns
}

lan: Local zone {
  pc: Workstations
  srv: Server { shape: cylinder }
}

net -> gw.fw: WAN
gw.dns -> lan.pc: LAN
gw.dns -> lan.srv: LAN
```

- The gateway shares Internet (NAT) and protects the zone (firewall).
- `dnsmasq` distributes addresses (DHCP) and resolves local names
  (`<host>.<zone>`).
- On the Internet side (WAN), everything is closed. On the local side (LAN), only
  SSH, DNS, DHCP and the home page are open.

## Ad blocking (AdGuardHome)

Optional service, enabled on the gateway. It inserts itself in front of `dnsmasq`.

```d2
style.fill: transparent
direction: down

pc: Workstation

agh: AdGuardHome\nport 53, filtering { shape: hexagon }

dns: dnsmasq\nlocal names { shape: cylinder }
up: External DNS\nencrypted { shape: cloud }

pc -> agh: DNS query
agh -> dns: Local names
agh -> up: Rest, filtered
```

- AdGuardHome becomes the DNS resolver for workstations (port 53).
- It blocks ads and trackers, and encrypts queries to the outside.
- `dnsmasq` moves to an internal port and keeps local names and DHCP.

## Wide area network (VPN)

Several zones are linked by a mesh VPN, the tailnet, coordinated by the
coordination server (HCS).

```d2
style.fill: transparent
direction: down

hcs: Coordination\nHeadscale (HCS) { shape: cylinder }

zoneA: Zone A {
  gwa: Gateway
  la: Clients
  gwa -> la
}
zoneB: Zone B {
  gwb: Gateway
  lb: Clients
  gwb -> lb
}
ext: Remote machine

hcs -> zoneA.gwa: Control { style.stroke-dash: 3 }
hcs -> zoneB.gwb: Control { style.stroke-dash: 3 }
hcs -> ext: Control { style.stroke-dash: 3 }
zoneA.gwa <-> zoneB.gwb: Direct traffic
ext <-> zoneA.gwa
```

- The HCS (Headscale) is public and coordinates the meshing; traffic goes
  directly from one node to another.
- Each gateway is a *subnet router*: it publishes the
  subnet of its zone into the VPN.
- Zones can see each other; remote machines (smartphone, PC)
  join the network via Tailscale.
- Nothing is allowed by default: an access policy, generated from
  `etc/config.yaml`, specifies who can reach what.
- A pivot resolver on the HCS routes each zone's names to its gateway.

Routing, DNS, MagicDNS, access policy, and activation keys are detailed in
[Tailnet operation](/en/doc/admin-guide/understand/tailnet/).

<Aside type="note" title="Optional VPN">
Meshing is only enabled when `network.coordination.enable` is true in
`etc/config.yaml`. Without it, zones remain local and independent.
</Aside>

## What goes through a gateway

A gateway routes, and a routed packet **never** goes through the port opening
rules&nbsp;: those only concern what is addressed to it. The two filters are
independent.

Only the following traffic goes through a gateway&nbsp;:

| Traffic | Usage |
|---|---|
| Zone → WAN | Internet sharing (NAT) |
| Zone → backup link | Internet sharing when the box goes down ([backup links](/en/doc/how-to/admin/gateway-backup-links/)) |
| Zone ↔ VPN | The other zones, remote machines |
| Port replies and redirections | Return of outbound traffic, `forwardPorts` |

Everything else is dropped. In particular, an Internet machine that set up a
static route to a zone subnet reaches nothing&nbsp;: without this filtering, a
gateway with a public address would let everything through.

Any extra routing requirement goes into the host file&nbsp;:

```nix
networking.firewall.extraForwardRules = ''
  iifname "lan0" oifname "wg0" accept
'';
```

## SSH access by role

Port 22 is never open "everywhere". A rule without an interface name applies to **all** interfaces, WAN included: on a gateway, this would expose SSH to the Internet.

| Host | SSH reachable from |
|---|---|
| Zone gateway | Its local network and the VPN |
| Global zone host (HCS) | The Internet — an intentional decision, since it hosts the VPN |
| Zone machine (workstation, server) | Its own interface only, i.e. the local network |

Practical consequence: **a gateway does not respond to SSH from the Internet.** Remote access goes through the VPN:

```sh
just enter gw
```

<Aside type="caution" title="A gateway does not open any port without an interface">
The `gateway` profile refuses to build if a port is opened without an interface name. A gateway service declares itself on `lan0` (the zone) or `tailscale0` (the VPN); a truly public port is placed on the WAN interface, explicitly.
</Aside>

## Scope of internal services

An internal service opens on the interface that matches its actual scope,
never on all of them. Three scopes coexist:

| Scope | Opening | Examples |
|---|---|---|
| Tailnet | `tailscale0` | Loki (logs), relay for exposed services |
| Local network | `lan0` on a gateway, the single interface elsewhere | DNS, DHCP, homepage, Nix cache |
| Address list | `ip saddr` rule, or client-side service list | NFS shares, LAN games |

The third case exists because a zone prefix is not an
identity: any machine that obtains a local address is part of it,
Wi-Fi guests included. Where the service allows it, the declared host
list replaces the prefix.

<Aside type="caution" title="Loki does not authenticate anyone">
`auth_enabled` is Loki's multi-tenant option, not an authentication mechanism.
Anyone who reaches port 3100 can read **and** write logs: it is
only open on the tailnet.
</Aside>

## Names and DNS resolution

Three families of names coexist on the network. All are generated from
`etc/config.yaml`.

| Name | Form | Scope | Example |
|---|---|---|---|
| **Simple name** | `<host>` | Entire internal network | `server` |
| **Zone FQDN** | `<name>.<zone>.<domain>` | Entire internal network | `cloud.home.domain.tld` |
| **Global service** | `<name>.<domain>` | Including the Internet | `git.domain.tld` |

- **Simple names**: these are the **machines** (declared hosts). Resolved
  everywhere on the network, to the machine's real address, whatever its zone.
- **Zone FQDN**: these are the **services of a zone**. They point to that
  zone's gateway, which serves them through its reverse proxy.
- **Global services**: services marked `global` in `etc/config.yaml`.
  Exposed on the HCS with **public DNS**: reachable from anywhere.

Who resolves what:

- `dnsmasq`, on **every gateway**, knows all internal names (machines and
  services of **all** zones): it resolves simple names and FQDNs.
- The current zone is resolved locally; the other zones and the global domain
  are routed to the right gateway, or to the HCS pivot resolver.
- Public (Internet) names are sent upstream to encrypted DNS, filtered by
  AdGuardHome if it is enabled.
- Only declared names exist&nbsp;: an unknown name under a zone answers
  `NXDOMAIN`, without redirecting to the gateway.
- Tailnet names (`<node>.tailnet.internal`) are relayed by each gateway to
  MagicDNS&nbsp;: also resolved from the LANs.

### The pivot resolver (HCS)

On the coordination server (HCS), a **pivot resolver** (unbound) centralizes
the internal VPN resolution. It knows the zone breakdown and simply routes&nbsp;:

- each zone FQDN goes to its zone's gateway, at its tailnet address&nbsp;;
- global services hosted on the HCS are resolved locally&nbsp;;
- everything else goes to an encrypted external DNS.

Remote devices query it via MagicDNS (split DNS), and gateways query it for names
in the domain they don't know. Between two zones, a gateway queries the other
zone's gateway directly. Details in
[DNS](/en/doc/admin-guide/understand/tailnet/#dns).

### Resolution from outside

A machine outside any zone (laptop on the go, smartphone) joins the
network via the VPN. Its DNS resolution is **split** (split-DNS) based on the
nature of the requested name:

- **internal names**: routed through the VPN to the HCS pivot resolver,
  which then directs them to the correct gateway;
- **tailnet node names** (`<node>.tailnet.internal`, or the short name):
  resolved on the device itself by
  [MagicDNS](/en/doc/admin-guide/understand/tailnet/#magicdns);
- **public names**: resolved by the local resolver of the visited network
  (home router, public access point), without going through the VPN.

```d2
style.fill: transparent
direction: down

pc: Mobile machine { shape: person }
split: Split-DNS routing { shape: diamond }

pivot: Pivot resolver\nHCS { shape: cylinder }
gwa: Zone A gateway
gwb: Zone B gateway
local: Local resolver\nof visited network { shape: cloud }
net: Internet { shape: cloud }

pc -> split
split -> pivot: Internal names\n(via VPN)
split -> local: Public names
pivot -> gwa: Zone A
pivot -> gwb: Zone B
local -> net
```

:::note[Why not route public names through the VPN]
Routing everything through the HCS resolver tunnels all DNS traffic over
the VPN. If the VPN path degrades (intermediate relay, blocked UDP), nothing
resolves anymore. Leaving public names to the local resolver preserves Internet
access even when the VPN link is unstable.
:::

:::tip[Laptop reconnected in a zone]
A traveling laptop reconnected via wired Ethernet in a zone no longer needs
the VPN to reach it. Its VPN client then pauses to hand off to the local
gateway (direct resolution and routing), and reactivates when it leaves.
:::

## Machines outside their zone

A machine is declared in **one** zone, but it is not always there. A laptop
goes on the road. A new gateway is installed from another zone, before being
delivered on site.

Without special provision, this machine receives an arbitrary address from the
DHCP range of the visited zone, and its name keeps pointing to its original
address, unreachable from there. Nothing allows reaching it reliably.

```d2
style.fill: transparent
direction: right

maison: Home zone (10.0) {
  gwa: Gateway
  pc: laptop\n10.0.2.4
  gwa -> pc
}

atelier: Workshop zone (10.1) {
  gwb: Gateway
  res: visiting laptop\n10.1.6.3
  gwb -> res: Reserved on its MAC
}

maison.pc -> atelier.res: Relocation
```

### A reserved address in each zone

Each zone reserves the `<prefix>.6.x` block for machines from the **other**
zones. The generator places a DHCP reservation there for every MAC address known
on the network that does not belong to the zone.

The number is assigned at the scale of the whole network&nbsp;: a machine keeps
the **same last octet** in every zone it visits.

| Machine | Declared zone | At home | Visiting `atelier` |
|---|---|---|---|
| `portable` | `maison` | `10.0.2.4` | `10.1.6.3` |
| `serveur` | `atelier` | `10.1.1.2` | (it is at home there) |

The address is therefore known **before** the machine boots, without observing
anything on the network.

{/* t:p 9bcaa563c5cc08308eaeb63d5c2d77d641f7ace70f95da33ca19f2311f041d2f */}
### A name that designates the place

The reservation comes with a DNS name in the visited zone. The simple name, for
its part, keeps its meaning.

| Name | Resolves to |
|---|---|
| `portable` | its original address, everywhere on the network |
| `portable.atelier.domain.tld` | its address in the `atelier` zone |

### A lease that no longer moves

`dnsmasq` indexes leases solely on the **MAC address**, not on the DHCP client
identifier.

The reason&nbsp;: a given device does not advertise the same identifier depending
on the system running on it. An installation image and the installed system
look like two different machines, and receive two addresses. Relying on the
MAC, the address no longer changes between installation and the first real
boot.

<Aside type="note" title="Machines without a declared MAC address">
A reservation requires a `mac` key in `etc/config.yaml`. Without it, away from
home, the machine is only reachable over the tailnet. `just install` requires it
before any formatting&nbsp;; `just host-info <host> <ip>` collects it from a
booted machine.
</Aside>

<Aside type="caution" title="The fixed address stays outside the dynamic range">
A `dhcp-host` reservation placed **inside** the `dhcp-range` range is only
honored as long as the address has not already been leased to someone else.
Otherwise the machine gets a different one, silently, at the worst moment: the
first boot after an installation. The generator now rejects a fixed address
that falls within its zone's dynamic range.
</Aside>

### What the tooling does

The installation recipes compute the address all by themselves. They first
identify the zone where the administration machine is located, based on its
**real default gateway** and not on its declared zone (an administration
laptop is precisely what moves around), then deduce the address
of the target.

This address is then **checked before being used**&nbsp;: a
reservation says where the machine *would be* if it were plugged in here, which is
correct during the installation and wrong as soon as it is back home. If nothing
responds at the reserved address, the tooling falls back to the host name
when the latter responds — port 22, or 2222 for an encrypted machine waiting
in its initrd. If nothing responds anywhere, the reserved address is kept&nbsp;:
it is the one on which the installer will appear.

<Aside type="caution" title="Management recipes out-of-zone">
Before this check, `just enter` and `just luks` targeted the reserved
address even for a host that stayed at home, joined through the VPN. `just enter`
gave up&nbsp;; `just luks` warned then exited with 0, while
Colmena — which addresses nodes by their name — deployed without noticing anything.
A `just apply` launched afterwards therefore installed a bootloader without the
initrd host key, and therefore without remote LUKS unlocking.
</Aside>

### Finding a machine again after a reboot

The calculation above gives **one** address to boot from. After the reboot that
closes an installation, it is no longer sufficient&nbsp;: the machine may
reappear elsewhere, or not really be up yet.

`just full-install` therefore probes **all** known addresses of the host, in
this order, on ports 22 **and** 2222, and continues with the first one that
answers&nbsp;:

1. the address used for the installation;
2. the fixed address of its origin zone, the one DNS publishes everywhere;
3. the transit address reserved by the local zone;
4. its name, resolved by the local gateway.

An answer on port 2222 means the host is waiting for its LUKS passphrase in
its initrd&nbsp;: `just unlock` answers it without intervention. See [Disk
encryption](/en/doc/admin-guide/operate/luks/).

### Joining a roaming host

[Colmena](https://colmena.cli.rs/) (`just apply`), `fleet-update` and
`just enter` target a host by its name, which denotes its original address. On
an administration machine, every SSH connection to a network host goes through
`dnf-locate`, which tries&nbsp;:

1. the name alone first&nbsp;: the common case costs nothing extra;
2. otherwise, in parallel, its reservation in each zone
   (`portable.workshop.domain.tld`) and its tailnet name
   (`portable.tailnet.internal`).

The first path that answers wins. `dnf-locate --print portable` displays the one
it finds.

<Aside type="caution" title="An address out of range is ignored">
A reservation must fall within its zone's subnet, a tailnet name within the
tailnet range. Without this check, a public DNS wildcard would send the
deployment to a stranger&nbsp;: the `nix` account verifies no host key.
</Aside>

The tailnet path only applies to an administration machine (`tag:admin`)&nbsp;:
the access policy opens no other tailnet client to the zones.

To enforce an address, `just configure` sets a temporary SSH redirection for a
roaming host, removed at the end of the installation or by hand&nbsp;:

```sh
just roaming             # show current redirections
just roaming-clear       # remove all of them
```
