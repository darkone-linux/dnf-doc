Monitoring collects **metrics** ([Prometheus](https://prometheus.io/))
and displays them ([Grafana](https://grafana.com/)). On top, a fully
declarative **alerting** layer notifies the administrator as soon as a node,
service, resource, or network goes awry. When enabled, it adapts automatically
to what is deployed.

{/* t:p 4fcdb11a54283225d2eb9c72a5a5aa314ad116b73a88e11234c1ec0538dca9f6 */}
## Two services, one host

A zone's collector runs **two** distinct services on the same host:

| Service | Role | Access |
|---|---|---|
| `prometheus` | Metrics, alert rules, network probes, Alertmanager | `https://prometheus.<zone>.domain.tld` (SSO-protected) |
| `monitoring` | Grafana dashboards | `https://stats.<zone>.domain.tld` (SSO-protected) |

`monitoring` **requires** `prometheus` on the same host: the generator refuses
a configuration where Grafana has no data source. You can enable `prometheus`
**alone** (metrics + alerts without Grafana).

<Aside type="note" title="One collector per zone">
Only one host runs `prometheus`/`monitoring` per zone. It monitors nodes whose
`monitoring-node` tag points to **its** zone.
</Aside>

## The alert flow

Prometheus evaluates rules **generated from the topology**; when one fires,
Alertmanager routes the notification according to its **severity**.

```d2
style.fill: transparent
direction: right

nodes: "Nodes\nnode-exporter" { shape: rectangle }
prom: "Prometheus\nrules + probes" { shape: hexagon }
am: Alertmanager { shape: diamond }
warn: "Matrix #warnings" { shape: rectangle }
inc: "Matrix #incidents" { shape: rectangle }
mail: "E-mail" { shape: rectangle }

nodes -> prom
prom -> am
am -> warn
am -> inc
am -> mail
```

Alertmanager **deduplicates**, **groups** (by alert and instance) and **inhibits**
redundant alerts: a `critical` silences the `warning` of the same incident.

:::note[A unit failing in a loop]
A unit restarted by a timer alternates between `failed` and `activating` on each
attempt. `SystemdUnitFailed` therefore stays firing for 30 minutes after the last
failure (`keep_firing_for`) → a single message, then a reminder every 4 hours,
instead of one alert and one resolution per attempt.
:::

## Severity and escalation

Escalation is driven by severity, not by time:

| Severity | Destination |
|---|---|
| `warning` | Matrix room `#alert-warnings` |
| `critical` | Matrix room `#alert-incidents` **+ e-mail** |

Mail is sent through the host's local Postfix relay; the Matrix bridge is a
dedicated bot (`@alertbot:domain.tld`) that posts to both rooms.

## Node classes

The severity of a failure depends on the **importance** of the node. A critical
server going down is an incident ; a powered-off workstation, a simple info.

| Class | Who | Effect |
|---|---|---|
| critical | `gateway`, `hcs`, `server` profiles | failures in `critical` |
| non-critical | desktops, laptops | failures in `warning` |
| disabled | | no alert on this node |

The default class follows the host profile ; it can be overridden with a **feature** :

- `alert-critical` : raises the node to critical level.
- `alert-non-critical` : lowers it.
- `alert-disabled` : removes it from alerts.

Like `monitoring-node:<zone>`, these features accept an owner zone :
`alert-critical:main` makes a node (typically the HCS) monitored by the
`main` zone.

## What is monitored

The rules are derived from what each node declares&nbsp;; nothing to list by hand.

| Family | Trigger |
|---|---|
| Unreachable node | silent `node-exporter` (`NodeDown`) |
| Active service but down | expected systemd unit not `active` (`ServiceDown`) |
| Failed unit | a `failed` systemd unit (`SystemdUnitFailed`) |
| Resources | disk, RAM, load, inodes, OOM (overridable thresholds) |
| Network | unreachable gateway, tailnet (headscale) or DNS (blackbox probes) |
| Remote site powered off | unreachable gateway of another zone (`PeerGatewayDown`) |
| Tailnet self-healing | detached Tailscale client or looping watchdog (`TailscaleUnhealthy`, `TailscaleFlapping`) |
| Tailnet audit | missing, mistagged or moved node, unexpected node, invalid policy, OIDC fallback, expiring device, blocked audit ([`Headscale*`](/en/doc/admin-guide/operate/vpn/#audit-and-alerts)) |

<Aside type="caution" title="A zone cannot report its own death">
A zone's Prometheus runs **on its gateway** and only scrapes that zone's nodes.
Gateway powered off, the observer goes down with it&nbsp;: no alert fires, and
the site becomes invisible without anything saying so.

Each zone therefore probes the **other** zones' gateways and raises
`PeerGatewayDown` (critical, after 5&nbsp;min) when one of them stops responding.
With three zones, an outage is seen by two witnesses&nbsp;: losing one observer
never masks the incident. The alert carries `reach="wan"`, so a **local**
Internet outage triggers `ZoneInternetDown` alone, without a flurry of false
alerts about peers. It also carries `host` (the targeted gateway)&nbsp;: a
silence route can thus target a single site.
</Aside>

<Aside type="note" title="One alert per partition, not per mount">
The same partition is often mounted several times&nbsp;: btrfs subvolumes
(`/`, `/nix`, `/home`, `/.swapfile`), `bind` mounts. Since metrics are emitted
**per mount**, one full disk used to raise as many alerts as there were mounts.

Disk rules therefore aggregate on the device&nbsp;: **one alert per partition**.
The message names the device then lists its mounts&nbsp;:

```
/dev/nvme0n1p3 below 15% free on 10.1.2.1:9100. Mounts: /, /.swapfile, /nix.
```
</Aside>

<Aside type="note" title="Network and read-only mounts">
Disk rules ignore **network** mounts (NFS, CIFS…)&nbsp;: they report the
server's space, which already alerts for its own disk. Likewise, a mount
intentionally set to **read-only** (share exported `ro`, optical media) does not
trigger `FilesystemReadOnly`&nbsp;: the rule targets filesystems remounted
read-only by the kernel after I/O errors.
</Aside>

## Silence during rebuilds

A `nixos-rebuild` may trigger alert flapping (services restarting). The node
being deployed drops a maintenance flag that Prometheus sees; Alertmanager
**then inhibits all alerts from that node** for the duration of the operation.
The flag is set and cleared with `dnf-maintenance on|off`, which the deployment
flow automatically wraps around the rebuild.
