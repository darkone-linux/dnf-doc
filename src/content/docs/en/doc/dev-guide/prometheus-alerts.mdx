## Pure logic vs wiring

The code is split in two to keep rule generation **testable**:

- `dnf/lib/alerts.nix` : **pure** functions that produce Prometheus rules
  from the topology. Tested in `dnf/tests/unit/lib/alerts_test.nix`.
- `dnf/modules/service/prometheus.nix` : impure **wiring** (Alertmanager, routing
  by severity, sops, Matrix bot, vhost, blackbox probes).

Any non-trivial logic goes into `alerts.nix` ; the module merely plugs it in.

## The helpers (`alerts.nix`)

Exposed via `dnfLib` (see `dnf/lib/default.nix`) :

| Helper | Role |
|---|---|
| `serviceUnits` | DNF service → systemd unit (e.g. `idm` → `kanidm.service`) |
| `nodeClass` | Node class (critical / non-critical / disabled): `alert-*` features then profile |
| `nodeAlertEligible` | Selection: a node is only monitored if it is a network/server node, carries `alert-non-critical`, or hosts a mapped service |
| `severityForClass` | Class → severity (`critical` or `warning`) |
| `hostExpectedUnits` | A host's expected units (from its enabled services) |
| `mkNodeRuleGroups` | `NodeDown`, `ServiceDown`, `SystemdUnitFailed` (+ local/WAN `reach` label) |
| `mkResourceRuleGroups` | Disk, RAM, load, inodes, OOM, read-only FS, disk prediction, clock, conntrack |
| `mkNetworkRuleGroups` | Blackbox probes (gateway, tailnet, DNS, `ZoneInternetDown`) |
| `mkHttpRuleGroups` | HTTP probes: `ServiceEndpointDown` + TLS certificate expiry |
| `mkResticRuleGroups` | Backup freshness (`ResticBackupStale`/`Critical`) |
| `mkSmartctlRuleGroups` | SMART disk health (`DiskSmartFailing`, `DiskTemperatureHigh`) |
| `mkPostfixRuleGroups` | Postfix relay (`PostfixRelayUnhealthy`, `PostfixDeferredQueueHigh`) |
| `mkSynapseRuleGroups` | Synapse (`SynapseRestarting`, `SynapseHighErrorRate`) |
| `mkMaintenanceRuleGroups` | Maintenance flag (silence during rebuild) |
| `mkTailscaleRuleGroups` | Tailnet self-repair (`TailscaleUnhealthy`, `TailscaleFlapping`) |
| `mkHeadscaleRuleGroups` | Tailnet audit on the HCS (`HeadscaleNodeDrift`, `HeadscaleUnexpectedNode`, `HeadscalePolicyInvalid`, `HeadscaleOidcFallback`, `HeadscaleNodeExpiring`, `HeadscaleAuditStale`) |
| `mergeRuleGroups` | Merges fragments into a **single** document |
| `mkAlertRuleGroups` | Shortcut: nodes + resources + restic + SMART + tailscale + headscale |
| `mkSilenceRoutes` | Alertmanager routes to the `null` receiver (known, accepted alerts) |

### The `host` label, or why alerts have names

Every scrape target carries a `host` label set to the hostname, placed by
`mkHostTargets` in `prometheus.nix` (one `static_config` per host rather than a
single target list). Two effects:

- the Matrix bot displays `DiskSpaceLow at srv-backup` instead of the raw
  `<ip>:<port>` instance;
- a silence route can target a single machine.

Placing it at scrape time propagates it for free to all alerts from these jobs,
including generic resource rules, which know nothing about topology at evaluation.

Blackbox probes have no `host` (the target is an IP). `PeerGatewayDown` therefore
sets it in the rule, with the name of the targeted gateway. Without it, rules from
a zone would only differ by their `expr` → `promtool` flags them as duplicates.

:::caution[Aggregations erase labels]
A `by (...)` clause drops any label not grouped on. `ResticBackupStale`
(`max by (instance, backup, host)`), `SynapseHighErrorRate`
(`sum by (instance, host)`) and FS rules (`byDevice`) therefore cite `host`
explicitly. Omitting it in a new aggregated rule causes the notification to fall
back to the raw instance.
:::

:::caution[An exported job label is renamed at scrape]
The scrape job sets its own `job` label. An exported metric's label (including
textfile collectors) therefore becomes `exported_job`. The restic metric carries
the job name in `backup`&nbsp;: grouping on `job` would merge all jobs on a host,
and a failed job would stay hidden as long as another one succeeds.
:::

:::note[A job that never succeeded has no series]
`dnf_restic_last_success_timestamp` only exists after a first success. The restic
module therefore also exports `dnf_restic_declared_timestamp`, the first
declaration date of each job. Rules take the success, `or` the declaration as a
fallback&nbsp;: two `by (instance, backup, host)` aggregates, the left side wins.
Without this list, a node keeps the old behavior.
:::

:::note[FS rules: one alert per partition]
`node_filesystem_*` is emitted **per mount**. A partition mounted multiple times
(btrfs subvolumes, `bind` mounts) therefore triggered each FS rule as many times
as it had mounts, for a single full disk.

`mkResourceRuleGroups` aggregates on `byDevice`
(`instance, job, host, device, fstype`)&nbsp;: `min` for space and inodes, `max`
for `FilesystemReadOnly`. Both members of `DiskWillFillSoon`'s `and` are
aggregated — a raw member still carries `mountpoint` and no longer matches
anything on the other side.

`mountpoint` disappears with aggregation. PromQL cannot concatenate label
values&nbsp;: the list of mounts is therefore resolved by the `query` function of
the Go template engine that Prometheus applies to annotations (`deviceMounts`).
Cost: one instant query per active alert and per evaluation, none as long as the
rule stays silent.
:::

:::note[The bot does not display `summary`]
The Matrix bot renders the title then the `description` annotation, and only falls
back to `summary` if `description` is absent&nbsp;: all DNF rules define one, so
`summary` never reaches it. Information to include in the notification must go in
`description`.
:::

### Monitored node selection

Monitoring is *opt-out* for infrastructure, *opt-in* for the rest.
`nodeAlertEligible` retains a node only if it is of class `critical`
(`gateway`/`hcs`/`server` profile or `alert-critical` feature), if it carries
`alert-non-critical` explicitly, or if it hosts at least one service mapped
in `serviceUnits`. A bare laptop/desktop therefore generates no node alerts.

### Internet outage vs remote host down

A zone's Prometheus connects to hosts in other zones (e.g. the public HCS)
only over the WAN. When internet goes down, these targets become unreachable
and would trigger a false "*host* down" alert. To prevent this:

- each node rule carries a `reach` label (`local` same zone, `wan` cross-zone);
- an ICMP blackbox probe to external IPs feeds `ZoneInternetDown`
  (fired only if **all** external targets fail);
- an Alertmanager inhibition rule (`equal: [zone]`) silences `reach="wan"` alerts
  of the zone while `ZoneInternetDown` is active — the real cause is notified,
  not the symptoms.

## The trap : a single rule document

:::caution[Never forget]
NixOS **concatenates** all entries of `services.prometheus.rules` (a list
of strings) into **a single file**. Multiple `groups:` documents without
`---` separator → **only the first one is read**. Stacking a second entry
**silently** breaks following groups.
:::

So we merge **everything** via `mergeRuleGroups`, then emit **only one** entry :

```nix
# dnf/modules/service/prometheus.nix
services.prometheus.rules = [
  (builtins.toJSON (dnfLib.mergeRuleGroups (
    [ (dnfLib.mkAlertRuleGroups { inherit nodes; /* … */ }) ]
    ++ lib.optional alerting.silenceOnRebuild (dnfLib.mkMaintenanceRuleGroups { /* … */ })
    ++ lib.optional alerting.network.enable (dnfLib.mkNetworkRuleGroups { /* … */ })
  )))
];
```

## Where to add what

| I want to… | I edit… |
|---|---|
| monitor a new service | `serviceUnits` in `alerts.nix` |
| add a new rule family | a `mkXRuleGroups` + add it to the module's `mergeRuleGroups` |
| wire a metrics exporter | exporter in its module (gated `monitoring-node`, bind `preferredIp`) + scrape job + `mkXRuleGroups` gated in `prometheus.nix` |
| change a default threshold | `defaultThresholds` in `alerts.nix` |
| stop alerting on an intentionally `ro`-mounted FS | `readOnlyByDesignFstypes` (thresholds) in `alerts.nix` |
| monitor (or not) the space of a network mount | `remoteFstypes` (thresholds) in `alerts.nix` |
| change a node's class | feature `alert-*[:zone]` (no code) |
| force/exclude a node from monitoring | feature `alert-non-critical` / `alert-disabled` |
| monitor a URL + its TLS certificate | `alerting.network.httpProbeUrls` in config |
| adjust internet failure detection | `alerting.network.internetProbeTargets` |
| silence a known and accepted alert | `alerting.silences` in a consumer module (no code) |
| silence a broken systemd unit fleet-wide | `ignoredUnits` in `dnf/config/alerts.nix` |
| add a new destination | the `alertmanager` block in `prometheus.nix` (receiver + route) |

:::note[Exclude rather than silence]
A permanent and intentional condition should not be silenced&nbsp;:
`alerting.silences` cuts the notification but lets the alert fire, turning UIs
red, forever. It must leave the rule's **selector**. Two threshold lists do
this, in `mkResourceRuleGroups`&nbsp;:

- `remoteFstypes` — removed from **all** FS rules. A client mount reports the
  **server**'s space&nbsp;: monitoring it turns a full export into the same
  alert on every machine that mounts it, while the server already alerts on its
  own, with the real partition.
- `readOnlyByDesignFstypes` — removed from `FilesystemReadOnly` only (optical
  media). The rule therefore only monitors mounts expected to be writable.
:::

:::tip[DNF convention]
A helper in `lib/` equals a test. Every function added to `alerts.nix` must be
paired with a case in `dnf/tests/unit/lib/alerts_test.nix` (`nix-unit`).
:::

:::caution[Alertmanager route order]
`continue` defaults to `false`&nbsp;: the first matching child route wins. Routes
from `mkSilenceRoutes` must therefore be inserted **before** the severity
routes, otherwise they are never reached and the alert notifies anyway. The
`null` receiver is shared with the maintenance route, hence its
`silenceOnRebuild || silences != []` guard&nbsp;: referencing a missing receiver
prevents Alertmanager from starting.
:::

:::caution[Textfile metric: permissions]
A `.prom` file from the textfile collector must be readable by `node-exporter`
(non-root user). `mktemp` creates with `0600`&nbsp;: run a `chmod 0644` **before**
the atomic `mv`, otherwise the file is ignored (`node_textfile_scrape_error 1`)
and the metric is never exposed, leaving the alert blind.
:::
