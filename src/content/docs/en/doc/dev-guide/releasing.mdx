## What each repository versions

| Repository | Source of truth | Rule |
| --- | --- | --- |
| `darkone-nixos-framework` | `VERSION` | Train reference |
| `dnf-generator` | `Cargo.toml` | Own version, pinned by the framework |
| `dnf-fleet-update` | `package.json` | Own version, packaged by the framework |
| `dnf-doc` | `package.json` | Framework's `MAJEUR.MINEUR`, own patch |
| `dnf-boilerplate`, `dnf-example` | latest tag | Mirror of the framework |

All six repositories keep a generated `CHANGELOG.md`, templates included.

The private consumer project is never tagged: it stays in
co-development and serves as a permanent integration testbed.

## The commit vocabulary

The changelog is generated from commit messages. A type not in the list
silently disappears from the release notes, so the format is checked:
a single line `<type>(<scope>): <subject>`, 80 characters max, type from the
following list.

```
feat fix perf refactor docs test build ci chore security revert
```

The same script, `scripts/check-commit-msg.sh`, checks every *push* to
`main` and every *pull request* in continuous integration, and every commit
locally via the `commit-msg` hook, installed once per clone:

```sh
ln -s ../../scripts/check-commit-msg.sh .git/hooks/commit-msg
```

A scope is never a type: `feat(matrix): …`, never `matrix(admin): …`.

| Type | Changelog section |
| --- | --- |
| `feat` | Added |
| `fix` | Fixed |
| `security` | Security |
| `perf`, `refactor`, `revert` | Changed |
| `docs` | Documentation |
| `chore(deps)` | Dependencies |
| subject in `drop` or `remove` | Removed |
| other `chore`, `ci`, `test`, `build` | not published |

`chore(deps)` is the train's pinning commit: the framework entry names the
generator and `fleet-update` it bundles this way.

<Aside type="caution" title="Marking a breaking change">
A breaking change carries a `!` after the scope, and its subject names the
broken surface. No `BREAKING CHANGE:` footer: the message stays on one line,
the migration is described in the documentation. It's the `!` that triggers
the **⚠ Breaking** section and the minor version bump.

```
feat(idm)!: replace network.idm.replicas with zones.<zone>.idm
```
</Aside>

## The recipes

| Recipe | Effect |
| --- | --- |
| `just versions` | Version, latest tag and branch of each repository |
| `just changelog` | Preview of the next entry, writes nothing |
| `just bump [level]` | Version, changelog, commit and tag of **one** repository |
| `just release [level]` | The full train across the six repositories (+ the root) |
| `just version` | Version, revision and pinned generator of the framework |

The level defaults to `auto`: [git-cliff](https://git-cliff.org/) deduces
the next number from the commits. `patch`, `minor`, `major` or a literal
`X.Y.Z` force the decision. Only unpublished commits (a `chore(deps)`, for
example) give a patch.

`just bump` never pushes: it prints the push command. It refuses to publish
if `HEAD` already carries the latest `v*` tag. Three flags pass to the
script:

- `--dry-run`: shows the entry then restores the file, committing nothing;
- `--yes`: proceeds without confirmation or `$EDITOR`;
- `--next`: prints the version the release would take, then stops.

<Aside type="tip" title="Run from the development environment">
`bump` and `changelog` call [git-cliff](https://git-cliff.org/), absent from
the default `PATH`. Enter the environment with `just develop` before
publishing.
</Aside>

## Writing by hand in an entry

The generated block only contains commit messages. A preamble, a companion
versions table or a migration note are written under `## [Unreleased]` in the
`CHANGELOG.md`: on publish, the script empties this section and folds its
content at the head of the entry, before the generated sections. The train
doesn't stop for editing: these notes are written **before** launching it.

<Aside type="caution" title="Leave nothing after the notes">
The section runs until the next `##` title. If the footer reference links are
the last content of the file, they are swallowed into the published entry.
Remove them, the script regenerates them.
</Aside>

<Aside type="note" title="The very first release">
With no `v*` tag, `auto` has nothing to deduce: the script takes the
declared version as-is, and git-cliff goes back to the first commit of the
repository. The entry then covers the whole history. A template, with no
version file, requires an explicit `X.Y.Z` (the train passes the framework's).
</Aside>

## The release train

`just release` runs at the root of the co-development workspace, which must contain all six repositories. Each repository is processed in order of its dependencies, and only if it has changed since its last tag.

<Steps>

1. **Pre-checks**&nbsp;: verify required tools are present (`git-cliff`, `jq`,
   `nix-update`), all repositories are clean, on `main`, and up to date with `origin`. No long-running tasks should be active before starting.

2. **Plan**&nbsp;: determine the current and next version for each repository, preview changelog entries, then request **a single** confirmation. If declined, nothing is written.
   From this point onward, everything runs automatically.

3. **Global gate**&nbsp;: `just check` (code and unit tests).

4. **Generator**, if it has changed&nbsp;: run `just gen-test`, release, and push. Since it owns the schema `etc/config.yaml`, it runs before anything that depends on it.
   Its tag is then pinned in `dnf/flake.nix` (commit `chore(deps)`),
   so the contract between the framework and the generator is visible in a diff.
   The pinned generator then regenerates `dnf/config/config.schema.json`,
   the schema read by projects via their `dnf/` link (commit
   `chore(schema)` if it changed).

5. **fleet-update**, if it has changed&nbsp;: run `ci` and `audit` gates using
   its `nix develop` environment, release, and push. Its tag is then pinned in
   `dnf/pkgs/fleet-update` via `just pkg-update`, and the package is built (commit `chore(deps)`).

6. **Framework**&nbsp;: `just simulate all` runs **after** all pinning,
   so it uses the dependencies that were actually released. These simulations do not run in CI&nbsp;: a failing simulation stops the train here. Next, update `VERSION`, pin the project template
   (`templates/project/flake.nix`), update `CHANGELOG.md`, commit, tag, and push.

7. **Documentation**&nbsp;: `just codegen` regenerates the reference, then runs translation and normalization. If there is anything to publish, the site is built (before tagging, so any broken link blocks the release), the version is aligned to the framework's `MAJOR.MINOR` line, and the site is deployed.

8. **Boilerplate and example**&nbsp;: the boilerplate is first copied from
   `templates/project/` at the framework's tag (`CHANGELOG.md` and `flake.lock`
   are preserved), with a "published copy" banner placed under the title of its README files.
   As a result, it is never edited manually. For both the boilerplate and the example, the framework's tag is written to their `flake.nix`, the `flake.lock` is **committed**
   (as this ensures a reproducible clone), then changelog and tag are created to match the framework's tag.
   Each host in the example is evaluated down to `system.build.toplevel`
   against the new framework, with hardware and secrets replaced by stubs (`dnf/just/scripts/eval-template-hosts.nix`)&nbsp;: a template has neither. The boilerplate, shipped without `var/generated/`, has nothing to evaluate before running `just generate`.

9. **Root**&nbsp;: run `just update-dnf`, commit only the `flake.lock`, then push the current branch (with no tag), last of all&nbsp;: its lockfile points to the releases that were just published. The root repository is never tagged.

</Steps>

Only the framework follows the `level` passed to the release command. Generator and
`fleet-update` always use `auto`, documentation follows the framework's line, and templates follow its version number.

Each repository is pushed with **its own** tag only (`git push --atomic origin main
refs/tags/vX.Y.Z`), never with `--tags`&nbsp;: any local working tags remain local.

<Aside type="tip" title="Restarting the train">
The release train is idempotent. If nothing has changed, it stops at the plan with the message:
"Nothing to release". After a failure, it resumes where it left off&nbsp;:
repositories already tagged are skipped, and any committed pinning changes are preserved.
Only a failed site deployment must be restarted manually&nbsp;:
`just --justfile doc/Justfile --working-directory doc deploy "Release vX.Y.Z"`.
</Aside>

<Aside type="caution" title="A template must never precede the framework">
A template carries the framework's version number. If a template changes but the framework does not, the train will report it and leave it as is&nbsp;: it will be released with the next framework release.
</Aside>

## Continuous integration safeguards

On a `v*` tag, `release.yml` refuses to publish if&nbsp;:

- the `VERSION` file does not match the tag;
- `CHANGELOG.md` does not contain a section for that version;
- the lockfile points to a `dnf-generator` checked out from a branch rather than from a published release.

The three checks in `ci.yml` (unit tests, evaluation, and lint) are rerun via `workflow_call`, and the corresponding changelog section becomes the GitHub release notes.

### Testing the installer

The `installer-test.yml` *workflow* runs `darkone new` end-to-end in a QEMU VM (KVM on the runner, real network)&nbsp;: the generic ISO boots, the assistant is driven via its serial console (pexpect), then the installed system reboots and is controlled over SSH. Two scenarios run in parallel, each taking about 25&nbsp;minutes&nbsp;:

- **scripted**&nbsp;: response file, `--non-interactive`, unencrypted disk, backup passphrase stored in a file&nbsp;;
- **interactive**&nbsp;: each question answered on the console, encrypted disk, USB backup key unplugged then replugged (QMP), first boot unlocked by the initrd sshd.

Checks&nbsp;: automatic launch on tty1, system `running` with no failed units, clean `/etc/nixos`, homepage installed, second backup run with `just backup-admin` from the installed system (the first kept under its date), backup opened from the host. The serial log is attached to the *run*.

Three triggers&nbsp;:

- **tag**&nbsp;: called by `release.yml`, any failure prevents the ISO from being included in the *release*&nbsp;;
- **every Monday**, on `main`&nbsp;: a regression from nixpkgs unstable is caught before the next tag&nbsp;;
- **manual**&nbsp;: `gh workflow run installer-test.yml --ref <branch>`, before a release or after an ISO change.

Same test locally, on the ISO from the current tree or another&nbsp;:

```sh
just test-installer                 # both scenarios
just test-installer interactive /chemin/de/l.iso
```

Disks and logs&nbsp;: `~/.cache/dnf-installer-test/<scénario>/`, about 25&nbsp;GB per scenario. Code&nbsp;: `dnf/tests/installer/`.

<Aside type="caution" title="Tag pushed, release missing">
Never move or recreate the tag&nbsp;: FlakeHub has already published it.

- Transient failure (runner stopped, network issue)&nbsp;: `gh run rerun <id> --failed` re-runs failed *jobs* using the *workflows* from the tag.
- Defect in the tagged tree&nbsp;: the version number is lost. Fix on `main`, then `just release patch`.
</Aside>

## Shared configuration

A single [git-cliff](https://git-cliff.org/) for the six repositories, in
`dnf/just/scripts/cliff.toml`. The script `dnf/just/scripts/bump.sh` discovers
the repository's version source (`VERSION`, `Cargo.toml`, `package.json`, or
failing that the latest tag), assembles the file around the generated block
and preserves the hand-written history.
