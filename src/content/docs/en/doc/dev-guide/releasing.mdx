## What each repository versions

| Repository | Source of truth | Rule |
| --- | --- | --- |
| `darkone-nixos-framework` | `VERSION` | Train reference |
| `dnf-generator` | `Cargo.toml` | Own version, pinned by the framework |
| `dnf-fleet-update` | `package.json` | Own version, packaged by the framework |
| `dnf-doc` | `package.json` | Framework's `MAJEUR.MINEUR`, own patch |
| `dnf-boilerplate`, `dnf-example` | latest tag | Mirror of the framework |

All six repositories keep a generated `CHANGELOG.md`, templates included.

The private consumer project is never tagged: it stays in
co-development and serves as a permanent integration testbed.

## The commit vocabulary

The changelog is generated from commit messages. A type not in the list
silently disappears from the release notes, so the format is checked:
a single line `<type>(<scope>): <subject>`, 80 characters max, type from the
following list.

```
feat fix perf refactor docs test build ci chore security revert
```

The same script, `scripts/check-commit-msg.sh`, checks every *push* to
`main` and every *pull request* in continuous integration, and every commit
locally via the `commit-msg` hook, installed once per clone:

```sh
ln -s ../../scripts/check-commit-msg.sh .git/hooks/commit-msg
```

A scope is never a type: `feat(matrix): …`, never `matrix(admin): …`.

| Type | Changelog section |
| --- | --- |
| `feat` | Added |
| `fix` | Fixed |
| `security` | Security |
| `perf`, `refactor`, `revert` | Changed |
| `docs` | Documentation |
| `chore(deps)` | Dependencies |
| subject in `drop` or `remove` | Removed |
| other `chore`, `ci`, `test`, `build` | not published |

`chore(deps)` is the train's pinning commit: the framework entry names the
generator and `fleet-update` it bundles this way.

<Aside type="caution" title="Marking a breaking change">
A breaking change carries a `!` after the scope, and its subject names the
broken surface. No `BREAKING CHANGE:` footer: the message stays on one line,
the migration is described in the documentation. It's the `!` that triggers
the **⚠ Breaking** section and the minor version bump.

```
feat(idm)!: replace network.idm.replicas with zones.<zone>.idm
```
</Aside>

## The recipes

| Recipe | Effect |
| --- | --- |
| `just versions` | Version, latest tag and branch of each repository |
| `just changelog` | Preview of the next entry, writes nothing |
| `just bump [level]` | Version, changelog, commit and tag of **one** repository |
| `just release [level]` | The full train on the six repositories (+ the root) |
| `just version` | Version, revision and pinned generator of the framework |

The level is `auto` by default&nbsp;: [git-cliff](https://git-cliff.org/) infers
the next number from the commits. `patch`, `minor`, `major` or a literal `X.Y.Z`
force the decision. Unpublished commits alone (a `chore(deps)`, for
example) yield a patch.

`just bump` never pushes: it prints the push command. It refuses to
publish if `HEAD` already carries the latest `v*` tag. Any stop before the release
commit (refusal, interruption, hook) restores the working tree to its state&nbsp;: you
can restart immediately. Three flags are passed to the script&nbsp;:

- `--dry-run` : shows the entry then restores the file, without committing anything ;
- `--yes` : proceeds without confirmation or opening `$EDITOR`, required
  without a terminal ;
- `--next` : shows the version the release would take, then stops.

<Aside type="tip" title="Run from the development environment">
`bump` and `changelog` call [git-cliff](https://git-cliff.org/), which is absent from
the default `PATH`. Enter the environment with `just develop` before
publishing.
</Aside>

## Writing by hand in an entry

The generated block only contains commit messages. A preamble, a companion
versions table or a migration note are written under `## [Unreleased]` in the
`CHANGELOG.md`: on publish, the script empties this section and folds its
content at the head of the entry, before the generated sections. The train
doesn't stop for editing: these notes are written **before** launching it.

<Aside type="caution" title="Leave nothing after the notes">
The section runs until the next `##` title. If the footer reference links are
the last content of the file, they are swallowed into the published entry.
Remove them, the script regenerates them.
</Aside>

<Aside type="note" title="The very first release">
With no `v*` tag, `auto` has nothing to deduce: the script takes the
declared version as-is, and git-cliff goes back to the first commit of the
repository. The entry then covers the whole history. A template, with no
version file, requires an explicit `X.Y.Z` (the train passes the framework's).
</Aside>

## The release train

`just release` runs at the root of the co-development workspace, which must
contain the six repositories. Each repository goes in the order of its
dependencies, and only if it has moved since its last tag.

<Steps>

1. **Pre-flight checks**&nbsp;: required tools present (`git-cliff`, `jq`,
   `nix-update`), repositories clean, on `main`, up to date with `origin`.
   Nothing long-running starts before this.

2. **Plan**&nbsp;: current and next version of each repository, preview of
   the changelog entries, then **a single** confirmation. Refusing writes
   nothing. `YES=1 just release` skips it (non-interactive run). After that,
   everything is automatic.

3. **Global gate**&nbsp;: `just check` (code and unit tests).

4. **Generator**, if it has moved&nbsp;: `just gen-test`, release and push. It
   owns the `etc/config.yaml` schema, so it goes before whatever depends on
   it. Its tag is then pinned in `dnf/flake.nix` (commit `chore(deps)`), so
   that the contract between framework and generator reads in a diff. The
   pinned generator finally regenerates `dnf/config/config.schema.json`, the
   schema that projects read through their `dnf/` link (commit
   `chore(schema)` if it changes).

5. **fleet-update**, if it has moved&nbsp;: `ci` and `audit` gates with the
   tooling of its `nix develop`, release and push. Its tag is then pinned in
   `dnf/pkgs/fleet-update` by `just pkg-update`, and the package is built
   (commit `chore(deps)`).

6. **Framework**&nbsp;: `just simulate all` runs **after** the pinning, so on
   the dependencies actually shipped. These scenarios do not run in continuous
   integration&nbsp;: a red scenario stops the train here. Then `VERSION`, the
   project template pin (`templates/project/flake.nix`), `CHANGELOG.md`,
   commit, tag and push.

7. **Documentation**&nbsp;: `just codegen` regenerates the reference, then
   translation and normalization. If there is anything to publish, the site is
   built (before the tag, so that a broken link blocks), the version aligns on
   the framework's `MAJOR.MINOR` line, then the site is deployed.

8. **Boilerplate and example**&nbsp;: the boilerplate is first copied from
   `templates/project/` at the framework tag (`CHANGELOG.md` and `flake.lock`
   kept), with a "published copy" banner under the title of its READMEs. It is
   therefore never edited by hand. Then, for both, the framework tag is written
   into their `flake.nix`, the `flake.lock` is **committed** (it is what makes a
   clone reproducible), then changelog and a tag identical to the framework's.
   Each host of the example is evaluated up to `system.build.toplevel`
   against the new framework, with hardware and secrets replaced by stubs
   (`dnf/just/scripts/eval-template-hosts.nix`)&nbsp;: a template has neither.
   The boilerplate, shipped without `var/generated/`, has nothing to evaluate
   before `just generate`.

9. **Root**&nbsp;: `just update-dnf`, commit of the single `flake.lock`, then
   push of the current branch (without tag), last of all&nbsp;: its lock points
   to the releases published just before. The root is never tagged.

</Steps>

Only the framework follows the `level` passed to the recipe. Generator and
`fleet-update` stay on `auto`, the documentation follows the framework line,
the templates their number.

Each repository is pushed with **its** tag alone (`git push --atomic origin
main refs/tags/vX.Y.Z`), never with `--tags`&nbsp;: local work tags stay local.

<Aside type="tip" title="Restarting the train">
The train is idempotent. With nothing new, it stops at the plan&nbsp;:
"Nothing to release". After a failure, it resumes where it stopped&nbsp;: the
already-tagged repositories are skipped, the committed pins remain in place.
Only a failed site deployment is restarted by hand&nbsp;:
`just --justfile doc/Justfile --working-directory doc deploy "Release vX.Y.Z"`.
</Aside>

<Aside type="caution" title="A template never precedes the framework">
A template carries the framework number. If it has moved without the framework
moving, the train reports it and leaves it&nbsp;: it will go with the next
framework release.
</Aside>

## Continuous integration safeguards

On a `v*` tag, `release.yml` refuses to publish if&nbsp;:

- the `VERSION` file does not match the tag;
- `CHANGELOG.md` does not contain a section for that version;
- the lockfile points to a `dnf-generator` checked out from a branch rather than from a published release.

The three checks in `ci.yml` (unit tests, evaluation, and lint) are rerun via `workflow_call`, and the corresponding changelog section becomes the GitHub release notes.

### Installer test

The `installer-test.yml` *workflow* runs `darkone new` end to end in a
QEMU VM (the runner's KVM, real network)&nbsp;: the `scripted`,
`interactive` and `resume` scenarios of the [installer test](/en/doc/dev-guide/installer-test/),
in parallel, about 25&nbsp;minutes each. The serial log is attached to the *run*.

Three triggers&nbsp;:

- **tag**&nbsp;: called by `release.yml`, a failure holds the ISO back from the
  *release*&nbsp;;
- **every Monday**, on `main`&nbsp;: a break coming from nixpkgs unstable shows up
  before the next tag&nbsp;;
- **manually**&nbsp;: `gh workflow run installer-test.yml --ref <branche>`, before
  a release or after a change to the ISO.

The same test runs locally, `just try` opens the ISO in a
window&nbsp;: see [Testing the installer](/en/doc/dev-guide/installer-test/#run-locally).

<Aside type="caution" title="Tag pushed, no release">
Never move or recreate the tag&nbsp;: FlakeHub has already published it.

- Transient failure (runner cut off, network)&nbsp;: `gh run rerun <id> --failed`
  replays the failed *jobs* with the tag's *workflows*.
- Defect in the tagged tree&nbsp;: the number is lost. Fix on `main`,
  then `just release patch`.
</Aside>

## Shared configuration

A single [git-cliff](https://git-cliff.org/) for the six repositories, in
`dnf/just/scripts/cliff.toml`. The script `dnf/just/scripts/bump.sh` discovers
the repository's version source (`VERSION`, `Cargo.toml`, `package.json`, or
failing that the latest tag), assembles the file around the generated block
and preserves the hand-written history.
