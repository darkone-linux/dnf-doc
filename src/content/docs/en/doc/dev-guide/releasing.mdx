## What each repository versions

| Repository | Source of truth | Rule |
| --- | --- | --- |
| `darkone-nixos-framework` | `VERSION` | Train reference |
| `dnf-generator` | `Cargo.toml` | Own version, pinned by the framework |
| `dnf-fleet-update` | `package.json` | Own version, packaged by the framework |
| `dnf-doc` | `package.json` | Framework `MAJOR.MINOR`, own patch |
| `dnf-boilerplate`, `dnf-example` | tag only | Framework mirror |

The private consumer project is never tagged: it stays in
co-development and serves as a permanent integration bench.

## Commit vocabulary

The changelog is generated from commit messages. A type not in the list is silently dropped from the release notes, so the format is enforced: a single line `<type>(<scope>): <subject>`, 80 characters max, type from the following list.

```
feat fix perf refactor docs test build ci chore security revert```

The same script, `scripts/check-commit-msg.sh`, checks every push to `main` and every pull request in continuous integration, and every local commit via the `commit-msg` hook, which needs to be installed once per clone:

```sh
ln -s ../../scripts/check-commit-msg.sh .git/hooks/commit-msg
```

A scope is never a type: `feat(matrix): …`, never `matrix(admin): …`.

| Type | Changelog section |
| --- | --- |
| `feat` | Added |
| `fix` | Fixed |
| `security` | Security |
| `perf`, `refactor`, `revert` | Changed |
| `docs` | Documentation |
| subject starts with `drop` or `remove` | Removed |
| `chore`, `ci`, `test`, `build` | not published |

<Aside type="caution" title="Marking a breaking change">
A breaking change carries a `!` after the scope, and its subject names the broken surface.
No `BREAKING CHANGE:` footer: the message stays on one line, the migration is described in the documentation. The `!` is what triggers the **⚠ Breaking** section and the minor version bump.

```
feat(idm)!: replace network.idm.replicas with zones.<zone>.idm
```
</Aside>

## The recipes

| Recipe | Effect |
| --- | --- |
| `just versions` | Version, last tag and branch of each repository |
| `just changelog` | Preview of the next entry, writes nothing |
| `just bump [niveau]` | Version, changelog, commit and tag of **one** repository |
| `just release [level]` | The full train across the six repositories |
| `just version` | Version, revision and pinned generator of the framework |

The level defaults to `auto`: [git-cliff](https://git-cliff.org/) deduces the
next number from the commits. `patch`, `minor`, `major` or a literal `X.Y.Z`
forces the decision.

`just bump` never pushes: it prints the push command. Two flags are passed to
the script: `--dry-run` shows the entry then restores the file without
committing anything, `--yes` goes on without confirmation.

<Aside type="tip" title="Run from the development environment">
`bump` and `changelog` call [git-cliff](https://git-cliff.org/), missing from
the default `PATH`. Enter the environment with `just develop` before
publishing.
</Aside>

## Writing by hand into an entry

The generated block only contains commit messages. A preamble, a table of
companion versions or a migration note is written under
`## [Unreleased]` in the `CHANGELOG.md`&nbsp;: at publication, the script empties
this section and folds its content at the top of the entry, before the
generated headings.

<Aside type="caution" title="Leave nothing after the notes">
The section runs until the next `##` heading. If the reference links at the
bottom of the page are the last content of the file, they get swallowed into the
published entry. Remove them, the script regenerates them.
</Aside>

<Aside type="note" title="The very first release">
Without a `v*` tag, `auto` has nothing to infer&nbsp;: the script reuses the
declared version as is, and git-cliff goes back up to the first commit of the
repository. The entry then covers the whole history, and must be trimmed before
pushing.
</Aside>

## The release train

`just release` runs at the root of the co-development workspace, which must
contain the six repositories.

<Steps>

1. **Quality gate**: `just check`, `just gen-test` and
   `just simulate all`. Virtual machine tests do not run in
   continuous integration, so a red scenario must stop the publication
   here. `dnf-fleet-update` also passes its `ci` and `audit` gates,
   with the tooling of its `nix develop`.

2. **Generator**, if it has moved since its last tag. It owns the
   `etc/config.yaml` schema, so it goes first, before anything that depends on it.

3. **Pinning** of the generator tag in `dnf/flake.nix`, so the contract
   between framework and generator can be read in a diff, not only in the
   lock.

4. **fleet-update**, if it has moved since its last tag. The framework
   packages it, so it goes before it.

5. **Pinning** of the `fleet-update` tag in `dnf/pkgs/fleet-update`,
   via `just pkg-update fleet-update <version>`, then packaging the build. At the
   first release, pinning to a `main` commit becomes a pinning
   to the tag.

6. **Framework**: `VERSION`, `CHANGELOG.md`, commit and tag, then immediate
   push. Any edit of the entry after this step would force
   a tag already consumed by `release.yml`, so it happens before.

7. **Documentation**: `just codegen` regenerates the reference from the
   framework, then the version aligns on the `MAJOR.MINOR` line, then the
   site is built and deployed.

8. **Boilerplate and example**: the framework tag is written into their
   `flake.nix`, `nix flake check` validates, and the `flake.lock` is **committed**.
   That is what makes a clone reproducible.

</Steps>

## Continuous integration safeguards

On a `v*` tag, `release.yml` refuses to publish if:

- the `VERSION` file does not match the tag;
- `CHANGELOG.md` does not contain a section for this version;
- the lock points to a `dnf-generator` taken from a branch rather than from a
  published release.

The three `ci.yml` checks (unit tests, evaluation, lint) are replayed via
`workflow_call`, then the changelog section becomes the notes of the GitHub
*release*.

## Shared configuration

A single [git-cliff](https://git-cliff.org/) for the four repositories that
produce a changelog, in `dnf/just/scripts/cliff.toml`. The script
`dnf/just/scripts/bump.sh` discovers the repository's version source
(`VERSION`, `Cargo.toml` or `package.json`), assembles the file around the
generated block and preserves the hand-written history.
