## What each repository versions

| Repository | Source of truth | Rule |
| --- | --- | --- |
| `darkone-nixos-framework` | `VERSION` | Train reference |
| `dnf-generator` | `Cargo.toml` | Its own version, pinned by the framework |
| `dnf-doc` | `package.json` | `MAJOR.MINOR` of the framework, its own patch |
| `dnf-boilerplate`, `dnf-example` | tag only | Mirror of the framework |

The consumer private project is never tagged: it stays in co-development and
serves as a permanent integration bench.

## The commit vocabulary

The changelog is generated from commit messages. Any type outside the list
silently disappears from the release notes, so the list is checked by
continuous integration on every *pull request*.

```
feat fix perf refactor docs test build ci chore security revert
```

A scope is never a type: `feat(matrix): …`, never `matrix(admin): …`.

| Type | Changelog section |
| --- | --- |
| `feat` | Added |
| `fix` | Fixed |
| `security` | Security |
| `perf`, `refactor`, `revert` | Changed |
| `docs` | Documentation |
| subject in `drop` or `remove` | Removed |
| `chore`, `ci`, `test`, `build` | not published |

<Aside type="caution" title="Marking a breaking change">
A breaking change carries a `!` after the scope **and** a `BREAKING CHANGE:`
footer that names the broken surface and the migration. This is what triggers
the **⚠ Breaking** section and the bump of the minor number.

```
feat(idm)!: drop the legacy replication scheme

BREAKING CHANGE: `network.idm.replicas` replaced by `zones.<zone>.idm`.
```
</Aside>

## The recipes

| Recipe | Effect |
| --- | --- |
| `just versions` | Version, latest tag and branch of each repository |
| `just changelog` | Preview of the next entry, writes nothing |
| `just bump [level]` | Version, changelog, commit and tag of **one** repository |
| `just release [level]` | The full train on the five repositories |
| `just version` | Pinned version, revision and generator of the framework |

The level defaults to `auto`&nbsp;: [git-cliff](https://git-cliff.org/) infers
the next number from the commits. `patch`, `minor`, `major` or a literal `X.Y.Z`
forces the decision.

`just bump` never pushes&nbsp;: it displays the push command. Two flags are
passed to the script&nbsp;: `--dry-run` shows the entry then restores the file
without committing anything, `--yes` chains without confirmation.

<Aside type="tip" title="Run from the development environment">
`bump` and `changelog` call [git-cliff](https://git-cliff.org/), absent from the
default `PATH`. Enter the environment with `just develop` before publishing.
</Aside>

## Writing by hand into an entry

The generated block only contains commit messages. A preamble, a table of
companion versions or a migration note is written under
`## [Unreleased]` in the `CHANGELOG.md`&nbsp;: at publication, the script empties
this section and folds its content at the top of the entry, before the
generated headings.

<Aside type="caution" title="Leave nothing after the notes">
The section runs until the next `##` heading. If the reference links at the
bottom of the page are the last content of the file, they get swallowed into the
published entry. Remove them, the script regenerates them.
</Aside>

<Aside type="note" title="The very first release">
Without a `v*` tag, `auto` has nothing to infer&nbsp;: the script reuses the
declared version as is, and git-cliff goes back up to the first commit of the
repository. The entry then covers the whole history, and must be trimmed before
pushing.
</Aside>

## The release pipeline

`just release` runs at the root of the co-development workspace, which must
contain the five repositories.

<Steps>

1. **Quality gate**&nbsp;: `just check`, `just gen-test`, and
   `just simulate all`. Virtual-machine tests do not run in
   continuous integration, so a failing scenario must stop the release
   here.

2. **Generator**, if it has changed since its last tag. It owns the
   `etc/config.yaml` schema, so it is built before anything that
   depends on it.

3. **Pinning** the generator's tag in `dnf/flake.nix`, so that the contract
   between the framework and the generator is readable in a diff, not just in
   the lock file.

4. **Framework**&nbsp;: `VERSION`, `CHANGELOG.md`, commit and tag, then immediate
   push. Any tweak to the entry after this step would require forcing
   a tag already consumed by `release.yml`, so it is done before.

5. **Documentation**&nbsp;: `just codegen` regenerates the reference from the
   framework, then the version is aligned to the `MAJEUR.MINEUR` line, and the
   site is built and deployed.

6. **Boilerplate and example**&nbsp;: the framework's tag is written into their
   `flake.nix`, `nix flake check` validates, and the `flake.lock` is **committed**.
   This is what makes a clone reproducible.

</Steps>

## Continuous integration safeguards

On a `v*` tag, `release.yml` refuses to publish if:

- the `VERSION` file does not match the tag;
- `CHANGELOG.md` does not contain a section for this version;
- the lock points to a `dnf-generator` taken from a branch rather than from a
  published release.

The three `ci.yml` checks (unit tests, evaluation, lint) are replayed via
`workflow_call`, then the changelog section becomes the notes of the GitHub
*release*.

## Shared configuration

A single [git-cliff](https://git-cliff.org/) for the three repositories that
produce a changelog, in `dnf/just/scripts/cliff.toml`. The script
`dnf/just/scripts/bump.sh` discovers the repository's version source
(`VERSION`, `Cargo.toml`, or `package.json`), assembles the file around the
generated block, and preserves the hand-written history.
