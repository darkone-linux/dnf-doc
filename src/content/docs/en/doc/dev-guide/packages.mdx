Some programs installed by the framework do not exist in
[nixpkgs](https://github.com/NixOS/nixpkgs). Their build recipes live in
`dnf/pkgs/`, and are exposed to all hosts like any other package, under
`pkgs.<name>`.

{/* t:p 680ed9a6e4a9eae44cfe07552a57eae70a3627225321682a812433894591f2ce */}
## Where to put what

Three locations exist for a package that is out of the ordinary, with three
different intentions.

| Location | For what | Lifespan |
|---|---|---|
| `dnf/pkgs/` | Absent from nixpkgs, installed by hosts or users. | Until published in nixpkgs. |
| `dnf/lib/overlays/` | Fix for an existing nixpkgs package (broken build, pending PR). | Temporary, [listed in the registry](/en/doc/dev-guide/workarounds/). |
| `inputs` of `dnf/flake.nix` | What the framework machinery needs (`dnf-generator`, `colmena`). | Permanent. |

:::note[Why not a flake input]
An input is downloaded on **every evaluation**, on **every** consumer,
even on a host that does not install the tool. A package from `dnf/pkgs/` is
downloaded only at the **build** of its derivation.
:::

## Layout

```
dnf/pkgs/
├── default.nix          <-- jeu de paquets, découvert depuis les dossiers
├── overlay.nix          <-- le même jeu en overlay -> pkgs.<nom>
└── <nom>/package.nix    <-- la dérivation
```

Un dossier = un paquet. `default.nix` scanne les dossiers, il n'y a donc **aucun
registre** à tenir à jour. L'overlay, lui, est appliqué une fois pour toutes par
`dnf/lib/flake/mk-configuration.nix`, sur tous les hôtes.

:::tip[Forme nixpkgs dès le départ]
`<nom>/package.nix` reprend la forme
[by-name](https://github.com/NixOS/nixpkgs/tree/master/pkgs/by-name) de nixpkgs :
une publication ultérieure se réduit à déplacer le dossier.
:::

## Adding a package

<Steps>

1. Create `dnf/pkgs/<nom>/package.nix`, as a classic `callPackage` expression, with
   a complete `meta` (`description`, `homepage`, `license`, `mainProgram`,
   `platforms`). Pin the stable version, not a branch.

2. `git add` the folder: flakes ignore untracked files.

3. Build once to fix the hashes, which Nix displays in its error message&nbsp;:

   ```sh
   nix build .#<nom>
   ```

4. `just clean` then commit.

</Steps>

Nothing else to wire up. The package can then be used in any NixOS module or
[Home Manager](/en/doc/dev-guide/modules/), like a nixpkgs package&nbsp;:

```nix
# dnf/home/modules/advanced.nix
(lib.mkIf cfg.enableEssentials rename-simple)
```

:::caution[ISO and SD images]
Installation media receive their `pkgs` already built
(`nixpkgs.pkgs`), without this overlay: `pkgs.<nom>` is not available there. Making
it visible requires applying the overlay to that instance, in
`dnf/lib/flake/mk-configuration.nix`.
:::

## Updating a package

Run it in `dnf/` or at the root of a co-development project&nbsp;: a `dnf/`
linked to the Nix store is read-only.

```sh
just pkg-update <nom>
```

[nix-update](https://github.com/Mic92/nix-update) looks up the latest release
published upstream, then rewrites the version and the hashes in `package.nix`.
Then check the upstream `changelog`, rebuild, and commit.

:::note[Package-specific arguments]
`pkg-update` reuses the arguments of `passthru.updateScript`
(`nix-update-script { extraArgs = [ … ]; }`), like nixpkgs. Example&nbsp;:
`fleet-update` (Bun) declares `--subpackage node_modules` there, to recompute
the hash of its dependencies along with the one of the sources.
:::

## Publishing to nixpkgs

The end goal, for every package of general interest&nbsp;:

<Steps>

1. Move the folder into a nixpkgs clone, under the two-letter shard of the
   name (`pkgs/by-name/re/rename-simple/`).
2. Add the `maintainers` entry, open the pull request.
3. Once the PR is merged and made it into `nixos-unstable`, remove the folder
   from `dnf/pkgs/`.

</Steps>

`pkgs.<name>` keeps resolving, this time from nixpkgs: no module needs to be
updated.
