Serveur d'accueil matrix (synapse) du DNF.

Sous-modules (`matrix/`) :
- `mas.nix` : authentification, déléguée à Matrix Authentication Service ;
- `bridges.nix` : passerelles mautrix, utilisables par chaque compte local ;
- `rtc.nix` : backend MatrixRTC (LiveKit) pour Element Call.

## Fédération

La fédération se configure via `darkone.service.matrix.federation` :

- `enable = false` : bloque toute fédération (liste blanche de domaines vide).
- `enable = true; whitelist = [ ]` : fédération ouverte avec tous les serveurs.
- `enable = true; whitelist = [ "ami.org" ]` : liste blanche (entrant + sortant).

La découverte reste verrouillée dans tous les cas (salons absents des annuaires distants, profils privés en fédération) : le réseau est joignable, mais pas recherchable.

:::caution[Sécurité pour les enfants]
La fédération ouverte permet à tout serveur fédéré d'envoyer des MP et des invitations aux utilisateurs locaux. Pour un réseau familial, ne renseigner `whitelist` qu'avec des serveurs de confiance.
:::

L'auto-inscription des amis (`friendRegistration.enable`) ouvre des comptes locaux à mot de passe, protégés par jeton, en plus des utilisateurs OIDC Kanidm. Générez un jeton sur l'hôte avec `sudo dnf-mas manage issue-user-registration-token`.

:::caution[Un seul espace de noms, identifiants définitifs]
Amis et utilisateurs déclarés puisent dans le même espace de noms de noms locaux, et un identifiant matrix n'est jamais libéré (unique dans `users` de MAS, la désactivation le conserve). Déclarer un utilisateur dont le nom local a déjà été pris par un ami fait échouer sa première connexion SSO : `on_conflict` de MAS reste sur `fail`, car toute autre valeur donnerait le compte existant à quiconque s'inscrit sous un nom correspondant en amont. Procédure de fusion dans le guide administrateur (`operate/matrix.mdx`).
:::

## Administrateurs

`network.matrix.admins` (noms locaux) est la source déclarative unique des deux administrations, appliquée au rebuild sans écriture en base :

- passerelles : niveau `admin` dans chaque map `permissions` mautrix ;
- serveur : `policy.data.admin_users`, que la politique MAS fournie transforme en scopes `urn:mas:admin` et `urn:synapse:admin:*` (API admin MAS, API admin synapse, connexion à l'interface `matrix-admin`).

:::caution[Les promotions impératives survivent]
La politique accorde l'admin sur `admin_users` OU sur le drapeau en base `can_request_admin` que définit `dnf-mas manage promote-admin`. Auditez les restes avec `list-admin-users`, retirez-les avec `demote-admin`.
:::

## Authentification (`mas.nix`)

Toute authentification passe par Matrix Authentication Service, sans exception : Element X, la connexion par QR code et le portail en libre-service `/account` n'existent que là, et l'authentification propre à synapse est dépréciée en amont (MSC3861). Kanidm reste la source d'identité : MAS est le client OIDC à la place de synapse, et synapse se contente de demander à MAS d'introspecter les jetons.

Même vhost : MAS gère la racine et les endpoints d'authentification compat, synapse garde `/_matrix/*` et `/_synapse/*`. La découverte client est automatique (synapse sert lui-même `auth_metadata`), sans changement de well-known.

Secrets sops requis, tous créés par `just configure-admin-host` : `mas-encryption-secret`, `mas-synapse-secret` et `mas-rsa-private-key`.

`dnf-mas` (root) enveloppe `mas-cli` pour l'administration côté hôte : jetons d'inscription, `promote-admin`, `register-user`, `syn2mas`. MAS tourne avec `DynamicUser` et lit ses secrets depuis les identifiants systemd, absents hors de l'unité en marche ; l'enveloppe reconstruit un répertoire d'identifiants équivalent depuis les fichiers sops, donc elle fonctionne que le service soit actif ou non (syn2mas exige qu'il soit arrêté).

`mas-cli` agit seulement, il ne liste pas : activez le service `matrix-admin` pour la lecture (comptes, appareils, sessions) ; il parle aux deux API d'administration.

:::danger[Immuable après le premier démarrage]
`mas-encryption-secret` et l'ULID du fournisseur Kanidm ne doivent jamais changer après le premier démarrage de MAS (données chiffrées en base, liens vers les comptes amont).
:::

:::danger[Migrer une instance antérieure à MAS]
Un serveur antérieur à MAS nécessite la migration `syn2mas` (comptes, mots de passe, sessions, identifiants externes), sinon plus personne ne se connecte. Déployez d'abord, puis, les deux services arrêtés : `sudo dnf-mas syn2mas check`, `... migrate --dry-run`, `... migrate`. Procédure : guide administrateur, *Matrix → Migrer un serveur déjà en production*.
:::

## Passerelles (`bridges.nix`)

Passerelles mautrix : WhatsApp, Signal, Telegram, Messenger, Discord. Chaque utilisateur relie son propre compte distant en écrivant au bot de la passerelle (`@whatsappbot`, `@signalbot`, ... puis `login`) ; les sessions sont isolées par utilisateur. Administrateurs des passerelles : cf. « Administrateurs » plus haut.

Double puppeting : méthode officielle des appservices (https://docs.mau.fi/bridges/general/double-puppeting.html). Un jeton d'appservice `doublepuppet` partagé permet aux passerelles d'envoyer les messages d'origine distante au nom du vrai compte matrix de l'utilisateur. Secrets sops requis : `mautrix-doublepuppet-as-token` et `mautrix-doublepuppet-hs-token` (générés par `just configure-admin-host`).

Les jetons as/hs de l'appservice de chaque passerelle sont fournis par sops, jamais générés automatiquement : le fichier d'enregistrement est une fonction pure des secrets, donc réinitialiser le répertoire d'état d'une passerelle n'invalide jamais l'enregistrement chargé par synapse (« as_token was not accepted », effacement de l'enregistrement et redémarrage de synapse).

## Appels (`rtc.nix`)

Deux piles coexistent, car aucune ne couvre à elle seule tous les clients :

- WebRTC 1:1 historique, négocié via synapse et relayé par coturn (`darkone.service.turn`). Seule technologie parlée par Element Classic.
- MatrixRTC (`matrixRtc.enable`) : un SFU LiveKit plus son service d'autorisation, pour les appels de groupe et pour Element Call. Element X ne parle *que* cette pile et affiche « call is not supported » (`MISSING_MATRIX_RTC_TRANSPORT`) sans elle ; Element Web/Desktop intègrent aussi Element Call et obtiennent les appels de groupe grâce à elle.

Les deux sont servies depuis le vhost matrix, à côté de synapse et MAS : le websocket du SFU sur `/livekit/sfu`, le service JWT sur `/livekit/jwt`. Les clients les découvrent via `matrix_rtc.transports` (synapse, MSC4143) et, en repli pour les anciens, via `rtc_foci` dans le well-known.

Secret sops requis : `livekit-secret` (`just configure-admin-host`), partagé par le SFU et le service JWT.

:::caution[Les ports média doivent atteindre l'hôte]
Les médias ne passent pas par le reverse proxy. La plage UDP et le repli TCP sont ouverts sur l'interface publique : un hôte derrière NAT doit les faire suivre, et régler `rtc.use_external_ip` (non testé ici : le HCS détient directement son adresse publique).
:::

:::caution[L'annulation d'écho ne se règle pas côté serveur]
`services.livekit.settings` est à clés libres : une clé inconnue atteint le fichier de configuration sans erreur. La section `audio` de LiveKit ne règle que la détection du locuteur actif et la redondance RED ; `echo_cancellation`, `noise_suppression` et `channels` n'y existent pas. Ce sont des contraintes `getUserMedia`, gérées par le client.

Aucun réglage du SFU ne peut corriger un participant qui fait écho :

- LiveKit transmet l'Opus sans jamais le décoder.
- L'AEC a besoin de la référence du haut-parleur local, qui ne quitte jamais l'appareil.
- Element Call chiffre les médias de bout en bout : le SFU ne peut pas les lire.

Le remède se situe côté appareil : un casque, ou les options de traitement audio d'Element Call. Attention au piège du diagnostic : un combiné dont l'AEC matérielle s'annonce sans rien faire fait écho pour tous les *autres*, jamais pour son propre utilisateur.
:::

## Options

* **enable** `bool` Active le service matrix (synapse)
* **federation.enable** `bool` Autorise la fédération serveur à serveur. `false` bloque toute fédération.
* **federation.whitelist** `listOf str` Vide = fédérer avec tous les serveurs ; non vide = seulement ces domaines (entrant + sortant).
* **matrixRtc.enable** `bool` Active le backend MatrixRTC (SFU LiveKit) pour les appels de groupe d'Element Call.
* **friendRegistration.enable** `bool` Autorise les amis à s'inscrire eux-mêmes avec un jeton d'invitation (protégé par jeton).
* **bridges.whatsapp.enable** `bool` Passerelle mautrix WhatsApp (connexion par QR code).
* **bridges.signal.enable** `bool` Passerelle mautrix Signal (connexion par QR code).
* **bridges.telegram.enable** `bool` Passerelle mautrix Telegram (connexion par numéro de téléphone).
* **bridges.messenger.enable** `bool` Passerelle mautrix Facebook Messenger (connexion par cookies).
* **bridges.discord.enable** `bool` Passerelle mautrix Discord (connexion par QR code, expérimental).
* **shared** `raw` Valeurs matrix partagées avec les sous-modules `matrix/`.

```nix
darkone.service.matrix = {
  enable = false;
  federation.enable = false;
  federation.whitelist = [ ];
  matrixRtc.enable = false;
  friendRegistration.enable = false;
  bridges.whatsapp.enable = true;
  bridges.signal.enable = true;
  bridges.telegram.enable = true;
  bridges.messenger.enable = true;
  bridges.discord.enable = false;
  shared = {
          inherit
            params
            masKanidmUlid
            livekitJwtUrl
            matrixAdmins
            ;
        };
};
```
