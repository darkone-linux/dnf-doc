### &#x2728; darkone.service.dnsmasq

dnsmasq pré-configuré pour la passerelle / routeur local.

:::note
Cette configuration lit la conf `network` dans le fichier `config.yaml`.
C'est la fonctionnalité essentielle de la passerelle locale.
:::

:::tip[Hôtes venant d'une autre zone]
Chaque zone réserve `<ipPrefix>.6.0/24` pour les hôtes dont le domicile est ailleurs.
Le générateur émet, dans `zone.extraDnsmasqSettings`, un `dhcp-host` par
MAC de flotte connu non natif ici, plus un `host-record` liant
`<host>.<this-zone-domain>` à cette adresse, de sorte qu'une machine branchée
sur la mauvaise zone (installation d'une passerelle, ordinateur portable en
itinérance) obtienne quand même un bail et un nom prévisibles. Son nom court
continue de résoudre vers son adresse de domicile. `zone.roaming` expose la
même table à l'outillage d'installation.
:::

* **enable** `bool` Active le service dnsmasq local

```nix
darkone.service.dnsmasq.enable = false;
```

### &#x2728; darkone.service.garage

Un service Garage S3 local entièrement configuré.

Fournit un stockage d'objets interne compatible S3 accessible
uniquement sur 127.0.0.1:3900.

:::note[Création manuelle des buckets]
Les buckets ne sont PAS créés automatiquement par ce module.
Chaque service consommateur provisionne son propre bucket et sa clé d'accès via
une unité systemd oneshot dédiée ordonnée After= `garage-init.service`.
Les identifiants de chaque consommateur sont stockés dans sops en tant que
`garage-<consumer>-key-id` et `garage-<consumer>-key-secret`, importés dans
Garage au premier démarrage.
:::

:::tip[Migration vers un cluster multi-nœuds]
Nœud unique, replication_factor = 1. Pour évoluer vers un cluster multi-nœuds,
augmenter `replication_factor`, exposer `rpc_public_addr` sur le maillage, et
étendre `garage-init` pour piloter un layout multi-nœuds.
:::

:::caution[Initialisation du layout du cluster]
En cas d'échec, attendre que le service garage soit pleinement opérationnel,
puis le redémarrer.
:::

* **enable** `bool` Activer le service Garage S3 local
* **srvPort** `port` Port de l'API S3 exposé sur l'IP interne
* **s3Region** `str` Nom de la région S3 (doit correspondre à la config du consommateur)
* **capacity** `str` Indication de capacité de stockage du nœud transmise à `garage layout assign`.
  Utilisée uniquement au premier démarrage pour l'initialisation du layout ; n'agit pas
  comme un quota strict sur le système de fichiers sous-jacent.
  Suffixes pris en charge : B, KB, MB, GB, TB, PB.

```nix
darkone.service.garage = {
  enable = false;
  srvPort = srvPort;
  s3Region = s3Region;
  capacity = "500GB";
};
```

### &#x2728; darkone.service.harmonia

Harmonia&nbsp;: serveur local de cache binaire Nix (sert le /nix/store de cet hôte).

Expose les chemins du store construits / réalisés localement sur HTTP simple (port 5000), signés avec la clé de cache binaire déployée sur tout le réseau. À activer par hôte depuis `usr/config.yaml` (services.harmonia), comme tout autre service DNF.

:::note[Comment harmonia fonctionne avec le proxy nix-cache]
Harmonia est une *source* de paquets, servis **directement** aux clients sur le LAN (in-zone) ou le tailnet (quand il est marqué `global`). Le proxy `nix-cache` par zone est un sujet séparé&nbsp;: il met en cache le cache binaire *public* (`cache.nixos.org`), jamais harmonia.

Les substituters de chaque hôte de la zone locale deviennent, par ordre de priorité&nbsp;:

- les instances harmonia de *sa propre zone* (priorité la plus haute, LAN), puis
- toute harmonia marquée `global` (typiquement sur le HCS, via le tailnet), puis
- le proxy `nix-cache` de la zone (cache public).

Cet ordre est figé côté client avec `?priority=` sur chaque URL de substituter (voir `nix-cache.nix`), car la `priority` définie ci-dessous est identique sur chaque instance et Nix trie les substituters par priorité annoncée, pas par ordre de liste.

Un hôte qui exécute harmonia ne reçoit **pas** sa propre instance comme substituter&nbsp;: elle ne servirait que des chemins que son store local possède déjà.

Les harmonia non-globales des autres zones ne sont jamais utilisées. La signature d'harmonia est transmise telle quelle, donc chaque hôte fait confiance à la clé publique harmonia déployée (`usr/secrets/harmonia.pub`). Le transport est en HTTP simple sur le LAN / VPN de confiance&nbsp;: l'intégrité vient de la signature NAR, pas de TLS.
:::

:::tip[Provisionnement de la clé de signature]
`just configure-admin-host` génère automatiquement la paire de clés déployée quand `usr/secrets/harmonia.pub` est absent&nbsp;: la clé publique est commitée et la clé privée est injectée dans le secret sops `harmonia-secret-key`.
:::

:::note[Avertissement de démarrage bénin sur les permissions de la clé de signature]
`WARN harmonia_cache::tls: /run/credentials/harmonia.service/sign-key-0 has
insecure permissions 0o440; recommend 0600` est un faux positif&nbsp;: systemd
expose les fichiers `LoadCredential` en mode 0440 appartenant à root, avec une
ACL qui n'accorde l'accès qu'à l'utilisateur du service
(systemd/systemd#29435)&nbsp;; harmonia vérifie naïvement les bits de chmod.
Surveillez quand même l'amont&nbsp;: harmonia rejette déjà fermement les clés
*TLS* lisibles par le groupe au démarrage&nbsp;; si cette politique s'étend un
jour aux clés de signature, cette unité cassera à la mise à jour.
:::

* **enable** `bool` Active un serveur de cache binaire Nix Harmonia local

```nix
darkone.service.harmonia.enable = false;
```

### &#x2728; darkone.service.matrix

Serveur Matrix (synapse) DNF avec les ponts mautrix.

Les ponts (whatsapp, signal, telegram, messenger, discord) sont utilisables par
tout compte local&nbsp;: chaque utilisateur lie son propre compte distant en
discutant avec le bot du pont (`@whatsappbot`, `@signalbot`, ... puis `login`)&nbsp;;
les sessions sont isolées par utilisateur. Le `network.matrix.admin` déclaré
administre les ponts.

Le double puppeting utilise la méthode officielle appservice
(https://docs.mau.fi/bridges/general/double-puppeting.html)&nbsp;: un jeton
`doublepuppet` appservice partagé permet aux ponts d'envoyer les messages
provenant du distant en tant que vrai compte matrix de l'utilisateur. Secrets
sops requis&nbsp;: `mautrix-doublepuppet-as-token` et
`mautrix-doublepuppet-hs-token` (`openssl rand -hex 32` chacun).

Les jetons as/hs appservice de chaque pont sont fournis par sops plutôt
qu'auto-générés&nbsp;: le fichier d'enregistrement devient une fonction pure
des secrets, donc réinitialiser le répertoire d'état d'un pont n'invalide
jamais l'enregistrement que synapse a chargé (ce qui autrement nécessiterait
un wipe d'enregistrement + redémarrage de synapse et produirait des erreurs
«&nbsp;as_token was not accepted&nbsp;»).

{/* t:p ff353801b94ac1fc282cf6ce672fdc79a049f111f00671c5ac098fd143bba110 */}
#### Fédération

La fédération se configure via `darkone.service.matrix.federation`&nbsp;:

- `enable = false`&nbsp;: bloque toute fédération (liste blanche de domaines vide).
- `enable = true; whitelist = [ ]`&nbsp;: fédération ouverte avec tous les serveurs.
- `enable = true; whitelist = [ "ami.org" ]`&nbsp;: liste blanche (entrante + sortante).

La découverte reste verrouillée dans tous les cas (salles absentes des
annuaires distants, profils privés sur la fédération), donc le réseau est
joignable mais pas recherchable.

:::caution[Sans risque pour les enfants]
Une fédération ouverte laisse n'importe quel serveur fédéré envoyer des MP ou
inviter des utilisateurs locaux. Pour un réseau familial, remplissez
`whitelist` avec uniquement les serveurs de confiance.
:::

L'auto-inscription des proches (`friendRegistration.enable`) ouvre des comptes
locaux protégés par jeton aux côtés des utilisateurs OIDC Kanidm. Sans MAS, la
frappe d'un jeton passe par l'API admin de Synapse (un admin serveur est
requis)&nbsp;; avec MAS, frappez-le sur l'hôte avec
`sudo dnf-mas manage issue-user-registration-token`.

:::caution[Un seul espace de noms, identifiants permanents]
Les proches et les utilisateurs déclarés tirent du même espace de noms
`localpart`, et un identifiant matrix n'est jamais libéré (unique dans
`users` de MAS, la désactivation le conserve). Déclarer un utilisateur dont le
`localpart` a déjà été pris par un proche fait échouer leur première connexion
SSO&nbsp;: `on_conflict` reste sur `fail` ci-dessous, puisque toute autre
valeur remettrait le compte existant à quiconque enregistre un nom
correspondant en amont. Procédure de fusion dans le guide admin
(`operate/matrix.mdx`).
:::

{/* t:p a40748eb781fccc4da58ca71ab300b213dd7a300121c552afc64553ab0e74bd3 */}
#### Authentification nouvelle génération (MAS)

`mas.enable` délègue toute l'authentification à Matrix Authentication Service
(requis par Element X, le login par QR, le portail libre-service `/account`).
Kanidm reste la source d'identité : MAS devient le client OIDC à la place de
synapse, et synapse ne demande plus qu'à MAS d'introspecter les jetons. Servi
sur le même vhost : MAS possède les endpoints racine + compat auth, synapse
garde `/_matrix/*` et `/_synapse/*` ; la découverte client est automatique
(synapse sert `auth_metadata` lui-même), donc aucun changement de well-known.

Secrets sops requis (`openssl rand -hex 32` sauf mention contraire) :
`mas-encryption-secret`, `mas-synapse-secret` et `mas-rsa-private-key`
(`openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096`).

`dnf-mas` (root) enveloppe `mas-cli` pour l'administration côté hôte : jetons
d'enregistrement, `promote-admin`, `register-user`, `syn2mas`. MAS tourne avec
`DynamicUser` et lit ses secrets depuis les credentials systemd, qui n'existent
pas en dehors de l'unité en cours d'exécution ; l'enveloppe reconstruit un
répertoire de credentials équivalent depuis les fichiers sops, elle fonctionne
donc que le service soit démarré ou arrêté (syn2mas en a besoin arrêté).

:::danger[Immuable une fois démarré]
`mas-encryption-secret` et l'ULID du provider Kanidm ne doivent jamais changer
après le premier démarrage de MAS (données chiffrées de la base / liens de
comptes en amont).
:::

:::caution[Migration d'une instance existante]
Activer `mas.enable` sur un homeserver en production requiert la migration
`syn2mas` (comptes, mots de passe, sessions, identifiants externes). Déployez
d'abord, puis, avec les deux services arrêtés : `sudo dnf-mas syn2mas check`,
`... migrate --dry-run`, `... migrate`. Les bridges n'ont pas besoin de
régénérer leur enregistrement : synapse impose MSC4190 sur chaque appservice
dès que l'authentification est déléguée. Procédure dans
`.specs/matrix-authentication-service.md`.
:::

:::caution[Pas d'enregistrement par secret partagé sous MAS]
`/_synapse/admin/v1/register` de Synapse (secret partagé d'enregistrement) est
désactivé en mode délégué, et c'est ce que `just configure-alert-bot` utilise
pour créer un compte bot manquant. Créez-le à l'avance, ou avec
`sudo dnf-mas manage register-user`.
:::

* **enable** `bool` Active le service matrix (synapse)
* **federation.enable** `bool` Autorise la fédération entre serveurs. False bloque toute la fédération.
* **federation.whitelist** `listOf str` Vide = fédération avec tous les serveurs ; non vide = uniquement ces domaines (entrant + sortant).
* **mas.enable** `bool` Délègue toute l'authentification à Matrix Authentication Service (support Element X).
* **matrixRtc.enable** `bool` Active le backend MatrixRTC (LiveKit SFU) pour les appels de groupe Element Call.
* **friendRegistration.enable** `bool` Autorise les amis à s'auto-enregistrer avec un jeton d'invitation (contrôlé par jeton).
* **bridges.whatsapp.enable** `bool` Bridge Mautrix WhatsApp (connexion par QR code).
* **bridges.signal.enable** `bool` Bridge Mautrix Signal (connexion par QR code).
* **bridges.telegram.enable** `bool` Bridge Mautrix Telegram (connexion par numéro de téléphone).
* **bridges.messenger.enable** `bool` Bridge Mautrix Facebook Messenger (connexion par cookies).
* **bridges.discord.enable** `bool` Bridge Mautrix Discord (connexion par QR code, expérimental).

```nix

  federation.whitelist = [ ];

  matrixRtc.enable = false;
  friendRegistration.enable = false;
  bridges.whatsapp.enable = true;
  bridges.signal.enable = true;
  bridges.telegram.enable = true;
  bridges.messenger.enable = true;
  bridges.discord.enable = false;
};
```

### &#x2728; darkone.service.nix-cache

Proxy de cache binaire Nix par zone (nginx `proxy_cache`).

Met en cache le cache Nix public (`cache.nixos.org`) sur la passerelle de la
zone afin qu'un déploiement à l'échelle de la flotte tire chaque closure du WAN
une seule fois, puis la sert sur le LAN à tous les autres hôtes. Les chemins
construits localement sont servis directement par `harmonia` (voir
`harmonia.nix`) ; ce proxy ne se place jamais devant harmonia.

:::note[Pourquoi nginx et pas un proxy de réécriture]
Un point de terminaison de cache fait face à **un** amont exactement. Un
`narinfo` et son `nar` sont deux requêtes distinctes et l'URL du `nar` ne dépend
pas de l'amont, donc un proxy multi-amont doit réécrire les URL `narinfo` dans
son propre espace de noms et les suivre dans une base de données (l'approche
qu'adoptait l'ancien proxy `ncps`, et la source de ses HTTP 500 « invalid nar
hash » récurrents). Avec un seul amont, il n'y a pas d'ambiguïté :
nginx met en cache `narinfo` + `nar` verbatim, les signatures transitent
intactes et les clients les vérifient. Pas de réécriture, pas de base de
données, ce bug est impossible par construction.
:::

:::tip[Topologie]
- serveur : l'hôte passerelle qui liste `nix-cache` dans `config.yaml` (un par
  zone). Exécute nginx sur l'IP interne, port `network.ports.nixCache`.
- clients : tous les hôtes de la zone locale. Leurs substituters deviennent les
  instances harmonia de la zone (directes, LAN/tailnet) plus ce proxy.
- clients nomades (`roaming = true`) : hôtes itinérants déplacés entre les zones.
  Leurs substituters sont les noms neutres de zone (`harmonia.dnf.internal`,
  `nix-cache.dnf.internal`) que le DNS de chaque zone résout vers ses propres
  services de cache (voir `service/dnsmasq.nix`), afin que le cache suive le
  portable.
:::

* **enable** `bool` le proxy de cache binaire Nix par zone (nginx devant cache.nixos.org)
* **maxSize** `str` Taille maximale du cache sur disque ; au-delà, nginx évince les entrées les moins récemment utilisées.
* **roaming** `bool` Hôte nomade (portable déplacé entre zones) : remplacer les
  substituters épinglés à la zone par les noms neutres de zone que le DNS de
  chaque zone résout vers ses propres services de cache. En dehors de toute
  zone DNF, les noms répondent NXDOMAIN instantanément et Nix retombe sur
  cache.nixos.org.

```nix
darkone.service.nix-cache = {
  enable = false;
  maxSize = "40g";
  roaming = false;
};
```

### &#x2728; darkone.service.prometheus

Serveur de monitoring Prometheus avec escalade Alertmanager déclarative.

:::tip[Prometheus & Grafana]
Service autonome de métriques + alerting, indépendant de Grafana :

- Scrape chaque nœud de zone portant la fonctionnalité `monitoring-node:<zone>`.
- Alertmanager route par sévérité : warning -> Matrix #warnings,
  critical -> Matrix #incidents + mail (relais Postfix local).
- blackbox_exporter sonde la joignabilité de la passerelle / du tailnet / du DNS.
- Les classes de nœuds (critical/non-critical/disabled) proviennent des
  fonctionnalités `alert-*` ou du profil hôte (voir `dnf/lib/alerts.nix`).

`monitoring` (Grafana) requiert un `prometheus` sur le même hôte
(imposé par le `require` du générateur). L'interface web est exposée sur
`https://prometheus.<zone>.<domain>` derrière oauth2-proxy (groupe `admins`),
ce qui corrige aussi les liens d'alerte pointant vers Prometheus.
:::

* **enable** `bool` Active le serveur de métriques + alerting Prometheus
* **retentionTime** `str` Durée de rétention des métriques Prometheus
* **alerting.enable** `bool` Active Alertmanager (activé par défaut une fois les salons d'alerte Matrix provisionnés)
* **alerting.matrix.enable** `bool` Livre les alertes dans les salons Matrix via le bot matrix-alertmanager
* **alerting.matrix.userId** `str` ID utilisateur Matrix du bot d'alerte (par défaut depuis network.matrix.bot)
* **alerting.matrix.warningsRoom** `str` ID du salon Matrix pour les warnings (par défaut depuis network.matrix.warningsRoom)
* **alerting.matrix.incidentsRoom** `str` ID du salon Matrix pour les incidents (par défaut depuis network.matrix.incidentsRoom)
* **alerting.email.enable** `bool` Envoie aussi les alertes critiques par mail (via le relais Postfix local)
* **alerting.email.to** `str` Destinataire des mails d'alerte critique
* **alerting.network.enable** `bool` Sonde la joignabilité réseau (gateway/tailnet/DNS) avec blackbox_exporter
* **alerting.network.internetProbeTargets** `listOf str` Adresses IP externes que la passerelle de zone ping pour détecter une coupure WAN. Quand toutes
  échouent, `ZoneInternetDown` se déclenche et inhibe les (fausses) alertes down des
  hôtes joignables uniquement via le WAN (ex. le HCS). Vide pour désactiver.
* **alerting.network.httpProbeUrls** `listOf str` URLs HTTP(S) sondées pour la vivacité (`ServiceEndpointDown`) et l'expiration des certificats TLS
  (`CertificateExpiringSoon`/`Critical`). Vide par défaut : listez les endpoints
  web publics à surveiller. Les redirections vers une connexion SSO (3xx) comptent
  comme up ; l'expiration du certificat est lue à partir de la poignée de main TLS,
  indépendamment du statut HTTP.
* **alerting.silenceOnRebuild** `bool` Livre le flag dnf-maintenance (collecteur textfile) pour que les rebuilds inhibent les alertes d'un nœud
* **alerting.thresholds** `attrs` Remplace les seuils d'alerte des ressources (voir les défauts de dnf/lib/alerts.nix)
* **alerting.silences** `listOf submodule` Alertes connues et acceptées qui ne doivent jamais notifier. Chaque entrée devient une
  route Alertmanager vers le récepteur `null` : l'alerte se déclenche toujours et
  reste visible dans les UIs Prometheus/Alertmanager/Grafana, elle cesse juste
  d'atteindre Matrix et le mail.

  Déclarées sur l'hôte exécutant Prometheus, car c'est là que les règles et routes
  de la zone sont générées. Un module consommateur à l'échelle de la flotte
  (`usr/modules/alerts.nix`) est l'endroit pratique : il est importé partout et ne
  prend effet que là où Prometheus tourne.

  :::caution[En dernier recours]
  Corrigez ou reconfigurez d'abord la condition sous-jacente. Un silence masque un
  vrai signal, donc `reason` est obligatoire et la liste reste auditable.
  :::
  * **alert** `str` Nom de l'alerte à mettre en sourdine (label `alertname`). Toujours contraint, pour que les sévérités voisines restent armées.
  * **host** `nullOr str` Restreint le silence à un seul hôte. Null met l'alerte en sourdine sur toute la flotte.
  * **matchers** `attrs` Matchers de labels exacts supplémentaires, combinés en ET avec les autres (ex. le montage ou le périphérique concerné par l'alerte).
  * **reason** `str` Pourquoi cette alerte est acceptée, et ce qui rendrait le silence retirable.

```nix
darkone.service.prometheus = {
  enable = false;
  retentionTime = "30d";
  alerting.enable = roomsReady;
  alerting.matrix.enable = true;
  alerting.matrix.userId = "@alertbot:domain.tld";
  alerting.matrix.warningsRoom = "!warnings:domain.tld";
  alerting.matrix.incidentsRoom = "!incidents:domain.tld";
  alerting.email.enable = true;
  alerting.email.to = "admin@${network.domain}";
  alerting.network.enable = true;
  alerting.network.internetProbeTargets = [ ];
  alerting.network.httpProbeUrls = [ ];
  alerting.silenceOnRebuild = true;
  alerting.thresholds = { };
  alerting.silences = [ ];
  alerting.silences.alert = "DiskSpaceLow";
  alerting.silences.host = "srv-main";
  alerting.silences.matchers = { };
  alerting.silences.reason = null;
};
```

### &#x2728; darkone.service.restic

Module de sauvegarde restic : serveur REST + cibles de sauvegarde par hôte.

:::tip[Deux rôles, un seul module]
- Serveur : un hôte avec `restic` dans ses services config.yaml fait tourner le
  serveur REST (`enableServer`) et stocke le dépôt de chaque hôte.
- Client : tout hôte avec `enable = true` déclare des `targets` de sauvegarde
  (chemin local ou `rest:http://restic.<zone>:<port>`).
:::

:::note[Deux mots de passe, à ne pas confondre]
- Phrase de passe du dépôt : `restic-password-<zone>`, chiffre le contenu du dépôt.
- Identifiant REST : `restic/<hostname>/rest-password` par hôte, authentifie
  l'hôte auprès du serveur REST. Généré par `just passwd-restic`.
:::

Exemple (configuration machine) :

```nix
darkone.service.restic = {
  enable = true;
  targets = [
    { name = "main"; root = "rest:http://restic.my-zone.my-domain.tld:8888";
      zone = "ag"; categories = [ "system" "nfs" ]; }
  ];
};
```

Plan du dépôt par cible : un dépôt par catégorie, nommé d'après elle.

```
<root>/<hostname>/system  <- "system" category (/ minus excludes)
<root>/<hostname>/nfs     <- "nfs" category    (/srv/nfs/<...>)
<root>/<hostname>/medias  <- "medias" category (/srv/medias/<...>)
```

:::caution[Le chemin du dépôt est exactement sur deux niveaux]
rest-server sert les dépôts au plus deux composants en dessous de son `--path` :
`<hostname>/medias` répond, `<hostname>/srv/medias` renvoie une 404 et restic
signale le message trompeur « repository does not exist ». Le sous-chemin est
donc le simple nom de catégorie, jamais le répertoire source. Un plan identique
pour les cibles locales et REST permet à un dépôt de passer de l'une à l'autre
sans renommage.
:::

:::danger[Migration des dépôts créés avant ce plan]
Les dépôts écrits quand le sous-chemin reflétait le répertoire source se trouvent
sous `<hostname>/srv/{nfs,medias}`. Renommez-les sur le serveur avant la prochaine
exécution : `initialize = true` créerait sinon un dépôt vide au nouveau chemin et
lancerait silencieusement une sauvegarde complète depuis zéro.

```sh
mv <data-dir>/<hostname>/srv/medias <data-dir>/<hostname>/medias
rmdir <data-dir>/<hostname>/srv
```
:::

* **enable** `bool` Active le client de sauvegarde restic
* **enableDryRun** `bool` Mode dry run
* **enableWaitRemoteFs** `bool` Ne lance les sauvegardes qu'après remote-fs.target
* **enableServer** `bool` Active le serveur REST restic
* **serverDataDir** `str` Racine de stockage locale du serveur REST (dépôts de tous les hôtes)
* **targets** `listOf submodule` Destinations de sauvegarde pour cet hôte (chemin local ou URL REST)
  * **name** `str` Identifiant de la cible, utilisé dans les noms de sauvegarde/unités (&lt;category&gt;-&lt;name&gt;)
  * **root** `str` Racine du dépôt : chemin local ou URL REST
  * **zone** `str` Zone qui sélectionne la phrase de passe du dépôt (restic-password-&lt;zone&gt;)
  * **categories** `listOf ( enum [ "system" "nfs" "medias" ] )` Ce qui est sauvegardé sur cette cible
* **nfsPaths** `listOf str` Répertoires NFS (/srv/nfs/&lt;xxx&gt;) inclus dans la catégorie 'nfs'
* **mediasPaths** `listOf str` Répertoires medias (/srv/medias/&lt;xxx&gt;) inclus dans la catégorie 'medias'

```nix
darkone.service.restic = {
  enable = false;
  enableDryRun = false;
  enableWaitRemoteFs = false;
  enableServer = false;
  serverDataDir = "/mnt/backup/restic";
  targets = [ ];
  targets.name = "main";
  targets.root = "rest:http://restic.${zone.domain}:${toString srvPort}";
  targets.zone = zone.name;
  targets.categories = [ ];
  nfsPaths = [ ];
  mediasPaths = [ ];
};
```
