### &#x2728; darkone.service.dnsmasq

dnsmasq pré-configuré pour la passerelle / routeur local.

:::note
Cette configuration lit la conf `network` dans le fichier `config.yaml`.
C'est la fonctionnalité essentielle de la passerelle locale.
:::

:::tip[Hôtes venant d'une autre zone]
Chaque zone réserve `<ipPrefix>.6.0/24` pour les hôtes dont le domicile est ailleurs.
Le générateur émet, dans `zone.extraDnsmasqSettings`, un `dhcp-host` par
MAC de flotte connu non natif ici, plus un `host-record` liant
`<host>.<this-zone-domain>` à cette adresse, de sorte qu'une machine branchée
sur la mauvaise zone (installation d'une passerelle, ordinateur portable en
itinérance) obtienne quand même un bail et un nom prévisibles. Son nom court
continue de résoudre vers son adresse de domicile. `zone.roaming` expose la
même table à l'outillage d'installation.
:::

* **enable** `bool` Active le service dnsmasq local

```nix
darkone.service.dnsmasq.enable = false;
```

### &#x2728; darkone.service.garage

Un service Garage S3 local entièrement configuré.

Fournit un stockage d'objets interne compatible S3 accessible
uniquement sur 127.0.0.1:3900.

:::note[Création manuelle des buckets]
Les buckets ne sont PAS créés automatiquement par ce module.
Chaque service consommateur provisionne son propre bucket et sa clé d'accès via
une unité systemd oneshot dédiée ordonnée After= `garage-init.service`.
Les identifiants de chaque consommateur sont stockés dans sops en tant que
`garage-<consumer>-key-id` et `garage-<consumer>-key-secret`, importés dans
Garage au premier démarrage.
:::

:::tip[Migration vers un cluster multi-nœuds]
Nœud unique, replication_factor = 1. Pour évoluer vers un cluster multi-nœuds,
augmenter `replication_factor`, exposer `rpc_public_addr` sur le maillage, et
étendre `garage-init` pour piloter un layout multi-nœuds.
:::

:::caution[Initialisation du layout du cluster]
En cas d'échec, attendre que le service garage soit pleinement opérationnel,
puis le redémarrer.
:::

* **enable** `bool` Activer le service Garage S3 local
* **srvPort** `port` Port de l'API S3 exposé sur l'IP interne
* **s3Region** `str` Nom de la région S3 (doit correspondre à la config du consommateur)
* **capacity** `str` Indication de capacité de stockage du nœud transmise à `garage layout assign`.
  Utilisée uniquement au premier démarrage pour l'initialisation du layout ; n'agit pas
  comme un quota strict sur le système de fichiers sous-jacent.
  Suffixes pris en charge : B, KB, MB, GB, TB, PB.

```nix
darkone.service.garage = {
  enable = false;
  srvPort = srvPort;
  s3Region = s3Region;
  capacity = "500GB";
};
```

### &#x2728; darkone.service.harmonia

Harmonia&nbsp;: serveur local de cache binaire Nix (sert le /nix/store de cet hôte).

Expose les chemins du store construits / réalisés localement sur HTTP simple (port 5000), signés avec la clé de cache binaire déployée sur tout le réseau. À activer par hôte depuis `usr/config.yaml` (services.harmonia), comme tout autre service DNF.

:::note[Comment harmonia fonctionne avec le proxy nix-cache]
Harmonia est une *source* de paquets, servis **directement** aux clients sur le LAN (in-zone) ou le tailnet (quand il est marqué `global`). Le proxy `nix-cache` par zone est un sujet séparé&nbsp;: il met en cache le cache binaire *public* (`cache.nixos.org`), jamais harmonia.

Les substituters de chaque hôte de la zone locale deviennent, par ordre de priorité&nbsp;:

- les instances harmonia de *sa propre zone* (priorité la plus haute, LAN), puis
- toute harmonia marquée `global` (typiquement sur le HCS, via le tailnet), puis
- le proxy `nix-cache` de la zone (cache public).

Cet ordre est figé côté client avec `?priority=` sur chaque URL de substituter (voir `nix-cache.nix`), car la `priority` définie ci-dessous est identique sur chaque instance et Nix trie les substituters par priorité annoncée, pas par ordre de liste.

Un hôte qui exécute harmonia ne reçoit **pas** sa propre instance comme substituter&nbsp;: elle ne servirait que des chemins que son store local possède déjà.

Les harmonia non-globales des autres zones ne sont jamais utilisées. La signature d'harmonia est transmise telle quelle, donc chaque hôte fait confiance à la clé publique harmonia déployée (`usr/secrets/harmonia.pub`). Le transport est en HTTP simple sur le LAN / VPN de confiance&nbsp;: l'intégrité vient de la signature NAR, pas de TLS.
:::

:::tip[Provisionnement de la clé de signature]
`just configure-admin-host` génère automatiquement la paire de clés déployée quand `usr/secrets/harmonia.pub` est absent&nbsp;: la clé publique est commitée et la clé privée est injectée dans le secret sops `harmonia-secret-key`.
:::

:::note[Avertissement de démarrage bénin sur les permissions de la clé de signature]
`WARN harmonia_cache::tls: /run/credentials/harmonia.service/sign-key-0 has
insecure permissions 0o440; recommend 0600` est un faux positif&nbsp;: systemd
expose les fichiers `LoadCredential` en mode 0440 appartenant à root, avec une
ACL qui n'accorde l'accès qu'à l'utilisateur du service
(systemd/systemd#29435)&nbsp;; harmonia vérifie naïvement les bits de chmod.
Surveillez quand même l'amont&nbsp;: harmonia rejette déjà fermement les clés
*TLS* lisibles par le groupe au démarrage&nbsp;; si cette politique s'étend un
jour aux clés de signature, cette unité cassera à la mise à jour.
:::

* **enable** `bool` Active un serveur de cache binaire Nix Harmonia local

```nix
darkone.service.harmonia.enable = false;
```

### &#x2728; darkone.service.idm

Service DNF Kanidm (gestionnaire d'identités).

:::note[Les secrets sont générés, pas saisis]
`just configure-admin-host` crée chaque entrée lue par ce module :
les mots de passe du compte de secours (`kanidm-admin-password`,
`kanidm-idm-admin-password`), le couple auto-signé de l'écouteur HTTPS
interne (`kanidm-tls-chain` / `kanidm-tls-key`, 10 ans, CN=127.0.0.1) et
un `oidc-secret-<client>` par client OAuth2 provisionné. Relisez-les avec
`just sops` lorsqu'un administrateur en a besoin, ce qui est rare.
:::

* **enable** `bool` Activer le SSO local avec Kanidm
* **oauth2** `attrs` Modèles de clients OAuth2/OIDC fournis par les modules de services.
  Kanidm provisionne un client pour chaque entrée correspondante dans `network.services`,
  avec `clientId = dnfLib.oauth2ClientName`.
  * **enable** `bool` Whether to provision OAuth2 clients for this template.
  * **clientName** `nullOr str` Override the kanidm client name. Defaults to dnfLib.oauth2ClientName.
  * **displayName** `str` Human-readable name shown on the kanidm consent screen.
  * **imageFile** `path` Application icon. Re-uploaded on every kanidm-provision run.
  * **redirectPaths** `listOf str` OAuth2 redirect paths (one per accepted callback URL).
  * **landingPath** `str` Auto-connect entry point path on the service.
  * **enableLegacyCrypto** `bool` Allow legacy JWT signing algorithms (eg. RS256).
  * **allowInsecureClientDisablePkce** `bool` Disable PKCE on the client (only for clients that do not implement it).
  * **preferShortUsername** `nullOr bool` Use the short username (no domain) in the `preferred_username` claim.
  * **extra** `attrs` Extra attributes merged into the provisioned client (claimMaps, etc).

```nix
darkone.service.idm = {
  enable = false;
  oauth2.enable = true;
  oauth2.clientName = null;
  oauth2.displayName = null;
  oauth2.imageFile = null;
  oauth2.redirectPaths = [ ];
  oauth2.landingPath = "/";
  oauth2.enableLegacyCrypto = false;
  oauth2.allowInsecureClientDisablePkce = false;
  oauth2.preferShortUsername = null;
  oauth2.extra = { };
};
```

### &#x2728; darkone.service.loki

Loki + Alloy, stats HTTP avec Grafana.

:::note
Collecte centralisée des journaux d'accès Caddy, consommés par Grafana via
un datasource Loki provisionné et un tableau de bord dédié.

Double pattern aligné avec monitoring.nix :
- `enable`   : déploie le serveur Loki + le datasource Grafana sur le
  même hôte que le service `monitoring` (Grafana).
- `isClient` : déploie Alloy sur chaque hôte exécutant Caddy. Les
  journaux Caddy sont attendus en JSON dans `/var/log/caddy/access-*.log`
  (voir `dnf/modules/system/services.nix`).

Par défaut, `enable` suit `darkone.service.monitoring.enable` et
`isClient` suit `services.caddy.enable` : la configuration est entièrement
automatique une fois le monitoring et Caddy actifs.
:::

:::tip[Débogage et nettoyage manuel]
Symptômes les plus courants après une (dés)activation de Loki ou un changement
de format de journal Caddy :

**1. « NO DATA » sur le tableau de bord Caddy malgré des requêtes entrantes.**
   Vérifier la chaîne d'ingestion de bout en bout :
   ```sh
   # Sur l'hôte Caddy : Alloy est-il en cours d'exécution ? lit-il les fichiers ?
   sudo systemctl status alloy --no-pager
   sudo journalctl -u alloy -n 100 --no-pager | grep -iE 'error|permission'
   ls -la /var/log/caddy/access-*.log   # doit appartenir à caddy:caddy

   # Sur l'hôte de supervision : Loki reçoit-il quelque chose ?
   # (remplacer <IP> par l'adresse interne de l'hôte de supervision, Loki ne se
   # lie PAS sur 127.0.0.1 — voir http_listen_address = bindAddr)
   curl -s http://<IP>:3100/loki/api/v1/labels | jq
   curl -sG http://<IP>:3100/loki/api/v1/query \
        --data-urlencode 'query={job="caddy"}' | jq '.data.result | length'
   ```

**2. `alloy.service: mkdir data-alloy/remotecfg: permission denied`.**
   Propriété orpheline de `/var/lib/alloy` héritée d'un ancien DynamicUser.
   Le `ExecStartPre` du service corrige normalement le problème, mais en cas
   de blocage (ex. unité dans `start-limit-hit`) :
   ```sh
   sudo systemctl stop alloy
   sudo chown -R caddy:caddy /var/lib/alloy
   sudo systemctl reset-failed alloy
   sudo systemctl start alloy
   ```

**3. Grafana refuse de démarrer : `Datasource provisioning error: data
   source not found`.** Conflit d'UID en base SQLite après modification du
   provisionnement (typiquement passage d'un UID auto-généré à `uid = "loki"`).
   L'option `deleteDatasources` gère cela en théorie ; sinon nettoyage manuel :
   ```sh
   sudo systemctl stop grafana
   sudo sqlite3 /var/lib/grafana/grafana.db \
        "DELETE FROM data_source WHERE name='Loki';"
   sudo systemctl reset-failed grafana
   sudo systemctl start grafana
   ```

**4. Fichiers journaux Caddy obsolètes** (ancienne dénomination avec `:` ou schéma, ex.
   `access-http:__nextcloud.log`). Inoffensifs mais polluent la sortie du tail Alloy.
   Nettoyage après migration :
   ```sh
   sudo rm /var/log/caddy/access-{http,https}:__*.log
   sudo rm /var/log/caddy/access-:*.log     # variantes `:80`, `:443`
   sudo systemctl reload caddy              # optionnel
   ```
:::

* **enable** `bool` Déploie le serveur Loki + le datasource Grafana (co-localisé avec Grafana).
* **isClient** `bool` Déploie Alloy pour collecter les journaux d'accès Caddy locaux.
* **retentionTime** `str` Durée de rétention des journaux dans Loki (30 jours par défaut).

```nix
darkone.service.loki = {
  enable = config.darkone.service.monitoring.enable;
  isClient = config.services.caddy.enable && hasMonitoringHost;
  retentionTime = "720h";
};
```

### &#x2728; darkone.service.matrix

Serveur Matrix (synapse) DNF avec les ponts mautrix.

Les ponts (whatsapp, signal, telegram, messenger, discord) sont utilisables par
tout compte local&nbsp;: chaque utilisateur lie son propre compte distant en
discutant avec le bot du pont (`@whatsappbot`, `@signalbot`, ... puis `login`)&nbsp;;
les sessions sont isolées par utilisateur. Le `network.matrix.admin` déclaré
administre les ponts.

Le double puppeting utilise la méthode officielle appservice
(https://docs.mau.fi/bridges/general/double-puppeting.html)&nbsp;: un jeton
`doublepuppet` appservice partagé permet aux ponts d'envoyer les messages
provenant du distant en tant que vrai compte matrix de l'utilisateur. Secrets
sops requis&nbsp;: `mautrix-doublepuppet-as-token` et
`mautrix-doublepuppet-hs-token` (`openssl rand -hex 32` chacun).

Les jetons as/hs appservice de chaque pont sont fournis par sops plutôt
qu'auto-générés&nbsp;: le fichier d'enregistrement devient une fonction pure
des secrets, donc réinitialiser le répertoire d'état d'un pont n'invalide
jamais l'enregistrement que synapse a chargé (ce qui autrement nécessiterait
un wipe d'enregistrement + redémarrage de synapse et produirait des erreurs
«&nbsp;as_token was not accepted&nbsp;»).

{/* t:p ff353801b94ac1fc282cf6ce672fdc79a049f111f00671c5ac098fd143bba110 */}
#### Fédération

La fédération se configure via `darkone.service.matrix.federation`&nbsp;:

- `enable = false`&nbsp;: bloque toute fédération (liste blanche de domaines vide).
- `enable = true; whitelist = [ ]`&nbsp;: fédération ouverte avec tous les serveurs.
- `enable = true; whitelist = [ "ami.org" ]`&nbsp;: liste blanche (entrante + sortante).

La découverte reste verrouillée dans tous les cas (salles absentes des
annuaires distants, profils privés sur la fédération), donc le réseau est
joignable mais pas recherchable.

:::caution[Sans risque pour les enfants]
Une fédération ouverte laisse n'importe quel serveur fédéré envoyer des MP ou
inviter des utilisateurs locaux. Pour un réseau familial, remplissez
`whitelist` avec uniquement les serveurs de confiance.
:::

L'auto-inscription des proches (`friendRegistration.enable`) ouvre des comptes
locaux protégés par jeton aux côtés des utilisateurs OIDC Kanidm. Sans MAS, la
frappe d'un jeton passe par l'API admin de Synapse (un admin serveur est
requis)&nbsp;; avec MAS, frappez-le sur l'hôte avec
`sudo dnf-mas manage issue-user-registration-token`.

:::caution[Un seul espace de noms, identifiants permanents]
Les proches et les utilisateurs déclarés tirent du même espace de noms
`localpart`, et un identifiant matrix n'est jamais libéré (unique dans
`users` de MAS, la désactivation le conserve). Déclarer un utilisateur dont le
`localpart` a déjà été pris par un proche fait échouer leur première connexion
SSO&nbsp;: `on_conflict` reste sur `fail` ci-dessous, puisque toute autre
valeur remettrait le compte existant à quiconque enregistre un nom
correspondant en amont. Procédure de fusion dans le guide admin
(`operate/matrix.mdx`).
:::

#### Authentification nouvelle génération (MAS)

`mas.enable` délègue toute l'authentification au Matrix Authentication Service
(requis par Element X, la connexion par QR code, le portail self-service
`/account`). Kanidm reste la source d'identité : MAS devient le client OIDC
à la place de synapse, et synapse se contente de demander à MAS d'inspecter
les jetons. Servi sur le même vhost : MAS possède la racine + les points
d'entrée d'auth compat, synapse conserve `/_matrix/*` et
`/_synapse/*` ; la découverte client est automatique (synapse sert
lui-même `auth_metadata`), donc pas de changement well-known.

Secrets sops requis, tous créés par `just configure-admin-host` :
`mas-encryption-secret`, `mas-synapse-secret` et `mas-rsa-private-key`.

`dnf-mas` (racine) encapsule `mas-cli` pour l'administration côté hôte : jetons
d'inscription, `promote-admin`, `register-user`, `syn2mas`. MAS tourne avec
`DynamicUser` et lit ses secrets depuis les credentials systemd, qui
n'existent pas en dehors de l'unité en cours ; le wrapper reconstitue un
répertoire de credentials équivalent à partir des fichiers sops, ce qui
fonctionne que le service soit en marche ou non (syn2mas nécessite qu'il
soit arrêté).

:::danger[Immuable une fois démarré]
`mas-encryption-secret` et l'ULID du fournisseur Kanidm ne doivent jamais
changer après le premier démarrage de MAS (données chiffrées de la BDD /
liens de compte amont).
:::

:::caution[Migrer une instance existante]
Activer `mas.enable` sur un homeserver en service nécessite la migration
`syn2mas` (comptes, mots de passe, sessions, identifiants externes).
Déployez d'abord, puis, avec les deux services arrêtés : `sudo dnf-mas syn2mas check`,
`... migrate --dry-run`, `... migrate`. Les bridges n'ont pas besoin d'un
réenregistrement : synapse force MSC4190 sur chaque appservice dès que
l'auth est déléguée. Procédure dans
`.specs/matrix-authentication-service.md`.
:::

:::caution[Pas d'enregistrement par secret partagé sous MAS]
`/_synapse/admin/v1/register` de synapse (enregistrement par secret partagé)
est désactivé en mode délégué, ce dont se sert `just configure-alert-bot`
pour créer un compte bot manquant. Créez-le au préalable, ou avec
`sudo dnf-mas manage register-user`.
:::

* **enable** `bool` Activer le service matrix (synapse)
* **federation.enable** `bool` Autoriser la fédération serveur-à-serveur. Faux bloque toute la fédération.
* **federation.whitelist** `listOf str` Vide = fédérer avec tous les serveurs ; non vide = uniquement ces domaines (entrant + sortant).
* **mas.enable** `bool` Déléguer toute l'authentification au Matrix Authentication Service (support Element X).
* **matrixRtc.enable** `bool` Activer le backend MatrixRTC (LiveKit SFU) pour les appels de groupe Element Call.
* **friendRegistration.enable** `bool` Autoriser les amis à s'auto-inscrire avec un jeton d'invitation (contrôlé par jeton).
* **bridges.whatsapp.enable** `bool` Bridge Mautrix WhatsApp (connexion par QR code).
* **bridges.signal.enable** `bool` Bridge Mautrix Signal (connexion par QR code).
* **bridges.telegram.enable** `bool` Bridge Mautrix Telegram (connexion par numéro de téléphone).
* **bridges.messenger.enable** `bool` Bridge Mautrix Facebook Messenger (connexion par cookies).
* **bridges.discord.enable** `bool` Bridge Mautrix Discord (connexion par QR code, expérimental).

### &#x2728; darkone.service.nix-cache

Proxy de cache binaire Nix par zone (nginx `proxy_cache`).

Met en cache le cache Nix public (`cache.nixos.org`) sur la passerelle de la
zone afin qu'un déploiement à l'échelle de la flotte tire chaque closure du WAN
une seule fois, puis la sert sur le LAN à tous les autres hôtes. Les chemins
construits localement sont servis directement par `harmonia` (voir
`harmonia.nix`) ; ce proxy ne se place jamais devant harmonia.

:::note[Pourquoi nginx et pas un proxy de réécriture]
Un point de terminaison de cache fait face à **un** amont exactement. Un
`narinfo` et son `nar` sont deux requêtes distinctes et l'URL du `nar` ne dépend
pas de l'amont, donc un proxy multi-amont doit réécrire les URL `narinfo` dans
son propre espace de noms et les suivre dans une base de données (l'approche
qu'adoptait l'ancien proxy `ncps`, et la source de ses HTTP 500 « invalid nar
hash » récurrents). Avec un seul amont, il n'y a pas d'ambiguïté :
nginx met en cache `narinfo` + `nar` verbatim, les signatures transitent
intactes et les clients les vérifient. Pas de réécriture, pas de base de
données, ce bug est impossible par construction.
:::

:::tip[Topologie]
- serveur : l'hôte passerelle qui liste `nix-cache` dans `config.yaml` (un par
  zone). Exécute nginx sur l'IP interne, port `network.ports.nixCache`.
- clients : tous les hôtes de la zone locale. Leurs substituters deviennent les
  instances harmonia de la zone (directes, LAN/tailnet) plus ce proxy.
- clients nomades (`roaming = true`) : hôtes itinérants déplacés entre les zones.
  Leurs substituters sont les noms neutres de zone (`harmonia.dnf.internal`,
  `nix-cache.dnf.internal`) que le DNS de chaque zone résout vers ses propres
  services de cache (voir `service/dnsmasq.nix`), afin que le cache suive le
  portable.
:::

* **enable** `bool` le proxy de cache binaire Nix par zone (nginx devant cache.nixos.org)
* **maxSize** `str` Taille maximale du cache sur disque ; au-delà, nginx évince les entrées les moins récemment utilisées.
* **roaming** `bool` Hôte nomade (portable déplacé entre zones) : remplacer les
  substituters épinglés à la zone par les noms neutres de zone que le DNS de
  chaque zone résout vers ses propres services de cache. En dehors de toute
  zone DNF, les noms répondent NXDOMAIN instantanément et Nix retombe sur
  cache.nixos.org.

```nix
darkone.service.nix-cache = {
  enable = false;
  maxSize = "40g";
  roaming = false;
};
```

### &#x2728; darkone.service.prometheus

Serveur de supervision Prometheus avec escalade déclarative via Alertmanager.

:::tip[Prometheus &amp; Grafana]
Service autonome de métriques + d'alerting, indépendant de Grafana&nbsp;:

- Interroge chaque nœud de zone portant la feature `monitoring-node:<zone>`.
- Alertmanager route par gravité&nbsp;: warning -&gt; Matrix #warnings,
  critical -&gt; Matrix #incidents + mail (relais Postfix local).
- blackbox_exporter sonde l'atteignabilité de la passerelle / du tailnet / du DNS, ainsi que
  les passerelles des autres zones&nbsp;: Prometheus d'une zone réside sur sa propre
  passerelle, seuls les pairs peuvent donc signaler qu'un site entier a disparu.
- Les classes de nœud (critical/non-critical/disabled) proviennent des
  features `alert-*` ou du profil d'hôte (voir `dnf/lib/alerts.nix`).

`monitoring` (Grafana) requiert un `prometheus` sur le même hôte
(imposé par le `require` du générateur). L'interface web est exposée à
`https://prometheus.<zone>.<domain>` derrière oauth2-proxy (groupe `admins`),
ce qui corrige aussi les liens d'alerte renvoyant vers Prometheus.
:::

* **enable** `bool` Activer le serveur de métriques + d'alerting Prometheus
* **retentionTime** `str` Durée de rétention des métriques Prometheus
* **alerting.enable** `bool` Activer Alertmanager (activé par défaut une fois les salons Matrix d'alerte provisionnés)
* **alerting.matrix.enable** `bool` Diffuser les alertes dans les salons Matrix via le bot matrix-alertmanager
* **alerting.matrix.userId** `str` ID utilisateur Matrix du bot d'alerte (par défaut depuis network.matrix.bot)
* **alerting.matrix.warningsRoom** `str` ID du salon Matrix pour les avertissements (par défaut depuis network.matrix.warningsRoom)
* **alerting.matrix.incidentsRoom** `str` ID du salon Matrix pour les incidents (par défaut depuis network.matrix.incidentsRoom)
* **alerting.email.enable** `bool` Envoyer aussi les alertes critiques par mail (via le relais Postfix local)
* **alerting.email.to** `str` Destinataire des mails d'alerte critique
* **alerting.network.enable** `bool` Sonder l'atteignabilité réseau (passerelle/tailnet/DNS) avec blackbox_exporter
* **alerting.network.internetProbeTargets** `listOf str` Adresses IP externes que la passerelle de zone ping pour détecter une coupure WAN.
  Si toutes échouent, `ZoneInternetDown` se déclenche et inhibe les alertes
  de down (erronées) des hôtes accessibles uniquement via le WAN (par ex. le HCS).
  Liste vide = désactivé.
* **alerting.network.httpProbeUrls** `listOf str` URLs HTTP(S) sondées pour la vivacité (`ServiceEndpointDown`) et
  l'expiration du certificat TLS (`CertificateExpiringSoon`/`Critical`). Vide par
  défaut&nbsp;: lister les endpoints web publics à surveiller. Les redirections vers
  un login SSO (3xx) sont comptées comme up&nbsp;; l'expiration du certificat est lue
  depuis la poignée de main TLS quelle que soit la réponse HTTP.
* **alerting.silenceOnRebuild** `bool` Émettre le flag dnf-maintenance (textfile collector) afin que les reconstructions inhibent les alertes d'un nœud
* **alerting.thresholds** `attrs` Remplacer les seuils d'alerte de ressources (voir les valeurs par défaut dans dnf/lib/alerts.nix)
* **alerting.silences** `listOf submodule` Alertes connues et acceptées qui ne doivent jamais notifier. Chaque entrée devient
  une route Alertmanager vers le récepteur `null`&nbsp;: l'alerte se déclenche toujours
  et reste visible dans les interfaces Prometheus/Alertmanager/Grafana, elle ne
  parvient simplement plus à Matrix ni par mail.

  Déclaré sur l'hôte qui fait tourner Prometheus, car c'est là que les
  règles et routes de la zone sont générées. Un module consommateur à
  l'échelle de la flotte (`usr/modules/alerts.nix`) est l'endroit
  pratique&nbsp;: il est importé partout et ne prend effet que là où
  Prometheus tourne.

  :::caution[Dernier recours]
  Corriger ou reconfigurer d'abord la condition sous-jacente. Un silence masque un
  vrai signal, donc `reason` est obligatoire et la liste reste auditable.
  :::
  * **alert** `str` Nom de l'alerte à mettre en sourdine (label `alertname`). Toujours restreint, afin que les niveaux de gravité voisins restent armés.
  * **host** `nullOr str` Restreindre le silence à un seul hôte. Null met en sourdine l'alerte pour toute la flotte.
  * **matchers** `attrs` Étiquettes de correspondance exacte supplémentaires, combinées en ET avec les autres (par ex. le point de montage ou le device visé par l'alerte).
  * **reason** `str` Pourquoi cette alerte est acceptée, et ce qui rendrait le silence supprimable.

```nix
  retentionTime = "30d";
  alerting.enable = roomsReady;

  alerting.matrix.warningsRoom = "!warnings:domain.tld";
  alerting.matrix.incidentsRoom = "!incidents:domain.tld";
  alerting.email.enable = true;
  alerting.email.to = "admin@${network.domain}";
  alerting.network.enable = true;
  alerting.network.internetProbeTargets = [ ];
  alerting.network.httpProbeUrls = [ ];
  alerting.silenceOnRebuild = true;
  alerting.thresholds = { };
  alerting.silences = [ ];
  alerting.silences.alert = "DiskSpaceLow";
  alerting.silences.host = "srv-main";
```

### &#x2728; darkone.service.restic

Module de sauvegarde Restic&nbsp;: serveur REST + cibles de sauvegarde par hôte.

:::tip[Deux rôles, un module]
- Serveur&nbsp;: un hôte disposant de `restic` dans ses services config.yaml lance le serveur
  REST (`enableServer`) et stocke le dépôt de chaque hôte.
- Client&nbsp;: tout hôte avec `enable = true` déclare des `targets` de sauvegarde
  (chemin local ou `rest:http://restic.<zone>:<port>`).
:::

:::note[Deux mots de passe, ne pas les confondre]
- Phrase de passe du dépôt&nbsp;: `restic-password-<zone>`, chiffre le contenu du dépôt.
- Identifiant REST&nbsp;: `restic/<hostname>/rest-password` par hôte, authentifie
  l'hôte auprès du serveur REST.

Les deux sont créés par `just configure-admin-host` (idempotent), qui lit
les hôtes et zones déclarés dans la flotte.
:::

Exemple (configuration machine)&nbsp;:

```nix
darkone.service.restic = {
  enable = true;
  targets = [
    { name = "main"; root = "rest:http://restic.my-zone.my-domain.tld:8888";
      zone = "ag"; categories = [ "system" "nfs" ]; }
  ];
};
```

Structure du dépôt par cible&nbsp;: un dépôt par catégorie, nommé d'après celle-ci.

```
<root>/<hostname>/system  <- catégorie "system" (/ moins les exclusions)
<root>/<hostname>/nfs     <- catégorie "nfs"    (/srv/nfs/<...>)
<root>/<hostname>/medias  <- catégorie "medias" (/srv/medias/<...>)
```

:::caution[Le chemin du dépôt fait exactement deux niveaux de profondeur]
Le serveur REST sert des dépôts à au maximum deux composantes sous son `--path`&nbsp;:
`<hostname>/medias` répond, `<hostname>/srv/medias` renvoie 404 et restic
affiche un message trompeur `repository does not exist`. Le sous-chemin est donc
le nom nu de la catégorie, jamais le répertoire source. Une structure identique pour
les cibles locales et REST permet de déplacer un dépôt de l'un vers l'autre sans renommage.
:::

:::note[Un serveur REST inaccessible ignore l'exécution]
Chaque cible `rest:` porte une sonde d'atteignabilité `ExecCondition`. Une sauvegarde
dont le serveur est arrêtée est *ignorée*, jamais en échec&nbsp;: pas de
SystemdUnitFailed nocturne, pas de quart d'heure de tentatives restic, et pas de `initialize`
créant un dépôt vide contre un endpoint mort. La sauvegarde manquante apparaît
néanmoins via ResticBackupStale / ResticBackupCritical, qui surveillent la
dernière exécution réussie.
:::

:::caution[`listenAll` élargit la liaison, pas le pare-feu]
Le serveur lie `params.ip`, c.-à-d. l'adresse LAN sur une passerelle. Les clients
l'atteignant depuis une autre zone via le tailnet nécessitent `listenAll = true`
(liaison sur `0.0.0.0`). Le pare-feu reste la frontière&nbsp;: `lan0` reçoit le port via
`getInternalInterfaceFwPath`, `tailscale0` est déjà une interface de confiance sur
une passerelle, et le WAN ne l'ouvre jamais.
:::

:::danger[Migrer les dépôts créés avant cette structure]
Les dépôts écrits lorsque le sous-chemin reflétait le répertoire source se trouvent sous
`<hostname>/srv/{nfs,medias}`. Renommez-les sur le serveur avant la prochaine exécution&nbsp;:
`initialize = true` créerait sinon un dépôt vide au nouveau chemin et
lancerait silencieusement un re-semis complet.

```sh
mv <data-dir>/<hostname>/srv/medias <data-dir>/<hostname>/medias
rmdir <data-dir>/<hostname>/srv
```
:::

* **enable** `bool` Activer le client de sauvegarde restic
* **enableDryRun** `bool` Mode simulation
* **enableWaitRemoteFs** `bool` Lancer les sauvegardes uniquement après remote-fs.target
* **enableServer** `bool` Activer le serveur REST restic
* **listenAll** `bool` Lier le serveur REST sur 0.0.0.0 (clients hors site)
* **serverDataDir** `str` Racine de stockage locale du serveur REST (dépôts de tous les hôtes)
* **targets** `listOf submodule` Destinations de sauvegarde pour cet hôte (chemin local ou URL REST)
  * **name** `str` Identifiant de cible, utilisé dans les noms de sauvegarde/unités (&lt;category&gt;-&lt;name&gt;)
  * **root** `str` Racine du dépôt&nbsp;: chemin local ou URL REST
  * **zone** `str` Zone sélectionnant la phrase de passe du dépôt (restic-password-&lt;zone&gt;)
  * **categories** `listOf ( enum [ "system" "nfs" "medias" ] )` Contenu à sauvegarder vers cette cible
* **nfsPaths** `listOf str` Répertoires NFS (/srv/nfs/&lt;xxx&gt;) inclus dans la catégorie 'nfs'
* **mediasPaths** `listOf str` Répertoires Médias (/srv/medias/&lt;xxx&gt;) inclus dans la catégorie 'medias'

```nix
darkone.service.restic = {
  enable = false;
  enableDryRun = false;
  enableWaitRemoteFs = false;
  enableServer = false;
  listenAll = false;
  serverDataDir = "/mnt/backup/restic";
  targets = [ ];
  targets.name = "main";
  targets.root = "rest:http://restic.${zone.domain}:${toString srvPort}";
  targets.zone = zone.name;
  targets.categories = [ ];
  nfsPaths = [ ];
  mediasPaths = [ ];
};
```

### &#x2728; darkone.service.tailscale

Service client Tailscale pour le HCS.

:::note
Un client tailscale pour connecter un hôte externe au HCS.
Ne pas l'utiliser pour connecter une passerelle d'un sous-réseau tailnet.

```nix
darkone.service.tailscale = {

  isGateway = false;
  isExitNode = false;
  selfHeal.enable = true;
  autoPauseOnLan.enable = false;
};
```
