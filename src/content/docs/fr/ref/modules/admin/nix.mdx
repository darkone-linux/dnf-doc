Configuration NixOS pour l’ordinateur administrateur du réseau local.

:::tip[Ferme de compilation (constructeurs distants)]
Un hôte d’administration compile localement la fermeture de chaque nœud et la pousse (`buildOnTarget` vide, voir `just/project.just`) ; c’est donc la machine qui effectue réellement la compilation. Tout hôte de la flotte marqué `build-farm` dans `config.yaml` devient l’une de ses `nix.buildMachines`, accessible par SSH en tant qu’utilisateur de déploiement `nix`.

La délégation est délibérément restreinte. `mandatoryFeatures` (`big-parallel` par défaut) signifie que la ferme ne reçoit **que** les dérivations déclarant `requiredSystemFeatures = [ "big-parallel" ]` — kernel, chromium, firefox, llvm, rustc… c.-à-d. les longues compilations pour lesquelles on souhaite un hôte puissant. Tout le reste reste local, ce qui compte lorsque la ferme se trouve derrière une liaison montante lente : seule la sortie demandée transite en retour.

Ne retirez jamais `big-parallel` des `nix.settings.system-features` de cet hôte pour forcer la délégation : le conserver signifie qu’une ferme injoignable fait refuser le hook de compilation et que la dérivation est simplement compilée localement au lieu d’échouer.

:::caution[Clé de déploiement requise]
`sshKey` pointe vers la clé de déploiement partagée que `just configure-admin-host` génère dans le répertoire personnel de l’utilisateur `nix`. Les hôtes d’administration la possèdent par construction ; un hôte qui active ce module sans la clé enregistre des échecs SSH à chaque compilation déléguée.
:::

:::tip[Commandes `darkone` et `dnf-generator`]
Le paquet du générateur (`pkgs.dnf-generator`, entrée de flake `dnf-generator`) est installé avec l’outillage d’administration : `darkone add ...` pilote le projet depuis l’hôte d’administration. x86_64 uniquement : sur une autre architecture, le paquet est absent et l’hôte s’évalue sans lui.
:::

:::note[Pourquoi pas un cache binaire]
Un `harmonia` sur la ferme partagerait ses résultats de compilation, mais harmonia sert l’intégralité du `/nix/store` et ne peut pas exprimer « uniquement ce que j’ai compilé » : il capte du trafic auquel le cache public devrait répondre. Le délestage est une question d’ordonnancement des compilations, pas de substitution — d’où `buildMachines` ici et une priorité de substitueur de dernier recours dans `service/nix-cache.nix`.
:::

## Options

* **enable** `bool` Active les outils de construction de la configuration NIX
* **enableNh** `bool` Active l'outil de gestion nix helper (nh)
* **remoteBuilders.enable** `bool` Déporte les compilations vers les hôtes de la flotte marqués `build-farm` dans
  `config.yaml`. Sans effet tant qu'aucun hôte ne porte ce marqueur.
* **remoteBuilders.maxJobs** `int` Nombre de créneaux de compilation parallèles à utiliser sur chaque ferme.
* **remoteBuilders.speedFactor** `int` Facteur de vitesse relatif d'une ferme, par rapport à cet hôte.
* **remoteBuilders.mandatoryFeatures** `listOf str` Fonctionnalités qu'une dérivation DOIT exiger pour qu'une ferme lui soit proposée. C'est ce qui
  évite que les petites dérivations transitent par une liaison distante (potentiellement lente).
  Une liste vide envoie toute dérivation éligible à la ferme.
* **remoteBuilders.supportedFeatures** `listOf str` Fonctionnalités système qu'une ferme peut fournir.
* **remoteBuilders.systems** `listOf str` Plateformes pour lesquelles une ferme compile. Explicite plutôt que déduit : `hosts.nix`
  ne porte une architecture que lorsqu'elle diffère de la valeur par défaut.

```nix
darkone.admin.nix = {
  enable = false;
  enableNh = false;
  remoteBuilders.enable = true;
  remoteBuilders.maxJobs = 8;
  remoteBuilders.speedFactor = 2;
  remoteBuilders.mandatoryFeatures = [ ];
  remoteBuilders.supportedFeatures = [ ];
  remoteBuilders.systems = [ ];
};
```
