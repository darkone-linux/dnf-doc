### &#x1F5BC; darkone.graphic.gnome

Environnement GNOME pré-configuré avec ses dépendances.

:::note[Trousseau de connexion après `just passwd`]
PAM déverrouille le trousseau de connexion avec le mot de passe de session,
qu'un changement effectué par l'administrateur ne peut pas rechiffrer (l'ancien
mot de passe est inconnu). À la connexion suivante par mot de passe, le trousseau
tombe&nbsp;: GNOME le recrée, vide, sur le nouveau mot de passe. Aucune invite, et
l'ancien mot de passe n'ouvre plus rien.
:::

:::caution[Secrets du trousseau perdus à chaque changement de mot de passe admin]
Les applications redemandent leurs identifiants. Pour y renoncer, au profit d'un
trousseau doté de son propre mot de passe&nbsp;: `darkone.home.gnome.keepKeyring`.
:::

* **enable** `bool` WM GNOME pré-configuré
* **enableDashToDock** `bool` Plugin Dash to dock
* **enableLightDM** `bool` Activer LightDM à la place de GDM
* **enableGdmSelector** `bool` Liste d'utilisateurs GDM à la place d'une connexion saisie
* **enableCaffeine** `bool` Désactiver la mise en veille automatique
* **enableGsConnect** `bool` Communication avec les appareils
* **enableOnlineServices** `bool` Comptes en ligne, CalDAV, CardDAV...
* **xkbVariant** `nullOr str` Variante de clavier&nbsp;; null suit la locale (`config/locales.json`), comme la disposition.
* **screenBlankDelay** `ints.unsigned` Délai d'extinction de l'écran en secondes (0 = jamais). Les portables le remplacent par 900 (15 min).
* **cursorSize** `ints.positive` Taille par défaut du pointeur en pixels, modifiable par l'utilisateur (Paramètres &gt; Accessibilité).

```nix
darkone.graphic.gnome = {
  enable = false;
  enableDashToDock = false;
  enableLightDM = false;
  enableGdmSelector = false;
  enableCaffeine = false;
  enableGsConnect = false;
  enableOnlineServices = false;
  xkbVariant = null;
  screenBlankDelay = 1800;
  cursorSize = 24;
};
```

### &#x1F5BC; darkone.graphic.qemu

VMs de test QEMU pontées sur le réseau DNF

Utilisé par `dnf/scripts/vm-start.sh`.
Enslave la carte filaire dans un pont NetworkManager et laisse des utilisateurs
non privilégiés connecter des VMs au pont via le `qemu-bridge-helper` setuid.
Une VM obtient alors son adresse depuis la passerelle de zone comme une machine
physique, donc `just full-install <host> nixos <ip>` l'atteint.

:::caution[Adresse MAC du pont]
`bridge.macAddress` doit être la MAC de la carte elle-même&nbsp;: le pont reprend
l'IP de l'hôte, et la réservation DHCP de la zone (`mac` dans `etc/config.yaml`)
correspond dessus.
:::

:::note[Activation]
Déployer ne charge que les profils. Redémarrer, ou `nmcli connection up br0`, pour
déplacer l'IP de l'hôte sur le pont.
:::

```nix
darkone.graphic.qemu = {
  enable = true;
  bridge.interface = "enp2s0";
  bridge.macAddress = "aa:bb:cc:dd:ee:ff";
};
```

* **enable** `bool` VMs de test QEMU pontées sur le réseau DNF
* **bridge.name** `str` Interface du pont dans laquelle les VMs se connectent.
* **bridge.interface** `str` Carte filaire esclavagée dans le pont.
* **bridge.macAddress** `str` Adresse MAC du pont&nbsp;: celle de la carte elle-même, pour conserver la réservation DHCP de la zone.

```nix
darkone.graphic.qemu = {
  enable = false;
  bridge.name = "br0";
  bridge.interface = "enp2s0";
  bridge.macAddress = "aa:bb:cc:dd:ee:ff";
};
```

### &#x1F5BC; darkone.graphic.remote-desktop

Bureau à distance pour l'administration : se connecter à une session graphique ouverte, ou en ouvrir une, via RDP.

:::note[Rien n'est installé, rien n'est exposé]
`gnome-remote-desktop` est déjà fourni et tourne sur chaque hôte GNOME (le
module GNOME de nixpkgs l'active par défaut) ; il reste simplement inactif
tant que son backend RDP n'est pas activé. Ce module n'ajoute aucun démon et
n'ouvre aucun port : il installe `dnf-remote-desktop`, un outil d'aide que la
recette `just remote-desktop` appelle par ssh pour armer une session, puis la
désarmer. Le listener RDP ne se lie que pendant qu'une session de support
tourne et n'est atteignable que via un tunnel ssh : le pare-feu reste fermé.
:::

:::tip[Trois modes]
`ro` reflète l'écran en lecture seule, `rw` le reflète et prend le contrôle. Les deux
exigent qu'un utilisateur soit connecté et échouent sinon, plutôt que de fournir
discrètement une session privée qu'un administrateur ayant demandé à *regarder*
un utilisateur n'attendrait pas. `login` est cette session privée, demandée
explicitement : un écran de connexion GDM servi par le démon système, pour
quiconque se trouve devant la machine.
:::

:::tip[Trois backends, un seul protocole]
Une session GNOME Wayland est servie par `gnome-remote-desktop`, piloté par
`grdctl` dans le propre bus du propriétaire de la session. Une session
Cinnamon X11 (le poste UMI à entrée multimodale, car GNOME 50 a abandonné sa
session Xorg) est servie par `freerdp-shadow-cli` sur l'écran existant. Une
session `login` est servie par le même `gnome-remote-desktop`, dans son mode
runtime système, qui confie le client à GDM. Même protocole, même client,
`ro`/`rw` imposés côté serveur.
:::

:::caution[Se connecter, c'est s'emparer de l'écran de quelqu'un]
La session cible appartient à un utilisateur qui est très probablement assis
devant elle. GNOME affiche un indicateur de partage, mais rien ne demande de
consentement : c'est un outil de support pour les machines que vous
administrez, et l'activer sur un hôte est une déclaration volontaire et
auditable dans `config.yaml`. `login` est le mode discret : il ne touche
jamais à l'écran du moniteur.
:::

:::tip[Activation]
Un hôte accepte via sa liste `features` dans `config.yaml` :
`features: [ "remote-desktop", ... ]`. Contrairement à `services:`, les
features sont héritées par les groupes d'hôtes modélisés (`range:` / `hosts:`),
ainsi toute une famille de bureaux identiques est couverte par une ligne.
:::

* **enable** `bool` Accès au support du bureau à distance (piloté par la feature de l'hôte, éviter d'activer manuellement).
* **timeout** `ints.positive` Minutes avant qu'une session de support armée ne se referme seule.
* **embedCursor** `bool` Patche gnome-remote-desktop pour que le curseur soit composité dans la
  vidéo. Sans cela, l'observateur ne voit pas où pointe l'utilisateur,
  ce qui prive le mode lecture seule de son intérêt. Coûte une
  recompilation locale de gnome-remote-desktop.

```nix
darkone.graphic.remote-desktop = {
  enable = hasFeature;
  timeout = 60;
  embedCursor = true;
};
```

### &#x1F5BC; darkone.graphic.supertuxkart

SuperTuxKart avec les configurations pour jouer en réseau local.

:::tip
À utiliser conjointement avec le module de jeux de homemanager&nbsp;!
:::

:::note[Circuits partagés]
Le partage des circuits vit dans `service/stk.nix`. `enableNfsClient` et
`nfsServer` sont les seuls réglages nécessaires sur un hôte&nbsp;: ils câblent
`darkone.service.stk.{enableClient,serverName}`, ainsi une configuration machine
n'a jamais à nommer deux modules pour un seul jeu.
:::

:::tip[Jouer entre zones]
Les ports de jeu et de découverte acceptent tous les préfixes de zone et le tailnet. La découverte
par diffusion reste dans la zone&nbsp;: depuis une autre zone, se connecter avec «&nbsp;Enter server
address&nbsp;» (IP du serveur, port 2759).
:::

:::caution[Pare-feu à l'échelle de la flotte]
Les sources sont filtrées sur les préfixes de flotte, jamais sur une interface&nbsp;: un hôte STK qui
possède aussi une adresse WAN ne publie pas le jeu sur celle-ci.
:::

* **enable** `bool` SuperTuxKart + configuration du pare-feu
* **enableNfsClient** `bool` Monte les circuits partagés du serveur `stk` de la zone
* **nfsServer** `nullOr str` Nom d'hôte servant les circuits, par défaut l'hôte du service `stk` de la zone

```nix
darkone.graphic.supertuxkart = {
  enable = false;
  enableNfsClient = false;
  nfsServer = null;
};
```
