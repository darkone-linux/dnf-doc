Le réseau DNF se comprend à deux échelles : une **zone** locale isolée, puis
plusieurs zones reliées par un **VPN** maillé. Le vocabulaire est défini dans
[Concepts](/fr/doc/admin-guide/understand/concepts/).

{/* t:p dc9534f835e0e09db41110a71aa8e46e59668b5a9a710b8379ec1c2ae465ed93 */}
## Réseau simple (une zone)

Une zone, c'est une passerelle et ses machines.

```d2
style.fill: transparent
direction: down

net: Internet { shape: cloud }

gw: Passerelle {
  fw: NAT + Pare-feu
  dns: dnsmasq\nDNS + DHCP
  fw -> dns
}

lan: Zone locale {
  pc: Postes
  srv: Serveur { shape: cylinder }
}

net -> gw.fw: WAN
gw.dns -> lan.pc: LAN
gw.dns -> lan.srv: LAN
```

- La passerelle partage Internet (NAT) et protège la zone (pare-feu).
- `dnsmasq` distribue les adresses (DHCP) et résout les noms locaux
  (`<hôte>.<zone>`).
- Côté Internet (WAN), tout est fermé. Côté local (LAN), seuls SSH, DNS, DHCP et
  la page d'accueil sont ouverts.

## Filtrage des publicités (AdGuardHome)

Service optionnel, activé sur la passerelle. Il s'intercale devant `dnsmasq`.

```d2
style.fill: transparent
direction: down

pc: Poste

agh: AdGuardHome\nport 53, filtrage { shape: hexagon }

dns: dnsmasq\nnoms locaux { shape: cylinder }
up: DNS externe\nchiffré { shape: cloud }

pc -> agh: Requête DNS
agh -> dns: Noms locaux
agh -> up: Reste, filtré
```

- AdGuardHome devient le résolveur DNS des postes (port 53).
- Il bloque publicités et traceurs, et chiffre les requêtes vers l'extérieur.
- `dnsmasq` recule sur un port interne et garde les noms locaux et le DHCP.

## Réseau étendu (VPN)

Plusieurs zones sont reliées par un VPN maillé, coordonné par le serveur de
coordination (HCS).

```d2
style.fill: transparent
direction: down

hcs: Coordination\nHeadscale (HCS) { shape: cylinder }

zoneA: Zone A {
  gwa: Passerelle
  la: Postes
  gwa -> la
}
zoneB: Zone B {
  gwb: Passerelle
  lb: Postes
  gwb -> lb
}
ext: Machine distante

hcs -> zoneA.gwa: VPN
hcs -> zoneB.gwb: VPN
hcs -> ext: VPN
zoneA.gwa <-> zoneB.gwb: Maillage
```

- Le HCS (Headscale) est public et orchestre le maillage.
- Chaque passerelle est *subnet router* : elle publie le
  sous-réseau de sa zone dans le VPN.
- Les zones se voient entre elles ; les machines distantes (smartphone, PC)
  rejoignent le réseau via Tailscale.
- Un résolveur pivot sur le HCS aiguille chaque zone vers son propre DNS.

<Aside type="note" title="VPN optionnel">
Le maillage n'est activé que si `network.coordination.enable` est vrai dans
`etc/config.yaml`. Sans lui, les zones restent locales et indépendantes.
</Aside>

## Ce qui traverse une passerelle

Une passerelle route, et un paquet routé ne passe **jamais** par les règles
d'ouverture de ports&nbsp;: celles-ci ne concernent que ce qui lui est adressé à
elle. Les deux filtrages sont indépendants.

Trois flux seulement traversent une passerelle&nbsp;:

| Flux | Usage |
|---|---|
| Zone → WAN | Partage d'Internet (NAT) |
| Zone ↔ VPN | Les autres zones, les machines distantes |
| Réponses et redirections de ports | Retour du trafic sortant, `forwardPorts` |

Tout le reste est jeté. En particulier, une machine d'Internet qui poserait une
route statique vers le sous-réseau d'une zone n'atteint rien&nbsp;: sans ce
filtrage, une passerelle à adresse publique laisserait passer.

Un besoin de routage supplémentaire s'ajoute dans le fichier de l'hôte&nbsp;:

```nix
networking.firewall.extraForwardRules = ''
  iifname "lan0" oifname "wg0" accept
'';
```

## Accès SSH selon le rôle

Le port 22 n'est jamais ouvert « partout ». Une règle sans nom d'interface
s'applique à **toutes** les interfaces, WAN compris&nbsp;: sur une passerelle,
cela publierait le SSH sur Internet.

| Hôte | SSH joignable depuis |
|---|---|
| Passerelle de zone | son réseau local et le VPN |
| Hôte de la zone globale (HCS) | Internet — décision assumée, il porte le VPN |
| Machine de zone (poste, serveur) | sa seule interface, donc le réseau local |

Conséquence pratique&nbsp;: **une passerelle ne répond pas au SSH depuis
Internet.** L'accès distant passe par le VPN&nbsp;:

```sh
just enter gw
```

<Aside type="caution" title="Une passerelle n'ouvre aucun port sans interface">
Le profil `gateway` refuse de construire si un port est ouvert sans nom
d'interface. Un service de passerelle se déclare sur `lan0` (la zone) ou
`tailscale0` (le VPN)&nbsp;; un port réellement public se pose sur l'interface
WAN, explicitement.
</Aside>

## Noms et résolution DNS

Trois familles de noms cohabitent sur le réseau. Toutes sont générées depuis
`etc/config.yaml`.

| Nom | Forme | Portée | Exemple |
|---|---|---|---|
| **Nom simple** | `<hôte>` | Tout le réseau interne | `serveur` |
| **FQDN de zone** | `<nom>.<zone>.<domaine>` | Tout le réseau interne | `cloud.maison.domain.tld` |
| **Service global** | `<nom>.<domaine>` | Internet inclus | `git.domain.tld` |

- **Noms simples** : ce sont les **machines** (hôtes déclarés). Résolus partout
  sur le réseau, vers l'adresse réelle de la machine, quelle que soit sa zone.
- **FQDN de zone** : ce sont les **services d'une zone**. Ils pointent vers la
  passerelle de cette zone, qui les sert via son proxy inverse.
- **Services globaux** : les services marqués `global` dans `etc/config.yaml`.
  Exposés sur le HCS avec un **DNS public** : joignables depuis n'importe où.

Qui résout quoi :

- `dnsmasq`, sur **chaque passerelle**, connaît tous les noms internes (machines
  et services de **toutes** les zones) : il résout les noms simples et les FQDN.
- La zone courante est résolue localement ; les autres zones et le domaine global
  sont aiguillés vers la bonne passerelle, ou vers le résolveur pivot du HCS.
- Les noms publics (Internet) partent vers les DNS chiffrés en amont, filtrés par
  AdGuardHome s'il est activé.

### Le résolveur pivot (HCS)

Sur le serveur de coordination (HCS), un **résolveur pivot** centralise la
résolution interne du VPN. Il connaît le découpage en zones et se contente
d'aiguiller&nbsp;:

- chaque FQDN de zone part vers la passerelle de sa zone&nbsp;;
- le reste part vers un DNS externe chiffré.

Toutes les machines du VPN l'interrogent sur l'adresse VPN du HCS. C'est lui qui
relie les zones entre elles pour la résolution des noms.

### Résolution depuis l'extérieur

Une machine hors de toute zone (portable en déplacement, smartphone) rejoint le
réseau par le VPN. Sa résolution DNS est **scindée** (split-DNS) selon la nature
du nom demandé&nbsp;:

- **noms internes** : dirigés, à travers le VPN, vers le résolveur pivot du HCS,
  qui les aiguille ensuite vers la bonne passerelle&nbsp;;
- **noms publics** : résolus par le résolveur local du réseau visité (box, point
  d'accès public), sans passer par le VPN.

```d2
style.fill: transparent
direction: down

pc: Machine itinérante { shape: person }
split: Aiguillage split-DNS { shape: diamond }

pivot: Résolveur pivot\nHCS { shape: cylinder }
gwa: Passerelle zone A
gwb: Passerelle zone B
local: Résolveur local\ndu réseau visité { shape: cloud }
net: Internet { shape: cloud }

pc -> split
split -> pivot: Noms internes\n(via VPN)
split -> local: Noms publics
pivot -> gwa: Zone A
pivot -> gwb: Zone B
local -> net
```

:::note[Pourquoi ne pas router les noms publics par le VPN]
Tout faire passer par le résolveur du HCS tunnelise l'intégralité du DNS dans le
VPN. Si le chemin du VPN faiblit (relais intermédiaire, UDP bloqué), plus rien ne
se résout. Laisser les noms publics au résolveur local préserve l'accès Internet
même quand le lien VPN est instable.
:::

:::tip[Poste rebranché dans une zone]
Un portable itinérant rebranché en filaire dans une zone n'a plus besoin du VPN
pour l'atteindre. Son client VPN se met alors en pause pour rendre la main à la
passerelle locale (résolution et routage directs), puis se réactive au départ.
:::

## Machines hors de leur zone

Une machine est déclarée dans **une** zone, mais elle ne s'y trouve pas toujours.
Un portable part en déplacement. Une passerelle neuve est installée depuis une
autre zone, avant d'être livrée sur place.

Sans disposition particulière, cette machine reçoit une adresse quelconque de la
plage DHCP de la zone visitée, et son nom continue de désigner son adresse
d'origine, injoignable depuis là. Rien ne permet de la joindre de façon fiable.

```d2
style.fill: transparent
direction: right

maison: Zone maison (10.0) {
  gwa: Passerelle
  pc: portable\n10.0.2.4
  gwa -> pc
}

atelier: Zone atelier (10.1) {
  gwb: Passerelle
  res: portable en visite\n10.1.6.3
  gwb -> res: Réservé sur sa MAC
}

maison.pc -> atelier.res: Déplacement
```

### Une adresse réservée dans chaque zone

Chaque zone réserve le bloc `<préfixe>.6.x` aux machines des **autres** zones.
Le générateur y place une réservation DHCP pour chaque adresse MAC connue du
réseau qui n'appartient pas à la zone.

Le numéro est attribué à l'échelle du réseau entier&nbsp;: une machine garde le
**même dernier octet** dans toutes les zones où elle passe.

| Machine | Zone déclarée | Chez elle | En visite dans `atelier` |
|---|---|---|---|
| `portable` | `maison` | `10.0.2.4` | `10.1.6.3` |
| `serveur` | `atelier` | `10.1.1.2` | (elle y est chez elle) |

L'adresse est donc connue **avant** que la machine ne démarre, sans rien
observer sur le réseau.

{/* t:p 9bcaa563c5cc08308eaeb63d5c2d77d641f7ace70f95da33ca19f2311f041d2f */}
### Un nom qui désigne l'endroit

La réservation vient avec un nom DNS dans la zone visitée. Le nom simple, lui,
ne change pas de sens.

| Nom | Résout vers |
|---|---|
| `portable` | son adresse d'origine, partout sur le réseau |
| `portable.atelier.domain.tld` | son adresse dans la zone `atelier` |

### Un bail qui ne bouge plus

`dnsmasq` indexe les baux sur la seule **adresse MAC**, et non sur l'identifiant
client DHCP.

La raison&nbsp;: un même équipement n'annonce pas le même identifiant selon le
système qui tourne dessus. Une image d'installation et le système installé
passent pour deux machines différentes, et reçoivent deux adresses. En
s'appuyant sur la MAC, l'adresse ne change plus entre l'installation et le
premier démarrage réel.

<Aside type="note" title="Machines sans adresse MAC déclarée">
La réservation exige une clé `mac` dans `etc/config.yaml`. Sans elle, la machine
reste joignable chez elle, mais pas ailleurs. `just install` la réclame avant
tout formatage&nbsp;; `just host-info <hôte> <ip>` la relève sur une machine
démarrée.
</Aside>

<Aside type="caution" title="L'adresse fixe reste hors de la plage dynamique">
Une réservation `dhcp-host` posée **dans** la plage `dhcp-range` n'est honorée
que tant que l'adresse n'a pas déjà été prêtée à quelqu'un d'autre. Sinon la
machine en reçoit une autre, en silence, au pire moment&nbsp;: le premier
démarrage après une installation. Le générateur refuse désormais une adresse
fixe qui tombe dans la plage dynamique de sa zone.
</Aside>

### Ce que fait l'outillage

Les recettes d'installation calculent l'adresse toutes seules. Elles identifient
d'abord la zone où se trouve la machine d'administration, à partir de sa
**passerelle par défaut réelle** et non de sa zone déclarée (un portable
d'administration est précisément ce qui se déplace), puis en déduisent l'adresse
de la cible.

Cette adresse est ensuite **vérifiée avant d'être utilisée**&nbsp;: une
réservation dit où la machine *serait* si elle était branchée ici, ce qui est
juste pendant l'installation et faux dès qu'elle est rentrée chez elle. Si rien
ne répond à l'adresse réservée, l'outillage retombe sur le nom de l'hôte
lorsque celui-ci répond — port 22, ou 2222 pour une machine chiffrée en attente
dans son initrd. Si rien ne répond nulle part, l'adresse réservée est conservée&nbsp;:
c'est celle sur laquelle l'installateur apparaîtra.

<Aside type="caution" title="Recettes de gestion hors zone">
Avant cette vérification, `just enter` et `just luks` visaient l'adresse
réservée même pour un hôte resté chez lui, joint par le VPN. `just enter`
abandonnait&nbsp;; `just luks` avertissait puis sortait avec 0, alors que
Colmena — qui s'adresse aux nœuds par leur nom — déployait sans rien remarquer.
Un `just apply` lancé derrière installait donc un chargeur de démarrage sans la
clé d'hôte de l'initrd, et donc sans déverrouillage LUKS à distance.
</Aside>

### Retrouver une machine après un redémarrage

Le calcul ci-dessus donne **une** adresse pour démarrer. Après le redémarrage
qui clôt une installation, ce n'est plus suffisant&nbsp;: la machine peut
réapparaître ailleurs, ou n'être pas encore vraiment démarrée.

`just full-install` sonde donc **toutes** les adresses connues de l'hôte, dans
cet ordre, sur les ports 22 **et** 2222, et poursuit sur la première qui
répond&nbsp;:

1. l'adresse utilisée pour l'installation ;
2. l'adresse fixe de sa zone d'origine, celle que le DNS publie partout ;
3. l'adresse de passage que réserve la zone locale ;
4. son nom, résolu par la passerelle locale.

Une réponse sur le port 2222 signifie que l'hôte attend sa passphrase LUKS dans
son initrd&nbsp;: `just unlock` y répond sans intervention. Voir [Chiffrement
des disques](/fr/doc/admin-guide/operate/luks/).

Reste le déploiement&nbsp;: [Colmena](https://colmena.cli.rs/) s'adresse à un
nœud par son nom, qui désigne l'adresse d'origine. Pour un hôte en visite,
`just configure` pose donc une redirection SSH temporaire, retirée en fin
d'installation ou à la main&nbsp;:

```sh
just roaming             # afficher les redirections en cours
just roaming-clear       # toutes les retirer
```
