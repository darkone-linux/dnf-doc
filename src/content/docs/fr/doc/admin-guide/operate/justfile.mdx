Les commandes ci-dessous sont toutes exécutées avec [`just`](https://just.systems/man/).

```sh title=Utilisation
just <commande> <arguments>
```

Chaque commande est préfixée d'une icône indiquant son contexte d'utilisation :

- 💠 **Commun** : disponible dans tous les contextes.
- 🔆 **Framework** : spécifique au framework DNF amont (`dnf/`).
- ✳️ **Projet** : spécifique au projet consommateur (mon réseau).
- 🔗 **Co-développement** : projet consommateur qui contient un clone du framework.

:::caution[Élévation des privilèges]
L'essentiel des commandes s'exécute avec l'utilisateur qui administre le projet, mais
certaines d'entre elles élèvent les privilèges sur l'utilisateur `nix` (`sudo -u nix ...`).
:::

:::tip[Commandes clés]
Les commandes marquées d'une ⭐ sont les plus utiles au quotidien.
:::

## Commandes disponibles

Les recettes vivent dans `dnf/just/`. Le `Justfile` du projet importe **un**
fichier d'amorçage, qui détermine les commandes disponibles en fonction du
contexte.

| Contexte | Ligne du `Justfile` | Commandes |
|---|---|---|
| Framework | `import 'just/dnf.just'` | 💠 🔆 |
| Projet consommateur | `import? 'dnf/just/project.just'` | 💠 ✳️ |
| Co-développement | `import 'dnf/just/codev.just'` | 💠 ✳️ 🔗 |

Dans un projet consommateur, `dnf/` est le lien vers le store Nix posé par
`nix run .#init`. Le `?` de `import?` laisse `just` démarrer tant que ce lien
n'existe pas.

Le co-développement remplace ce lien par un clone git du framework. Les recettes
🔆 `unit-tests`, `check-recipes`, `simulate`, `simulate-debug`, `fixtures` et
`pkg-update` s'y lancent aussi depuis la racine. Les modèles de projet portent
la ligne `codev.just`, commentée.

:::note[Adaptation au contexte]
Un projet se reconnaît à son `etc/config.yaml`, un clone du framework à
`dnf/.git`. Un `dnf/` lié au store est en lecture seule&nbsp;: `generate`,
`format` et `check` le laissent de côté.
:::

## Commandes de développement

Communes à tous les contextes, ces commandes aident à maintenir le code et à
générer les fichiers déclaratifs.

{/* t:p eb4a577e49e9efa153acd9d8fd2b10c3417afab6dcccd1cefc2f6547932ca292 */}
### 💠 `develop` / `d`

Lance `nix develop -c zsh` pour obtenir un shell avec les outils du projet.

```sh
just develop
```

{/* t:p 646466489fa0e2fa6a91e0ba7d50103b5b27b91822cf4b6efd88871c1e6b240d */}
### 💠 `clean` / `c` ⭐

Exécute la chaîne complète : `statix fix` → `check-code` → `generate` → `format` → `_fix_fs_permissions`.

:::tip[Avant de commiter]
`just clean` est le point d'entrée recommandé avant chaque commit.
:::

```sh
just clean
```

{/* t:p b749b4f5b8a1ff6c59273ae71c210d208399fdbda62e9133ef2edaa62b33eb46 */}
### 💠 `format`

Lance `treefmt` sur tous les fichiers avec la config partagée du framework. En
co-développement, formate aussi `dnf/`.

```sh
just format
```

{/* t:p 68ab2120accf9872167017ad6862d92b9cb1ef3c6083161023dd23265f05e0a5 */}
### 💠 `generate`

Régénère les `default.nix` des dossiers de modules et, dans un projet, les
fichiers `var/generated/*.nix` depuis `etc/config.yaml`.

:::note[Deux modes]
- **Sources du générateur présentes** (`src/generator/`) : `cargo run`.
- **Sinon** : binaire `dnf-generator` fourni par la devShell (`just develop`).
:::

```sh
just generate
```

## Commandes de vérification

### 💠 `check`

Enchaîne la vérification du code (`check-code`), les tests unitaires DNF et la
vérification du flake (`check-flake`). Les tests unitaires ne tournent que sur
un clone du framework&nbsp;: un `dnf/` lié au store a été testé avant sa
publication.

:::tip[Avant de déployer]
Exécutez `just check` pour attraper les régressions tôt.
:::


### 🔆 `simulate [scénario]`

Lance les scénarios de test NixOS (NixOS Test Driver).

| Argument | Effet |
|---|---|
| _(vide)_ | Liste les scénarios disponibles |
| `all` | Exécute tous les scénarios (`nix flake check`) |
| `full` | Régénère les fixtures puis exécute tout |
| `<nom>` | Exécute un scénario nommé |

```sh

just simulate modules-node-console-git
```

seule.
:::

```sh

```

## Commandes d'installation

L'installation d'un nouvel hôte suit un enchaînement précis.

{/* t:p 26ad8f4341e8d4b7a67a0c437f484feb81b4b1cba7bc9705cd22c18186860e3e */}
### ✳️ `install <hôte> [user] [ip]`

Formate les disques via **disko** et installe NixOS via **nixos-anywhere**.

:::danger[Destructeur]
Toutes les données sur l'hôte cible sont effacées. Une confirmation est
demandée avant d'exécuter.
:::

:::note[Configuration requise]
L'hôte doit avoir une configuration disko dans `etc/config.yaml`, un dossier
`usr/machines/<hôte>/default.nix`, une clé `mac` et une adresse fixe
(`zone: "<zone>:<x.y>"`). Les deux derniers points sont vérifiés avant tout
formatage&nbsp;: sans eux, la machine change d'adresse au redémarrage qui suit
l'installation. Voir [Installation
initiale](/fr/doc/admin-guide/install/first-network-installation/#installer-un-poste).
:::

L'argument `ip` vaut `auto` par défaut&nbsp;: l'adresse est calculée comme pour
`full-install`, inutile de la relever.

:::caution[L'adresse doit être celle que la machine garde]
`nixos-anywhere` fige son adresse cible pour toute la durée du run et ne sait
pas suivre une renumérotation. Or l'installeur refait un DHCP&nbsp;: si la
machine tournait jusque-là sur un bail dynamique plus ancien que sa réservation
(le cas typique d'une installation **par-dessus un autre système**), elle
bascule sur son adresse réservée en pleine installation et le run parle dans le
vide.

La recette refuse donc de démarrer sur une adresse que l'hôte ne garde pas, et
affiche celles qu'il accepte. Avant d'installer par-dessus un OS existant,
redémarrez la machine pour qu'elle prenne son adresse réservée.
:::

La recette dépose aussi sur la cible, **avant** l'installation du système, la
clé age `/etc/sops/age/infra.key` et, sur un hôte chiffré, la clé d'hôte SSH de
son initrd&nbsp;: sops fonctionne dès la première activation et le tout premier
démarrage écoute déjà sur le port 2222. Le volume est formaté avec la
passphrase partagée du parc, il n'y a donc rien à saisir.

```sh
just install myserver
just install myserver nixos 10.0.0.5     # IP personnalisée
just install myserver nix auto test      # VM test uniquement
```

:::caution[LUKS et `do=test`]
`nixos-anywhere` refuse `--vm-test` en même temps que les options qui déposent
des fichiers et la clé de formatage&nbsp;: le mode test ne peut donc pas
formater un volume chiffré. La recette le signale.
:::

{/* t:p 332f678ae6aba4cf91ff9de59d833c42c4410666cb70c507792612466a979694 */}
### ✳️ `full-install <hôte> [user] [ip]` ⭐

Chaîne complète&nbsp;: `install` + attente reboot + `unlock` + `configure` +
`apply` + `gc` + reboot.

L'adresse de départ est calculée toute seule&nbsp;: nom de l'hôte dans sa propre
zone, adresse de passage réservée s'il est branché ailleurs. Voir [Machines hors
de leur zone](/fr/doc/admin-guide/understand/network/#machines-hors-de-leur-zone).

Après le redémarrage, la machine n'est pas forcément revenue au même
endroit&nbsp;: la recette sonde **toutes** ses adresses connues, sur les ports
22 et 2222, et poursuit sur celle qui répond. Un hôte chiffré est déverrouillé
au passage par `just unlock`.

Le redémarrage final n'est pas décoratif&nbsp;: `apply` active l'espace
utilisateur mais pas le noyau ni l'initrd, et ce reboot est la seule preuve
automatique que la machine repart **toute seule**. Sur un hôte chiffré, il
prouve du même coup que le déverrouillage à distance fonctionne, pendant que
vous êtes encore devant et non à la première coupure de courant. `unlock` est
donc rappelé juste après.

```sh
just full-install myserver
just full-install myserver nixos 10.0.3.42   # adresse forcée
```

### ✳️ `configure <hôte> [ip]`

Enchaîne `copy-id` → `copy-hw` → `push-key` → `luks` (ce dernier ne fait rien
sur un hôte non chiffré).

L'adresse est résolue une fois et transmise à toute la chaîne. Si l'hôte est
branché hors de sa zone, la redirection SSH est posée dans la foulée, pour que
l'`apply` qui suit l'atteigne&nbsp;: `just roaming-clear <hôte>` une fois la
machine revenue chez elle.

:::caution[Uniquement pour un hôte réellement ailleurs]
La redirection désactive la vérification de la clé d'hôte, **et elle le reste
tant qu'on ne la retire pas**. Elle n'est donc posée que si l'adresse utilisée
n'est ni le nom de l'hôte ni l'adresse fixe de sa zone. `just install` retire au
passage celle qu'aurait pu laisser une installation interrompue.
:::

```sh
just configure myserver
```

{/* t:p dd3f2f07c7d5a8f393df3542fbf46928a844826687c9ed08f13e5e7a370a02a7 */}
### ✳️ `copy-id <hôte>`

Vérifie que la clé de déploiement `nix` ouvre bien l'hôte cible, et pousse la
clé **privée** partagée sur les passerelles (synchronisation des certificats
TLS depuis le HCS).

:::caution[Ne dépose plus de clé]
SSH est par clé uniquement et `~/.ssh/authorized_keys` n'est plus lu :
`ssh-copy-id` n'a plus de canal d'amorçage. La clé de déploiement est
déclarative (`usr/secrets/nix.pub`). Si la recette échoue, corrigez la
configuration puis appliquez depuis un canal encore ouvert (console, sshd
d'initrd LUKS sur le port 2222).
:::

```sh
just copy-id myserver
```

### ✳️ `host-info <hôte> [ip]`

Affiche l'adresse MAC de la première interface active d'une machine, pour la

### ✳️ `luks <hôte> [action] [ip]`

Provisionne le chiffrement d'un hôte&nbsp;: passphrases partagée et par hôte
dans sops, clé SSH de l'initrd dans sops puis sur la cible, manifeste
`usr/secrets/luks.json`, IP WAN des passerelles. Voir
[Chiffrement des disques (LUKS)](/fr/doc/admin-guide/operate/luks/).

| Action | Effet |
|---|---|
| (défaut) | Prépare les secrets, puis converge la machine |
| `pre` | Moitié hors ligne seulement, sans toucher à la machine |
| `passwd` | Fait tourner la passphrase par hôte, puis converge |
| `show` | Audit en lecture seule&nbsp;: keyslots et déverrouillage distant |

:::tip[Idempotent]
`pre` est appelée par `just install` avant la construction, la version par
défaut par `just configure`. Sans volume LUKS dans le disko de l'hôte, c'est un
no-op journalisé.
:::

```sh
just luks myserver
just luks myserver show
just luks myserver passwd
```

{/* t:p 40874d9bfd781dfb02423530d635f069985c211874beaaa18c75567a4056b453 */}
### ✳️ `roaming [hôte] [ip]`

Redirige SSH vers un hôte branché hors de sa zone, le temps de l'installation.
Colmena s'adresse à un nœud par son nom, qui désigne son adresse d'origine&nbsp;;
cette redirection le renvoie là où la machine se trouve vraiment.

Posée par `just configure` quand c'est nécessaire, retirée par `full-install`
en fin de course. Sans argument, affiche les redirections en cours.

```sh
just roaming             # afficher
just roaming myserver    # rediriger (adresse calculée)
```

### ✳️ `roaming-clear [hôte]`


### ✳️ `configure-admin-host` ⭐

Configure la machine d'administration : clés SSH, clés age SOPS,
`.sops.yaml`, secrets par défaut, clé de signature Harmonia, et **tous les
secrets internes** que réclament les services déclarés (clients OAuth2,
sauvegarde, jetons de service…).

:::tip[Idempotent]
Peut être relancé sans risque : chaque étape vérifie si elle est déjà faite, et
aucun secret existant n'est écrasé. À relancer après avoir activé un service,
ajouté un hôte ou une zone. Voir
[Secrets](/fr/doc/admin-guide/operate/secrets/#secrets-internes-et-secrets-externes).
:::

```sh
just configure-admin-host
```

## Commandes de déploiement

Les commandes `apply*` reposent sur [colmena](https://github.com/zhaofengli/colmena)
et rafraîchissent d'abord le verrou DNF via `update-dnf`. `fleet-update` pilote
une mise à jour complète avec des commandes Nix natives.

{/* t:p ece18c6d5eea966020a1665a58fb2d9a5f883a5877b62e92e5884a772cb90e58 */}
### ✳️ `apply <cible> [action]` / `a` ⭐

Déploie la configuration sur une ou plusieurs cibles.

| Paramètre | Description |
|---|---|
| `cible` | Nom d'hôte, motif (`'*'`), liste (`a,b`), tag colmena (`@server`) |
| `action` | `switch` (défaut), `boot`, `test`, `build` |

:::note[Construction centralisée]
Le poste qui lance `just` construit chaque système une seule fois, puis
harmonia le partage avec le parc. Pour construire sur les cibles (architecture
que le poste ne sait pas construire)&nbsp;: `just buildOnTarget=1 apply <cible>`.
:::

```sh
just apply @all                 # tous les hôtes
just apply myserver             # switch (défaut)
just apply myserver boot        # boot
just apply 'db-*'               # tous les hôtes commençant par db-
```

## Commandes d'administration

Ces commandes permettent d'interagir avec les hôtes du parc : maintenance,
redémarrage, nettoyage et réparation du boot.

{/* t:p 9d330bebbc10ed7f0f1d8f494deb95df3363124b85db188c57f5347b25b011f0 */}
### ✳️ `enter <hôte>` / `e` ⭐

Ouvre une session SSH interactive en tant que `nix@<hôte>`. Si l'hôte attend
sa passphrase LUKS au démarrage (port 22 fermé), bascule sur le sshd de son
initrd (port 2222, avec repli sur l'IP WAN du manifeste pour une passerelle)
et présente la demande de passphrase. Voir
[Chiffrement des disques (LUKS)](/fr/doc/admin-guide/operate/luks/).

```sh
just enter myserver
```

{/* t:p 9f400b7be7d3bc1a8e6bc34f3cdb28a586672c31447cf4e5309adcab3094c35e */}
### ✳️ `unlock <hôte> [ip] [délai]`

Répond au prompt LUKS d'un hôte resté dans son initrd, **sans humain**&nbsp;:
la passphrase est lue dans sops et poussée par le sshd du port 2222. Attend que
l'hôte apparaisse (un point par tentative), ce qui permet de l'enchaîner juste
après un redémarrage. Appelée automatiquement par `just full-install`.

Sur un hôte sans volume LUKS, c'est un no-op journalisé.

```sh
just unlock myserver
```

{/* t:p 02fa3ced2db0dd6fdcdf8d51363f67974b3c73d0ae89e57b14dcf6bd883d56c4 */}
### ✳️ `remote-desktop <hôte> [ro|rw|login]` / `rd` ⭐

Ouvre le bureau à distance d'un hôte. `ro` (défaut) observe la session
graphique **déjà ouverte**, `rw` y prend la main ; les deux échouent si
personne n'est connecté. `login` ouvre à la place **votre propre session**
derrière un écran de login GDM. Aucun port n'est ouvert sur l'hôte : le flux
passe par un tunnel SSH monté par `nix`. Voir
[Bureau à distance](/fr/doc/admin-guide/operate/remote-desktop/).

```sh
just rd mypc                # observation
just rd mypc rw             # prise en main
just rd mypc login          # session à soi, via GDM
```

{/* t:p 9b7b4e97dc24da8d0af1bcb9ff36b375c3556753bead84315fd0c1df5f548041 */}
### ✳️ `reboot <hôte>`

Redémarre l'hôte via colmena exec.

:::caution[Confirmation]
Une confirmation est demandée avant d'exécuter.
:::

```sh
just reboot myserver
just reboot 'web-*'         # tous les web-*
```

{/* t:p 5b92b2b3461e03f1ef3881f56890275686d37ddf4c55fea4b20dc2e43d4cef10 */}
### ✳️ `halt <hôte>`

Arrête (poweroff) l'hôte via colmena exec, après confirmation.

```sh
just halt myserver
```

{/* t:p 71beeec2634e08d87b3b8f32f12176f837eab8d22e62218197d3ed8ff0a700cd */}
### ✳️ `gc <hôte> [keep]` ⭐

Supprime les anciennes générations, nettoie le store puis régénère les entrées
de démarrage (`switch-to-configuration boot`). `keep` fixe ce qui est conservé&nbsp;:

| `keep` | Générations conservées |
|---|---|
| (vide) | La courante uniquement, tous profils (`nix-collect-garbage -d`) |
| `N` (1 à 99) | Les `N` dernières du profil système, courante incluse |
| `Nd` (1 à 99) | Celles de moins de `N` jours, plus celle active à cette date |

```sh
# Nettoyage des hôtes dont le nom commence par "server-"
just gc "server-*"    # Garde uniquement la génération courante
just gc "server-*" 3  # Garde les 3 dernières générations, courante incluse
just gc "server-*" 3d # Supprime les générations de plus de 3 jours
```

{/* t:p 71bf7ccbff6cfed3261bc2c1d64c5fa1493ec3d4cee07f20635d95de21416c80 */}
### ✳️ `nfs-cleanup <hôtes> [mode]`

Nettoie les dossiers personnels d'un hôte sorti du partage NFS&nbsp;: liens XDG
morts supprimés, sauvegardes `.bak` restaurées. `check` (défaut) n'écrit rien et
affiche ce que ferait `apply`. `hôtes` est une liste séparée par des virgules,
ou `all`. Voir [Sortir du partage NFS des homes](/fr/doc/how-to/admin/leave-nfs/).

```sh
just nfs-cleanup myserver          # simulation, n'écrit rien
just nfs-cleanup myserver apply    # exécution
```

{/* t:p 4873218939a6b08ab3b5c3fcb2627475521a93d2f57aad33722e0d5bbd58c4bb */}
### ✳️ `fix-boot <hôte>`

Réinstalle le bootloader avec `NIXOS_INSTALL_BOOTLOADER=1`.

```sh
just fix-boot myserver
```

### ✳️ `yubikey <utilisateur> [clé] [action]`

Enrôle une YubiKey (`main` par défaut, ou `backup`) pour un utilisateur : PAM
(session/sudo), LUKS et lien d'enrôlement Kanidm, en un seul passage sur le
poste admin. `action=revoke` révoque la clé sur tout le parc au prochain
déploiement. Voir [Authentification forte](/fr/doc/admin-guide/operate/yubikey/).

```sh

```

{/* t:p c721a639832b45fbdbb521264d00054fd9c54ef53c41e0d1c85d79114186406b */}
### ✳️ `rotate init|push-keys|finalize`

Rotation de la clé age `/etc/sops/age/infra.key` en 3 étapes avec vérifications
d'intégrité.

| Étape | Action |
|---|---|
| `init` | Génère une nouvelle clé, conserve l'ancienne, rechiffre les secrets |
| `push-keys` | Pousse la clé combinée (nouvelle + ancienne) vers tous les hôtes |
| `finalize` | Vérifie que tous les hôtes ont la nouvelle clé, supprime l'ancienne |

:::danger[Rotation non terminée]
Ne pas interrompre une rotation. Les sidecars `.cur` / `.old` marquent une rotation en cours.
:::

```sh
just rotate init
just rotate push-keys
just rotate finalize
```

## Commandes de co-développement

À la racine d'un projet de co-développement. Les commandes git travaillent sur
**tous les dépôts** du projet (par défaut `src/*/`, `dnf`, `doc`, et la
racine). L'alias court de `git` est `g`.

{/* t:p cbdefe32a6a73a2abcf623b8ad6b1f49de48dd5cd3c568090291f76d7773aef0 */}
### 🔗 `git <cmd> [projet]`

Exécute n'importe quelle commande git sur un ou tous les projets.

:::tip[Projets itérés]
Listés par `just git-show-repos` (par défaut tous).
:::

```sh
just git "log --oneline -5"       # derniers commits de tous projets
just git "status" dnf             # git status sur dnf/ seulement
just git "remote -v"              # remotes de tous les projets
```

{/* t:p efacc1b9c33481552ed92afa9e004ec4b3bf35f16486327796bc46b3929d5a85 */}
### 🔗 `commit <message> [projet]` ⭐

`add -A` + `commit -m` sur un ou tous les projets. Si le message est
identique au dernier commit, la recette **amende** au lieu de créer un nouveau
commit.

Sur tous les projets, la racine passe en dernier, après `update-dnf`&nbsp;: son
commit épingle la révision de `dnf/` qui vient d'être commitée.

```sh
just commit "fix(net): update dns config"
just commit "fix(net): update dns config" dnf    # dnf/ seulement
```

Ajoute les modifications en cours au dernier commit de chaque projet
(`--no-edit`). Sur tous les projets, le verrou de la racine est ensuite
réaligné sur `dnf/`.

```sh
just amend
```
