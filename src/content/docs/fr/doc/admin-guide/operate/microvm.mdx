Un **invité microVM** est un hôte DNF ordinaire (IP de zone, services,
supervision) qui tourne dans une machine virtuelle légère, sur un autre hôte du
parc&nbsp;: l'**hyperviseur**. DNF s'appuie sur
[microvm.nix](https://github.com/microvm-nix/microvm.nix) et cloud-hypervisor.
Usage type&nbsp;: un espace IA clos par personne ou par équipe.

## Déclarer un invité

<Steps>

1. **Déclarer l'hôte**

   La feature `microvm-guest` nomme l'hyperviseur, de la même zone. L'IP fixe
   est obligatoire&nbsp;: l'interface et l'adresse MAC en dérivent. Comme tout
   hôte, l'invité n'est supervisé qu'avec la feature `monitoring-node`.

   ```yaml
   # etc/config.yaml
   hosts:
     - hostname: "espace1"
       zone: "maison:1.40"
       profile: "ai-space"
       features: ["microvm-guest:serveur", "monitoring-node"]
   ```

2. **Dimensionner**

   Facultatif, 2 vCPU et 4096 Mio par défaut.

   ```nix
   # usr/machines/espace1/configuration.nix
   {
     darkone.system.microvm.guest = {
       vcpu = 4;
       mem = 6144; # Mio
     };
   }
   ```

3. **Figer la version d'état**

   Un invité ne passe jamais par `just install`&nbsp;: créer le fichier à la
   main, avec la version NixOS du premier déploiement.

   ```nix
   # usr/machines/espace1/install/state.nix
   { system.stateVersion = "26.05"; }
   ```

4. **Initialiser ses secrets**

   L'invité ne lit que ses propres secrets&nbsp;: voir
   [hôtes isolés](/fr/doc/admin-guide/operate/secrets/#hôtes-isolés).

   ```sh
   just space-init espace1
   ```

5. **Déployer l'hyperviseur**

   ```sh
   just generate
   just apply serveur
   ```

</Steps>

## Déployer et mettre à jour

Un invité n'est pas une cible de déploiement&nbsp;: `just apply <hyperviseur>`
construit les invités, démarre les nouveaux et redémarre ceux qui ont changé.
Les invités démarrent avec l'hyperviseur.

| Élément | Emplacement |
|---|---|
| Données persistantes | `/var/lib/microvms/<invité>/` sur l'hyperviseur, fermé à ses comptes sauf root (`0770`) et monté `nosuid,nodev`&nbsp;: un fichier setuid ou un périphérique créé par l'invité y reste inerte |
| `/persist`, `/var/lib`, `/home` | Partages virtiofs de ce dossier |
| Racine `/` | En mémoire, vidée à chaque démarrage |
| Store Nix | Celui de l'hyperviseur en lecture seule, plus une couche en mémoire pour ce que l'invité installe (`nix shell`, Home Manager), vidée à chaque démarrage |

## Isolation réseau

Chaque invité a sa propre interface `vm-X-Y`, routée en `/32` par
l'hyperviseur, qui répond pour lui sur le LAN (proxy ARP). Le lien de
l'hyperviseur vers le LAN n'est pas modifié, il n'y a pas de pont.

| Flux | Autorisé |
|---|---|
| Invité → Internet | Oui |
| Invité → DNS de la passerelle | Oui |
| Invité → LAN, tailnet, autres invités | Non |
| Invité → hyperviseur | Non |
| Passerelle → invité | Oui (proxy, supervision) |
| Autre hôte → invité | Ping et SSH seulement |

## FAQ

{/* t:p b2b56a6c3a435b7fcf9c83bdc0fb919786b2d5da878bee450a6f13e446a06899 */}
### Se connecter à un invité ?

Comme tout hôte, depuis un poste d'administration&nbsp;: `just enter <invité>`.
Son nom est publié par le DNS des passerelles, qui doivent donc être
redéployées après l'ajout de l'invité.

{/* t:p 5edf6712e8f1a6fb19617f07ba341ad1037ebe941aea82d9a3a530eabbd8ca37 */}
### Effacer un invité ?

Le retirer de `etc/config.yaml`, déployer l'hyperviseur, puis supprimer
`/var/lib/microvms/<invité>/` sur l'hyperviseur.
