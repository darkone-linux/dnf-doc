Un **espace IA** est un hôte DNF de profil `ai-space`, en général un
[invité microVM](/fr/doc/admin-guide/operate/microvm/). Il porte un assistant
[OpenClaw](https://openclaw.ai) réservé à ses membres, avec ses propres secrets
et ses propres données.

:::caution[En cours]
Accès web, SSO, canal Matrix, Claude Code, Codex, OpenCode, MCP et skills en
place.
Hermes arrive dans une prochaine version.
:::

## Créer un espace

<Steps>

1. **Déclarer l'hôte et ses membres**

   Les `users` de l'hôte sont ses membres&nbsp;: DNF crée pour eux le groupe
   Kanidm `space-<hôte>`.

   ```yaml
   # etc/config.yaml
   - hostname: "ia-pro"
     zone: "lan:1.40"
     profile: "ai-space"
     features: ["microvm-guest:hyperviseur", "monitoring-node"]
     users: ["alice", "bob"]
     services:
       openclaw: {}
   ```

   `monitoring-node` place l'espace sous la supervision de la zone&nbsp;: sans
   lui, ni la panne de l'espace ni l'arrêt de l'assistant ne déclenchent
   d'alerte.

   Le **propriétaire** est le membre dont l'abonnement fait tourner
   l'assistant&nbsp;: il reçoit les demandes de validation et les messages
   spontanés (rappels, tâches planifiées). Seul membre, il est implicite.
   Avec plusieurs membres, il se déclare dans
   `usr/machines/ia-pro/configuration.nix` (l'ordre des `users` n'est pas
   conservé)&nbsp;:

   ```nix
   { darkone.service.openclaw.owner = "alice"; }
   ```

2. **Initialiser l'espace**

   `just space-init ia-pro`&nbsp;: clé d'hôte, secrets (cf.
   [Hôtes isolés](/fr/doc/admin-guide/operate/secrets/)) et, si le réseau a
   Matrix, le bot `@ia-pro:<domaine>`. Committer ensuite `usr/secrets/` et
   `var/generated/spaces/`.

3. **Déployer**

   L'hyperviseur, la passerelle de la zone (vhost, DNS) et le HCS (groupe
   Kanidm)&nbsp;: `just apply hyperviseur,gw,hcs`.

4. **Connecter le fournisseur d'IA**

   Une fois par espace, depuis l'hôte (`just enter ia-pro`), pour chaque
   abonnement du propriétaire qui sert aux modèles de l'espace (cf.
   [Modèles et abonnements](#modèles-et-abonnements))&nbsp;:

   | Abonnement | Modèles | Connexion |
   |---|---|---|
   | Claude Pro/Max, par le CLI `claude` | `anthropic/*` (défaut&nbsp;: `anthropic/claude-sonnet-5-5`) | `sudo -u openclaw -H claude auth login` |
   | ChatGPT Plus/Pro, par le plugin `codex` | `openai/*` | `openclaw models auth login --provider openai` |

   La commande `openclaw` de l'hôte passe d'elle-même sous l'utilisateur du
   service. `openclaw models status` vérifie la connexion, qui reste dans
   `/var/lib/openclaw`, persistant.

</Steps>

:::note[Pourquoi un utilisateur `openclaw`]
L'assistant lit des contenus non fiables (web, messages, documents)&nbsp;: un
utilisateur système dédié le tient à l'écart des comptes des membres, de
leurs clés et de leurs connexions. Les membres n'ont pas `sudo` (réservé au
groupe `wheel`)&nbsp;: l'administration passe par le compte `nix`.
:::

:::caution[Mise à jour]
Un espace créé avant le mot de passe local de l'assistant doit repasser par
`just space-init <hôte>` avant son déploiement&nbsp;: il génère le secret
`openclaw-gateway-password`, par lequel la commande `openclaw` de l'hôte joint
le service.
:::

## Modèles et abonnements

Un modèle passe par l'abonnement du propriétaire quand son fournisseur figure
dans `subscriptions`, sinon par une clé d'API.

```nix
# usr/machines/ia-pro/configuration.nix
{
  darkone.service.openclaw = {
    model = "anthropic/claude-sonnet-5-5";
    extraModels = [ "openai/gpt-6-astra" "openrouter/moonshotai/kimi-k3" ];
    subscriptions = [ "anthropic" "openai" ]; # défaut
    apiKeys = [ "OPENROUTER_API_KEY" ];
  };
}
```

| Option | Rôle |
|---|---|
| `model` | Modèle principal, `<fournisseur>/<modèle>` |
| `extraModels` | Autres modèles, choisis dans la conversation par `/model` |
| `subscriptions` | Abonnements du propriétaire&nbsp;: `anthropic`, `openai` |
| `apiKeys` | Clés d'API, par nom de variable |
| `providers` | Fournisseurs absents d'OpenClaw, compatibles OpenAI |

Chaque clé (`apiKeys`, `providers.<nom>.apiKey`) se range avant le
déploiement dans les secrets de l'espace, sous `openclaw/<VARIABLE>`
(`just space-sops <hôte>`).

:::caution[Clé Anthropic et abonnement Claude]
Le CLI `claude` préfère `ANTHROPIC_API_KEY` à sa connexion&nbsp;: à côté de
l'abonnement `anthropic`, DNF ne transmet pas cette clé. Pour payer Claude à
l'usage, retirer `anthropic` de `subscriptions`.
:::

### Fournisseur compatible OpenAI

Un fournisseur absent d'OpenClaw, comme Nous Portal, se déclare avec son
adresse, sa clé et ses modèles&nbsp;:

```nix
# usr/machines/ia-pro/configuration.nix
{
  darkone.service.openclaw = {
    providers.nous = {
      baseUrl = "https://inference-api.nousresearch.com/v1";
      apiKey = "NOUS_API_KEY";
      models = [ "Hermes-4-405B" ];
    };
    model = "nous/Hermes-4-405B";
  };
}
```

### Abonnements partagés

| Usage | Compte |
|---|---|
| Assistant (web, Matrix, tâches planifiées) | Celui du propriétaire, quota partagé par les membres |
| Claude Code, Codex, OpenCode d'un membre | Le sien |

Un abonnement personnel (ChatGPT, Claude) partagé par plusieurs membres sort
des conditions d'utilisation&nbsp;: un espace d'équipe prend un plan équipe ou
des clés d'API (`subscriptions = [ ]`).

## Matrix

Les membres écrivent au bot `@<hôte>:<domaine>` en message direct, chiffré de
bout en bout. Le canal n'existe que si le réseau déclare le service `matrix`&nbsp;:
sans lui, l'espace fonctionne par son interface web seule.

| Élément | Règle |
|---|---|
| Qui est écouté | Les membres de l'espace (`@<login>:<domaine>`), en MP seulement&nbsp;; les autres comptes sont ignorés |
| Salons | Ignorés&nbsp;: des non-membres y liraient les réponses |
| Sessions | Une par membre quand ils sont plusieurs, sinon une seule pour tous les canaux |
| Validation des commandes | Aucune par défaut (cf. [Sécurité](#sécurité))&nbsp;; une demande éventuelle va au propriétaire, en MP |
| Messages spontanés | Envoyés au propriétaire, en MP |
| Clés de chiffrement | Dans `/var/lib/openclaw`, persistant |

:::caution[Vérification de l'appareil]
Au premier démarrage, le bot demande à vérifier sa session (`openclaw matrix
verify status` sur l'hôte). Tant qu'elle n'est pas vérifiée, Element signale
ses messages comme non vérifiés.
:::

## Conversation orale

Le bouton micro de l'interface web ouvre une conversation à la voix,
interruptible, sur PC comme sur téléphone. La voix temps réel d'OpenAI
(GPT-Live) répond&nbsp;; l'assistant de l'espace fait le travail (outils,
fichiers, MCP), quel que soit son modèle.

```nix
# usr/machines/ia-pro/configuration.nix
{ darkone.service.openclaw.talk.enable = true; }
```

| Option | Défaut | Rôle |
|---|---|---|
| `talk.model` | `gpt-live-1-codex` | Abonnement ChatGPT, sinon `OPENAI_API_KEY` |
| `talk.voice` | `cove` | Aussi `arbor`, `breeze`, `ember`, `juniper`, `maple`, `sol`, `spruce`, `vale` |
| `talk.instructions` | aucune | Consignes ajoutées (langue, ton) |

Il faut la connexion ChatGPT du propriétaire
(`openclaw models auth login --provider openai`), même avec un assistant sous
Claude, ou une clé `OPENAI_API_KEY` (cf.
[Modèles et abonnements](#modèles-et-abonnements)). Huit conversations au plus
à la fois, de 30 minutes chacune.

:::caution[À valider]
Pas encore essayé dans un navigateur ni sur téléphone.
:::

## Outils des agents

Les MCP, les skills et les outils se déclarent une seule fois par espace, dans
`usr/machines/<hôte>/configuration.nix`. L'assistant et chaque membre (Claude
Code, Codex, OpenCode) reçoivent les mêmes.

```nix
{ pkgs, ... }:
{
  darkone.host.ai-space = {
    mcp.fetch = {
      command = "uvx";
      args = [ "mcp-server-fetch" ];
    };
    mcp.github = {
      command = "github-mcp-server";
      args = [ "stdio" ];
      secretEnv = [ "GITHUB_PERSONAL_ACCESS_TOKEN" ];
    };
    mcp.docs.url = "https://mcp.example.com/mcp";
    skills.rapport = ./skills/rapport;   # dossier avec SKILL.md
    packages = [ pkgs.uv pkgs.pandoc pkgs.github-mcp-server ];
  };

  darkone.service.openclaw = {
    workspace."AGENTS.md" = ./AGENTS.md;
    projects.notes = "https://forge.example.com/alice/notes.git";
  };
}
```

| Option | Rôle |
|---|---|
| `darkone.host.ai-space.mcp` | Serveurs MCP, locaux (`command`, `args`, `env`, `secretEnv`) ou distants (`url`, `headers`) |
| `darkone.host.ai-space.skills` | Skills par nom&nbsp;: contenu de `SKILL.md`, fichier ou dossier |
| `darkone.host.ai-space.packages` | Outils dans le PATH de l'assistant et chez les membres |
| `darkone.host.ai-space.enableClaude`, `enableCodex`, `enableOpenCode` | Claude Code, Codex et OpenCode, actifs par défaut |
| `darkone.host.ai-space.projectsDir` | Dossier projets partagé (défaut `/var/lib/projects`) |
| `darkone.service.openclaw.exec` | Politique des commandes (cf. [Sécurité](#sécurité)) |
| `darkone.service.openclaw.identity` | Nom, emoji et avatar de l'assistant (`name`, `emoji`, `avatar`) |
| `darkone.service.openclaw.workspace` | Fichiers du workspace de l'assistant (`AGENTS.md`, `SOUL.md`…) |
| `darkone.service.openclaw.projects` | Dépôts git clonés une fois dans le dossier projets |
| `darkone.service.openclaw.transcription` | Transcription des notes vocales (cf. [Transcription](#transcription)) |

:::danger[Secrets des MCP&nbsp;: `secretEnv` seulement]
`env` et `headers` sont écrits dans le store Nix, lisible par tous. Une clé
d'API passe par `secretEnv`, pour un serveur local&nbsp;: chaque variable est
lue dans le fichier de secrets de l'espace, sous la clé
`mcp/<serveur>/<VARIABLE>` (`just space-sops <hôte>`, avant le déploiement).
Un serveur distant ne reçoit aucun secret.
:::

:::note[Workspace]
Les fichiers déclarés sont réécrits à chaque démarrage de l'assistant. Les
autres (mémoire, fichiers créés par l'agent) lui appartiennent. Les projets ne
sont jamais mis à jour automatiquement&nbsp;; un clonage en échec est signalé
dans `journalctl -u openclaw-projects` sans bloquer le déploiement. Un dépôt
SSH utilise la clé de l'utilisateur `openclaw`, à créer une fois
(`sudo -u openclaw -H ssh-keygen -t ed25519`) puis à déclarer sur la forge
(`/var/lib/openclaw/.ssh/id_ed25519.pub`)&nbsp;; la clé du serveur est
acceptée au premier clonage.
:::

### Transcription

Les notes vocales, Matrix ou web, sont transcrites par whisper.cpp, sans
service externe&nbsp;:

| Espace | Transcription |
|---|---|
| Invité microVM | Serveur de l'hyperviseur, modèle `large-v3-turbo` |
| Machine physique | Sur l'espace, modèle `small` (466&nbsp;Mo, CPU) |

Serveur de l'hyperviseur injoignable ou trop lent&nbsp;: l'espace transcrit
lui-même avec `small`. `transcription.backend = "local"` garde toujours la
transcription dans l'invité. La langue est détectée à chaque note&nbsp;;
`transcription.language = "fr"` la fixe.

## Projets et agents de code

Le dossier projets (`/var/lib/projects`, lien `~/projects` chez chaque membre)
est partagé&nbsp;: tout fichier créé par un membre ou par l'assistant reste
modifiable par les autres. C'est le dossier de travail de l'assistant&nbsp;; ses
consignes et sa mémoire restent dans son workspace.

Depuis la conversation (web ou Matrix), l'assistant confie du code à Claude
Code, Codex ou OpenCode&nbsp;:

| Mode | Usage |
|---|---|
| `/acp spawn claude` (ou `codex`, `opencode`) | Session de code liée à la conversation, reprise possible |
| Tâche de fond (skill `coding-agent`) | Travail long, fin signalée par message |

Chaque outil se connecte une fois, sur l'hôte&nbsp;:

| Outil | Connexion |
|---|---|
| Claude Code | Celle du propriétaire (cf. [Créer un espace](#créer-un-espace)) |
| Codex (session) | `sudo -u openclaw -H codex login --device-auth` |
| Codex (tâche de fond) | `sudo -u openclaw -H env CODEX_HOME=/var/lib/openclaw/.codex-coding-agent codex login --device-auth` |
| OpenCode | `sudo -u openclaw -H opencode auth login` |

:::caution[Mise à jour]
Les `projects` étaient clonés dans `/var/lib/openclaw/workspace/projects/`.
Ils le sont désormais dans le dossier projets&nbsp;: y déplacer les clones
existants, ou les laisser se recloner au prochain démarrage.
:::

## Workflows

| Outil | Usage |
|---|---|
| Automatisations | Tâches planifiées de l'assistant (briefing du matin, veille) |
| [Lobster](https://docs.openclaw.ai/tools/lobster) | Enchaînement d'étapes avec validations, reprise sans tout refaire |

L'assistant et l'interface créent leurs propres automatisations&nbsp;; Nix
peut aussi en déclarer&nbsp;:

```nix
# usr/machines/ia-pro/configuration.nix
{
  darkone.service.openclaw.automations.briefing = {
    schedule = "0 7 * * 1-5"; # cron, ou "every 2h"
    message = "Résume mon agenda et mes mails non lus.";
  };
}
```

| Option | Rôle |
|---|---|
| `schedule`, `message` | Quand, et la demande faite à l'assistant |
| `announce` | Envoie la réponse dans la conversation (défaut) |
| `model` | Modèle propre à cette tâche |
| `enable` | `false`&nbsp;: désactivée, puis réactivable depuis l'interface seulement |

Les automatisations déclarées sont resynchronisées à chaque démarrage&nbsp;: une
modification faite dans l'interface est écrasée, une déclaration retirée
supprime sa tâche. Les autres ne sont jamais touchées.

Lobster s'active par `lobster = true`&nbsp;; ses fichiers passent par le
workspace (`workspace."workflows/tri.lobster" = ./tri.lobster;`), et
l'assistant les lance à la demande.

:::caution[À valider]
Lobster n'a pas encore été essayé sur un espace.
:::

## Comptes des membres

Chaque membre a un compte Linux sur l'espace, allégé&nbsp;:

| Élément | Sur l'espace |
|---|---|
| Profil Home Manager | `space-member` (zsh, git, vim, tmux), à la place du sien |
| Outils de l'espace | Claude Code, Codex et OpenCode, avec les MCP et skills de l'espace (`darkone.home.aiSpace`) |
| Personnalisations | `usr/users/<login>/space.nix` (tous ses espaces), puis `usr/users/<login>/spaces/<hôte>.nix` (cet espace), s'ils existent |
| `usr/users/<login>/default.nix` | Ignoré&nbsp;: réservé à ses postes |
| Droits | Groupe `projects` seulement (pas de `sudo`), quel que soit son profil |

L'administration de l'espace passe par le compte `nix` (`just enter <hôte>`).

:::tip[Personnaliser un espace]
Ces fichiers sont des modules Home Manager ordinaires&nbsp;: paquets, alias,
configuration git, autres modules importés. Un MCP personnel s'y ajoute par
`programs.mcp.servers.<nom>`.
:::

Chaque membre connecte ses propres abonnements, une fois&nbsp;: `claude` (puis
`/login`), `codex login --device-auth` et `opencode auth login`. OpenCode
accepte un abonnement ChatGPT ou une clé d'API, pas l'abonnement Claude.

## Configuration modifiable

Par défaut, Nix fige la configuration de l'assistant&nbsp;: l'interface web
l'affiche en lecture seule. `darkone.service.openclaw.mutableConfig = true` la
rend modifiable, dans l'interface ou par `openclaw config set` sur l'hôte, et
donne au propriétaire le droit d'administration.

| Réglages | Qui décide |
|---|---|
| Accès, canal Matrix, plugins, MCP, transcription | Nix&nbsp;: rétablis au démarrage et à chaque modification |
| Modèle, commandes, identité | Nix au premier démarrage, puis l'interface |
| Autres | L'interface |

:::caution[Réglage semé par Nix]
Une fois écrit, un réglage du modèle, des commandes ou de l'identité ne suit
plus Nix. `openclaw config unset <clé>` le retire&nbsp;: Nix le réécrit aussitôt
avec sa valeur.
:::

## Sécurité

Par défaut, l'assistant exécute ses commandes sans validation, comme
OpenClaw&nbsp;: la barrière est l'espace lui-même (microVM coupée du LAN,
secrets propres à l'espace). Son service est en plus confiné&nbsp;: il n'écrit
que dans `/var/lib/openclaw` et le dossier projets, et ne voit ni les dossiers
personnels ni les processus des membres.

`darkone.service.openclaw.exec` choisit la politique&nbsp;:

| Valeur | Commandes |
|---|---|
| `full` (défaut) | Toutes, sans validation |
| `ask` | Celles de la liste blanche passent, les autres sont soumises au propriétaire |
| `auto` | Un modèle examine celles hors liste blanche et soumet au propriétaire les cas douteux |
| `allowlist` | Celles de la liste blanche seulement |
| `deny` | Aucune |

La liste blanche se remplit sur l'hôte&nbsp;:
`openclaw approvals allowlist add --agent main <chemin>`.

:::caution[Validation et Claude Code]
Avec un modèle `anthropic/*` (CLI `claude`), hors `full`, les pipes,
redirections et substitutions sont refusés sans demande&nbsp;: l'assistant
devient nettement moins capable. La validation évite les erreurs, elle
n'arrête pas un assistant détourné, qui tourne sous le même utilisateur que le
service.
:::

:::note[Validation réservée au propriétaire]
Seul le propriétaire valide, en MP ou dans l'interface web. Un appareil
appairé avant ce réglage garde son droit&nbsp;: le retirer avec `openclaw
devices list` puis `openclaw devices remove <id>`, il se réappaire à la visite
suivante.
:::

:::caution[Ce que l'assistant peut lire]
Il tourne sous l'utilisateur `openclaw`&nbsp;: tout ce que le service détient
est à sa portée, dont la connexion du propriétaire au fournisseur d'IA et le
jeton du bot Matrix. Un contenu piégé (page web, document, message) peut lui
faire divulguer ces informations&nbsp;: ne rien confier à un espace qui ne
doive pas pouvoir en sortir.
:::

:::note[Des membres de confiance]
Un espace est un seul cercle de confiance&nbsp;: l'interface web de chaque
membre affiche toutes les sessions, MP des autres compris. Des personnes qui ne
se font pas confiance prennent chacune leur espace.
:::
