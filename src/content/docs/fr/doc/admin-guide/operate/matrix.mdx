## Activer Matrix

<Steps>

1. Déclarer les services sur l'hôte cible dans `etc/config.yaml`&nbsp;:

   ```yaml
   # etc/config.yaml
       services:
         matrix:
           title: "Matrix"
           description: "Messagerie instantanée"
         element:        # client web
         turn:           # relais audio/vidéo des clients historiques
   ```

2. Déclarer l'administrateur Matrix (clé globale, hors hôtes)&nbsp;:

   ```yaml
   # etc/config.yaml
   matrix:
     admin: "alice"    # local part du compte administrateur
   ```

   Ce compte administre les ponts et reçoit les
   [alertes de supervision](/fr/doc/admin-guide/operate/alerts/).

3. Créer les [secrets](/fr/doc/admin-guide/operate/secrets/) requis
   (voir tableau ci-dessous), puis déployer.

</Steps>

L'authentification passe par le [SSO Kanidm](/fr/doc/admin-guide/operate/sso/)
(OIDC)&nbsp;: tout utilisateur déclaré se connecte avec son compte réseau,
aucune création de compte Matrix n'est nécessaire.

### Secrets requis

Tous internes&nbsp;: `just configure-admin-host` les crée dans
`usr/secrets/secrets.yaml`, sans jamais écraser l'existant.

| Clé sops | Rôle |
|---|---|
| `matrix-rss-password` | Registration shared secret Synapse |
| `oidc-secret-matrix` | Secret du client OIDC Kanidm (cf. [SSO](/fr/doc/admin-guide/operate/sso/)) |
| `turn-secret` | Secret partagé coturn (si `turn` activé) |
| `livekit-secret` | Secret partagé MatrixRTC (si `matrixRtc` activé) |
| `mautrix-doublepuppet-as-token` | Token appservice *double puppeting* (commun aux ponts) |
| `mautrix-doublepuppet-hs-token` | Idem, requis par Synapse, jamais utilisé |

## Deux modes d'authentification

Le serveur fonctionne dans **un seul** de ces deux modes, réglé par
`darkone.service.matrix.mas.enable`. Le mode choisi change les clients
compatibles, la façon d'inscrire des amis et les outils d'administration.

| | Synapse historique (défaut) | MAS activé (recommandé) |
|---|---|---|
| Option | `mas.enable = false` | `mas.enable = true` |
| Connexion SSO | Synapse est client OIDC de Kanidm | MAS est client OIDC de Kanidm |
| Element Web / Desktop | oui | oui |
| **Element X** (Android, iOS) | **non** | **oui** |
| Connexion par QR code | non | oui |
| Application proposée sur mobile | Element Classic | Element X |
| Portail de compte | aucun | `https://matrix.domain.tld/account/` |
| Jetons d'inscription | API admin Synapse | `dnf-mas` sur l'hôte |
| Promotion administrateur | SQL dans la base Synapse | `dnf-mas manage promote-admin` |

<Aside type="tip" title="Element X exige MAS">
L'application mobile nouvelle génération [Element X](https://element.io/app/)
ne sait se connecter qu'à un serveur piloté par MAS. Sans MAS, elle échoue à
la connexion&nbsp;; il faut rester sur l'application Element classique.

Le client web s'aligne tout seul&nbsp;: sa page d'accueil mobile propose
Element X quand l'hôte porte un serveur Matrix avec MAS, Element Classic
sinon. Rien à régler.
</Aside>

### Activer MAS

Le [Matrix Authentication Service](https://element-hq.github.io/matrix-authentication-service/)
remplace l'authentification interne de Synapse. Pour ce qu'il change et
comment il s'insère, voir
[l'architecture](/fr/doc/admin-guide/understand/matrix/#authentification-nouvelle-génération-mas).

<Steps>

1. Générer les trois secrets dédiés (idempotent, n'écrase jamais
   l'existant)&nbsp;:

   ```sh
   just configure-admin-host
   ```

   | Clé sops | Rôle |
   |---|---|
   | `mas-encryption-secret` | Chiffrement interne MAS |
   | `mas-synapse-secret` | Secret partagé MAS ↔ Synapse |
   | `mas-rsa-private-key` | Clé de signature des tokens |

2. Activer l'option dans la config nix de l'hôte&nbsp;:

   ```nix
   # usr/machines/<host>/default.nix
   darkone.service.matrix.mas.enable = true;
   ```

3. Déployer. Sur un serveur **neuf**, c'est terminé. Sur un serveur qui a déjà
   des comptes, enchaîner sur la [migration](#migrer-un-serveur-déjà-en-production)
   **sans laisser personne se connecter entre les deux**.

</Steps>

:::danger[Secret immuable]
`mas-encryption-secret` ne doit **jamais** changer après le premier démarrage
de MAS&nbsp;: il protège des données chiffrées en base, qui deviendraient
illisibles. Idem pour l'ULID du fournisseur Kanidm, figé dans le module.
:::

### Migrer un serveur déjà en production

MAS devient propriétaire des comptes et des sessions&nbsp;: ils doivent être
importés avec l'outil officiel `syn2mas`, servi par la commande `dnf-mas` de
l'hôte. Sans cet import, tous les comptes sont invisibles et tout le monde est
déconnecté.

<Steps>

1. **Sauvegarder**, dans cet ordre (le dump doit entrer dans l'instantané)&nbsp;:

   ```sh
   sudo systemctl start postgresqlBackup.service
   sudo systemctl start restic-backups-system-main.service
   ```

2. **Déployer** la configuration avec `mas.enable = true` (cf. ci-dessus). La
   fenêtre de maintenance commence ici.

3. **Arrêter** les deux services&nbsp;: `syn2mas` exige Synapse hors ligne, et
   MAS ne doit pas provisionner de compte entre-temps.

   ```sh
   sudo systemctl stop matrix-synapse matrix-authentication-service
   ```

4. **Vérifier**, puis répéter à blanc, puis migrer&nbsp;:

   ```sh
   sudo dnf-mas syn2mas check
   sudo dnf-mas syn2mas migrate --dry-run
   sudo dnf-mas syn2mas migrate
   ```

   Le compte-rendu annonce les comptes, liens SSO, jetons d'accès et devices
   repris. Les centaines d'utilisateurs « ignorés » sont les fantômes des
   ponts&nbsp;: c'est normal.

5. **Redémarrer**, MAS d'abord&nbsp;:

   ```sh
   sudo systemctl start matrix-authentication-service
   sudo systemctl start matrix-synapse
   ```

</Steps>

<Aside type="note" title="Ce que la migration préserve">
Les sessions en cours **survivent**&nbsp;: les jetons d'accès existants sont
convertis en sessions de compatibilité, personne n'a besoin de se
reconnecter, et le bot d'alertes garde son jeton. Les ponts n'ont **pas**
besoin d'une régénération de registration&nbsp;: Synapse impose MSC4190 à tous
les appservices dès que l'authentification est déléguée.
</Aside>

:::caution[Sens unique]
La migration n'est pas réversible&nbsp;: revenir en arrière impose de
restaurer la sauvegarde. Ne pas la lancer sans avoir vérifié l'étape 1.
:::

## Inscrire des amis

En plus des utilisateurs du SSO, on peut ouvrir une inscription **sur jeton**
pour des comptes locaux à mot de passe (les amis). Sans jeton, aucune
inscription n'est possible. Le commutateur est le même dans les deux modes,
seule la fabrication du jeton diffère.

```nix
# usr/machines/<host>/default.nix
darkone.service.matrix.friendRegistration.enable = true;
```

<Tabs>
<TabItem label="Avec MAS">

<Steps>

1. Créer un jeton sur l'hôte Matrix. Ici valable **une fois** et **7 jours**
   (sans option, le jeton est à usage unique et sans expiration)&nbsp;:

   ```sh
   sudo dnf-mas manage issue-user-registration-token --usage-limit 1 --expires-in 604800
   ```

   La réponse affiche le jeton, par exemple `Created user registration token:
   9SwPTGIFGQPa`. Le transmettre à l'ami.

2. L'ami ouvre `https://matrix.domain.tld/register` et choisit la création par
   mot de passe.

3. Il saisit son identifiant et son mot de passe, **puis** le jeton, réclamé à
   l'étape suivante.

4. Il se connecte ensuite avec ce couple identifiant / mot de passe depuis
   n'importe quel client, Element X compris.

</Steps>

<Aside type="tip" title="Gérer son compte">
Un ami change son mot de passe et révoque ses sessions depuis le portail
`https://matrix.domain.tld/account/`, sans intervention de l'administrateur.
</Aside>

</TabItem>
<TabItem label="Sans MAS">

<Steps>

1. Promouvoir le compte `matrix.admin` en *server admin* (une seule fois), sur
   l'hôte Matrix&nbsp;:

   ```sh
   sudo -u matrix-synapse psql matrix-synapse \
     -c "UPDATE users SET admin = 1 WHERE name = '@alice:domain.tld';"
   ```

2. Récupérer un *access token* du compte promu&nbsp;: dans Element,
   *Paramètres → Aide & à propos → Avancé*.

3. Créer un jeton d'inscription via l'API d'administration&nbsp;:

   ```sh
   curl -X POST \
     -A "Mozilla/5.0" \
     -H "Authorization: Bearer <ACCESS_TOKEN>" \
     -H "Content-Type: application/json" \
     -d '{"uses_allowed": 1, "expiry_time": null}' \
     https://matrix.domain.tld/_synapse/admin/v1/registration_tokens/new
   ```

   La réponse contient le `token` à transmettre à l'ami.

4. L'ami s'inscrit dans Element&nbsp;: *Créer un compte* → serveur `domain.tld`
   → il colle le jeton lorsqu'il est demandé.

</Steps>

<Aside type="caution" title="Le filtre anti-robots">
Le vhost Matrix renvoie `403` à tout appel dont l'*User-Agent* contient
`curl`, `wget` ou `bot`. D'où le `-A "Mozilla/5.0"` ci-dessus&nbsp;: sans lui,
l'appel échoue sans rapport avec le jeton.
</Aside>

</TabItem>
</Tabs>

### Collision d'identifiant avec un utilisateur déclaré

Amis et utilisateurs SSO partagent **un seul espace de noms**&nbsp;:
`@bob:domain.tld` n'appartient qu'à un compte, quelle que soit son origine. Et
un identifiant Matrix est **définitif** — la table `users` de MAS impose son
unicité, et désactiver un compte ne libère pas son identifiant. On ne renomme
pas, on ne recycle pas.

Le cas typique&nbsp;: un ami s'inscrit comme `bob`, puis `bob` est déclaré plus
tard comme utilisateur DNF dans `etc/config.yaml`. Sa première connexion SSO
s'arrête alors sur une page d'erreur **`User exists`**&nbsp;:

```text
Upstream account provider returned "bob" as username, which is not linked to
that upstream account. Your homeserver does not allow linking an upstream
account to an existing account
```

Vérifier avant de déclarer un utilisateur, sur l'hôte Matrix&nbsp;:

```sh
sudo -u postgres psql matrix-authentication-service \
  -c "SELECT username FROM users WHERE lower(username) = lower('bob');"
```

Deux issues, selon ce qu'on veut garder&nbsp;:

<Tabs>
<TabItem label="Fusionner les deux comptes">

Rattache l'identité Kanidm au compte ami existant, qui **conserve tout**&nbsp;:
salons, historique, clés de chiffrement, ponts. C'est presque toujours ce
qu'on veut, et l'intéressé le fait lui-même.

<Steps>

1. Déclarer d'abord `bob` dans `etc/config.yaml` et déployer, pour qu'il ait
   des identifiants Kanidm.

2. Bob se connecte sur `https://matrix.domain.tld/account/` avec son **mot de
   passe d'ami**.

3. Dans le **même navigateur**, il ouvre le lien de rattachement du
   fournisseur IDM&nbsp;:

   ```text
   https://matrix.domain.tld/upstream/authorize/01JDNF0000000000000KAN1DM0
   ```

4. Il s'identifie sur Kanidm&nbsp;; MAS propose alors «&nbsp;Lier à votre
   compte existant&nbsp;», qu'il valide.

</Steps>

Bob se connecte ensuite par le SSO comme n'importe quel utilisateur déclaré.
Son mot de passe d'ami reste valable&nbsp;: le supprimer se fait depuis le
portail de compte.

<Aside type="note" title="L'ULID du fournisseur">
`01JDNF0000000000000KAN1DM0` est fixé par le framework et identique sur tout
déploiement DNF (cf. [architecture](/fr/doc/admin-guide/understand/matrix/#authentification-nouvelle-génération-mas)).
</Aside>

</TabItem>
<TabItem label="Renoncer à l'identifiant">

Si le compte ami n'a rien à sauver, il reste plus simple de **déclarer
l'utilisateur DNF sous un autre login**&nbsp;: l'identifiant `bob` est perdu
pour de bon, désactiver le compte ami ne le rendra pas disponible.

Verrouiller l'ancien compte pour éviter la confusion&nbsp;:

```sh
sudo dnf-mas manage lock-user bob
```

</TabItem>
</Tabs>

<Aside type="caution" title="Pourquoi la fusion n'est pas automatique">
MAS sait rattacher tout seul une identité amont à un compte homonyme, via
`claims_imports.localpart.on_conflict`. DNF le laisse volontairement sur sa
valeur par défaut&nbsp;:

| Valeur | Effet |
|---|---|
| `fail` *(défaut DNF)* | Refuse la connexion amont |
| `add` | Rattache au compte homonyme, qu'un lien existe déjà ou non |
| `replace` | Remplace le lien existant de ce fournisseur sur ce compte |
| `set` | Rattache uniquement si ce fournisseur n'a pas déjà un lien |

Tout sauf `fail` signifie que **le premier venu dont le login Kanidm coïncide
avec un compte local en prend le contrôle**, sans que personne ne valide rien.
Sur un réseau où les logins sont attribués à la main, le risque est faible
mais le gain est nul&nbsp;: la fusion manuelle ci-dessus fait le même travail,
une fois, en connaissance de cause.
</Aside>

## Gérer les ponts

Les ponts WhatsApp, Signal, Telegram et Messenger sont **activés par
défaut** avec Matrix&nbsp;; Discord est **désactivé par défaut**. Réglage par hôte dans la
configuration nix de la machine&nbsp;:

```nix
# usr/machines/<host>/default.nix
darkone.service.matrix.bridges = {
  discord.enable = true;     # opt-in
  messenger.enable = false;  # désactiver un pont par défaut
};
```

Chaque pont a ses secrets propres&nbsp;:

| Pont | Clés sops | Remarque |
|---|---|---|
| WhatsApp | `mautrix-whatsapp-as-token`, `mautrix-whatsapp-hs-token`, `mautrix-whatsapp-encryption-pickle-key` | `openssl rand -hex 32` chacun |
| Signal | `mautrix-signal-as-token`, `mautrix-signal-hs-token`, `mautrix-signal-encryption-pickle-key` | `openssl rand -hex 32` chacun |
| Messenger | `mautrix-meta-as-token`, `mautrix-meta-hs-token`, `mautrix-meta-encryption-pickle-key` | `openssl rand -hex 32` chacun |
| Telegram | `mautrix-telegram-api-id`, `mautrix-telegram-api-hash`, `mautrix-telegram-as-token`, `mautrix-telegram-hs-token` | API id/hash à créer sur [my.telegram.org](https://my.telegram.org) |
| Discord | `mautrix-discord-as-token`, `mautrix-discord-hs-token` | `openssl rand -hex 32` chacun |

Les tokens `as`/`hs` rendent la *registration* appservice de chaque pont
déterministe (voir
[les tokens d'appservice](/fr/doc/admin-guide/understand/matrix/#les-tokens-dappservice)).

<Aside type="caution" title="Migration d'un pont déjà déployé">
Sur un pont WhatsApp ou Signal déployé **avant** l'introduction de ces tokens,
l'enregistrement existant conserve les anciens tokens auto-générés. Pour basculer
sur les tokens sops&nbsp;: supprimer `/var/lib/mautrix-<pont>/<pont>-registration.yaml`,
redémarrer le pont (l'enregistrement est régénéré depuis la config), puis
redémarrer `matrix-synapse`. Pour Messenger et Discord, un simple redéploiement
suivi d'un redémarrage de Synapse suffit&nbsp;: leurs modules réécrivent la
registration depuis la config à chaque démarrage.
</Aside>

### Permissions

Rien à gérer&nbsp;: tout compte local (`@*:domain.tld`) peut utiliser chaque
pont avec **son propre compte** distant, sans interférence entre
utilisateurs. Le compte `matrix.admin` dispose des commandes
d'administration des bots (`help` en conversation directe avec le bot pour
la liste).

{/* t:p 57866a0b0c836e99e3a85df4799b3a07fa81c8c06bcd8807ab57b6fae2e5fbb9 */}
### Double puppeting

Les ponts partagent un appservice `doublepuppet` (token
`mautrix-doublepuppet-as-token`)&nbsp;: les messages envoyés depuis le
téléphone apparaissent dans Matrix comme venant du **vrai compte** de
l'utilisateur. C'est automatique pour tous les comptes locaux, aucune action
par utilisateur.

## Appels audio et vidéo

Deux piles cohabitent, parce qu'aucune ne couvre tous les clients. Elles
s'activent séparément et ne se remplacent pas&nbsp;:

| | WebRTC historique | MatrixRTC |
|---|---|---|
| Option | `darkone.service.turn.enable` | `darkone.service.matrix.matrixRtc.enable` |
| Composants | coturn | LiveKit (SFU) + service d'autorisation |
| Appels à deux | oui | oui |
| Appels de groupe | non | oui |
| Element Classic (Android) | **oui** | non |
| Element Web / Desktop | oui | oui |
| **Element X** (Android, iOS) | **non** | **oui** |

Garder **les deux** activées&nbsp;: Element Classic ne parle que la première,
Element X que la seconde.

<Aside type="danger" title="Les deux piles ne se parlent pas">
Un appel lancé depuis Element X est **invisible** dans Element Classic, et
réciproquement&nbsp;: les deux signalent par des événements Matrix différents
(`m.call.*` contre `m.rtc.member`), et l'ancienne application ne contient
aucun code LiveKit. Aucune configuration serveur ne les réconcilie&nbsp;; côté
amont, le cas est
[classé «&nbsp;not planned&nbsp;»](https://github.com/element-hq/element-x-android/issues/3937).

Le seul client qui parle **les deux** est Element Web/Desktop&nbsp;: un
utilisateur resté sur Element Classic peut donc rejoindre un appel Element X
en ouvrant `https://element.domain.tld` dans le navigateur de son téléphone.
Sinon, migrer vers Element X — l'application classique est en maintenance
seule, sans nouvelle fonctionnalité.
</Aside>

<Aside type="caution" title="Element X : deux prérequis distincts">
Element X refuse d'appeler avec *«&nbsp;L'appel n'est pas pris en
charge&nbsp;»* (code `MISSING_MATRIX_RTC_TRANSPORT`) tant que MatrixRTC est
absent, **même** si MAS est actif. MAS conditionne la connexion, MatrixRTC les
appels&nbsp;: activer l'un ne donne pas l'autre.
</Aside>

<Steps>

1. Activer la pile MatrixRTC dans la config nix de l'hôte&nbsp;:

   ```nix
   # usr/machines/<host>/default.nix
   darkone.service.matrix = {
     mas.enable = true;         # requis par Element X pour se connecter
     matrixRtc.enable = true;   # requis par Element X pour appeler
   };
   ```

2. Générer le secret partagé, puis déployer&nbsp;:

   ```sh
   just configure-admin-host
   just apply <host> switch
   ```

3. Vérifier que le serveur annonce bien un transport&nbsp;:

   ```sh
   # doit contenir "org.matrix.msc4143.rtc_foci"
   curl -A Mozilla/5.0 https://domain.tld/.well-known/matrix/client

   # org.matrix.msc4143 doit valoir true
   curl -A Mozilla/5.0 https://matrix.domain.tld/_matrix/client/versions
   ```

</Steps>

Aucun sous-domaine ni certificat supplémentaire&nbsp;: le SFU et son service
d'autorisation sont servis sur le vhost Matrix, sous `/livekit/sfu` et
`/livekit/jwt`. Côté client, rien à régler non plus&nbsp;— Element X et Element
Web embarquent Element Call et découvrent le transport tout seuls.

### Ports média

Le média ne passe **pas** par le proxy inverse&nbsp;: les clients joignent
l'hôte directement. Ces ports doivent donc être ouverts jusqu'à lui, et
redirigés s'il est derrière un NAT&nbsp;:

| Port | Pile | Usage |
|---|---|---|
| 30000-30100/udp | MatrixRTC | Média WebRTC, un port par participant |
| 7881/tcp | MatrixRTC | Repli pour les réseaux qui bloquent l'UDP |
| 3478/udp, 3478/tcp, 5349/tcp | coturn | STUN et négociation TURN |
| 61000-65535/udp | coturn | Média relayé |

<Aside type="note" title="Pourquoi pas les plages par défaut">
Les deux plages amont tombent dans une fenêtre déjà occupée. Celle de LiveKit
(50000-51000/udp) est contenue dans la plage de relais par défaut de coturn
(49152-65535)&nbsp;: co-hébergés, les deux se disputeraient les mêmes ports et
feraient échouer des appels au hasard. Et cette plage coturn chevauche la plage
éphémère du noyau (`net.ipv4.ip_local_port_range`, 32768-60999 par
défaut)&nbsp;: n'importe quelle connexion sortante d'un service voisin peut y
voler un port média. DNF remonte donc coturn au-dessus de la plage éphémère et
descend LiveKit en dessous.
</Aside>

### Appels relayés en permanence

Un client WebRTC découvre son adresse publique avec une requête **STUN
Binding**, qu'il envoie toujours **sans authentification**, y compris vers le
serveur TURN. Si coturn la refuse (option `secure-stun`), le client n'obtient
aucun candidat *server-reflexive*&nbsp;: il ne lui reste que ses adresses
locales, inutilisables hors du réseau local, et son adresse de relais. Aucun
chemin direct n'est alors jamais tenté&nbsp;: **tous** les appels traversent
coturn, plus longs à s'établir et sans repli quand le relais sature.

DNF laisse donc `secure-stun` désactivé. Les allocations TURN, elles, restent
authentifiées par le secret partagé (`use-auth-secret`)&nbsp;: seul le Binding
est anonyme.

Contrôler depuis une machine extérieure&nbsp;:

```sh
nix shell nixpkgs#stuntman --command stunclient turn.domain.tld 3478
```

`Binding test: success` suivi de l'adresse vue par le serveur&nbsp;: correct.
`Binding test: fail`&nbsp;: les requêtes anonymes sont refusées, tous les
appels seront relayés.

## Ouvrir le réseau à la fédération

Par défaut, le serveur fédère avec **tous** les serveurs Matrix, tout en restant
**invisible dans les recherches** (annuaires non exposés). Pour contrôler la
portée, régler `darkone.service.matrix.federation` dans la config nix de
l'hôte&nbsp;:

```nix
# usr/machines/<host>/default.nix
darkone.service.matrix.federation = {
  enable = true;       # false = fédération totalement bloquée
  whitelist = [ ];     # vide = ouverte ; sinon liste blanche
};
```

| Objectif | Réglage |
|---|---|
| Réseau isolé (aucune fédération) | `enable = false;` |
| Ouvert à tout l'écosystème Matrix | `enable = true; whitelist = [ ];` |
| Restreint à des serveurs de confiance | `enable = true; whitelist = [ "ami.org" "matrix.org" ];` |

<Aside type="caution" title="Réseau familial">
La liste blanche est **bidirectionnelle**&nbsp;: un serveur non listé ne peut ni
écrire à vos utilisateurs ni recevoir d'eux. Pour un réseau utilisé par des
enfants, renseigner `whitelist` plutôt que de laisser la fédération ouverte.
</Aside>

Vérifier après déploiement&nbsp;:

<Steps>

1. Tester la fédération entrante avec
   [federationtester.matrix.org](https://federationtester.matrix.org/) sur
   `domain.tld` → tous les voyants verts.

2. En liste blanche, un serveur **non listé** est refusé (journal Synapse&nbsp;:
   `Federation denied`), un domaine listé fonctionne.

</Steps>

## Salons publics avec validation (knock)

Un salon **public** au sens Matrix se rejoint **librement**&nbsp;: pas de
validation. Pour un salon «&nbsp;joignable mais sur approbation&nbsp;», utiliser
la règle d'accès **knock** (toquer) — réglage **par salon**, côté client, sans
configuration serveur.

<Steps>

1. Dans Element&nbsp;: salon → *Paramètres du salon* → *Sécurité &
   confidentialité*.

2. Accès au salon → **«&nbsp;Demander à rejoindre&nbsp;»** (knock).

3. Un utilisateur (local ou distant fédéré) demande l'accès&nbsp;; un modérateur
   approuve ou refuse.

</Steps>

<Aside type="tip" title="Vraiment privé ?">
Pour un salon confidentiel&nbsp;: le retirer de l'annuaire **et** le passer en
`knock` ou sur invitation. Le chiffrement de bout en bout est déjà actif par
défaut sur les nouveaux salons.
</Aside>

### Administrer les comptes avec MAS

`dnf-mas` enveloppe l'outil officiel `mas-cli` sur l'hôte Matrix&nbsp;: il
reconstitue la configuration et les secrets du service, et fonctionne donc
**service arrêté comme démarré**. Toujours en `sudo`.

| Action | Commande |
|---|---|
| Créer un jeton d'inscription | `sudo dnf-mas manage issue-user-registration-token` |
| Promouvoir un administrateur | `sudo dnf-mas manage promote-admin alice` |
| Lister les administrateurs | `sudo dnf-mas manage list-admin-users` |
| Créer un compte (bot, service) | `sudo dnf-mas manage register-user` |
| Changer un mot de passe | `sudo dnf-mas manage set-password alice` |
| Fermer les sessions d'un compte | `sudo dnf-mas manage kill-sessions alice` |
| Verrouiller un compte | `sudo dnf-mas manage lock-user alice` |
| Diagnostic complet | `sudo dnf-mas doctor` |

<Aside type="caution" title="Plus de secret d'inscription partagé">
Avec MAS, `/_synapse/admin/v1/register` est désactivé. C'est le mécanisme
qu'utilise [`just configure-alert-bot`](/fr/doc/admin-guide/operate/justfile/)
pour créer un compte de bot manquant&nbsp;: créer ce compte **avant** de
migrer, ou le recréer avec `sudo dnf-mas manage register-user`.
</Aside>

### Diagnostiquer une connexion SSO refusée

Après une migration, les sessions déjà ouvertes continuent de fonctionner&nbsp;:
une connexion cassée ne se voit donc **qu'au premier login neuf**. Suivre MAS
pendant une tentative&nbsp;:

```sh
journalctl -u matrix-authentication-service -f
```

| Message | Cause | Correctif |
|---|---|---|
| `wrong signature alg` sur `/upstream/callback/…` | MAS attend un `id_token` RS256, Kanidm signe en ES256 | `id_token_signed_response_alg` du fournisseur amont&nbsp;: réglé sur `ES256` par le module |
| `client registration denied by the policy: invalid redirect_uri` | Le `client_uri` annoncé par le client ne correspond pas à son schéma de redirection | Ne pas forcer `oidc_metadata` dans la config Element&nbsp;; ses valeurs par défaut passent |
| `M_UNRECOGNIZED` sur `/login/sso/redirect` | Le chemin part vers Synapse au lieu de MAS | Vérifier le matcher `@masCompat` du vhost Caddy |
| Page `User exists` : «&nbsp;returned "bob" as username, which is not linked&nbsp;» | Un compte ami occupe déjà l'identifiant de l'utilisateur déclaré | Fusionner ou renommer (cf. [collision d'identifiant](#collision-didentifiant-avec-un-utilisateur-déclaré)) |
| «&nbsp;Le code QR n'est pas pris en charge&nbsp;» côté client | Le canal de rendez-vous MSC4108 est absent | `experimental_features.msc4108_enabled`&nbsp;: activé par le module avec MAS |
| «&nbsp;L'appel n'est pas pris en charge&nbsp;», `MISSING_MATRIX_RTC_TRANSPORT` | Aucun backend MatrixRTC annoncé | Activer `matrixRtc.enable` (cf. [Appels audio et vidéo](#appels-audio-et-vidéo)) |
| Appel qui sonne mais reste muet, ou coupe au bout de quelques secondes | Les ports média n'atteignent pas l'hôte | Ouvrir 30000-30100/udp et 7881/tcp jusqu'à lui |
| Appel long à s'établir, voire qui échoue, et tout le trafic passe par coturn | Les clients n'obtiennent aucun candidat *server-reflexive*, donc aucun chemin direct | coturn doit répondre aux requêtes STUN Binding **anonymes** (cf. [Appels relayés en permanence](#appels-relayés-en-permanence)) |

Contrôles rapides, sans se connecter&nbsp;:

```sh
# org.matrix.msc4108 doit valoir true
curl -A Mozilla/5.0 https://matrix.domain.tld/_matrix/client/versions

# doit répondre 201 et une url publique
curl -A Mozilla/5.0 -X POST --data probe \
  https://matrix.domain.tld/_matrix/client/unstable/org.matrix.msc4108/rendezvous
```

<Aside type="note" title="Deux symptômes, deux causes">
Un client qui bascule sur une authentification **dans le navigateur** au lieu
de son écran natif signale un refus d'enregistrement dynamique&nbsp;; l'erreur
qui suit éventuellement est un problème distinct. Traiter les deux.
</Aside>

### Diagnostiquer un bot muet

:::note[Vérifications côté client]
Vérifier sur le client (Element, Fractal...) que le bot n'est pas ignoré.
Faire un clic droit sur l'utilisateur correspondant au bot → information
→ sécurité, puis "ignoré". Si le bot répond bien dans les logs mais que
rien ne se passe, il se peut que le blocage soit côté client.
:::

Un bot qui ne répond pas à `help` alors que son service tourne tombe presque
toujours dans l'un des deux cas&nbsp;: ses tokens ne correspondent plus à la
registration chargée par Synapse, ou il reçoit les messages mais ne peut pas
les **déchiffrer**. Diagnostic dans l'ordre&nbsp;:

<Steps>

1. **Le service tourne-t-il vraiment ?**

   ```sh
   systemctl status mautrix-<pont>
   journalctl -u mautrix-<pont> -n 50
   ```

   S'il redémarre en boucle avec «&nbsp;The as_token was not accepted&nbsp;»,
   l'enregistrement en mémoire de Synapse ne correspond plus aux tokens du
   pont (typique après un reset ou une migration, voir l'encart plus
   haut)&nbsp;: `systemctl restart matrix-synapse`, puis redémarrer le pont.

2. **Le message arrive-t-il au pont ?** Suivre Synapse pendant l'envoi
   d'un `help` au bot&nbsp;:

   ```sh
   journalctl -u matrix-synapse -f | grep transactions
   ```

   Une ligne `PUT .../_matrix/app/v1/transactions/... 200` doit apparaître.
   Si rien ne part, l'appservice n'est pas chargé&nbsp;: vérifier la présence
   de l'enregistrement dans `/var/lib/mautrix-<pont>/` et redémarrer Synapse.

3. **Le pont peut-il le déchiffrer ?** Si la transaction passe (200) mais
   que le bot reste muet, suivre ses logs pendant un nouvel envoi&nbsp;:

   ```sh
   journalctl -u mautrix-<pont> -f
   ```

   Chercher `decrypt`, `session`, `verification`, `dropping`. Un échec de
   déchiffrement signifie que la clé de session du salon n'a pas été
   partagée avec le device actuel du bot (cas classique après un reset du
   pont&nbsp;: son identité e2ee a changé).

4. **Recréer la conversation.** Quitter le message direct avec le bot et en
   démarrer un nouveau&nbsp;: le client établit une session de chiffrement
   neuve et partage la clé avec le device actuel du bot. Vérifier au passage
   que sa propre session Element est **vérifiée**.

5. **Dernier recours**&nbsp;: réinitialiser l'état du pont (encart
   ci-dessous), puis redémarrer Synapse pour recharger l'enregistrement.

</Steps>

<Aside type="note" title="Statuts WhatsApp désactivés">
Le pont WhatsApp ne relaie pas les « statuts » (stories) : l'option
`network.enable_status_broadcast` est forcée à `false`, sans quoi chaque
utilisateur serait réinvité en boucle dans un salon « WhatsApp Status
Broadcast ».
</Aside>

<Aside type="caution" title="Réinitialiser un pont">
Les données d'un pont (sessions, correspondance des salons) vivent dans
`/var/lib/mautrix-*`. Supprimer ce répertoire déconnecte **tous** les
utilisateurs du pont et casse la correspondance des salons existants :
à ne faire qu'en dernier recours, service arrêté.
</Aside>
