Le parc se déploie avec [colmena](https://github.com/zhaofengli/colmena) : une
commande construit et applique la configuration sur un ou plusieurs hôtes, à
distance, depuis le poste admin.

{/* t:p d4a06fc139c0d5029ddc5205311c422d5da5a5e1fe1b2e6d014d42aae5b8629c */}
## Appliquer une configuration

```sh
just apply <cible> [action]    # alias : a
```

- **cible** = nom d'hôte, motif (`'*'`), liste (`a,b`) ou tag colmena (`@server`).
- **action** = `switch` (défaut), `boot`, `test` ou `build`.

| Commande | Pour quoi |
|---|---|
| `just apply <cible>` | Construire + activer sur la (les) cible(s) |
| `just apply-local` | Appliquer sur la machine courante (alias `al`) |
| `just apply-verbose <cible>` | Idem `apply` en mode trace (alias `av`) |

:::tip[Construire sur la cible]
`apply` construit **sur l'hôte cible** (`--build-on-target`) : le poste admin n'a
pas besoin de la puissance ni de l'architecture des machines déployées.
:::

## Déployer en sécurité

**Monter en confiance par l'action** : chaque étape est moins risquée que la
suivante.

```sh
just apply <hôte> build      # télécharge + compile : 100 % sûr, rien n'est activé
just apply <hôte> test       # active sans switcher : ni génération, ni boot
just apply <hôte>            # switch : active et crée une nouvelle génération
```

**Progresser du cœur vers la périphérie** : déployez les nœuds dans cet ordre,
pour ne jamais vous couper l'accès à un nœud par celui qui le précède.

```d2
style.fill: transparent
direction: right

hcs: HCS
gwl: Passerelle locale
hl: Hôtes locaux
gwd: Passerelles distantes
hd: Hôtes distants

hcs -> gwl -> hl -> gwd -> hd
```

:::caution[Pourquoi cet ordre]
La connectivité d'un hôte distant dépend de sa passerelle, qui dépend du VPN
coordonné par le HCS. Déployer un maillon avant son support peut rendre les
suivants injoignables.
:::

## Mettre à jour

Le système est figé par les *flakes*. Mettre à jour = rafraîchir les entrées,
puis redéployer.

```sh
just update-flake     # met à jour dnf/ + racine, commit les locks
just apply '*'        # déploie la mise à jour
```

:::caution[Toujours tester avant]
Avant un déploiement large, validez localement : `just check`, puis
`just apply <hôte-pilote>` sur **un** hôte témoin.
:::

## Mettre à jour le parc avec fleet-update

`fleet-update` enchaîne toute la mise à jour en une commande&nbsp;: flakes,
construction de tous les hôtes, test par vagues (les hôtes dont dépend le
réseau d'abord), puis activation définitive des hôtes validés.

![Interface de fleet-update](../../../../../../assets/dfu-screenshot-01.png)

:::caution[Options pas encore disponibles]
Les options `--ai-*` sont acceptées, sans effet pour l'instant.
:::

### Lancer

```sh
just fleet-update [options]
```

La recette choisit l'outil à lancer, dans cet ordre&nbsp;:

| Situation | Outil lancé |
|---|---|
| Co-développement (`src/dnf-fleet-update/` présent) | Les sources, avec `bun` |
| Module `darkone.admin.fleet-update` actif | La commande `fleet-update` installée |
| Autre cas | `nix run .#fleet-update`, selon le `flake.lock` du projet |

:::caution[Prérequis]
- Arbres git propres : projet, et `dnf/` en co-développement.
- `var/deployments/` ignoré par git : règle `/var/*` du boilerplate.
:::

{/* t:p 5a5612c044a6c26c7b9082190d8fa9494c2c9c9af02ece0f48358324cbbf49d3 */}
### Le déroulé d'un lancement

<Steps>
1. **Mise à jour** : `nix flake update` du projet puis de `dnf/` (co-développement), `just clean`, un commit par dépôt.
2. **Sélection** : hôtes, profils et zones lus dans `var/generated/`, filtrés par `--on` ; zone courante déduite de l'IP locale.
3. **Construction** : tous les hôtes sélectionnés, joignables ou non, sur la machine de déploiement.
4. **Test** : `switch-to-configuration test`, une vague par profil ; la vague suivante démarre quand tous ses hôtes sont OK ou écartés.
5. **Switch** : tous les hôtes validés en test, **d'un seul coup**, hors ordre des vagues.
</Steps>

Trois options raccourcissent ce déroulé&nbsp;:

| Option | Effet |
|---|---|
| `--build-only` | S'arrête après la construction ; en interactif, propose de continuer |
| `--skip-test` | Pas de test : le switch se fait vague par vague, directement après la construction |
| `--skip-switch` | Pas de switch : le lancement s'arrête sur ce que le test a laissé en place |

:::note[Pourquoi le switch n'est pas par vagues]
Les vagues protègent une configuration non prouvée. Une fois le test réussi sur
chaque hôte, il n'y a plus rien à protéger&nbsp;: le switch part en une fois, au
plus `--max-parallel` hôtes activés simultanément. Avec `--skip-test`, rien n'a
été prouvé&nbsp;: le switch reprend l'ordre des vagues.
:::

:::tip[Reprendre un lancement interrompu]
`--resume` repart du dernier dossier de `var/deployments/`&nbsp;: mise à jour
sautée, vagues et options du lancement d'origine, et les hôtes qui restaient à
faire (restants, hors ligne, en échec, ou seulement testés). Les constructions
sont réutilisées si les révisions du projet et de `dnf/` n'ont pas bougé et que
les chemins sont encore dans le store&nbsp;; sinon elles sont refaites. Rien à
reprendre&nbsp;: code de sortie `2`, aucun lancement.
:::

### Ordre des vagues et hôtes critiques

Les valeurs par défaut du parc se déclarent dans `config.yaml`&nbsp;:

```yaml
# etc/config.yaml
network:
  fleetUpdate:
    deploymentOrder: "hcs:gateway:server:[others]:laptop"
    criticalProfiles: "hcs:gateway:server"
```

| Clé | Rôle |
|---|---|
| `deploymentOrder` | Une vague de test par profil d'hôte, dans cet ordre |
| `criticalProfiles` | Profils dont les échecs vont aussi au salon des incidents |

Profils séparés par `:`, `[others]` désigne les profils non listés. Bloc
facultatif&nbsp;: sans lui, l'outil applique les valeurs ci-dessus. Les options
`--deployment-order` et `--critical-profiles` priment sur `config.yaml`.

### Délais et surveillance

Deux autres blocs facultatifs de `config.yaml` règlent les durées&nbsp;:

```yaml
# etc/config.yaml
network:
  fleetUpdate:
    pingInterval: 15
    timeouts:
      build: 10800
      ssh: 30
```

| Clé | Rôle | Défaut |
|---|---|---|
| `pingInterval` | Secondes entre deux pings des hôtes suivis | `15` |
| `timeouts.<clé>` | Durée maximale d'une opération, en secondes | selon l'opération |

Clés de `timeouts`, dans l'ordre du déroulé&nbsp;:

| `timeouts.<clé>` | Défaut (s) |
|---|---|
| `flakeUpdate` | 120 |
| `clean` | 60 |
| `commit` | 60 |
| `eval` | 1200 |
| `build` | 10800 |
| `copy` | 3600 |
| `activation` | 300 |
| `ssh` | 30 |
| `ping` | 5 |
| `matrix` | 30 |
| `killGrace` | 10 |

:::note[Une clé inconnue arrête la génération]
`just generate` vérifie les noms de clés et refuse un délai nul ou négatif&nbsp;:
une faute de frappe retomberait sinon sur la valeur par défaut, en silence.
:::

### Rapport et alertes Matrix

Chaque lancement écrit son dossier dans `var/deployments/<date>-<mode>/`&nbsp;:
`report.md` (le rapport), `state.json` (l'état que `--resume` reprend),
`events.jsonl` et les journaux par hôte. Le chemin s'affiche en fin de lancement.

L'option `--send-report` envoie ce rapport aux salons du
[bot d'alertes](/fr/doc/admin-guide/operate/alerts/), installé au préalable par
`just configure-alert-bot`.

| Situation | Salon | Contenu |
|---|---|---|
| Lancement terminé | warnings | Résumé&nbsp;: hôtes par état, durée, erreurs connues |
| Hôtes critiques non déployés | incidents | Message séparé&nbsp;: hôtes concernés et raisons |
| Arrêt sur erreur | incidents | Erreur qui a arrêté le lancement, puis résumé |

Un hôte est critique quand son profil figure dans `criticalProfiles`. Après un
arrêt, les hôtes laissés en `test` complètent le message d'incident&nbsp;: un
redémarrage les ramènerait à leur génération précédente.

:::note[Envoi impossible]
Le lancement reste valide et le rapport est écrit, mais la commande sort en `3`.
Sous le timer, l'unité passe en échec, donc l'alerte `SystemdUnitFailed`.
:::

:::caution[Ce que l'envoi exige]
Le compte qui lance l'outil déchiffre le jeton `alertmanager-matrix-token` avec
sa clé age, et les salons viennent de `var/generated/matrix.nix`. Un abandon
(`^C`, arrêt du service) n'envoie rien.
:::

### Exécution quotidienne

Sur l'hôte de déploiement, le module installe l'outil et, avec `timer.enable`,
lance chaque jour `fleet-update --no-ui`&nbsp;:

```nix
# usr/machines/<hôte>/default.nix
darkone.admin.fleet-update = {
  enable = true;
  user = "admin";
  timer.enable = true;
};
```

| Option | Défaut | Rôle |
|---|---|---|
| `user` | aucun | Propriétaire du projet : git, clé age, IA, Matrix |
| `workDir` | `/etc/nixos` | Projet consommateur sur le disque |
| `timer.onCalendar` | `*-*-* 04:00` | Heure de lancement |
| `timer.extraArgs` | `[ ]` | Options ajoutées à `--no-ui`, `--send-report` par exemple |
| `timer.timeout` | `6h` | Durée maximale d'un lancement |

:::note[Codes de sortie et alertes]
Un lancement déjà en cours (code `4`) n'est pas une erreur. Tout autre échec,
ou un dépassement de `timer.timeout`, met l'unité en échec et déclenche
l'[alerte](/fr/doc/admin-guide/operate/alerts/) `SystemdUnitFailed`.
:::

:::caution[Compte et hôte de déploiement]
Le timer exige `darkone.admin.nix` sur l'hôte, et un compte `user` disposant de
`sudo` sans mot de passe.
:::

:::note[Rapport quotidien]
`--send-report` deviendra le défaut de `timer.extraArgs` quand la version
empaquetée de l'outil saura l'envoyer. Ajoutez-la d'ici là, après avoir vérifié
l'envoi à la main.
:::

## Cache binaire

Deux services se combinent pour éviter de recompiler ou de retélécharger les
dérivations à chaque déploiement.

| Service | Rôle |
|---|---|
| `harmonia` | Sert le `/nix/store` local, signé, **directement** aux hôtes (LAN, ou VPN s'il est `global`). |
| `nix-cache` | Proxy `nginx` par zone qui met en cache le cache public `cache.nixos.org` sur la passerelle. |

Un hôte interroge ces sources dans l'ordre de priorité suivant. La première
récupération depuis Internet est ainsi mutualisée pour toute la zone.

| Priorité | Source | Portée |
|---|---|---|
| 20 | `harmonia` de la zone | LAN, ce que la zone a compilé |
| 35 | proxy `nix-cache` de la zone | LAN, miroir mutualisé du cache public |
| 40 | `cache.nixos.org` en direct | filet de sécurité si la passerelle est HS |
| 45 | `harmonia` `global` | dernier recours, par le VPN |

:::note[Comment l'ordre est garanti]
Nix ne suit pas l'ordre de la liste `substituters`, il trie les caches selon la
priorité que chacun annonce dans son `nix-cache-info`. Or ces valeurs annoncées
sont à égalité&nbsp;: toutes les `harmonia` déclarent 30, et le proxy relayant
`cache.nixos.org` tel quel déclare 40, comme l'accès direct au cache public.
DNF fixe donc la priorité dans l'URL du substituter (`?priority=35`), ce qui
écrase la valeur annoncée et rend l'ordre du tableau explicite.

Deux conséquences voulues. Le proxy de zone passe **devant** l'accès direct au
cache public, sans quoi la mutualisation de zone ne se ferait jamais. Et une
`harmonia` `global` passe **derrière** ce cache public&nbsp;: `harmonia` sert un
`/nix/store` entier, sans pouvoir distinguer ce qu'elle a compilé du reste, donc
un hôte bien garni capterait tout le trafic que le cache public doit servir. En
dernier recours, elle n'est consultée que pour ce que `cache.nixos.org` n'a pas,
c'est-à-dire ses propres constructions.
:::

:::note[Un hôte ne se sert pas de sa propre `harmonia`]
Ce service sert son propre `/nix/store`, il ne peut donc fournir que des chemins
déjà présents localement. Sur cet hôte, tout ce qui manque vient forcément d'une
autre source&nbsp;: c'est normal, sa `harmonia` ne profite qu'aux **autres**
machines de la zone.
:::

:::tip[Hôte nomade (portable multi-zones)]
Un portable qui change de zone ne doit pas garder des substituters figés sur sa
zone déclarée&nbsp;: injoignables ailleurs, ils coûtent des timeouts à chaque
requête. Activez le mode *roaming*&nbsp;:

```nix
# usr/machines/<hôte>/default.nix
darkone.service.nix-cache.roaming = true;
```

Ses substituters deviennent des noms **neutres** (`harmonia.dnf.internal`,
`nix-cache.dnf.internal`) que le DNS de chaque zone résout vers ses propres
caches → le cache suit la machine. Hors de toute zone, réponse NXDOMAIN
immédiate → repli direct sur `cache.nixos.org`, sans délai. Les clés de
signature étant communes à tout le réseau, rien d'autre à configurer.
:::

:::note[Activation]
`harmonia` et `nix-cache` sont des [services](/fr/doc/admin-guide/operate/services/)
à activer sur un hôte du réseau (`nix-cache` sur la passerelle de zone). La clé
de signature de harmonia est gérée par
[sops](/fr/doc/admin-guide/operate/secrets/) (`just configure-admin-host`).
:::

:::tip[Pourquoi un proxy à upstream unique]
`nix-cache` ne relaie qu'**un seul** upstream (`cache.nixos.org`)&nbsp;: il met
en cache `narinfo` et `nar` tels quels, signatures intactes. Pas de réécriture
d'URL ni de base de données, donc pas l'erreur HTTP 500 « invalid nar hash » de
l'ancien relais `ncps`.
:::

## Ferme de build

Récupérer un paquet et le construire sont deux besoins distincts. Le cache
binaire ci-dessus couvre le premier. Pour le second, un hôte puissant du réseau
peut prendre à sa charge les compilations longues d'un hôte d'administration.

Déclarez-le par la fonctionnalité `build-farm`&nbsp;:

```yaml
# etc/config.yaml
    features: ["build-farm"]
```

Chaque hôte d'administration l'ajoute alors à ses `nix.buildMachines`, joint en
SSH par le compte de déploiement `nix`. Rien d'autre à configurer&nbsp;: la clé
et l'autorisation sont déjà en place sur tout le parc.

:::tip[Seules les compilations longues partent]
La délégation est volontairement étroite&nbsp;: la ferme ne se voit proposer que
les dérivations déclarant `requiredSystemFeatures = [ "big-parallel" ]`, soit le
noyau, les navigateurs, `llvm`, `rustc`… Tout le reste est construit sur place.
C'est décisif quand la ferme est derrière une liaison lente, puisque seul le
résultat demandé fait le trajet retour.

Ajustez avec `darkone.admin.nix.remoteBuilders`&nbsp;: `maxJobs`, `speedFactor`,
et `mandatoryFeatures` (liste vide = tout part à la ferme).
:::

:::caution[Une ferme n'est pas un cache prioritaire]
Ne promouvez pas une ferme distante en `harmonia` `global` prioritaire pour
partager ses résultats&nbsp;: `harmonia` sert le `/nix/store` entier et
capturerait le trafic que le cache public doit servir, à travers la liaison la
plus lente du réseau. C'est le rôle du niveau 45 du tableau plus haut&nbsp;:
dernier recours, jamais source principale.
:::

:::note[Repli si la ferme est injoignable]
L'hôte d'administration conserve `big-parallel` dans ses propres
`system-features`. Quand la ferme ne répond pas, Nix reprend simplement la
compilation en local au lieu d'échouer. Ne retirez pas cette fonctionnalité pour
forcer la délégation.
:::
