## Créer un compte Linux (POSIX)

Les utilisateurs sont déclarés **une fois** dans `etc/config.yaml`, puis
**rattachés** aux hôtes où ils doivent ouvrir une session. Le même compte peut
exister sur plusieurs machines.

:::tip[Création de bout en bout]
Coffre-fort, identité Kanidm, alternatives&nbsp;: voir
[Créer un compte utilisateur](/fr/doc/admin-guide/operate/onboarding/).
:::

### Déclarer un utilisateur

```yaml
# etc/config.yaml
users:
  alice:
    uid: 1000
    name: "Alice Martin"
    email: "alice@domain.tld"
    profile: "advanced"
    groups: ["global", "idm-devs"]
```

| Champ | Rôle |
|---|---|
| *(clé)* | Login du compte (ex. `alice`) |
| `uid` | Identifiant numérique stable |
| `name` | Nom affiché |
| `email` | Adresse (sert aussi à l'identité SSO) |
| `profile` | [Profil utilisateur](/fr/doc/admin-guide/understand/user-profiles/) (environnement) |
| `groups` | Groupes (accès réseau et [services](/fr/doc/admin-guide/operate/sso/#identités-et-groupes)) |

Le déploiement du HCS lui crée aussi un compte [Kanidm](/fr/doc/admin-guide/operate/sso/),
sans identifiant.

### Rattacher à un hôte

Sous un hôte, `users` liste les **logins existants** autorisés à s'y connecter :

```yaml
# etc/config.yaml
hosts:
  poste-alice:
    profile: "desktop"
    users: ["alice"]
```

:::tip[Via un groupe]
Autre possibilité : rattacher un utilisateur à un hôte grâce à un groupe commun déclaré dans la liste `groups` commune.
:::

### Déployer les modifications

Toute modification de `etc/config.yaml` suit le **même cycle** :

<Steps>

1. **Décrire le changement**

   Créer ou modifier l'utilisateur et ses postes dans `etc/config.yaml`.

2. **Régénérer et nettoyer le code**

   ```sh
   just clean       # generate + fix + format
   ```

3. **Valider dans git**

   ```sh
   just commit "user(new): alice"
   ```

4. **Déployer**

   ```sh
   just apply @user-alice,hcs     # postes d'alice + compte Kanidm
   ```

</Steps>

:::caution[Toujours committer avant de déployer]
`just clean` réécrit `var/generated/`. Sans `clean` + `commit`, le
déploiement part d'un état incohérent ou non versionné.
:::

### Définir le mot de passe

<Steps>

1. **Définir l'empreinte**

   ```sh
   just passwd alice
   ```

   L'utilisateur peut saisir lui-même son mot de passe. À distance, il envoie
   son empreinte (`mkpasswd -m sha-512`), à coller avec `just sops` sous
   `user.alice.password-hash`.

2. **Valider dans git**

   ```sh
   just commit "chore(user): alice password"
   ```

3. **Déployer**

   ```sh
   just apply @user-alice,hcs
   ```

</Steps>

:::note[Seul `just passwd` fait foi]
- Pas de session avant `just passwd <login>`.
- Changé sur un hôte, le mot de passe est écrasé au déploiement suivant.
- `just passwd-default` n'enregistre que le mot de passe de référence du parc ([Secrets](/fr/doc/admin-guide/operate/secrets/)).
:::

## Accès SSH

L'accès SSH est **par clé uniquement** et **entièrement déclaratif**, sur toute
la flotte&nbsp;:

- Mot de passe et clavier interactif sont désactivés.
- Déclarer les clés dans `users.users.<login>.openssh.authorizedKeys`.
- Un compte sans clé déclarée peut ouvrir une session locale, hors SSH.

:::note[La forge fait exception]
Le compte `forgejo` sert le `git push` de tous les dépôts : ses clés sont
celles que chaque utilisateur dépose dans l'interface web de la forge, pas
celles de la configuration NixOS. `sshd` les lui demande par
`AuthorizedKeysCommand` et non par un fichier. Une clé s'ajoute donc dans
Forgejo (**Paramètres → Clés SSH / GPG**).
:::

### Interdire SSH à un groupe

Les `groups` de `config.yaml` sont **logiques** : ils ne deviennent pas des
groupes Unix, `DenyGroups` ne verrait donc rien. DNF les traduit en `DenyUsers`,
hôte par hôte :

```nix
# Défaut : les comptes invités gardent leur session locale, pas SSH.
darkone.user.build.sshDeniedGroups = [ "guests" ];
```

## Désactiver un compte

- **Sur un hôte** : retirer le login de la liste `users` de l'hôte.
- **Partout** : retirer l'entrée sous `users:`.
- **Accès services** : retirer l'utilisateur des `groups` coupe l'accès SSO.

Dans tous les cas, appliquer ensuite le cycle `just clean` → `just commit` →
`just apply` sur les hôtes concernés.
