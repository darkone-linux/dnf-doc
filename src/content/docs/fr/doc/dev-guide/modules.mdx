Les fonctionnalités du framework sont fournies sous forme de **modules NixOS**
haut-niveau, regroupés par catégorie sous `dnf/modules/` et documentés dans la
[référence des modules](/fr/ref/modules/).

{/* t:p 3bf80247fe9f1844ccc35d0dadbe9a13f383bf4093b643b67a071c590dbb6c9e */}
## Catégories

- **standard** : `system`, `security`, `console`, `graphic`, `service`, `admin`, `user`.
- **mixin** : macro-modules composant des profils d'hôtes et compléments de profils utilisateurs.
- **home** : modules et profils [Home Manager](https://github.com/nix-community/home-manager).

{/* t:p 10a2f5c71d2c646b2d53ca8137f3e4f6072a9a49d2df2de909140905cf84f2ed */}
## Créer un module

<Steps>

1. Choisir la catégorie (`dnf/modules/<catégorie>/` ou `dnf/modules/mixin/`).
2. Écrire l'en-tête du fichier selon les règles (voir [headers de code](/fr/doc/how-to/dev/code-headers/)).
3. Déclarer les `options` puis la `config` du module.
4. Régénérer (`just generate`) et tester avant de commiter.

</Steps>

Pour un service auto-hébergé (web UI, API, stockage…), suivre le guide dédié
[Créer un module de service](/fr/doc/dev-guide/create-service-module/) : reverse
proxy, persistance, pare-feu, SSO Kanidm et activation par hôte.

:::note[Référence du code]
Le détail des options exposées par chaque module est généré automatiquement
dans la [référence](/fr/ref/modules/) → ne pas l'éditer à la main.
:::

## Anatomie d'un module

Un module DNF suit le patron NixOS classique : un en-tête, un bloc `options` et
un bloc `config` activé par `enable`.

```nix
# dnf/modules/service/hello.nix
{ lib, config, ... }:
let
  cfg = config.darkone.service.hello;
in
{
  options.darkone.service.hello = {
    enable = lib.mkEnableOption "Enable the hello service";
    port = lib.mkOption {
      type = lib.types.port;
      default = 8080;
      description = "Listening port.";
    };
  };

  config = lib.mkIf cfg.enable {
    # ... configuration réelle, activée seulement si enable = true
  };
}
```

## Convention de nommage

Toutes les options du framework vivent sous l'espace de noms `darkone` :

```
darkone.<catégorie>.<nom>.<option>
```

- `darkone.service.immich.enable` : un service.
- `darkone.system.security.level` : un réglage système.
- `darkone.host.desktop.enable` : un profil d'hôte (mixin).

:::tip[Toujours un `enable`]
Chaque module expose un `enable` (souvent `mkEnableOption`) et garde sa `config`
sous `lib.mkIf cfg.enable` : un module inactif n'a **aucun** effet.
:::

## Les helpers (`dnfLib`)

`dnfLib` (défini dans `dnf/lib/`) fournit les fonctions transverses, injectées
dans chaque module. Les plus utiles :

| Helper | Rôle |
|---|---|
| `extractServiceParams` / `buildServiceParams` | Lire les paramètres d'un service (domaine, titre, icône…). |
| `serviceHref` | Résoudre l'URL publique d'un service déclaré ailleurs sur le réseau. |
| `mkOidcContext` / `mkKanidmEndpoints` | Brancher un service au SSO Kanidm (OIDC). |
| `mkInternalFirewall` | Ouvrir des ports sur l'interface interne uniquement. |
| `findHost` / `findService` / `isGateway` / `isHcs` | Interroger la topologie réseau. |
| `mkHomepageSection` | Déclarer l'entrée du portail. |
| `mkIsActive` | Activer une règle de sécurité selon niveau/catégorie. |

:::note[Avant d'écrire un helper]
Vérifier `dnf/lib/default.nix` : la fonction existe peut-être déjà. Réutiliser
plutôt que dupliquer.
:::

## Le registre des services

Un service déclare sa **topologie** dans `dnf/config/modules.nix` (et non dans
son `.nix`) : reverse proxy, unicité par zone, accès externe, activation
automatique par profil d'hôte.

```nix
# dnf/config/modules.nix
adguardhome = {
  uniquePerZone = true;
  activation.profiles.gateway.triggers.keys.adguardhome = [ "enable" ];
};
```

| Drapeau | Défaut | Effet |
|---|---|---|
| `reverseProxy` | `true` | Le service est exposé via Caddy. |
| `uniquePerZone` | `false` | Un seul exemplaire admis par zone. |
| `externalAccess` | `false` | Joignable hors zone (via le HCS). |
| `require` | `[ ]` | Services à activer sur le **même hôte** (sinon erreur de génération). |
| `activation.profiles.<profil>` | | Activé d'office sur les hôtes d'un profil. |

:::caution[Valeurs littérales uniquement]
Le générateur lit ce fichier comme du texte, sans l'évaluer : pas de `let`, de
fonction, de `//`, d'`inherit` ni d'interpolation. Il refuse ce qu'il ne sait
pas lire, plutôt que d'appliquer un défaut.
:::

## Le `default.nix` généré

Chaque dossier de modules possède un `default.nix` qui **importe** ses fichiers.
Il est **généré** par `just generate` (liste des imports) → ne pas l'éditer.

```sh
just generate    # régénère les default.nix + var/generated/
```

:::caution[Nouveau fichier = régénérer]
Un module ajouté n'est pris en compte qu'après `just generate` (ou `just clean`),
qui l'inscrit dans le `default.nix` du dossier.
:::
