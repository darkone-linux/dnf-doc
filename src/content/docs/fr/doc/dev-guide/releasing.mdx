Publier, c'est produire des tags cohérents sur les six dépôts en une seule
commande, depuis l'espace de co-développement.

## Ce que chaque dépôt versionne

| Dépôt | Source de vérité | Règle |
| --- | --- | --- |
| `darkone-nixos-framework` | `VERSION` | Référence du train |
| `dnf-generator` | `Cargo.toml` | Version propre, épinglée par le framework |
| `dnf-fleet-update` | `package.json` | Version propre, empaquetée par le framework |
| `dnf-doc` | `package.json` | `MAJEUR.MINEUR` du framework, correctif propre |
| `dnf-boilerplate`, `dnf-example` | dernier tag | Miroir du framework |

Les six dépôts tiennent un `CHANGELOG.md` généré, modèles compris.

Le projet privé consommateur n'est jamais taggué : il reste en
co-développement et sert de banc d'intégration permanent.

## Le vocabulaire de commit

Le changelog est généré à partir des messages de commit. Un type hors liste
disparaît silencieusement des notes de version, donc le format est vérifié :
une seule ligne `<type>(<scope>): <sujet>`, 80 caractères max, type de la liste
suivante.

```
feat fix perf refactor docs test build ci chore security revert
```

Le même script, `scripts/check-commit-msg.sh`, contrôle chaque *push* vers
`main` et chaque *pull request* dans l'intégration continue, et chaque commit
en local via le hook `commit-msg`, à installer une fois par clone :

```sh
ln -s ../../scripts/check-commit-msg.sh .git/hooks/commit-msg
```

Un scope n'est jamais un type&nbsp;: `feat(matrix): …`, jamais `matrix(admin): …`.

| Type | Section du changelog |
| --- | --- |
| `feat` | Added |
| `fix` | Fixed |
| `security` | Security |
| `perf`, `refactor`, `revert` | Changed |
| `docs` | Documentation |
| `chore(deps)` | Dependencies |
| sujet en `drop` ou `remove` | Removed |
| autres `chore`, `ci`, `test`, `build` | non publié |

`chore(deps)` est le commit d'épinglage du train&nbsp;: l'entrée du framework
nomme ainsi le générateur et le `fleet-update` qu'elle embarque.

<Aside type="caution" title="Marquer une rupture">
Une rupture porte un `!` après le scope, et son sujet nomme la surface cassée.
Pas de pied `BREAKING CHANGE:` : le message tient sur une ligne, la migration
est décrite dans la documentation. C'est le `!` qui déclenche la section
**⚠ Breaking** et la montée du numéro mineur.

```
feat(idm)!: replace network.idm.replicas with zones.<zone>.idm
```
</Aside>

## Les recettes

| Recette | Effet |
| --- | --- |
| `just versions` | Version, dernier tag et branche de chaque dépôt |
| `just changelog` | Aperçu de la prochaine entrée, n'écrit rien |
| `just bump [niveau]` | Version, changelog, commit et tag d'**un** dépôt |
| `just release [niveau]` | Le train complet sur les six dépôts (+ la racine) |
| `just version` | Version, révision et générateur épinglé du framework |

Le niveau vaut `auto` par défaut&nbsp;: [git-cliff](https://git-cliff.org/) déduit
le numéro suivant des commits. `patch`, `minor`, `major` ou un `X.Y.Z` littéral
forcent la décision. Des commits non publiés seuls (un `chore(deps)`, par
exemple) donnent un correctif.

`just bump` ne pousse jamais : il affiche la commande de poussée. Il refuse de
publier si `HEAD` porte déjà le dernier tag `v*`. Trois drapeaux passent au
script&nbsp;:

- `--dry-run` : montre l'entrée puis restaure le fichier, sans rien commiter ;
- `--yes` : enchaîne sans confirmation ni passage dans `$EDITOR` ;
- `--next` : affiche la version que prendrait la release, puis s'arrête.

<Aside type="tip" title="Lancer depuis l'environnement de développement">
`bump` et `changelog` appellent [git-cliff](https://git-cliff.org/), absent du
`PATH` par défaut. Entrer dans l'environnement avec `just develop` avant de
publier.
</Aside>

## Écrire à la main dans une entrée

Le bloc généré ne contient que des messages de commit. Un préambule, un tableau
de versions compagnes ou une note de migration s'écrivent sous
`## [Unreleased]` dans le `CHANGELOG.md`&nbsp;: à la publication, le script vide
cette section et replie son contenu en tête de l'entrée, avant les rubriques
générées. Le train ne s'arrête pas pour éditer&nbsp;: ces notes s'écrivent
**avant** de le lancer.

<Aside type="caution" title="Ne rien laisser après les notes">
La section court jusqu'au titre `##` suivant. Si les liens de référence de bas
de page sont le dernier contenu du fichier, ils sont avalés dans l'entrée
publiée. Les retirer, le script les régénère.
</Aside>

<Aside type="note" title="La toute première release">
Sans tag `v*`, `auto` n'a rien à déduire&nbsp;: le script reprend la version
déclarée telle quelle, et git-cliff remonte jusqu'au premier commit du dépôt.
L'entrée couvre alors tout l'historique. Un modèle, sans fichier de version,
exige un `X.Y.Z` explicite (le train passe celui du framework).
</Aside>

## Le train de release

`just release` s'exécute à la racine de l'espace de co-développement, qui doit
contenir les six dépôts. Chaque dépôt part dans l'ordre de ses dépendances, et
seulement s'il a bougé depuis son dernier tag.

<Steps>

1. **Contrôles préalables**&nbsp;: outils présents (`git-cliff`, `jq`,
   `nix-update`), dépôts propres, sur `main`, à jour de `origin`. Rien de long
   ne tourne avant.

2. **Plan**&nbsp;: version actuelle et prochaine de chaque dépôt, aperçu des
   entrées de changelog, puis **une seule** confirmation. Refuser n'écrit rien.
   Ensuite, tout est automatique.

3. **Barrière globale**&nbsp;: `just check` (code et tests unitaires).

4. **Générateur**, s'il a bougé&nbsp;: `just gen-test`, release et poussée. Il
   possède le schéma `etc/config.yaml`, donc il part avant ce qui en dépend.
   Son tag est ensuite épinglé dans `dnf/flake.nix` (commit `chore(deps)`),
   pour que le contrat entre framework et générateur se lise dans un diff.

5. **fleet-update**, s'il a bougé&nbsp;: barrières `ci` et `audit` avec
   l'outillage de son `nix develop`, release et poussée. Son tag est ensuite
   épinglé dans `dnf/pkgs/fleet-update` par `just pkg-update`, et le paquet
   est construit (commit `chore(deps)`).

6. **Framework**&nbsp;: `just simulate all` tourne **après** les épinglages,
   donc sur les dépendances réellement livrées. Les tests en machine virtuelle
   ne tournent pas dans l'intégration continue&nbsp;: un scénario rouge arrête
   le train ici. Puis `VERSION`, `CHANGELOG.md`, commit, tag et poussée.

7. **Documentation**&nbsp;: `just codegen` régénère la référence, puis
   traduction et normalisation. S'il y a quelque chose à publier, le site est
   construit (avant le tag, pour qu'un lien cassé bloque), la version s'aligne
   sur la ligne `MAJEUR.MINEUR` du framework, puis le site est déployé.

8. **Boilerplate et exemple**&nbsp;: le tag du framework est écrit dans leur
   `flake.nix`, le `flake.lock` est **commité** (c'est lui qui rend un clone
   reproductible), puis changelog et tag identique à celui du framework.
   `nix flake check` valide l'exemple ; le boilerplate, livré sans
   `var/generated/`, n'a rien à évaluer avant `just generate`.

9. **Racine**&nbsp;: `just update-dnf`, commit du seul `flake.lock`, puis
   poussée de la branche courante (sans tag), en tout dernier&nbsp;: son verrou
   pointe sur les releases publiées juste avant. La racine n'est jamais
   tagguée.

</Steps>

Seul le framework suit le `niveau` passé à la recette. Générateur et
`fleet-update` restent en `auto`, la documentation suit la ligne du framework,
les modèles son numéro.

Chaque dépôt est poussé avec **son** tag seul (`git push --atomic origin main
refs/tags/vX.Y.Z`), jamais avec `--tags`&nbsp;: les tags locaux de travail
restent locaux.

<Aside type="tip" title="Relancer le train">
Le train est idempotent. Sans rien de nouveau, il s'arrête au plan&nbsp;:
« Nothing to release ». Après un échec, il reprend là où il s'est arrêté&nbsp;:
les dépôts déjà taggués sont sautés, les épinglages commités restent acquis.
Seul un déploiement du site raté se relance à la main&nbsp;:
`just --justfile doc/Justfile --working-directory doc deploy "Release vX.Y.Z"`.
</Aside>

<Aside type="caution" title="Un modèle ne précède jamais le framework">
Un modèle porte le numéro du framework. S'il a bougé sans que le framework
bouge, le train l'annonce et le laisse&nbsp;: il partira avec la prochaine
release du framework.
</Aside>

## Les garde-fous d'intégration continue

Sur un tag `v*`, `release.yml` refuse de publier si&nbsp;:

- le fichier `VERSION` ne correspond pas au tag ;
- `CHANGELOG.md` ne contient pas de section pour cette version ;
- le verrou pointe un `dnf-generator` pris sur une branche plutôt que sur une
  release publiée.

Les trois contrôles de `ci.yml` (tests unitaires, évaluation, lint) sont
rejoués via `workflow_call`, puis la section du changelog devient les notes de
la *release* GitHub.

## Configuration partagée

Un seul [git-cliff](https://git-cliff.org/) pour les six dépôts, dans
`dnf/just/scripts/cliff.toml`. Le script `dnf/just/scripts/bump.sh` découvre la
source de version du dépôt (`VERSION`, `Cargo.toml`, `package.json`, ou à
défaut le dernier tag), assemble le fichier autour du bloc généré et préserve
l'historique écrit à la main.
